**Problem:** Queries on `Franchise Outlet` and `Sales Invoice` get slow past 10,000+ records. You need a systematic path to the right indexes — not sprinkled everywhere.

**Solution:** Diagnose with the slow query log, confirm with `EXPLAIN`, add indexes via the bench CLI or a migration patch, then verify the planner actually uses them.

## Step 1: Identify slow queries

Turn on MariaDB's slow query log temporarily — anything over 500ms gets recorded:

```bash
bench --site scoopjoy.localhost mariadb

# Enable slow query log (temporary)
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 0.5;  -- queries > 500ms
SET GLOBAL slow_query_log_file = '/tmp/slow-queries.log';

# After running the app, check the log:
# bench --site scoopjoy.localhost mariadb -e "SELECT * FROM mysql.slow_log ORDER BY start_time DESC LIMIT 20;"
```

## Step 2: EXPLAIN a suspicious query

The `type` and `rows` columns tell you whether an index is doing any work:

```sql
EXPLAIN SELECT franchise_outlet, SUM(grand_total), COUNT(*)
FROM `tabSales Invoice`
WHERE docstatus = 1
  AND posting_date BETWEEN '2025-01-01' AND '2025-03-31'
  AND franchise_outlet IS NOT NULL
GROUP BY franchise_outlet;

-- Look for:
-- type: ALL          (full table scan — BAD)
-- type: ref or range (index used — GOOD)
-- rows: 500000       (scanning many rows — potentially BAD)
-- Extra: Using where; Using filesort  (no index for ORDER BY)
```

## Step 3: Add indexes via bench CLI (recommended)

The bench command creates a Property Setter, so the index survives migrations and restores. Pass `--column` once per column to build a composite index in that order:

```bash
# Single-column index
bench --site scoopjoy.localhost add-database-index \
    --doctype "Sales Invoice" \
    --column franchise_outlet

# Composite index for the common query pattern
bench --site scoopjoy.localhost add-database-index \
    --doctype "Sales Invoice" \
    --column docstatus \
    --column posting_date \
    --column franchise_outlet
```

## Step 4: Add indexes in a migration patch

For indexes versioned with your app, add them in a patch. It checks `information_schema.statistics` first so it's idempotent — safe to re-run on every migration:

```python title="scoopjoy/patches/v1_0/add_performance_indexes.py"
import frappe


def execute():
    """Add custom indexes for franchise reporting performance."""

    # Single-column indexes for frequently filtered fields
    indexes = [
        ("Sales Invoice", ["franchise_outlet"]),
        ("Sales Invoice", ["order_type"]),
        ("Sales Invoice Item", ["item_code", "parent"]),
        ("Franchise Outlet", ["region"]),
        ("Franchise Outlet", ["is_active"]),
        ("Franchise Outlet", ["franchise_owner"]),
    ]

    for doctype, columns in indexes:
        table = f"tab{doctype}"
        index_name = f"idx_{'_'.join(columns)}"

        existing = frappe.db.sql("""
            SELECT 1 FROM information_schema.statistics
            WHERE table_schema = DATABASE()
              AND table_name = %s
              AND index_name = %s
            LIMIT 1
        """, (table, index_name))

        if not existing:
            col_str = ", ".join([f"`{c}`" for c in columns])
            frappe.db.sql_ddl(f"ALTER TABLE `{table}` ADD INDEX `{index_name}` ({col_str})")
            frappe.db.commit()
            print(f"  Added index {index_name} on {table}({col_str})")
        else:
            print(f"  Index {index_name} already exists on {table}")


    # Composite index for the most common report query pattern:
    #   WHERE docstatus=1 AND posting_date BETWEEN x AND y GROUP BY franchise_outlet
    composite_table = "tabSales Invoice"
    composite_name = "idx_docstatus_posting_date_franchise_outlet"

    existing = frappe.db.sql("""
        SELECT 1 FROM information_schema.statistics
        WHERE table_schema = DATABASE()
          AND table_name = %s
          AND index_name = %s
        LIMIT 1
    """, (composite_table, composite_name))

    if not existing:
        frappe.db.sql_ddl(f"""
            ALTER TABLE `{composite_table}`
            ADD INDEX `{composite_name}` (`docstatus`, `posting_date`, `franchise_outlet`)
        """)
        frappe.db.commit()
        print(f"  Added composite index {composite_name}")
```

Register the patch in `scoopjoy/patches.txt`:

```text title="scoopjoy/patches.txt"
scoopjoy.patches.v1_0.add_performance_indexes
```

## Step 5: Verify indexes are used

Re-run `EXPLAIN` after the index lands — `type` should drop from `ALL` to `range` and `rows` should shrink dramatically:

```sql
EXPLAIN SELECT franchise_outlet, SUM(grand_total), COUNT(*)
FROM `tabSales Invoice`
WHERE docstatus = 1
  AND posting_date BETWEEN '2025-01-01' AND '2025-03-31'
GROUP BY franchise_outlet;

-- Expected improvement:
-- type: range (was: ALL)
-- key: idx_docstatus_posting_date_franchise_outlet
-- rows: 15000 (was: 500000)

SHOW INDEX FROM `tabSales Invoice`;

SELECT index_name, rows_read, rows_requested
FROM information_schema.index_statistics
WHERE table_schema = DATABASE()
  AND table_name = 'tabSales Invoice';
```

## When NOT to add indexes

An index is a write-time cost paid for a read-time gain. The decision guide:

| Add an index when | Don't when |
|---|---|
| Column is in the WHERE clause of frequent queries | Column has LOW cardinality (e.g. `docstatus` 0/1/2, `is_active` 0/1) — unless first in a composite |
| Column appears in JOIN conditions | Table has < 1,000 rows (full scan is faster than index lookup) |
| Column is in ORDER BY with large result sets | Column is rarely used in WHERE/JOIN/ORDER BY |
| Column has HIGH cardinality (100+ distinct values) | Table has very frequent INSERT/UPDATE (indexes slow writes — e.g. Communication, Activity Log) |
| — | Column is already the first column of an existing composite index |

Gotcha: `frappe.get_list` wraps nullable columns in `IFNULL`/`COALESCE` by default, and `COALESCE(column, '') = 'value'` **cannot** use an index on `column`. Fix: pass `ignore_ifnull=True` in your `get_list` call.

:::note[Why this works]
MariaDB B-tree indexes narrow rows before scanning. A composite index on `(docstatus, posting_date, franchise_outlet)` satisfies the WHERE clause left-to-right. `bench add-database-index` creates a Property Setter so the index survives migrations and restores.
:::

:::caution[Common mistake]
Adding an index on `docstatus` alone — with only 3 values (0, 1, 2) it has terrible selectivity. But as the *first column* of a composite index it works well, because it immediately eliminates ~60% of rows (drafts and cancelled docs).
:::
