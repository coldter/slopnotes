## Activate your shell

Activation makes `cd`-ing into a project swap your tools automatically. Add the right line to your **interactive** rc file:

<Tabs syncKey="shell">
  <TabItem label="Bash">
    ```bash title="~/.bashrc"
    eval "$(mise activate bash)"
    ```
  </TabItem>
  <TabItem label="Zsh">
    ```bash title="~/.zshrc"
    eval "$(mise activate zsh)"
    ```
  </TabItem>
  <TabItem label="Fish">
    ```fish title="~/.config/fish/config.fish"
    mise activate fish | source
    ```
  </TabItem>
  <TabItem label="PowerShell">
    ```powershell title="$PROFILE"
    (&mise activate pwsh) | Out-String | Invoke-Expression
    ```
  </TabItem>
</Tabs>

:::caution[`.bashrc`, not `.bash_profile`]
Put activation in the file that runs for *interactive* shells (`.bashrc` / `.zshrc`), **not** `.bash_profile` or `.zshenv` — those run too early or in the wrong context. For non-interactive environments (IDEs, CI, cron), use shims instead — see below.
:::

Reload (`exec $SHELL`) and you're live.

## The one concept: PATH activation vs shims

**PATH activation** hooks your shell prompt. On every `cd` and prompt, mise runs `hook-env`, which rewrites `PATH` (and `[env]` vars) for the directory you're in.

<Mermaid title="hook-env: PATH rewrite on cd / prompt (PATH-activation mode)" height={420} code={`
sequenceDiagram
  participant U as You
  participant Sh as Shell
  participant M as mise hook-env
  participant P as PATH
  U->>Sh: cd ~/proj (has mise.toml: node = "22")
  Sh->>M: prompt hook fires -> mise hook-env
  M->>M: walk up, resolve config + tool versions
  M->>P: prepend ~/.local/share/mise/installs/node/22/bin
  P-->>Sh: node -> 22.x now first on PATH
  U->>Sh: node --version  (=> v22.x)
  U->>Sh: cd ~  (leave project)
  Sh->>M: prompt hook fires -> mise hook-env
  M->>P: remove the project's bin entries
  P-->>Sh: PATH restored to global defaults
`} />

**Shims** are static wrapper scripts in `~/.local/share/mise/shims`. Put that one directory on `PATH` and forget it. Calling `node` runs the shim, which asks mise which version this directory wants, then execs it. No prompt hook — which is why shims work where there's no shell.

```bash
eval "$(mise activate bash --shims)"   # or just add the shims dir to PATH
export PATH="$HOME/.local/share/mise/shims:$PATH"
```

| | PATH activation | Shims |
|---|---|---|
| **How** | prompt hook rewrites `PATH` per directory | static wrapper scripts on `PATH` |
| **Sets `[env]` vars** | yes | no (env vars only via activation) |
| **Needs an interactive shell** | yes | no |
| **Speed** | fast; resolves once per prompt | tiny per-call exec overhead |
| **New binary appears** | picked up automatically | run `mise reshim` |
| **Best for** | your daily terminal | IDEs, CI, cron, `Dockerfile`, scripts |

:::tip[Use both — for different jobs]
PATH activation in your terminal, shims everywhere a shell doesn't run. See [editors and CI](/mise/07-ci-docker-ide/).
:::

Under PATH activation, `which node` may report a shim or installed path. Use mise's own resolver for the real binary:

```bash
mise which node     # → ~/.local/share/mise/installs/node/22.14.0/bin/node
mise where node     # → the install dir
mise reshim         # regenerate shims after a tool adds a new binary
```

## Run a tool without activating: `mise exec`

```bash
mise exec node@22 -- node --version    # ad-hoc, nothing written to config
mise x python@3.13 -- python script.py
mise x -- npm test                     # use the versions this dir already pins
```

`mise exec` (alias `mise x`) resolves, installs if missing, and runs in a one-off subshell. Use it in scripts, `cron`, `systemd` units, and CI where you never ran `mise activate`.

## Where mise reads config

mise walks **up** from your cwd to the filesystem root, then layers in user and system config. Nearer files win, merged **key by key** — a project `mise.toml` overrides your global Node version without discarding your global env.

<Mermaid title="Config resolution: walk up from cwd, merge (nearer overrides)" height={520} code={`
flowchart TD
  start["cwd: ~/work/api/svc"] --> walk{"walk up,<br/>collect every config"}
  walk --> p1["~/work/api/svc/mise.toml"]
  walk --> p2["~/work/api/mise.toml"]
  walk --> p3["~/work/mise.toml"]
  p1 --> user["user: ~/.config/mise/config.toml<br/>+ conf.d/*.toml"]
  p2 --> user
  p3 --> user
  user --> sys["system: /etc/mise/config.toml"]
  sys --> merge["merge all layers, key by key"]
  merge --> win["nearer + project-local wins"]
  win --> result["effective tools / env / tasks"]
`} />

Within one directory, precedence (highest first):

| Order | File | Commit it? |
|---|---|---|
| 1 | `mise.local.toml` | no — gitignore |
| 2 | `mise.<env>.local.toml` | no — gitignore |
| 3 | **`mise.toml`** | **yes** |
| 4 | `mise.<env>.toml` | yes |
| 5 | `mise/config.toml`, `.mise/config.toml` | yes |
| 6 | `.mise.toml` (legacy dotted form) | yes |
| — | then user `~/.config/mise/config.toml`, then system `/etc/mise/` | — |

:::note[Prefer the visible `mise.toml`]
Use plain `mise.toml` (and `mise.local.toml` for untracked personal overrides). The dotted `.mise.toml` works but is legacy. Per-environment files like `mise.production.toml` are covered in [Environments & Secrets](/mise/03-environments-secrets/).
:::

There's also `.miserc.toml` — a new-in-2026 early-init settings file read before the rest, for things like selecting the active environment.

## `.tool-versions` vs `mise.toml` — pick `mise.toml`

mise still reads asdf's `.tool-versions` (lowest precedence) for backwards compat:

```text title=".tool-versions"
node 22.14.0
python 3.13.2
```

But it only carries **tool versions** — no `[env]`, no `[tasks]`, no `[settings]`. The equivalent `mise.toml` does all three in one committed file:

```toml title="mise.toml"
[tools]
node = "22"          # fuzzy → latest 22.x
python = "3.13"

[env]
DATABASE_URL = "postgres://localhost/dev"

[tasks.test]
run = "npm test"
```

:::tip[New projects: always `mise.toml`]
Keep `.tool-versions` only while migrating off asdf. `mise.toml` is the single file that pins tools, env, and tasks.
:::
