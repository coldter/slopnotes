## use vs install vs exec

| Command | Edits config? | Installs? | When |
|---|---|---|---|
| `mise use <tool>@<v>` | yes (nearest `mise.toml`) | yes | adopt a tool into a project |
| `mise install [tool]` | no | yes | hydrate a cloned repo / CI |
| `mise exec -- <cmd>` | no | yes (if missing) | ad-hoc, scripts, cron |

```bash
mise use node@22        # install + write into the nearest mise.toml
mise install            # install everything the config already declares
mise exec node@22 -- node build.js   # pin the version just for this command
mise x python@3.13 -- python -V       # x is the alias
mise exec -- node -v    # run a one-off in a tool's env
```

:::tip
`mise exec` is the non-interactive escape hatch — perfect inside a script, `systemd` unit, or cron job where you never ran `mise activate`. More in the [Cookbook](/mise/09-recipes/).
:::

## Global vs local

`mise use` writes to the **nearest** `mise.toml`, walking up from your cwd. Two flags steer where it lands:

```bash
mise use node@22                # → ./mise.toml (project-local)
mise use -g node@22             # → ~/.config/mise/config.toml (global default)
mise use --env local node@22    # → ./mise.local.toml (gitignored, your machine only)
mise use --pin node@22          # write the resolved EXACT version, not "22"
mise use --remove node          # drop a tool from the config
```

:::note
Commit project-local `mise.toml` for anything a project needs. Reserve the **global** config for personal conveniences. Keep machine-specific overrides in gitignored `mise.local.toml`.
:::

## Version specifiers

| Specifier | Example | Meaning |
|---|---|---|
| exact | `"20.11.0"` | that version, nothing else |
| fuzzy | `"20"`, `"3.12"` | latest matching that prefix |
| `latest` | `"latest"` | newest stable release |
| `lts` | `"lts"` | newest long-term-support release |
| `prefix:` | `"prefix:1.20"` | latest within the prefix (explicit form) |
| `ref:` | `"ref:main"` | build from a git ref / tag / commit |
| `path:` | `"path:/opt/node"` | use a binary already on disk |
| `sub-N:` | `"sub-2:lts"` | N releases behind the resolved target |

```toml title="mise.toml"
[tools]
node = "22"            # fuzzy: newest 22.x
python = "3.13.1"      # exact
go = "latest"          # newest stable
ruby = "lts"
```

:::caution[No npm-style ranges, no `system`]
mise does **not** understand `^20` or `~3.12` — no semver ranges, only the specifiers above. There's no first-class `system` keyword (an asdf-ism); use `path:` or don't manage that tool. A *bare* fuzzy version means "latest matching" for most tools, but a few (notably Go) treat a bare version as exact — be explicit when in doubt.
:::

## The `[tools]` table

```toml title="mise.toml"
[tools]
node = "22"                       # single version
python = ["3.13", "3.12"]         # array — first entry is the default on PATH
"npm:prettier" = "latest"         # backend-prefixed key — quote it
```

For tools that need extra setup, use the **table form**:

```toml title="mise.toml"
[tools]
node = { version = "22", postinstall = "corepack enable" }
ripgrep = { version = "latest", os = ["linux", "macos"] }
my-cli = { version = "1.2", depends = ["node"] }
```

| Key | What it does |
|---|---|
| `version` | the version specifier |
| `postinstall` | shell command run after install (gets `MISE_TOOL_NAME` / `MISE_TOOL_VERSION`) |
| `os` | restrict install to these OSes, e.g. `["linux", "macos"]` |
| `depends` | install these tools first |
| `install_env` | env vars set during the install |

### A polyglot project

```toml title="mise.toml"
[tools]
node = { version = "22", postinstall = "corepack enable" }  # gives you pnpm/yarn
python = "3.13"
go = "1.23"
"npm:typescript" = "5.6"                                    # tsc, from the npm backend
ripgrep = "latest"                                          # from the registry (aqua)
```

```bash
mise install     # one command, the whole toolchain
```

## Backends & the registry

When you write `node = "22"`, mise looks up the short name `node` in its **registry**, which maps it to a *backend* — the actual installation mechanism. See every mapping with `mise registry`.

<Mermaid title="How a short name resolves to a backend" height={360} code={`
flowchart TD
  name["node = 22  —  short name in mise.toml"] --> reg{"mise registry<br/>lookup"}
  reg -->|"preferred"| aqua["aqua:owner/repo<br/>verified downloads, no plugins, Windows"]
  reg -->|"fallback"| gh["github: / gitlab:<br/>release assets"]
  reg -->|"needs a toolchain"| lang["language backend<br/>cargo: npm: pipx: go: gem: dotnet:"]
  aqua --> bin["installed under ~/.local/share/mise"]
  gh --> bin
  lang --> bin
`} />

Skip the registry and address a backend directly:

```toml title="mise.toml"
[tools]
"aqua:BurntSushi/ripgrep" = "latest"
"github:cli/cli" = "2.55"
"cargo:tokei" = "latest"
"npm:prettier" = "3.3"
"pipx:ruff" = "latest"
"go:github.com/air-verse/air" = "latest"
```

### The 2026 preference order — and why

mise picks backends in this order. It's a **supply-chain** decision, not just ergonomics:

1. **aqua** — the **default** in 2026. Downloads pre-built release binaries with **checksum + signature verification**, needs **no plugins**, works on **Windows**.
2. **github / gitlab** — pull release assets straight from a repo when there's no aqua entry.
3. **language backends** — `cargo` `npm` `pipx` `go` `gem` `dotnet`. Great coverage, but they require the toolchain installed first.

Legacy / avoid:

- **ubi** — *deprecated*, folded into `github`.
- **asdf** — *legacy*; not accepted for new registry entries.
- **vfox** — not accepted for new entries (but it's the default backend on Windows).

:::tip[Why aqua over asdf]
asdf plugins are **arbitrary bash scripts**, often third-party and unmaintained — every install runs someone's shell code. aqua uses a curated, signed manifest and **verifies downloads** against checksums. This is also the heart of the [migration story](/mise/08-migration/).
:::

```bash
mise settings add disable_backends asdf   # opt out of a backend entirely
```

:::note
aqua is **download-only** — it can't set environment variables. For env, that's [Environments & Secrets](/mise/03-environments-secrets/)'s job.
:::

## The lockfile: `mise.lock`

Versions like `"22"` are *fuzzy* — `mise install` today and next month can resolve differently. The **lockfile** pins the resolved version, checksum, and per-platform download URL. It's **stable in 2026** — no experimental flag:

```toml title="mise.toml"
[settings]
lockfile = true        # or set MISE_LOCKFILE=1
```

The lockfile is **not** created automatically. Generate or refresh it:

```bash
mise lock                 # resolve current config → mise.lock
mise install              # also updates mise.lock when lockfile = true
```

The file mirrors its config's basename: `mise.toml` → `mise.lock`, `mise.local.toml` → `mise.local.lock`.

### Strict installs

In CI and Docker, fail loudly if the lockfile can't satisfy the current platform:

```bash
mise install --locked     # error if no resolved URL for this platform
```

```toml title="mise.toml"
[settings]
locked = true             # make --locked the default
```

:::caution
The flag is `--locked`. There is **no `--frozen`** in mise — don't reach for the Cargo muscle memory.
:::

### Multi-platform

Team on macOS, CI on Linux (and maybe arm64)? Record entries for every platform up front:

```bash
mise lock --platform linux-x64,macos-arm64
```

:::tip[Commit `mise.lock`]
Check it into git next to `mise.toml`. It's the `package-lock.json` of your *toolchain*. Wired into [CI and Docker](/mise/07-ci-docker-ide/) with `mise install --locked`.
:::

## Listing, outdated & upgrading

```bash
mise ls                    # installed tools (versions, source config)
mise ls --current          # just what's active here (-c)
mise ls --outdated         # installed vs latest available
mise ls-remote node        # every installable version of a tool
mise outdated              # report tools with newer versions
mise outdated --bump       # report newest, ignoring your current spec
```

### `upgrade` vs `upgrade --bump`

```bash
mise upgrade               # upgrade WITHIN your spec — "22" → newest 22.x; no config edit
mise upgrade --bump        # jump to the newest major/minor AND rewrite mise.toml
mise upgrade node --dry-run
```

| Command | Crosses your version spec? | Edits `mise.toml`? |
|---|---|---|
| `mise upgrade` | no (stays within `"22"`) | no |
| `mise upgrade --bump` | yes (e.g. `"22"` → `"24"`) | yes |

:::caution[The `-l` flag means different things]
In `mise ls`, `-l` is `--local`. In `mise outdated` / `mise upgrade`, `-l` is `--bump`. Spell long flags out in scripts. (`-g/--global` only applies to `use` and `ls`.)
:::

## Supply-chain: `--minimum-release-age`

Tell mise to ignore releases younger than a cooling-off window — brand-new releases are where supply-chain attacks land first:

```bash
mise use node@22 --minimum-release-age "7d"
mise install --minimum-release-age "30d"
```

Accepted on `use`, `install`, `ls-remote`, and `upgrade`.
