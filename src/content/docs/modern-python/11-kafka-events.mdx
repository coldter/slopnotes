In Python the modern async-native Kafka client is **`aiokafka`**: an `asyncio` producer and consumer that plug into the async world from modules 05/06 — a consumer is literally `async for msg in consumer`. Start Kafka from the shared stack: `cd shared-infra && docker compose up -d kafka kafka-ui` (broker on localhost:29092, Kafka UI on http://localhost:8090). Kafka 4 runs **KRaft** (no ZooKeeper); use `replicas=1` in dev.

```bash
uv add aiokafka pydantic
```

## The client: which library

| Library | Style | Use it when |
|---|---|---|
| **`aiokafka`** | Pure-Python, `asyncio`-native | **Default** for async apps. Its calls are coroutines — `await producer.send_and_wait(...)`, `async for msg in consumer`. No loop-blocking C calls. |
| `confluent-kafka` | C wrapper (librdkafka), blocking | Highest throughput, richest config; sync API — run it in a thread pool. |
| `kafka-python` | Pure-Python, sync | Legacy/simple scripts. No async. |

Do you even need Kafka? For lighter needs: **NATS** (`nats-py`, JetStream adds persistence) for fast service-to-service messaging, or **Redis Streams** (module 10) if you already run Redis. Choose Kafka when you genuinely need a long-retention, replayable event log with high-throughput consumer groups.

## The mental model: events vs request/response

Request/response: the caller waits, and the callee must be up *right now*. Event-driven flips that — a producer appends a fact to a log and moves on; consumers read later, at their own pace, maybe more than once. The producer doesn't know or care who reads it.

| | Request/response (HTTP, gRPC) | Event-driven (Kafka) |
|---|---|---|
| Coupling | Caller knows the callee | Producer doesn't know consumers |
| Timing | Synchronous — callee must be up | Asynchronous — consumers catch up later |
| Backpressure | Caller blocks / times out | Log buffers; consumers pull at their pace |
| Failure | Request fails, caller retries | Event persists; reprocess any time |
| Fan-out | One call, one handler | One event, N independent consumer groups |
| Shape | "Do this and tell me the result" | "This happened" (a fact in past tense) |

Events are **facts in the past tense** — `OrderPlaced`, `PaymentCaptured` — not commands (`PlaceOrder`). A command can be rejected; a fact already happened.

### Topics, partitions, consumer groups, offsets

| Concept | What it is | Analogy |
|---|---|---|
| **Topic** | Named, append-only log of messages | A channel name / an event "table" |
| **Partition** | One ordered shard of a topic. Order is guaranteed *within* a partition, not across. | A single-writer log file |
| **Offset** | A message's position in its partition (monotonic int) | Array index / a bookmark |
| **Key** | Optional bytes; same key → same partition → ordered | Shard key |
| **Consumer group** | Consumers sharing a topic's partitions; each partition goes to exactly one member | A worker pool with sticky assignment |

Two rules that explain most surprises: **ordering is per-partition** (key by `order_id` so one order's events land on the same partition, in sequence), and **parallelism is capped by partition count** (10 consumers on a 6-partition topic leaves 4 idle — pick partitions for your target concurrency up front).

The **offset is the only state a consumer keeps** — "where am I in each partition?" Commit it and a restart resumes there; reset it to replay. Delivery guarantees come down to *when* you commit relative to *when* you process.

## Producing events

### A typed event model with Pydantic

Don't ship raw dicts onto a topic — a message's shape is a contract other services depend on. Model events as Pydantic v2 (module 04) and serialize with `model_dump_json()`:

```python title="app/events.py"
from datetime import datetime, timezone
from decimal import Decimal
from pydantic import BaseModel, Field


def _now() -> datetime:
    return datetime.now(timezone.utc)


class OrderPlaced(BaseModel):
    event_id: str                       # unique per event — used for idempotency
    order_id: str
    user_id: int
    amount: Decimal
    currency: str = "USD"
    occurred_at: datetime = Field(default_factory=_now)
    schema_version: int = 1             # see "Schema discipline" below
```

### `AIOKafkaProducer`

The producer is an async object: `await producer.start()`, send, `await producer.stop()`. Serialization is just turning your model into `bytes`:

  <TabItem label="TypeScript">

```ts
import { Kafka } from "kafkajs";

const kafka = new Kafka({ brokers: ["localhost:29092"] });
const producer = kafka.producer({ idempotent: true });
await producer.connect();

await producer.send({
  topic: "orders",
  messages: [{ key: order.orderId, value: JSON.stringify(order) }],
  acks: -1, // all replicas
});
await producer.disconnect();
```

```python title="app/producer.py"
from aiokafka import AIOKafkaProducer
from app.events import OrderPlaced


async def make_producer() -> AIOKafkaProducer:
    producer = AIOKafkaProducer(
        bootstrap_servers="localhost:29092",
        acks="all",                  # wait for all in-sync replicas
        enable_idempotence=True,     # no duplicates on internal retry
    )
    await producer.start()
    return producer


async def publish_order(producer: AIOKafkaProducer, event: OrderPlaced) -> None:
    await producer.send_and_wait(
        topic="orders",
        key=event.order_id.encode(),          # same order_id -> same partition
        value=event.model_dump_json().encode(),  # Pydantic -> JSON -> bytes
    )
```

`send_and_wait` awaits the broker ack — use it when the caller needs delivery confirmation (inside a request handler); `send` returns a future immediately for high-throughput firehoses where you check futures later.

### Keys & partitioning

The key decides the partition (`partition = hash(key) % num_partitions`) — how you get ordering where you need it:

| Key | Effect | Use for |
|---|---|---|
| Entity id (`order_id`, `user_id`) | All events for that entity share a partition → ordered | Order/user lifecycles |
| `None` | Round-robin across partitions, no ordering | Metrics, independent events |
| Composite (`f"{tenant}:{user}"`) | Grouped ordering | Per-tenant streams |

```python
# Ordered per order: every OrderPlaced/OrderPaid/OrderShipped for one order
# lands on the same partition and is consumed in sequence.
await producer.send_and_wait("orders", key=order_id.encode(), value=payload)

# Unordered: telemetry where order doesn't matter — let Kafka balance it.
await producer.send_and_wait("metrics", key=None, value=payload)
```

### Delivery semantics & idempotence

| Guarantee | Meaning | How you get it |
|---|---|---|
| At-most-once | May lose, never duplicates | Commit offset *before* processing |
| **At-least-once** | Never lose, may duplicate | Commit *after* processing (the sane default) |
| Exactly-once | Processed once | Transactions + idempotent consumer (costly) |

Set **`enable_idempotence=True`** on the producer (implies `acks="all"`). It stops *producer-side* duplicates — on an internal retry after a network blip, the broker dedups by `(producer_id, sequence_number)`. It does **not** dedup your application re-sending the same logical event — give each event an `event_id` and dedup on the consumer.

:::caution[Idempotent producer ≠ exactly-once pipeline]
`enable_idempotence=True` is cheap and almost always on, but it only covers the producer→broker hop. End-to-end exactly-once (consume → process → produce, atomically) needs Kafka transactions, and even then "once" holds only *inside Kafka* — the moment you touch Postgres or call an external API, you're back to needing an idempotent consumer. Plan for at-least-once and dedup.
:::

## Consuming events

### `AIOKafkaConsumer` and `async for`

The poll loop you hand-write in `kafkajs` or `sarama` *is* the `async for`:

<Tabs syncKey="lang">
  <TabItem label="TypeScript">

```ts
const consumer = kafka.consumer({ groupId: "order-processor" });
await consumer.connect();
await consumer.subscribe({ topic: "orders", fromBeginning: true });

await consumer.run({
  eachMessage: async ({ message }) => {
    const order = JSON.parse(message.value!.toString());
    await handle(order); // kafkajs auto-commits after this resolves
  },
});
```

  </TabItem>
  <TabItem label="Go">

```go
r := kafka.NewReader(kafka.ReaderConfig{
    Brokers: []string{"localhost:29092"},
    GroupID: "order-processor",
    Topic:   "orders",
})
defer r.Close()

for {
    m, err := r.FetchMessage(ctx) // explicit poll loop
    if err != nil { break }
    var order Order
    json.Unmarshal(m.Value, &order)
    handle(order)
    r.CommitMessages(ctx, m) // commit AFTER processing
}
```

  </TabItem>
  <TabItem label="Python">

```python title="app/consumer.py"
from aiokafka import AIOKafkaConsumer
from app.events import OrderPlaced


async def consume() -> None:
    consumer = AIOKafkaConsumer(
        "orders",
        bootstrap_servers="localhost:29092",
        group_id="order-processor",      # the consumer group
        auto_offset_reset="earliest",    # no committed offset? start from the top
        enable_auto_commit=False,        # we commit manually, after processing
    )
    await consumer.start()
    try:
        async for msg in consumer:                  # the poll loop, as iteration
            event = OrderPlaced.model_validate_json(msg.value)
            await handle(event)                     # do the work...
            await consumer.commit()                 # ...then commit (at-least-once)
    finally:
        await consumer.stop()                       # leaves group + commits cleanly
```

  </TabItem>
</Tabs>

`async for msg in consumer` hands you `ConsumerRecord`s (`.key`, `.value`, `.topic`, `.partition`, `.offset`, `.headers`) and never blocks the loop. It's the same cold, pull-driven iteration as module 06 — a Kafka consumer is just an async stream whose source is a partitioned log.

### Manual vs auto commit

**Commit = "I'm done with everything up to this offset; don't redeliver it."** The single most important consumer decision:

| Mode | Config | Guarantee | Risk |
|---|---|---|---|
| Auto commit | `enable_auto_commit=True` (timer, default 5s) | At-most-once-ish | Commits on a timer, *not* after processing — crash after commit but before work = **lost message** |
| **Manual commit** | `enable_auto_commit=False` + `await consumer.commit()` | At-least-once | Crash before commit = **redelivery** (fine if handlers are idempotent) |

```python
# Auto-commit trap: the offset advances on a timer regardless of whether
# handle() finished. A crash mid-handle silently drops the message.
consumer = AIOKafkaConsumer(..., enable_auto_commit=True)   # convenient, lossy

# Manual: commit only after the work is durably done.
consumer = AIOKafkaConsumer(..., enable_auto_commit=False)
async for msg in consumer:
    await handle(msg)
    await consumer.commit()
```

Prefer **manual commit + at-least-once + idempotent handlers**. For throughput, process a batch and commit once at the end (`aiokafka`'s `getmany()` fetches a batch explicitly) — you trade a slightly larger redelivery window for far fewer commits.

### Graceful shutdown

A consumer is a long-running worker — stop it cleanly so it commits offsets and leaves the group (fast rebalance, not a 10s session timeout). Catch the signal, break the loop, run cleanup in `finally` (module 05's shutdown discipline):

```python title="app/worker.py"
import asyncio
import signal
from aiokafka import AIOKafkaConsumer
from app.events import OrderPlaced


async def run_consumer(stop: asyncio.Event) -> None:
    consumer = AIOKafkaConsumer(
        "orders",
        bootstrap_servers="localhost:29092",
        group_id="order-processor",
        enable_auto_commit=False,
    )
    await consumer.start()
    try:
        async for msg in consumer:
            if stop.is_set():
                break
            event = OrderPlaced.model_validate_json(msg.value)
            await handle(event)
            await consumer.commit()
    finally:
        await consumer.stop()        # commits + leaves the group cleanly


async def main() -> None:
    stop = asyncio.Event()
    loop = asyncio.get_running_loop()
    for sig in (signal.SIGINT, signal.SIGTERM):
        loop.add_signal_handler(sig, stop.set)   # flip the event on Ctrl-C / SIGTERM
    await run_consumer(stop)


if __name__ == "__main__":
    asyncio.run(main())
```

`consumer.stop()` in the `finally` flushes pending commits and sends a graceful `LeaveGroup`, so Kafka reassigns your partitions in milliseconds.

## Dead letter queues: never block on a poison message

Some messages never succeed — malformed JSON, an unparseable schema, a business rule that rejects them forever. If your handler just throws and you don't commit, Kafka redelivers the *same* message forever and the partition is stuck — head-of-line blocking behind every good message.

The pattern: **retry transient failures a few times, then divert poison messages to a Dead Letter Queue** topic and move on.

<Mermaid title="handle() ok → commit; transient → retry with backoff; poison or exhausted → orders.DLQ, then commit either way" code={`
flowchart TB
  Orders["orders"] --> Consumer["consumer"]
  Consumer --> Handle["handle()"]
  Handle -->|"ok"| Commit["commit offset"]
  Handle -->|"raises"| Transient{"transient?"}
  Transient -->|"yes"| Retry["retry (n times, backoff)"]
  Retry -->|"still failing"| DLQ["orders.DLQ<br/>(commit + continue)"]
  Transient -->|"no (poison)"| DLQ
  DLQ --> DLQConsumer["DLQ consumer:<br/>log / store / alert / replay"]
`} />

`aiokafka` has **no built-in DLQ** (unlike Spring Kafka's `DeadLetterPublishingRecoverer`) — you wire it explicitly, which is clearer about what's happening. Classify the error, retry the transient ones, republish the rest to the DLQ with the failure reason in headers:

```python title="app/dlq.py"
import asyncio
from aiokafka import AIOKafkaConsumer, AIOKafkaProducer
from app.events import OrderPlaced

DLQ_TOPIC = "orders.DLQ"
MAX_RETRIES = 3


class PoisonMessage(Exception):
    """Non-retryable: bad data / failed validation. Straight to DLQ."""


async def to_dlq(producer: AIOKafkaProducer, msg, reason: str) -> None:
    await producer.send_and_wait(
        DLQ_TOPIC,
        key=msg.key,
        value=msg.value,                      # preserve the raw bytes
        headers=[                             # breadcrumbs for the DLQ consumer
            ("x-original-topic", msg.topic.encode()),
            ("x-original-offset", str(msg.offset).encode()),
            ("x-error", reason.encode()),
        ],
    )


async def consume_with_dlq(
    consumer: AIOKafkaConsumer, producer: AIOKafkaProducer
) -> None:
    async for msg in consumer:
        try:
            event = OrderPlaced.model_validate_json(msg.value)  # may raise (poison)
            await process_with_retries(event)                   # transient retries
        except PoisonMessage as exc:
            await to_dlq(producer, msg, f"poison: {exc}")
        except Exception as exc:                                # retries exhausted
            await to_dlq(producer, msg, f"exhausted: {exc}")
        finally:
            await consumer.commit()   # ALWAYS advance — handled or parked, never stuck


async def process_with_retries(event: OrderPlaced) -> None:
    delay = 0.5
    for attempt in range(1, MAX_RETRIES + 1):
        try:
            await handle(event)
            return
        except PoisonMessage:
            raise                              # don't retry poison
        except Exception:
            if attempt == MAX_RETRIES:
                raise                          # give up -> caller sends to DLQ
            await asyncio.sleep(delay)         # backoff
            delay *= 2
```

Two rules make this robust: **commit no matter what** (whether processed or parked on the DLQ, you've dealt with it — advance the offset), and **separate poison from transient** (a validation error will never succeed; a DB timeout might). For high-throughput pipelines, graduate from in-process backoff to **retry topics** (`orders.retry.5s`, `orders.retry.30s`…) so one slow message never blocks the main topic.

## Idempotent consumers (the at-least-once survival kit)

At-least-once means **your handler will occasionally see the same event twice** — a redelivery after a crash, a producer resend. Make `handle()` safe to run twice:

```python title="app/idempotency.py"
# 1. Dedup table: record event_ids you've handled, in the SAME transaction as
#    the work. A replay finds the id already present and no-ops.
async def handle(event: OrderPlaced, db) -> None:
    async with db.transaction():
        already = await db.fetchval(
            "SELECT 1 FROM processed_events WHERE event_id = $1", event.event_id
        )
        if already:
            return                              # seen it — skip
        await db.execute(
            "INSERT INTO orders (order_id, user_id, amount, status) "
            "VALUES ($1, $2, $3, 'PLACED')",
            event.order_id, event.user_id, event.amount,
        )
        await db.execute(
            "INSERT INTO processed_events (event_id) VALUES ($1)", event.event_id
        )
```

```python
# 2. Natural idempotency: write so re-running is a no-op. UPSERTs and
#    "set to this state" operations are inherently safe to repeat.
await db.execute(
    "INSERT INTO orders (order_id, status) VALUES ($1, 'PLACED') "
    "ON CONFLICT (order_id) DO NOTHING",
    event.order_id,
)
```

The dedup-table approach needs a stable, producer-assigned **`event_id`** (not the Kafka offset — a republish to a DLQ or retry topic changes the offset but is the same logical event). That's why `OrderPlaced` carries one.

### Event sourcing, briefly

Store the **stream of events** as the source of truth and derive state by replaying them — Kafka's durable, ordered, replayable log is a natural event store:

<Mermaid title="Events are the source of truth; projections are derived by folding/replaying the log and can be rebuilt from offset 0" code={`
flowchart TB
  subgraph Events["events (source of truth, append-only)"]
    direction LR
    E1["OrderPlaced(o1)"] --> E2["OrderPaid(o1)"] --> E3["OrderShipped(o1)"]
  end
  Events -->|"replay / fold"| Projections
  subgraph Projections["projections (read models, rebuildable)"]
    direction TB
    OrdersTable["orders_table:<br/>o1 = {status: SHIPPED, ...}"]
    DailyRevenue["daily_revenue:<br/>2026-06-19 = $4,210"]
  end
`} />

- **Events** are immutable facts; you only ever append.
- **Projections** (read models) are *derived* — a consumer folds the event stream into whatever shape a query needs (a Postgres table, a Redis cache). Because they're derived, you can **drop and rebuild** a projection by replaying from offset 0, or build a brand-new view of historical data.
- Projection-building consumers **must be idempotent** — you'll replay events when rebuilding.

:::caution[Honest take on event sourcing and exactly-once]
Full event sourcing is powerful but not a free upgrade: schema evolution on events you can never delete, snapshotting so replays stay fast, eventual consistency between log and projections, genuinely hard debugging. Adopt it where the audit log and replayability are the product (ledgers, workflow engines) — not as a default architecture.

And on **exactly-once**: Kafka's transactions give you exactly-once *within Kafka* (consume-transform-produce, all-or-nothing). The instant a side effect leaves Kafka — a row in Postgres, a Stripe charge, an email — that guarantee evaporates. The honest answer for almost every service is **at-least-once delivery plus idempotent consumers**. Reach for transactions only for Kafka-to-Kafka pipelines that truly can't tolerate a duplicate.
:::

## Schema discipline

A message on a topic is a contract with every current and future consumer. Treat event schemas like a public API:

- **Add fields, don't break them.** New fields must have defaults so old consumers (which ignore them) and new messages (which omit them) both deserialize — Pydantic defaults give you this free. Never rename or retype a field: that's a remove + add and it breaks existing messages on the log.
- **Be lenient on read.** `extra="ignore"` so a newer producer's extra field doesn't crash an older consumer.
- **Version explicitly.** Carry a `schema_version` on the event. For a truly breaking change, prefer a new versioned topic (`orders.v2`) and run both consumers during migration over silently mutating `v1`.

```python title="app/events.py"
from pydantic import BaseModel, ConfigDict


class OrderPlaced(BaseModel):
    # ignore unknown fields a newer producer might add -> forward compatible
    model_config = ConfigDict(extra="ignore")

    event_id: str
    order_id: str
    amount: Decimal
    schema_version: int = 1
    # v2 ADDED this, with a default -> old messages (no currency) still parse:
    currency: str = "USD"
```

:::tip[Schema Registry / Avro — when JSON isn't enough]
At organizational scale, teams put a **Schema Registry** (Confluent's, or open-source Apicurio) in front of topics with **Avro** or **Protobuf** payloads — the registry *enforces* compatibility, and Avro is smaller and faster on the wire than JSON (in Python via `confluent-kafka`'s `AvroSerializer`). Right call for many teams sharing many topics; overkill for one service learning the ropes. Start with versioned Pydantic JSON; adopt a registry when schema drift across teams becomes a real problem.
:::

## Integrating with FastAPI

**Producer → in the app, via lifespan.** The web process produces events as a side effect of handling requests (place an order → emit `OrderPlaced`). One producer at startup, shared across requests, closed at shutdown — same lifespan pattern as a DB pool:

```python title="app/main.py"
from contextlib import asynccontextmanager
from fastapi import FastAPI, Request
from aiokafka import AIOKafkaProducer
from app.events import OrderPlaced


@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.producer = AIOKafkaProducer(
        bootstrap_servers="localhost:29092",
        acks="all",
        enable_idempotence=True,
    )
    await app.state.producer.start()       # one producer for the whole app
    try:
        yield
    finally:
        await app.state.producer.stop()     # flush + close on shutdown


app = FastAPI(lifespan=lifespan)


@app.post("/orders", status_code=202)        # 202 Accepted: queued, not done
async def place_order(req: Request) -> dict[str, str]:
    event = OrderPlaced(event_id="...", order_id="...", user_id=1, amount=Decimal("9.99"))
    producer: AIOKafkaProducer = req.app.state.producer
    await producer.send_and_wait("orders", key=event.order_id.encode(),
                                 value=event.model_dump_json().encode())
    return {"order_id": event.order_id, "status": "accepted"}
```

**Consumer → a separate worker process.** Do *not* run the consumer loop inside the web process: web pods scale on request rate, consumers on partition count and lag (coupling them wastes resources and caps consumer parallelism); `async for` is an infinite loop that would fight request handlers for the event loop; and you want to deploy/restart each independently. The consumer is its own entrypoint — `python -m app.worker` — deployed as a separate process. The web app *writes* to Kafka; the worker *reads*. The order-pipeline sub-project builds exactly this split.
