Python type hints are what make the rest of modern Python click: FastAPI reads them to generate routes and OpenAPI, Pydantic reads them to validate, your editor reads them for autocomplete. The one thing to internalize first: **hints are erased at runtime** — a separate tool (`ty`/`mypy`) checks them statically.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">

```typescript
// TS types are erased at compile time. tsc checks them, then emits plain JS.
function greet(name: string): string {
  return `Hello, ${name}`;
}
// At runtime, `name` could be anything — JS doesn't check.
greet(42 as any); // compiles fine if you fight the checker; runs fine too
```

  </TabItem>
  <TabItem label="Go">

```go
// Go types are real at compile AND runtime. The compiler refuses to build
// if types don't line up. There is no "ignore the error and run anyway".
func Greet(name string) string {
    return "Hello, " + name
}
// Greet(42) does not compile. Period.
```

  </TabItem>
  <TabItem label="Python">

```python
def greet(name: str) -> str:
    return f"Hello, {name}"

# The hint `str` is metadata. Python NEVER checks it at runtime.
greet(42)          # runs without error; produces "Hello, 42"
# A separate tool (ty / mypy) flags this BEFORE you run. The interpreter won't.
```

  </TabItem>
</Tabs>

Python is **like TypeScript, not like Go**: a separate checker validates statically, then the runtime ignores the hints. Run `ty` (or `mypy`) as a separate gate — in your editor and CI.

| | TypeScript | Go | Python |
|---|---|---|---|
| Types checked | at build (`tsc`) | at build (compiler) | by a separate tool (`ty`/`mypy`) |
| Types at runtime | erased | enforced | erased (just `__annotations__` metadata) |
| Can you run code that fails the checker? | yes (emit-on-error) | no | yes — the interpreter never looks |
| Gradual / opt-in typing | yes | no | yes |

:::caution[Hints don't validate your data]
Coming from Go, "if it typechecks, the value is that type" does not hold. A `dict[str, int]` off the wire is whatever the JSON contained — the hint is a promise to the checker, not a guard. Runtime validation (API bodies, env config) is Pydantic's job (module 04).
:::

## Why bother — everything reads hints

- **ty / mypy** catch bugs statically — your CI gate, like `tsc --noEmit`.
- **Editors** give autocomplete, go-to-def, inline errors from hints alone.
- **FastAPI** turns `user_id: int` in a route signature into parsing, validation, and OpenAPI docs.
- **Pydantic** builds validators from field types.
- **dataclasses** use them to generate `__init__`.

Annotate every function signature and dataclass field. Inside function bodies, let inference work (like Go's `:=`); annotate locals only when the checker can't figure it out.

## Basic hints and built-in generics

```python
age: int = 30
name: str = "Alice"
ratio: float = 19.99       # Python has ONE float (64-bit) and ONE int (arbitrary precision)
active: bool = True

def add(a: int, b: int) -> int:
    return a + b

def log(message: str) -> None:   # `None` = returns nothing, like void/Unit
    print(message)
```

The type mapping you'll reach for constantly:

| TypeScript | Go | Python | Notes |
|---|---|---|---|
| `number` | `int` / `int64` | `int` | arbitrary precision — no overflow |
| `number` | `float64` | `float` | always 64-bit |
| `boolean` | `bool` | `bool` | |
| `string` | `string` | `str` | |
| `T[]` / `Array<T>` | `[]T` | `list[T]` | mutable, ordered |
| `[A, B]` (tuple) | — | `tuple[A, B]` | fixed-size; `tuple[int, ...]` = variadic |
| `Record<string, V>` | `map[string]V` | `dict[str, V]` | |
| `Set<T>` | `map[T]struct{}` | `set[T]` | |
| `T \| null` | `*T` | `T \| None` | |
| `A \| B` | interface / `any` | `A \| B` | union |
| `unknown` | `any` | `object` | safe top type |
| `any` | `any` / `interface{}` | `Any` | escape hatch (opts out of checking) |
| `void` | — | `None` | |
| `never` | — | `Never` | bottom type |

### Use built-in generics — stop importing from `typing`

The biggest "your Python is dated" tell. Pre-3.9 made you import `List`, `Dict`, `Optional`, `Union` from `typing`. Modern Python uses the builtins and `|` directly:

```python
# THE OLD WAY (pre-3.10) — recognize it, then never write it:
from typing import List, Dict, Optional, Union, Tuple, Set
def old(xs: List[int], m: Dict[str, int], x: Optional[str]) -> Union[int, str]: ...

# THE MODERN WAY (3.10+, what you write in 2026):
def new(xs: list[int], m: dict[str, int], x: str | None) -> int | str: ...
```

```python
xs: list[str]                  # was List[str]
m: dict[str, int]              # was Dict[str, int]
pair: tuple[int, str]          # fixed 2-tuple, was Tuple[int, str]
nums: tuple[int, ...]          # variadic tuple ("a tuple of ints, any length")
tags: set[str]                 # was Set[str]
maybe: str | None              # was Optional[str]
either: int | str             # was Union[int, str]
mixed: list[dict[str, int | None]]   # nests exactly like you'd expect
```

`X | None` is the idiom you'll use most — literally `Optional[X]`, but it reads like TS's `string | null`.

```typescript
function findUser(id: number): User | null {
  return users.get(id) ?? null;
}
const tags: Set<string> = new Set();
const scores: Record<string, number> = {};
```

```go
tags := map[string]struct{}{}
```

```python
tags: set[str] = set()
scores: dict[str, int] = {}
```

## Special forms: Literal, Final, Annotated, Self, Never

### `Literal` — exact values as types

Like TS string-literal unions. The value itself is the type.

```python
from typing import Literal

Method = Literal["GET", "POST", "PUT", "DELETE"]

def request(method: Method, url: str) -> None: ...

request("GET", "/users")     # ok
request("PATCH", "/users")   # ty error: "PATCH" is not a valid Method
```

```typescript
// TS equivalent — identical idea
type Method = "GET" | "POST" | "PUT" | "DELETE";
```

Go has no equivalent — you'd use a named type plus runtime validation, or a set of `const`s with no compiler guarantee.

### `Final` — can't be reassigned

Like TS `const` / `readonly` (the checker enforces it; the runtime doesn't).

```python
from typing import Final

MAX_RETRIES: Final = 3          # type inferred as int, reassignment is a checker error
API_BASE: Final[str] = "https://api.example.com"

MAX_RETRIES = 5                 # ty error: cannot assign to Final
```

### `Annotated` — attach metadata to a type

`Annotated[T, ...]` is `T` plus payload that tools read. FastAPI and Pydantic lean on it (modules 04, 07), so recognize it:

```python
from typing import Annotated

UserId = Annotated[int, "primary key"]   # reads as `int`, carries metadata
# In FastAPI: def handler(q: Annotated[str, Query(max_length=50)]): ...
```

### `Self` — methods returning their own type (PEP 673)

For fluent/builder APIs and `from_*` classmethods — no naming the class or a `TypeVar` bound to it:

```python
from typing import Self

class QueryBuilder:
    def where(self, cond: str) -> Self:    # returns the actual subclass type
        ...
        return self

    @classmethod
    def new(cls) -> Self:
        return cls()
```

```typescript
// TS: `this` type does the same job
class QueryBuilder {
  where(cond: string): this { /* ... */ return this; }
}
```

### `Never` + `assert_never` — exhaustiveness checking

`Never` is the bottom type (TS `never`, Kotlin `Nothing`). Its killer use: making the checker prove you handled every case of a union.

```python
from typing import Literal, assert_never

Shape = Literal["circle", "square"]

def area(shape: Shape, size: float) -> float:
    match shape:
        case "circle":
            return 3.14159 * size * size
        case "square":
            return size * size
        case _:
            assert_never(shape)   # add "triangle" to Shape -> ty errors HERE
```

Extend `Shape` and forget a case, and `ty` reports that `shape` reaching `assert_never` isn't `Never` — a static guarantee you covered the union. Same trick as TS's `const _exhaustive: never = x` and Go's "default panics," but checked statically.

## PEP 695 generics — the modern syntax

Pre-3.12 generics meant hand-declaring `TypeVar`s; 3.12+ has inline syntax that reads almost exactly like TS and Go.

```python
type Vector = list[float]              # `type` statement (PEP 695)
type Pair[T] = tuple[T, T]             # generic alias
type Handler = Callable[[Request], Response]
```

### Generic classes

<Tabs syncKey="lang">

```typescript
class Box<T> {
  constructor(private value: T) {}

}
```

```python
class Box[T]:                         # PEP 695: no TypeVar import, no Generic[T] base
```

### Bounds and constraints

A bound says "T must be a subtype of X" — like TS `<T extends X>` and Go's `[T Constraint]`.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">

```typescript
function maxOf<T extends { valueOf(): number }>(a: T, b: T): T {
  return a.valueOf() >= b.valueOf() ? a : b;
}
```

  </TabItem>
  <TabItem label="Go">

```go
import "cmp"

func MaxOf[T cmp.Ordered](a, b T) T {
    if a >= b {
        return a
    }
    return b
}
```

  </TabItem>
  <TabItem label="Python">

```python
def max_of[T: (int, float, str)](a: T, b: T) -> T:   # constraint: T is one of these
    return a if a >= b else b

# Or an upper bound (T must be a subtype of a Protocol/class):
def biggest[T: Comparable](items: list[T]) -> T:     # T: Bound  ==  <T extends Bound>
    ...
```

  </TabItem>
</Tabs>

| Concept | TypeScript | Go | Python (PEP 695) |
|---|---|---|---|
| Generic fn | `function f<T>(...)` | `func F[T any](...)` | `def f[T](...)` |
| Generic class | `class Box<T>` | `type Box[T any] struct` | `class Box[T]` |
| Upper bound | `<T extends X>` | `[T X]` (interface) | `[T: X]` |
| Constraint set | union in bound | union interface | `[T: (A, B, C)]` |
| Type alias | `type V = ...` | `type V = ...` | `type V = ...` |

The old `T = TypeVar("T")` / `class Box(Generic[T])` still works in existing codebases — recognize it when you read it, write the PEP 695 form in new code.

## Protocols — structural typing as a contract

Python has two ways to express "an interface": **ABCs** (nominal — a type counts only if it inherits; like Kotlin `interface` / TS `implements`) and **Protocols** (PEP 544, structural — a type counts if it has the right shape; exactly a Go interface and a TS interface).

<Tabs syncKey="lang">
  <TabItem label="TypeScript">

```typescript
// TS interfaces are structural: anything shaped right satisfies them.
interface Reader {
  read(n: number): string;
}

function consume(r: Reader) { /* ... */ }

// No `implements` needed — this object just has to fit.
consume({ read: (n) => "x".repeat(n) });
```

  </TabItem>
  <TabItem label="Go">

```go
// Go interfaces are structural: implement the method set, you satisfy it.
type Reader interface {
    Read(n int) string
}

func Consume(r Reader) { /* ... */ }

// A type satisfies Reader just by having Read — never says "implements Reader".
type Stub struct{}
func (Stub) Read(n int) string { return "" }
```

  </TabItem>
  <TabItem label="Python">

```python
from typing import Protocol

# A Protocol is structural: any class with a matching `read` satisfies it,
# WITHOUT inheriting Reader. Duck typing made into a checked contract.
class Reader(Protocol):
    def read(self, n: int) -> str: ...

def consume(r: Reader) -> None: ...

class Stub:                       # note: does NOT inherit Reader
    def read(self, n: int) -> str:
        return ""

consume(Stub())                   # ty: ok — Stub is shaped like Reader
```

  </TabItem>
</Tabs>

**`Protocol` is Python's `interface` in the Go/TS sense.** Define the shape where it's used; any conforming type fits without a declaration. Functions depend on a shape, not a concrete class, so tests can pass a stub.

### Protocol vs ABC — when to use which

```python
from abc import ABC, abstractmethod
from typing import Protocol

# ABC — nominal. Implementers MUST subclass. Use when YOU own the hierarchy
# and want shared implementation, or to forbid instantiation of the base.
class Storage(ABC):
    @abstractmethod
    def save(self, key: str, value: bytes) -> None: ...

class S3Storage(Storage):              # must explicitly subclass
    def save(self, key: str, value: bytes) -> None: ...

# Protocol — structural. Implementers need only the right shape. Use when you
# want to accept types you DON'T own (stdlib types, third-party classes, mocks).
class SupportsSave(Protocol):
    def save(self, key: str, value: bytes) -> None: ...
```

| | ABC | Protocol |
|---|---|---|
| Conformance | nominal (must subclass) | structural (right shape) |
| Closest TS analog | `class X implements I` | `interface I` |
| Closest Go analog | embedding a base | `interface` |
| Can shared code live in it? | yes (concrete methods) | no (just shape) |
| Accept types you don't own? | no | yes |
| Use it when | you own the hierarchy | you describe a capability |

Reach for **Protocol by default** — it keeps coupling low. Reach for ABC when you genuinely want shared behavior or to prevent direct instantiation.

### `@runtime_checkable`

Protocols are erased like all hints, so `isinstance(x, Reader)` normally fails. Add `@runtime_checkable` to allow it — but it only checks method names exist, not signatures:

```python
from typing import Protocol, runtime_checkable

@runtime_checkable
class Reader(Protocol):
    def read(self, n: int) -> str: ...

isinstance(Stub(), Reader)    # True — but only checks `read` EXISTS, not its types
```

## `match` / `case` — structural pattern matching

`match` (PEP 634) is far more than a `switch`: it destructures and binds while it branches — TS's `switch` plus destructuring, or Go's type switch plus struct fields, in one construct.

### Literals, capture, and the wildcard

<Tabs syncKey="lang">
  <TabItem label="TypeScript">

```typescript
switch (status) {
  case 200: return "OK";
  case 404: return "Not Found";
  case 500: case 502: case 503: return "Server Error";
  default: return "Unknown";
}
```

  </TabItem>
  <TabItem label="Go">

```go
switch status {
case 200:
    return "OK"
case 404:
    return "Not Found"
case 500, 502, 503:
    return "Server Error"
default:
    return "Unknown"
}
```

  </TabItem>
  <TabItem label="Python">

```python
match status:
    case 200:
        return "OK"
    case 404:
        return "Not Found"
    case 500 | 502 | 503:        # `|` combines patterns (like Go's comma cases)
        return "Server Error"
    case code:                   # bare name CAPTURES the value (binds `code`)
        return f"Unknown: {code}"
    # `case _:` is the wildcard if you don't want to bind
```

  </TabItem>
</Tabs>

:::caution[A bare name in `case` captures, it does not compare]
`case foo:` does **not** mean "if status equals the variable `foo`." It always binds a new variable `foo` to the matched value and matches everything — so it must come last. To match an existing constant, use a dotted name (`case Status.OK:`) or a literal.
:::

### Class patterns — Go's type switch, but with destructuring

Match on type **and** pull fields out at once:

```python
from dataclasses import dataclass

@dataclass
class Circle:
    radius: float

@dataclass
class Rectangle:
    width: float
    height: float

def area(shape: Circle | Rectangle) -> float:
    match shape:
        case Circle(radius=r):                 # match type AND bind its field
            return 3.14159 * r * r
        case Rectangle(width=w, height=h):
            return w * h
```

```go
// Go's type switch is the closest analog, but you bind the whole value
// then reach into fields manually:
switch s := shape.(type) {
case Circle:
    return math.Pi * s.Radius * s.Radius
case Rectangle:
    return s.Width * s.Height
}
```

### Guards, mapping, and sequence patterns

```python
def describe(value: object) -> str:
    match value:
        case int() | float() if value < 0:        # GUARD: pattern + `if` condition
            return "negative number"
        case [first, *rest]:                       # SEQUENCE: bind head and tail
            return f"list starting with {first}, {len(rest)} more"
        case {"type": "user", "name": str(name)}:  # MAPPING: match dict shape + bind
            return f"user named {name}"
        case str() if not value:
            return "empty string"
        case _:
            return "something else"
```

Sequence patterns (`[first, *rest]`) and mapping patterns (`{"key": value}`) have no direct TS/Go equivalent — they're destructuring assignment fused into the branch condition. Combined with `Literal` unions and `assert_never`, `match` is how you get exhaustive, type-narrowed dispatch in Python.

## TypedDict, NamedTuple, and Enums

### `TypedDict` — typed shapes for plain dicts

When data really is a `dict` (JSON payloads, config) but you want it typed. Almost exactly a TS interface over an object — purely structural and erased:

```python
from typing import TypedDict, NotRequired

class UserDict(TypedDict):
    id: int
    name: str
    email: NotRequired[str]      # optional key (like TS `email?: string`)

u: UserDict = {"id": 1, "name": "Alice"}   # checker validates the shape
```

```typescript
interface UserDict {
  id: number;
  name: string;
  email?: string;
}
```

Use `TypedDict` when you must stay a `dict` (interop, JSON). When you control the type, prefer a `dataclass` (module 03) or Pydantic model (module 04) — real objects, methods, runtime validation.

### `NamedTuple` — a lightweight typed record

An immutable tuple with named fields — handy for small fixed records and multiple return values:

```python
from typing import NamedTuple

class Point(NamedTuple):
    x: float
    y: float

p = Point(1.0, 2.0)
p.x            # 1.0  (attribute access)
px, py = p     # also unpacks like a tuple
```

### Enums — `Enum`, `StrEnum`, `IntEnum`

In 2026, **`StrEnum`** is what you usually want for string-valued enums — members *are* strings, so they serialize and compare cleanly.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">

```typescript
enum Direction { North = "NORTH", South = "SOUTH" }
// or `const Direction = {...} as const` for the lighter idiom
```

  </TabItem>
  <TabItem label="Go">

```go
type Direction int
const (
    North Direction = iota
    South
)
func (d Direction) String() string { return [...]string{"NORTH", "SOUTH"}[d] }
```

  </TabItem>
  <TabItem label="Python">

```python
from enum import Enum, StrEnum, IntEnum, auto

class Direction(Enum):
    NORTH = auto()             # plain enum: members are unique opaque values
    SOUTH = auto()

class Status(StrEnum):         # members ARE strings (3.11+) — best for APIs/JSON
    ACTIVE = "active"
    BANNED = "banned"

Status.ACTIVE == "active"      # True — StrEnum members compare equal to their str

class Priority(IntEnum):       # members ARE ints — sortable, comparable
    LOW = 1
    HIGH = 10
```

  </TabItem>
</Tabs>

`match` pairs beautifully with enums for exhaustive dispatch:

```python
def handle(s: Status) -> str:
    match s:
        case Status.ACTIVE: return "ok"
        case Status.BANNED: return "blocked"
        # add a member and your `match` (with assert_never) flags the gap
```

## Gotchas that bite TS/Go devs

### Mutable default arguments — the classic trap

Default argument values are evaluated **once, at function definition**, and shared across calls. A mutable default (`[]`, `{}`) becomes a persistent shared object:

```python
def add_item(item: str, bucket: list[str] = []) -> list[str]:   # BUG
    bucket.append(item)
    return bucket

add_item("a")    # ['a']
add_item("b")    # ['a', 'b']  <-- the SAME list!

# Fix: default to None, create inside.
def add_item(item: str, bucket: list[str] | None = None) -> list[str]:
    if bucket is None:
        bucket = []
    bucket.append(item)
    return bucket
```

Ruff flags this (`B006`). No Go/TS analog — in both, a literal default would be re-created each call.

### Truthiness — empty containers are falsy

`0`, `""`, `[]`, `{}`, `set()`, and `None` are all falsy — broader than Go (no truthiness) and bites in TS:

```python
items: list[str] = get_items()
if not items:        # True if the list is EMPTY *or* None — often what you want
    ...

count = 0
if count:            # False! 0 is falsy. If you meant "is it set", this is a bug.
    ...
if count is not None:   # check existence explicitly
    ...
```

Rule: use truthiness for "empty or absent"; use explicit `is None` / `is not None` when `0`, `""`, or `False` are valid values you must distinguish from "missing."

### `is` vs `==` — identity vs equality

`==` compares values (calls `__eq__`); `is` compares object identity. **Always use `is` for `None`, `True`, `False`** — they're singletons — and `==` for everything else.

```python
x is None          # CORRECT — identity check against the None singleton
x == None          # works but wrong style; ty/ruff nudge you to `is None`

a = [1, 2]
b = [1, 2]
a == b             # True  (same value)
a is b             # False (different objects) — like JS `===` on objects, Go ptr ==
```

From Go: `is` ≈ comparing pointers, `==` ≈ comparing values. From TS: `is` ≈ `===` on references, `==` ≈ deep value equality.

### `None` checks narrow the type

Like TS narrowing / Kotlin smart casts, the checker tracks `None` checks:

```python
def name_length(name: str | None) -> int:
    if name is None:
        return 0
    return len(name)     # ty knows `name` is `str` here
```

### Gradual typing, `Any`, `cast`, and `# type: ignore`

Typing is gradual: untyped and typed code coexist, and `Any` is the seam — the escape hatch that opts out of checking. Treat it like TS `any`, not `unknown`:

```python
from typing import Any, cast

data: Any = parse_untyped()    # checker stops checking anything touching `data`

# `cast` = "trust me, it's this type" — no runtime effect (TS `as`, not a conversion)
user = cast(dict[str, int], data)

# `# type: ignore` silences ONE line. Scope it and say why:
result = legacy_lib.do_thing()  # type: ignore[no-untyped-call]  # vendor has no stubs
```

Discipline: prefer `object` over `Any` when you just need "some value" — `object` stays checked (like TS `unknown`). Never blanket-ignore a file; scope to the specific error code. `cast` is a promise, not a conversion — if you're wrong, you get a real runtime bug with no warning.

## Verify it: run the checker

```bash
uv run ty check                 # check the whole project (Astral's fast checker)
uv run ty check src/app/main.py # one file
```

`mypy` is the mature alternative — `uv run mypy src` if a project already uses it. `ty` is shown because it's fast and from the same team as `uv`/`ruff`, but it's younger; switch freely, they check the same hints.

Turn the checker up to strict from day one — like `strict: true` in `tsconfig.json`:

```toml
[tool.ty.rules]
possibly-unbound = "error"

[tool.mypy]            # if you use mypy instead
strict = true          # the single flag that turns on the full strict bundle
warn_return_any = true
```
