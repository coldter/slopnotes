You know Redis from `ioredis` (TS) or `go-redis` (Go) — set a key, read it, slap a TTL, build a rate limiter out of `INCR`. None of that changes in Python. What changes is the client: the **`redis`** package (redis-py), specifically its async client at **`redis.asyncio`** — `await`-everything, same dialect as the rest of your FastAPI app. (`aioredis` was merged into redis-py in 2.0 and is dead; `import aioredis` is history.)

Start Redis from the shared stack: `cd shared-infra && docker compose up -d redis` — connection `redis://localhost:6379`, no auth.

## The client comparison

| Concern | ioredis (TS) | go-redis (Go) | redis-py async (Python) |
|---|---|---|---|
| Package | `ioredis` | `github.com/redis/go-redis/v9` | `redis` (import `redis.asyncio`) |
| Client object | `new Redis()` | `redis.NewClient(&Options{})` | `redis.asyncio.from_url(...)` |
| Connection model | single socket + auto-pipeline | pool | pool (`ConnectionPool`) |
| Async | native Promises | `context.Context` per call | `async`/`await`, coroutines |
| Cluster / Sentinel | built-in | built-in | `RedisCluster`, `Sentinel` |
| Serialization | manual (JSON) | manual (JSON) | manual (JSON via Pydantic) |
| Pipelines / transactions | `pipeline()` / `multi()` | `Pipeline` / `TxPipeline` | `client.pipeline()` |

There's no Spring-`@Cacheable` framework annotation in Python — caching is explicit: you write the get→miss→load→set yourself, or wrap it in a small decorator. No AOP proxy magic to debug, just a function.

### from_url + the connection pool

`redis.asyncio.from_url` is the one call you need. It does **not** open a socket eagerly — it builds a lazy `ConnectionPool`; connections are created on first command. Cheap, and you share one client across the whole app.

```ts

export const redis = new Redis("redis://localhost:6379", {
  maxRetriesPerRequest: 3,
});

await redis.set("user:1:name", "Alice");
const name = await redis.get("user:1:name"); // "Alice"
```

# decode_responses=True returns str instead of bytes (skip it for binary values).

    "redis://localhost:6379",
    decode_responses=True,

:::caution[`decode_responses` is the gotcha everyone hits]
By default redis-py returns **`bytes`** — `await client.get(k)` gives `b"Alice"`. Pass `decode_responses=True` and you get `str` back. Exception: if you store binary blobs on *some* keys, you can't decode globally — use a second client without the flag for those keys, or decode per-call. Don't mix.
:::

### Lifespan integration with FastAPI

Open the pool in the FastAPI **lifespan** (module 07) and stash it on `app.state` — one client per process, like a singleton `*redis.Client` in a Go server struct. The async client's shutdown method is `aclose()` (bare `close()` is deprecated); always `await` it in teardown so pool sockets close cleanly.

```python title="app/main.py"
from contextlib import asynccontextmanager
from collections.abc import AsyncIterator

import redis.asyncio as redis
from fastapi import FastAPI, Request


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    # Startup: build the pool once.
    app.state.redis = redis.from_url(
        "redis://localhost:6379",
        decode_responses=True,
        max_connections=20,
    )
    await app.state.redis.ping()  # fail fast if Redis is down
    yield
    # Shutdown: drain the pool.
    await app.state.redis.aclose()


app = FastAPI(lifespan=lifespan)


def get_redis(request: Request) -> redis.Redis:
    """FastAPI dependency: hand the shared client to route functions."""
    return request.app.state.redis
```

```python title="app/routes.py"
from typing import Annotated

import redis.asyncio as redis
from fastapi import APIRouter, Depends

from app.main import get_redis

router = APIRouter()
RedisDep = Annotated[redis.Redis, Depends(get_redis)]


@router.get("/ping")
async def ping(r: RedisDep) -> dict[str, bool]:
    return {"ok": await r.ping()}
```

## Core data types & commands

Command names are identical to `redis-cli` and nearly identical across all three clients — only `await` and casing differ:

| Redis type | Commands | ioredis | go-redis | redis-py async |
|---|---|---|---|---|
| String | `GET/SET/INCR` | `get/set/incr` | `Get/Set/Incr` | `get/set/incr` |
| Hash | `HSET/HGETALL` | `hset/hgetall` | `HSet/HGetAll` | `hset/hgetall` |
| List | `LPUSH/RPOP/LRANGE` | `lpush/rpop/lrange` | `LPush/RPop/LRange` | `lpush/rpop/lrange` |
| Set | `SADD/SMEMBERS` | `sadd/smembers` | `SAdd/SMembers` | `sadd/smembers` |
| Sorted set | `ZADD/ZRANGE` | `zadd/zrange` | `ZAdd/ZRange` | `zadd/zrange` |

```python title="data types"
# --- String + counter ---
await r.set("greeting", "hello", ex=60)          # SET ... EX 60 (TTL in seconds)
await r.get("greeting")                          # "hello"
await r.incr("page:home:views")                  # atomic counter -> 1, 2, 3...
await r.setnx("lock:job", "1")                   # SET if Not eXists -> True/False

# --- Hash (a record) ---
await r.hset("user:1", mapping={"name": "Alice", "score": "100"})
await r.hgetall("user:1")                         # {"name": "Alice", "score": "100"}
await r.hincrby("user:1", "score", 5)             # 105

# --- List (a FIFO queue: LPUSH to enqueue, RPOP to dequeue) ---
await r.lpush("jobs", "job-a", "job-b")
await r.rpop("jobs")                              # "job-a"
await r.lrange("jobs", 0, -1)                     # ["job-b"]
await r.blpop("jobs", timeout=5)                  # blocking pop, waits up to 5s

# --- Set (unique membership, set algebra) ---
await r.sadd("article:1:tags", "python", "redis")
await r.sismember("article:1:tags", "python")     # True
await r.sinter("tag:python", "tag:redis")         # articles with BOTH tags

# --- Sorted set (leaderboard: members scored, rankable) ---
await r.zadd("leaderboard", {"alice": 100, "bob": 80})
await r.zincrby("leaderboard", 5, "bob")          # bob -> 85
await r.zrevrange("leaderboard", 0, 2, withscores=True)  # top 3 [(b"alice",100.0),...]
await r.zrevrank("leaderboard", "bob")            # 1 (0-based, 0 = highest)
```

One Python trap: `await r.lrange(k, 0, -1)` returns `[]` on a missing list and `hgetall` returns `{}` on a missing hash — both falsy, just like populated ones. If you must distinguish "missing" from "empty," check `await r.exists(k)` explicitly (module 03's truthiness rule).

### Serialization: JSON via Pydantic

Redis stores bytes. Cache a domain object by serializing with Pydantic v2's `model_dump_json()` / `model_validate_json()` (module 04) — fast (Rust core), handles `datetime`/`UUID`/`Decimal`, and validates on the way back out so a corrupt or schema-drifted entry fails loudly instead of silently:

```python title="serializing a model"
from datetime import datetime
from pydantic import BaseModel


class Product(BaseModel):
    id: int
    name: str
    price: float
    created_at: datetime


async def cache_product(r, product: Product) -> None:
    # model_dump_json() -> compact str; round-trips datetime as ISO-8601.
    await r.set(f"product:{product.id}", product.model_dump_json(), ex=300)


async def load_product(r, product_id: int) -> Product | None:
    raw = await r.get(f"product:{product_id}")
    if raw is None:
        return None
    # Validates types on the way out — a malformed entry raises, doesn't lie.
    return Product.model_validate_json(raw)
```

:::caution[Never `pickle` untrusted data]
`pickle` can serialize *any* object — but unpickling executes arbitrary code embedded in the payload. A poisoned cache entry becomes remote code execution. **Never `pickle` anything that crosses a trust boundary**, and treat a shared Redis as a trust boundary. Use JSON. Reach for `pickle` only for ephemeral, single-process, fully-trusted data — and even then JSON or msgpack is usually better.
:::

## Cache-aside

Cache-aside (lazy loading) is the pattern you'll use 90% of the time: on a read, check the cache; on a miss, load from the source and populate the cache with a TTL; on a write, invalidate.

<Mermaid title="Cache-aside read path: hit returns cached; miss loads, sets with TTL, returns" code={`
flowchart TB
  A["read(id)"] --> B["GET cache:id"]
  B -->|"hit"| C["return cached value (no DB hit)"]
  B -->|"miss"| D["load from DB"]
  D --> E["SET cache:id value EX ttl"]
  E --> F["return value"]
`} />

```ts

  const cached = await redis.get(`product:${id}`);
  if (cached) return JSON.parse(cached);

  const product = await db.product.findUnique({ where: { id } });
  if (product) {
    await redis.set(`product:${id}`, JSON.stringify(product), "EX", 300);
  }
  return product;
}
```

### Invalidation: write the DB, then delete the key

On a write, the safe default is **delete the cache key, don't update it** — the next read repopulates from the source of truth. And order matters: commit the DB **first**, then delete the key. Deleting before the commit lets a concurrent read slip in, miss the cache, read the *old* committed row, and repopulate the cache with stale data that lives until TTL (the "delayed double delete" is the paranoid extra pass):

```python title="invalidate on write"
async def update_product(r, db, product_id: int, patch: ProductPatch) -> Product:
    product = await save_to_db(db, product_id, patch)
    await r.delete(f"product:{product_id}")   # next read repopulates
    return product
```

### A reusable cache decorator

Wrap cache-aside in a decorator — the closest Python gets to Spring's `@Cacheable`, twelve readable lines. PEP 695 generics (`[**P, T]`) keep the wrapper fully typed:

```python title="app/cache.py"
import functools
import json
from collections.abc import Awaitable, Callable
from typing import Any

import redis.asyncio as redis


def cached(r: redis.Redis, *, ttl: int, prefix: str = "cache"):
    """Cache-aside decorator for async functions returning JSON-able values."""

    def decorator[**P, T](fn: Callable[P, Awaitable[T]]) -> Callable[P, Awaitable[T]]:
        @functools.wraps(fn)
        async def wrapper(*args: P.args, **kwargs: P.kwargs) -> T:
            # Build a stable key from the call signature.
            key = f"{prefix}:{fn.__name__}:" + ":".join(map(str, args))

            hit = await r.get(key)
            if hit is not None:
                return json.loads(hit)

            result = await fn(*args, **kwargs)
            await r.set(key, json.dumps(result, default=str), ex=ttl)
            return result

        return wrapper

    return decorator


# Usage
@cached(client, ttl=300, prefix="reports")
async def expensive_report(year: int, region: str) -> dict[str, Any]:
    ...  # a 2-second aggregation query
```

Keying caveat: `str(args)` is fine for scalars (`int`, `str`, `UUID`) but breaks for objects whose `repr` isn't stable or unique — hash a canonical representation (`hashlib.sha256(json.dumps(...).encode())`) or take an explicit `key=`, same discipline as a memoization key in TS or a `map[string]` cache key in Go.

### Write-through, briefly

Write-through updates the cache *and* the DB on every write, keeping the cache permanently warm — at the cost of two writes and the risk of caching a value the DB never committed. Use it only for hot, read-heavy keys you control:

```python title="write-through"
async def set_product(r, db, product: Product) -> Product:
    saved = await save_to_db(db, product)
    # Write the fresh value straight into the cache instead of deleting.
    await r.set(f"product:{saved.id}", saved.model_dump_json(), ex=300)
    return saved
```

Cache-aside-with-delete is the safer default.

## Rate limiting

The counter lives in Redis so **every instance of your service shares one limit per client** — what an in-memory `express-rate-limit` or `golang.org/x/time/rate` can't do across a fleet. The check must be **atomic** (single `INCR` or one Lua script), otherwise a read-then-write race lets two concurrent requests both pass.

| Algorithm | Data structure | Accuracy | Cost | Notes |
|---|---|---|---|---|
| Fixed window | `INCR` + `EXPIRE` | low (boundary burst) | 1 key | cheapest; allows 2× at edges |
| Sliding window | sorted set of timestamps | high | O(log n) per req | precise; what most APIs want |
| Token bucket | hash (tokens + last-refill) | high, allows bursts | small Lua | smooth refill + burst capacity |

### Fixed window

Bucket the clock into slices of `window` seconds, `INCR` the bucket, `EXPIRE` on first hit — one atomic Lua script. Cheap, but a client can fire `limit` requests at the end of one window and `limit` more at the start of the next:

```python title="app/ratelimit.py — fixed window"
import time

FIXED_WINDOW_LUA = """
local count = redis.call('INCR', KEYS[1])
if count == 1 then
  redis.call('EXPIRE', KEYS[1], ARGV[1])
end
local ttl = redis.call('TTL', KEYS[1])
return {count, ttl}
"""


async def fixed_window_allow(r, client_id: str, limit: int, window: int) -> bool:
    bucket = int(time.time()) // window
    key = f"rate:fixed:{client_id}:{bucket}"
    count, _ttl = await r.eval(FIXED_WINDOW_LUA, 1, key, window)
    return count <= limit
```

### Sliding window (sorted sets + Lua)

Keep one sorted set per client, members = requests, score = timestamp. On each request: prune old (`ZREMRANGEBYSCORE`), count (`ZCARD`), reject if at limit, else `ZADD` + refresh TTL — all one atomic script:

```python title="app/ratelimit.py — sliding window"
import time
import uuid

SLIDING_WINDOW_LUA = """
-- KEYS[1] = zset key
-- ARGV: now_ms, window_ms, limit, member, ttl_seconds
local now    = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit  = tonumber(ARGV[3])

redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, now - window)
local count = redis.call('ZCARD', KEYS[1])
if count >= limit then
  local oldest = redis.call('ZRANGE', KEYS[1], 0, 0, 'WITHSCORES')
  return {0, oldest[2]}
end
redis.call('ZADD', KEYS[1], now, ARGV[4])
redis.call('EXPIRE', KEYS[1], ARGV[5])
return {1, 0}
"""


async def sliding_window_allow(r, client_id: str, limit: int, window: int) -> bool:
    now_ms = int(time.time() * 1000)
    member = f"{now_ms}-{uuid.uuid4()}"  # unique: two reqs in the same ms must not collide
    allowed, _oldest = await r.eval(
        SLIDING_WINDOW_LUA, 1,
        f"rate:sliding:{client_id}",
        now_ms, window * 1000, limit, member, window,
    )
    return bool(allowed)
```

### Token bucket

A bucket holds up to `capacity` tokens, refilled at `rate`/second. Each request spends one; empty rejects. Allows bursts up to `capacity` while enforcing the long-run average — the model behind `golang.org/x/time/rate`. Store `tokens` + `last_refill` in a hash, reconcile lazily in Lua:

```lua title="Lua: token bucket"
-- KEYS[1] = bucket hash   ARGV: capacity, refill_per_sec, now, requested
local capacity = tonumber(ARGV[1])
local refill   = tonumber(ARGV[2])
local now      = tonumber(ARGV[3])
local want     = tonumber(ARGV[4])

local data   = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(data[1]) or capacity
local ts     = tonumber(data[2]) or now

tokens = math.min(capacity, tokens + (now - ts) * refill)  -- lazy refill
local allowed = tokens >= want
if allowed then tokens = tokens - want end

redis.call('HMSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('EXPIRE', KEYS[1], math.ceil(capacity / refill) * 2)
return allowed and 1 or 0
```

### As a FastAPI dependency

FastAPI's idiomatic unit is a **dependency** — it runs before the route, can read the request, and short-circuits with `HTTPException`. Use a dependency when limits vary per route; use `@app.middleware("http")` for one global blanket cap:

func RateLimit(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, req *http.Request) {
        if !allow(req.Context(), clientID(req), 10, 60) {
            w.Header().Set("Retry-After", "60")
            http.Error(w, "Too Many Requests", http.StatusTooManyRequests)
            return
        }
        next.ServeHTTP(w, req)
    })
}

def rate_limit(limit: int = 10, window: int = 60):

## Pub/Sub

Fire-and-forget real-time messaging: publish to a channel, every current subscriber gets it, and if nobody's listening the message vanishes. Perfect for cross-instance cache invalidation and live UI nudges — wrong for anything that must not be lost. The async client gives a `pubsub()` object consumed with `async for` — the same `async for` as module 06's streams:

<Tabs syncKey="lang">
  <TabItem label="TypeScript">

```ts
const pub = new Redis();
await pub.publish("invalidate", JSON.stringify({ key: "product:1" }));

const sub = new Redis(); // a subscriber connection is dedicated — can't run other cmds
sub.subscribe("invalidate");
sub.on("message", (_chan, msg) => cache.delete(JSON.parse(msg).key));
```

  </TabItem>
  <TabItem label="Go">

```go
rdb.Publish(ctx, "invalidate", `{"key":"product:1"}`)

sub := rdb.Subscribe(ctx, "invalidate")
for msg := range sub.Channel() {
    cache.Delete(parseKey(msg.Payload))
}
```

  </TabItem>
  <TabItem label="Python">

```python
# --- Publisher (any client) ---
await r.publish("invalidate", json.dumps({"key": "product:1"}))

# --- Subscriber (a supervised background task started in the lifespan) ---
async def invalidation_listener(r) -> None:
    async with r.pubsub() as pubsub:
        await pubsub.subscribe("invalidate")
        async for message in pubsub.listen():
            if message["type"] != "message":   # skip the "subscribe" ack
                continue
            payload = json.loads(message["data"])
            local_cache.pop(payload["key"], None)
```

  </TabItem>

A subscribed connection can't issue normal commands — Redis dedicates it to messages. Run the listener as a supervised background task (started in lifespan, cancelled on shutdown — module 06) using a separate connection from the one request handlers use for `GET`/`SET`.

**Redis Streams** (`XADD`/`XREAD`/consumer groups) is the durable, replayable cousin of pub/sub — messages persist, late consumers read history, consumer groups give Kafka-style partitioned, acknowledged consumption. A genuine lightweight event log. But for durable events as a first-class architectural concern — ordering guarantees, long retention, many consumer groups — reach for Kafka ([module 11](/modern-python/11-kafka-events/)). Rule of thumb: Streams for intra-app work queues you already have Redis for; Kafka when the event log *is* the system.

## Distributed locks & idempotency

### A simple lock with SET NX

`SET key token NX EX ttl` coordinates "only one worker does X at a time" across instances. Release by deleting **only if you still own it** — checked atomically in Lua, because a naive `GET`-then-`DEL` can delete a lock another worker acquired after yours expired:

```python title="app/lock.py"
import uuid
from contextlib import asynccontextmanager

RELEASE_LUA = """
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0
"""


@asynccontextmanager
async def redis_lock(r, name: str, ttl: int = 10):
    token = str(uuid.uuid4())  # proves ownership on release
    acquired = await r.set(f"lock:{name}", token, nx=True, ex=ttl)
    if not acquired:
        raise RuntimeError(f"could not acquire lock {name}")
    try:
        yield
    finally:
        await r.eval(RELEASE_LUA, 1, f"lock:{name}", token)  # release iff still ours
```

:::caution[This lock is "good enough", not bulletproof]
Single-node `SET NX` is fine for "don't run this cron twice." It is **not** safe for correctness-critical mutual exclusion: if the TTL expires while your worker is still running, a second worker acquires it and two run concurrently. **Redlock** was proposed to harden this but is contested — it still relies on bounded clocks and pauses. Honest guidance: if losing the lock would corrupt data, don't rely on a Redis lock for correctness — use a fencing token (a monotonic counter the downstream resource checks) or a DB advisory lock. Use Redis locks for *efficiency* (avoiding duplicate work), not for *safety*.
:::

### Idempotency keys

The flip side of locking: make a request safe to retry. The client sends an `Idempotency-Key` header; you `SET NX` it before doing the work and return the stored response on a replay — how Stripe-style "retry won't double-charge" works:

```python title="idempotency dependency"
async def idempotent(request: Request) -> str | None:
    key = request.headers.get("idempotency-key")
    if key is None:
        return None
    r = request.app.state.redis
    # Reserve the key; if it already holds a response, this returns it.
    first = await r.set(f"idem:{key}", "in-progress", nx=True, ex=86400)
    if not first:
        cached = await r.get(f"idem:{key}")
        raise HTTPException(409, detail=f"duplicate request (status: {cached})")
    return key
    # On success, the handler overwrites idem:{key} with the serialized response.
```

## Gotchas TS/Go devs hit

### Thundering herd / cache stampede

When a hot key expires, every concurrent request misses at once and stampedes the DB with the same expensive query. The fix is **single-flight**: one caller recomputes, the rest wait — an `asyncio.Lock` per key in-process (Go's `singleflight`), plus a short Redis `SET NX` lock cross-process:

```python title="single-flight cache-aside"
import asyncio

_locks: dict[str, asyncio.Lock] = {}


async def get_single_flight(r, db, product_id: int) -> Product | None:
    key = f"product:{product_id}"
    cached = await r.get(key)
    if cached is not None:
        return Product.model_validate_json(cached)

    # Per-key in-process lock: collapse concurrent misses in THIS worker to one load.
    lock = _locks.setdefault(key, asyncio.Lock())
    async with lock:
        cached = await r.get(key)          # double-check: someone may have filled it
        if cached is not None:
            return Product.model_validate_json(cached)
        product = await load_from_db(db, product_id)
        if product is not None:
            await r.set(key, product.model_dump_json(), ex=300)
        return product
```

For cross-instance herds, add jitter to TTLs (`ex=300 + random.randint(0, 30)`) so a million keys set in the same deploy don't all expire in the same second, and/or gate the recompute with the Redis `SET NX` lock.

### The rest of the checklist

| Gotcha | What bites you | Discipline |
|---|---|---|
| **Stale cache** | serving old data after a write | delete key *after* DB commit; short TTL as a backstop |
| **No TTL** | keys live forever, Redis OOMs | every cache key gets an `ex=`; reserve no-TTL for durable state |
| **TTL stampede** | mass-set keys expire together | add random jitter to TTLs |
| **`bytes` vs `str`** | `if value == "x"` silently false | `decode_responses=True` (or decode explicitly) |
| **Empty vs missing** | `[]`/`{}` are falsy like missing | check `await r.exists(k)` when it matters |
| **`pickle`** | RCE from a poisoned entry | JSON only across trust boundaries |
| **Caching `None`** | one miss poisons the cache for the TTL | decide explicitly whether negatives are cached, short TTL if so |

**TTL discipline is the whole game:** every cache key has a TTL, and you can justify its number. A cache without TTLs isn't a cache — it's a second database that drifts and never reconciles. When in doubt, pick a *shorter* TTL: a cache miss is cheap; serving stale data for an hour is not.
