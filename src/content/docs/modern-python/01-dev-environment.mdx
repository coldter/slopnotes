One tool runs the whole Python workflow: [`uv`](https://docs.astral.sh/uv/). It installs Python itself, manages projects, locks dependencies, and runs code — a single Rust binary, 10–100× faster than the tools it replaces. Lint/format is `ruff`, type-checking is `ty`. That's the whole toolbox.

## Install uv

| TypeScript | Go | Python (2026) |
|---|---|---|
| `nvm` manages Node versions | Go toolchain manages itself | **`uv` manages Python versions** |
| `npm` / `pnpm` installs deps | `go mod` | **`uv` installs deps** |
| `node_modules/` | `$GOPATH/pkg/mod` | **`.venv/`** (managed for you) |
| `npx` (run a one-off tool) | `go run pkg@latest` | **`uvx`** (run a one-off tool) |
| V8 runtime | compiled in | CPython interpreter (uv-installed) |

<Steps>

1. Install the standalone binary (no Python needed first):

   ```bash
   # macOS / Linux
   curl -LsSf https://astral.sh/uv/install.sh | sh

   # Windows (PowerShell)
   powershell -c "irm https://astral.sh/uv/install.ps1 | iex"

   # or via Homebrew
   brew install uv
   ```

2. Verify, and let uv install a Python for you:

   ```bash
   uv --version            # uv 0.7.x or later
   uv python install 3.14  # download & manage CPython 3.14
   uv python list          # show installed + available versions
   ```

3. Keep uv itself current:

   ```bash
   uv self update
   ```

</Steps>

:::tip[Let uv own your interpreters]
Don't use system Python, Homebrew Python, or `pyenv` — same rule as never `apt install nodejs` and fighting the OS package manager. `uv python install` keeps interpreters in its own directory and never touches the distro Python.
:::

### Pin a Python version

This is `.nvmrc` / the `go` directive, managed by uv:

```bash
uv python pin 3.14   # writes ".python-version" with "3.14"
```

Commit `.python-version` to git — anyone running a `uv` command gets that interpreter auto-installed if missing. No "works on my machine."

Python 3.13+ also ships an experimental **free-threaded** (no-GIL) build: `uv python install 3.14t` (the `t` suffix). Stick with the default build for backend work; module 05 covers when the no-GIL build helps.

## Your first project: `uv init`

```bash
uv init example-app
cd example-app
```

For a backend service, use the packaged `src/` layout:

```bash
uv init --package --app example-app   # src/ layout, packaged app
```

<FileTree>
- example-app/
  - pyproject.toml deps + metadata (like package.json / go.mod)
  - uv.lock resolved lockfile (like package-lock.json / go.sum)
  - .python-version pinned interpreter (like .nvmrc)
  - README.md
  - .gitignore
  - src/
    - example_app/
      - **\_\_init\_\_.py** marks the package
- (.venv/ created on first `uv run` — gitignored)
</FileTree>

Add a dependency and run something:

```bash
uv add httpx            # adds to dependencies + updates uv.lock + installs
uv add --dev pytest ty  # dev-only dependency group
uv run python -c "import httpx; print(httpx.__version__)"
```

Notice what you did **not** do: no `python -m venv`, no `source .venv/bin/activate`, no `pip install`, no `pip freeze > requirements.txt`. `uv run` creates and syncs the venv on demand, every time. Treat `.venv` like `node_modules` — generated, gitignored, never hand-managed.

### The command map: uv ↔ npm ↔ go

| What you want | npm | go | uv |
|---|---|---|---|
| Install the language runtime | `nvm install 22` | (bundled) | `uv python install 3.14` |
| Pin the runtime version | `.nvmrc` | `go` line in `go.mod` | `uv python pin 3.14` |
| Create a new project | `npm init -y` | `go mod init` | `uv init` |
| Add a dependency | `npm install axios` | `go get pkg` | `uv add httpx` |
| Add a dev dependency | `npm install -D vitest` | `go get` (test) | `uv add --dev pytest` |
| Remove a dependency | `npm uninstall axios` | `go get pkg@none` | `uv remove httpx` |
| Install everything (CI/fresh clone) | `npm ci` | `go mod download` | `uv sync` |
| Update the lockfile | `npm update` | `go get -u ./...` | `uv lock --upgrade` |
| Run your app | `npm start` | `go run .` | `uv run python -m app.main` |
| Run an arbitrary command in-env | `npm exec` | — | `uv run <cmd>` |
| Run a tool without installing it | `npx prettier` | `go run pkg@latest` | `uvx ruff check` |
| Install a global CLI tool | `npm i -g eslint` | `go install pkg@latest` | `uv tool install ruff` |
| Show the dependency tree | `npm ls` | `go mod graph` | `uv tree` |
| Lockfile | `package-lock.json` | `go.sum` | `uv.lock` |
| Manifest | `package.json` | `go.mod` | `pyproject.toml` |

:::caution[`uv add`, not `pip install`]
`pip install` mutates the environment without touching `pyproject.toml` or `uv.lock`, so it silently drifts — the exact problem `requirements.txt` had. Always `uv add`: it edits the manifest and re-locks atomically. `uv pip install` exists as an escape hatch, but you almost never need it.
:::

### `uv run` and the lockfile workflow

`uv run` is the workhorse. It checks that `.venv` matches `uv.lock` and re-syncs if not — the environment is always correct, like `go run` always compiling against the resolved module graph.

```bash
uv run main.py                 # run a script
uv run python                  # REPL inside the project env
uv run pytest                  # run a dev tool
uv run -- uvicorn app.main:app --reload   # args after --
```

| Action | npm | uv |
|---|---|---|
| Resolve & write the lockfile | `npm install` (implicitly) | `uv lock` |
| Materialize the env from the lock | `npm ci` | `uv sync` |
| Both, on demand | `npm install` | `uv run` (auto) |

`uv.lock` is cross-platform and hashed — commit it. It's the source of truth for reproducible installs in CI and Docker.

### One-off tools with `uvx`

`uvx` is `npx`: run a tool in an ephemeral, cached environment without adding it to your project.

```bash
uvx ruff check .                 # lint without installing ruff into the project
uvx --from 'httpie' http GET example.com
uvx cowsay@latest -t "modern python"
```

Use `uvx` for tools you run occasionally; `uv add --dev` for tools the project workflow depends on (locked and reproducible for the team).

## Single-file scripts (PEP 723)

One file with dependencies, no project. PEP 723 inline metadata in a comment block — `uv run` reads it, builds a throwaway env, runs it:

```python title="fetch.py"
# /// script
# requires-python = ">=3.13"
# dependencies = ["httpx"]
# ///
import httpx

resp = httpx.get("https://api.github.com/zen")
print(resp.text)
```

```bash
uv run fetch.py                 # uv reads the header, installs httpx in a cache, runs it
uv add --script fetch.py rich   # uv can add inline deps to a script for you
```

## `pyproject.toml` anatomy

`pyproject.toml` is `package.json` **and** `go.mod` **and** tool config, in one standardized file:

```toml title="pyproject.toml"
# ===== PROJECT METADATA (PEP 621) — like the top of package.json =====
[project]
name = "example-app"              # distribution name (like "name" in package.json)
version = "0.1.0"                 # like package.json "version"
description = "An example backend service"
readme = "README.md"
requires-python = ">=3.13"        # like "engines.node" / the go directive
authors = [{ name = "You", email = "you@example.com" }]

# Runtime dependencies — like package.json "dependencies" / go.mod "require"
dependencies = [
    "fastapi>=0.115",
    "httpx>=0.27",
]

# ===== DEPENDENCY GROUPS (PEP 735) — like "devDependencies", but plural =====
# Not installed for consumers; `uv sync` installs the "dev" group by default.
[dependency-groups]
dev = [
    "pytest>=8",
    "ruff>=0.6",
    "ty",
]

# ===== ENTRY POINTS — like package.json "bin" =====
[project.scripts]
example-app = "example_app.main:main"   # creates a CLI named example-app

# ===== TOOL CONFIG — ruff, ty, etc. live here (no extra config files) =====
[tool.ruff]
line-length = 100
target-version = "py314"

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B"]   # pycodestyle, pyflakes, isort, pyupgrade, bugbear

[tool.ty]
# ty configuration goes here (sane defaults; see the type-checking section)

# ===== BUILD BACKEND — how the package is built (uv's, by default) =====
[build-system]
requires = ["uv_build>=0.7"]
build-backend = "uv_build"
```

| Concept | package.json | go.mod | pyproject.toml |
|---|---|---|---|
| Package name | `name` | module path | `[project] name` |
| Version | `version` | (tags) | `[project] version` |
| Runtime version constraint | `engines.node` | `go 1.23` | `requires-python` |
| Runtime deps | `dependencies` | `require` | `[project] dependencies` |
| Dev deps | `devDependencies` | (test imports) | `[dependency-groups] dev` |
| Optional/extra deps | `peerDependencies` | build tags | `[project.optional-dependencies]` |
| CLI entry points | `bin` | — | `[project.scripts]` |
| Tool config | `.eslintrc`, `.prettierrc` | — | `[tool.*]` (one file) |
| Build config | `tsconfig.json` build | — | `[build-system]` |

`[dependency-groups]` (PEP 735) are developer extras — test runners, linters — never shipped to consumers. `[project.optional-dependencies]` are consumer-facing extras a user opts into (`pip install example-app[redis]`), like npm `peerDependencies` you toggle. Backend apps mostly use `dependency-groups`.

## Ruff: lint + format in one tool

[`ruff`](https://docs.astral.sh/ruff/) replaces `black` (formatter), `flake8` (linter), `isort` (import sorter), and most of `pylint` — one Rust binary, effectively instant. Think `eslint` + `prettier` collapsed into one tool.

| Concern | TypeScript | Go | Python (2026) |
|---|---|---|---|
| Format | `prettier --write .` | `gofmt -w .` | `ruff format` |
| Lint | `eslint .` | `go vet` / `golangci-lint` | `ruff check` |
| Autofix lint | `eslint --fix` | — | `ruff check --fix` |
| Sort imports | eslint-plugin-import | `goimports` | `ruff check --fix` (the `I` rules) |

```bash
uv run ruff check .          # lint
uv run ruff check --fix .    # lint + autofix what's safe
uv run ruff format .         # format (the black-compatible formatter)
uv run ruff format --check . # CI: fail if unformatted (like prettier --check)
```

Config lives in `pyproject.toml` — no separate file:

```toml title="pyproject.toml"
[tool.ruff]
line-length = 100
target-version = "py314"

[tool.ruff.lint]
# E/F = pycodestyle+pyflakes (the flake8 core), I = import sorting (isort),
# UP = pyupgrade (modernize syntax), B = bugbear, SIM = simplify.
select = ["E", "F", "I", "UP", "B", "SIM"]
ignore = ["E501"]   # line length is handled by the formatter
```

Install the official Ruff editor extension (VS Code: `charliermarsh.ruff`; JetBrains: Ruff plugin) and enable format-on-save — red squiggles and auto-formatting with zero config beyond `[tool.ruff]`, the same DX as Prettier-on-save.

## ty: fast type checking

Python type annotations (`x: int`, `-> str`) are checked by a separate tool, the way `tsc` checks TypeScript. The modern fast checker is [**`ty`**](https://github.com/astral-sh/ty) — another Astral Rust binary, fast enough to run on every keystroke.

```bash
uv add --dev ty
uv run ty check          # type-check the project (like `tsc --noEmit`)
uv run ty check src/     # check a path
```

| TypeScript | Go | Python |
|---|---|---|
| `tsc --noEmit` | compiler (built-in) | `ty check` (or `mypy`) |
| Types are erased at runtime | static, enforced | Types are erased at runtime (hints only) |
| `strict: true` in tsconfig | always strict | configured in `[tool.ty]` / `[tool.mypy]` |

:::caution[ty is new — mypy is the battle-tested option]
`ty` is fast and improving quickly, but younger than `mypy` and still stabilizing some inference edge cases. They're equivalent for the code in this guide. If `ty` trips on something, swap in one line:

```bash
uv add --dev mypy
uv run mypy src/
```
:::

## Project structure & imports

Python organizes code into **modules** (a `.py` file) and **packages** (a directory with `__init__.py`). Imports are dotted module paths relative to your `src/` root — closer to Go's package-path model than TS's file-path model.

### Imports, three ways

<Tabs syncKey="lang">
  <TabItem label="TypeScript">

```typescript
// src/main.ts
import { User } from "./models/user";

const u: User = { id: 1, name: "Ada", email: "ada@example.com" };
console.log(u.name);
```

  </TabItem>
  <TabItem label="Go">

```go
// cmd/server/main.go
package main

import (
    "fmt"
    "myapp/internal/user"
)

func main() {
    u := user.User{ID: 1, Name: "Ada", Email: "ada@example.com"}
    fmt.Println(u.Name)
}
```

  </TabItem>
  <TabItem label="Python">

```python
# src/app/main.py
from app.models.user import User


def main() -> None:
    u = User(id=1, name="Ada", email="ada@example.com")
    print(u.name)


if __name__ == "__main__":
    main()
```

  </TabItem>
</Tabs>

**What trips up TS/Go devs:**

- **`__init__.py`** marks a directory as a package. Usually empty — its job is "this folder is importable."
- **Absolute imports** (`from app.models.user import User`) are the norm with the `src/` layout. Prefer them over relative imports (`from ..models.user import User`).
- **Indentation is syntax.** No braces — 4 spaces, always (`ruff format` enforces it). A stray space is a `SyntaxError`, not a style nit. The biggest adjustment from C-family languages.

### Entry points & `if __name__ == "__main__"`

There's no `func main()` the runtime calls automatically. A Python file runs top to bottom when executed. The idiom:

```python title="src/app/main.py"
def main() -> None:
    print("Hello from modern Python!")


# True only when this file is *run directly*, not when it's *imported*.
if __name__ == "__main__":
    main()
```

```bash
uv run python -m app.main      # run as a module (recommended)
uv run example-app             # if you defined [project.scripts]
```

Use `-m app.main`, not a bare path: `-m` runs the module as part of the package so absolute imports resolve; `python src/app/main.py` can break them.

code --install-extension ms-python.python      # Python core (debugger, env)

Point VS Code at the uv-managed interpreter and enable format-on-save:

{
  "python.defaultInterpreterPath": ".venv/bin/python",
  "[python]": {
    "editor.defaultFormatter": "charliermarsh.ruff",

    "editor.codeActionsOnSave": { "source.organizeImports": "explicit" }

## Docker infrastructure

One shared Docker Compose stack (`shared-infra/`) provides PostgreSQL, Redis, and Kafka. Every module that needs a database or cache points at it — same ports, same credentials.

<Steps>

1. Start all services:

   ```bash
   cd shared-infra
   docker compose up -d
   ```

2. Check status:

   ```bash
   docker compose ps
   # postgres   running   0.0.0.0:5432->5432/tcp
   # redis      running   0.0.0.0:6379->6379/tcp
   # kafka      running   0.0.0.0:29092->29092/tcp
   # kafka-ui   running   0.0.0.0:8090->8080/tcp
   ```

3. Verify each service:

   ```bash
   docker exec -it shared-infra-postgres-1 pg_isready -U dev   # accepting connections
   docker exec -it shared-infra-redis-1 redis-cli ping         # PONG
   # Kafka UI is at http://localhost:8090
   ```

</Steps>

| Service | Host:Port | Credentials |
|---|---|---|
| PostgreSQL 17 | localhost:5432 | user `dev`, password `dev`, db `app` |
| Redis 8 | localhost:6379 | no auth |
| Kafka 4 (KRaft) | localhost:29092 | no auth |
| Kafka UI | localhost:8090 | web UI |

Connection strings reused across the guide:

```text
postgresql+asyncpg://dev:dev@localhost:5432/app   # SQLAlchemy async
postgresql://dev:dev@localhost:5432/app           # asyncpg raw
redis://localhost:6379/0                          # Redis
localhost:29092                                   # Kafka bootstrap server
```

```bash
docker compose stop        # stop, keep data
docker compose down        # remove containers, keep volumes
docker compose down -v     # remove EVERYTHING, including data
docker compose logs -f postgres   # tail a service's logs
docker compose restart redis      # restart a single service
```

### Docker for TS/Go devs — Python flavor

| Concept | Node.js | Go | Python (uv) |
|---|---|---|---|
| Base image | `node:22-slim` | `golang:1.23` → `scratch` | `python:3.14-slim` |
| Install deps | `npm ci` | `go mod download` | `uv sync --frozen` |
| Build step | `npm run build` | `go build` | (none — Python isn't compiled) |
| Runtime size | ~200MB | ~10MB (static) | ~120MB (slim) / ~60MB (distroless) |
| Hot reload | `nodemon` | `air` | `uvicorn --reload` / `uv run --watch` |

A first-pass uv Dockerfile (the optimized multi-stage build is in module 17):

```dockerfile title="Dockerfile"
FROM python:3.14-slim

# Copy the uv binary from Astral's published image — no install step needed
COPY --from=ghcr.io/astral-sh/uv:latest /uv /uvx /bin/

WORKDIR /app

# Install deps first (layer-cached) from the lockfile, before copying source
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-install-project --no-dev

# Now the source, then install the project itself
COPY . .
RUN uv sync --frozen --no-dev

EXPOSE 8000
CMD ["uv", "run", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

`--frozen` tells uv to install exactly what `uv.lock` says and error if the lock is stale — the `npm ci` of the Python world. Splitting the deps `COPY`/`sync` from the source `COPY` is the same layer-caching trick as `package.json` in a Node Dockerfile.

Local hot reload: `uvicorn --reload` for servers (module 07); `uv run --watch main.py` reruns a script on change.
