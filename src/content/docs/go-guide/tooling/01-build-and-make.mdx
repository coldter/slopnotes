## The variables that drive every loop

The top of the Makefile defines the values every recipe expands:

```makefile
SHELL := /bin/bash
ROOT := $(shell pwd)
export ROOT
PROTOC_VER = 25.1
# ...
CMDS = gateway pooler dbctld orchestrator platformctl admin portpoolserver
BIN_DIR = bin
```

- `SHELL := /bin/bash` — recipes use bash features (loops, `$$()`), not POSIX `sh`.
- `ROOT := $(shell pwd)` is **exported**, so child scripts (notably the build-tools setup script) see the repo root.
- `CMDS` is the list of seven service/CLI commands. Almost every build/install/clean target is a `for cmd in $(CMDS)` loop over `./cmd/$$cmd` — mapping one-to-one to the services in the [architecture overview](/go-guide/project/01-architecture-request-flow/).
- `BIN_DIR = bin` — every service binary lands here.

`make help` prints only targets carrying a `## ` description, via an awk one-liner. Targets without one (`build-coverage`, `pb`, `images`) are real and runnable but **hidden** from the listing.

## What to run when

Rule of thumb: you only regenerate the thing whose *input* you changed.

| You changed... | Run | Why |
| --- | --- | --- |
| Fresh clone, nothing built yet | `make tools` then `make build` | Download external tools, then compile |
| Only Go source under `cmd/` and `internal/` | `make build` | Recompile the seven binaries |
| A `.proto` file in `proto/` | `make proto` | Regenerate `pb/*` |
| `postgres.y` / parser grammar | `make parser` | Regenerate `postgres.go` |
| **AST node types** in `internal/parser/ast/` | `make build-all` | Regenerate `ast_clone.go` / `ast_rewrite.go` (see [the AST rule](#the-ast-rule-the-one-that-bites)) |
| OpenTelemetry instrument definitions | `make metrics` | Regenerate the metric catalog |
| Anything generated, want to check it | `make validate-generated-files` | Mirror the CI gate locally |
| Need a shippable static binary | `make build-release` | Stripped, CGO-disabled |
| Need coverage-instrumented binaries | `make build-coverage` | For end-to-end coverage runs |

## `make tools` — the one-time bootstrap

```makefile
tools: ## Install protobuf and build tools.
	echo $$(date): Installing build tools
	mkdir -p "$$(git rev-parse --git-dir)/hooks"
	ln -sf "$(ROOT)/misc/git/pre-commit" "$$(git rev-parse --git-dir)/hooks/pre-commit"
	ln -sf "$(ROOT)/misc/git/commit-msg" "$$(git rev-parse --git-dir)/hooks/commit-msg"
	./tools/setup_build_tools.sh
```

Two jobs:

1. **Git hooks** — symlinks `misc/git/pre-commit` and `misc/git/commit-msg` into `.git/hooks/`. After this, commits run the project's pre-commit checks and conventional-commit message validation. See [lint and format](/go-guide/tooling/03-lint-and-format/).
2. **`./tools/setup_build_tools.sh`** — the heavy lifter. Its `install_all()` downloads, builds, and installs: `protoc` pinned to `PROTOC_VER = 25.1` into `dist/protoc-25.1/`; `etcd`/`etcdctl`, `pgbackrest`, `sqllogictest` as prebuilt downloads into `dist/`; `pgproto` **built from source** from the pgpool-II release tarball; Go plugins via `GOBIN=$ROOT/bin go install` (`protoc-gen-go`, `protoc-gen-go-grpc`, `protoc-gen-grpc-gateway`); and `addlicense`.

Run it **once per clone** (and again after `make clean-all`). It needs network access.

:::note[`goyacc` is not downloaded]
The parser generator is vendored Go source at `internal/parser/goyacc/goyacc.go`, invoked with `go run ./goyacc` from the parser's `go:generate` directives. Don't look for it in `dist/` or `bin/`. More in [parser, lexer, AST, codegen](/go-guide/project/06-parser-lexer-ast-codegen/).
:::

## `make proto` — regenerate `pb/`

```makefile
proto: tools $(PROTO_GO_OUTS) ## Generate protobuf files.
```

`proto` depends on `tools` (so the pinned `protoc` and the `protoc-gen-*` plugins exist) and on the `pb` target, which does the actual work — the **pinned** `protoc` from `dist/` with the **local** plugins from `bin/`, emitting into a temporary `github.com/example/platform/pb/...` tree, copied into `pb/`, then the scratch `github.com/` and `google.golang.org/` dirs deleted. Run it after editing any file under `proto/`. The generated client/server code is dissected in [gRPC and protobuf](/go-guide/project/04-grpc-and-protobuf/).

## `make parser` — regenerate the SQL parser and AST helpers

```makefile
parser: ## Generate PostgreSQL parser from grammar.
	@echo "$$(date): Generating PostgreSQL parser from grammar and AST helpers"
	go generate ./internal/parser/...
	@echo "Parser and ast helpers generation completed"
```

A single recursive `go generate ./internal/parser/...` that fires every `go:generate` directive under that package tree:

- `internal/parser/generate.go` — goyacc on `postgres.y` → `postgres.go`, then `goimports -w` and `gofumpt -w` on it:
  ```go
  //go:generate go run ./goyacc -f -o postgres.go postgres.y
  //go:generate go tool goimports -w postgres.go
  //go:generate go tool gofumpt -w postgres.go
  ```
- `internal/parser/ast/generate.go` — asthelpergen, producing `ast_clone.go` and `ast_rewrite.go`:
  ```go
  //go:generate go run ../../tools/asthelpergen/main --in . --iface github.com/example/platform/internal/parser/ast.Node
  ```
- `internal/parser/replparser/generate.go` — the same goyacc dance for the replication grammar (`grammar.y` → `grammar.go`).

Each generated file is formatted with goimports and gofumpt (via `go tool ...`) so it survives the lint gate.

:::caution[Gotcha — `make parser` is not enough after AST changes]
`make parser` covers the grammar; the project convention is to run `make build-all` after AST changes, because that is what CI is built around. The why is in [the AST rule](#the-ast-rule-the-one-that-bites) below — don't shortcut it.
:::

## `make metrics` — regenerate the metric catalog

```makefile
metrics: ## Generate the Prometheus metric catalog/keep-list.
	@echo "$$(date): Generating metric catalog"
	go run ./tools/metricsgen/main
	@echo "Metric catalog generation completed"
```

`metricsgen` scans `./...` for OpenTelemetry instrument definitions and writes `internal/observability/metriccatalog/catalog_generated.go`. The same command has a `-verify` mode that fails instead of writing if the on-disk catalog is stale:

```bash
go run ./tools/metricsgen/main          # write the catalog
go run ./tools/metricsgen/main -verify  # fail if it is stale
```

Run it after adding or changing a metric instrument. Background: [errors and observability](/go-guide/project/09-errors-and-observability/).

### `make generate` — alias

```makefile
generate: parser metrics ## Alias for parser and metrics catalog.
```

Just `parser` + `metrics`. Note what it does **not** include: `proto`.

## The three build flavors

All three loop over `$(CMDS)` and build `./cmd/$$cmd`. They differ only in the `go build` flags.

### `make build` — debug (default)

```makefile
build: ## Build Go binaries (debug, with symbols).
	mkdir -p $(BIN_DIR)
	@for cmd in $(CMDS); do \
		echo "Building $$cmd (debug)"; \
		go build -o $(BIN_DIR)/$$cmd ./cmd/$$cmd; \
	done
```

Plain `go build` with symbol table and DWARF debug info intact — the one to build when you want to attach a debugger. `all: build` makes this the default target, so a bare `make` runs it. It does **not** regenerate proto/parser/metrics; it compiles whatever sources are on disk.

### `make build-coverage` — coverage-instrumented

```makefile
build-coverage:
	mkdir -p bin/cov/
	@for cmd in $(CMDS); do \
		echo "Building $$cmd (coverage)"; \
		go build -cover -covermode=atomic -coverpkg=./... -o $(BIN_DIR)/cov/$$cmd ./cmd/$$cmd; \
	done
```

Binaries built with `-cover -covermode=atomic -coverpkg=./...` land in `bin/cov/<cmd>` (not `bin/<cmd>`), so they don't clobber your normal builds. Used for end-to-end coverage of running services. Hidden from `make help`. See [testing workflow](/go-guide/tooling/02-testing-workflow/).

### `make build-release` — release (static, stripped)

```makefile
build-release: ## Build Go binaries (release, static, stripped).
	mkdir -p $(BIN_DIR)
	@for cmd in $(CMDS); do \
		echo "Building $$cmd (release)"; \
		CGO_ENABLED=0 go build -ldflags="-w -s" -o $(BIN_DIR)/$$cmd ./cmd/$$cmd; \
	done
```

- `CGO_ENABLED=0` → a fully static binary with no libc dependency, so it runs in a scratch or alpine container.
- `-ldflags="-w -s"` → strips DWARF (`-w`) and the symbol table (`-s`), shrinking the binary.

This is what the production image builds — the `Dockerfile` builder stage (`golang:1.25-alpine`) runs `make build-release`. Because release binaries are stripped, they are **not** debugger-friendly; use `make build` (debug) when you need a debugger. See [debugging and profiling](/go-guide/tooling/05-debugging-profiling/).

## `make build-all` — the full regenerate-and-compile path

```makefile
build-all: proto parser metrics build ## Build everything (proto + parser + metrics + binaries).
```

`build-all` regenerates everything (`proto` → `parser` → `metrics`), then compiles (`build`). Because it pulls in `proto`, it transitively depends on `tools` — so on a clean checkout it needs the external tools installed, or network access to fetch them. Reach for it when you've touched generated inputs and want a guaranteed-consistent tree, and specifically after AST changes.

<Mermaid title="build-all dependency chain" height={360} code={`
flowchart LR
  BA["make build-all"] --> PROTO["proto"]
  BA --> PARSER["parser"]
  BA --> METRICS["metrics"]
  BA --> BUILD["build"]
  PROTO --> TOOLS["tools (network)"]
`} />

So `make build` on its own never needs the network, but `make build-all` does on a clean clone — because `proto` insists `tools` ran first.

## The AST rule (the one that bites)

> Run `make build-all` after adding or removing AST node types in `internal/parser/ast/`. The asthelpergen tool walks the AST types and regenerates `ast_clone.go` and `ast_rewrite.go` — they must be committed alongside the new types, or the `validate-generated-files` check will fail.

The loop: change an AST node type → `make build-all` → `git add` the regenerated `ast_clone.go` and `ast_rewrite.go` → commit them with your change. Forget it and the gate (next section) catches you. The directive doing this work is `internal/parser/ast/generate.go`. More on the AST machinery: [parser, lexer, AST, codegen](/go-guide/project/06-parser-lexer-ast-codegen/).

## `make validate-generated-files` — the CI gate, runnable locally

```makefile
validate-generated-files: clean build-all ## Validate that generated files match source.
	go mod tidy
	echo ""
	echo "Checking files modified during build..."
	MODIFIED_FILES=$$(git status --porcelain | grep "^ M" | awk '{print $$2}') ; \
	if [ -n "$$MODIFIED_FILES" ]; then \
		echo "Modified files found:"; \
		...
		echo "Please run 'make build-all && go mod tidy' and commit the changes"; \
		exit 1; \
	else \
		echo "Generated files are up-to-date."; \
	fi
```

In order: `clean` (wiping the service binaries), `build-all` (full regen plus compile), `go mod tidy`, then checks `git status --porcelain` for modified tracked files. If anything changed, it prints the offending files and exits 1. The same target runs in CI, so you can reproduce a red CI run locally with one command.

:::caution[Gotcha — a stale `go.mod` can fail this gate too]
Because the target also runs `go mod tidy`, a stale `go.mod`/`go.sum` fails the job just like stale generated code does. The fix message is literal: run `make build-all && go mod tidy` and commit. Also note the check only flags *tracked* files (it greps `^ M`) — a brand-new untracked generated file won't be flagged, so commit new generated files explicitly. See [modules, deps, codegen](/go-guide/tooling/04-modules-deps-codegen/).
:::

## `make install` and `make images`

```makefile
install: ## Install binaries to GOPATH/bin.
	@for cmd in $(CMDS); do \
		echo "Installing $$cmd"; \
		go install ./cmd/$$cmd; \
	done
```

`install` runs `go install` for each command, so binaries land in `$GOPATH/bin` (or `$GOBIN`) rather than the repo's `bin/`. It does **not** depend on `tools` and does no codegen.

```makefile
images:
	docker build -t example/platform:latest .
	docker build -f Dockerfile.dbctld -t example/dbctld-postgres:latest .
	docker build -t example/admin-web:latest web/admin
```

`images` builds three Docker images (`platform`, `dbctld-postgres`, `admin-web`). The main image's builder stage runs `make build-release`. Convenience target, hidden from `make help`.

## Cleaning

```makefile
clean: ## Remove build artifacts and temp files.
	go clean -i ./...
	@for cmd in $(CMDS); do \
		echo "Removing $(BIN_DIR)/$$cmd"; \
		rm -f $(BIN_DIR)/$$cmd; \
	done
```

`clean` runs `go clean -i ./...` and removes each `bin/<cmd>`. It leaves `dist/` and the downloaded tools alone.

```makefile
clean-all: clean ## Remove build dependencies and distribution files.
	echo "Removing build dependencies..."
	rm -rf $(ROOT)/dist $(ROOT)/bin
	echo "Build dependencies removed. Run 'make tools' to reinstall."
```

`clean-all` does `clean` plus `rm -rf dist/ bin/`, **wiping the downloaded and built external tools** (protoc, etcd, pgbackrest, sqllogictest, pgproto) along with the `protoc-gen-*` plugins. After `clean-all` you must re-run `make tools` before `make proto` or `make build-all` will work again.

## `bin/` layout

`bin/` and `dist/*` are **gitignored** — built binaries and downloaded tools are never committed. Once everything has run:

<FileTree>
- bin/
  - **gateway** service binary (`make build` / `build-release`)
  - pooler
  - dbctld
  - orchestrator
  - platformctl
  - admin
  - portpoolserver
  - protoc-gen-go go-installed by `make tools`
  - protoc-gen-go-grpc
  - protoc-gen-grpc-gateway
  - cov/ from `make build-coverage`
    - … coverage-instrumented binaries
</FileTree>

<FileTree>
- dist/ downloaded by `make tools` (gitignored)
  - protoc-25.1/
  - etcd/
  - pgbackrest/
  - sqllogictest-v0.29.1/
  - pgproto-4.6.6/ built from source
</FileTree>

The seven service binaries go to `bin/<cmd>` — release and debug builds both write there and overwrite each other, while coverage builds go to `bin/cov/<cmd>` instead. `make tools` go-installs the `protoc-gen-*` plugins into `bin/` (via `GOBIN=$ROOT/bin`) and downloads the heavier tooling under `dist/`.
