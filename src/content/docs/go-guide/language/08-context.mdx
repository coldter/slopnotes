`context.Context` is the spine of the request path: a `statement_timeout` set at the gateway becomes a deadline on the context, and that one context flows all the way down — a cancellation at the top stops work at the bottom without any layer knowing about the others.

## The interface

An immutable node in a tree: derive children from a parent; cancelling/timing out a parent cancels every descendant. Four methods:

```go title="context.Context (standard library)"
type Context interface {
    Deadline() (deadline time.Time, ok bool) // when (if ever) this ctx expires
    Done() <-chan struct{}                    // closed when cancelled/expired
    Err() error                               // why Done() closed (nil if not yet)
    Value(key any) any                        // request-scoped lookup
}
```

You almost never implement it yourself — derive children with `WithCancel`, `WithTimeout`, `WithDeadline`, `WithValue`.

## Roots: `Background()` vs `TODO()`

`context.Background()` is the empty, never-cancelled root — use it at the true top of a goroutine tree (process startup, a server's main loop, a CLI command, a test):

```go
func main() {
    ctx := context.Background() // the root; nothing above it
    run(ctx)
}
```

A service entry point that owns a long-lived lifecycle creates its root from `Background()` and immediately wraps it in `WithCancel` so it can shut the whole tree down later:

```go title="cmd/dbctld/command/server.go"
ctx, cancel := context.WithCancel(context.Background())
```

`context.TODO()` is byte-for-byte identical to `Background()` at runtime, but means *"a real context should be threaded in here, but it isn't yet"* — a marker for incomplete plumbing. Example: `GetLeadershipView` takes no `ctx`, so it manufactures one from `TODO()`:

```go title="internal/pooler/heartbeat/reader.go"
func (r *Reader) GetLeadershipView() (*LeadershipView, error) {
    ctx, cancel := context.WithTimeout(context.TODO(), r.interval)
    defer cancel()
    // ...
}
```

The cost: the *caller's* cancellation never reaches this query — if the owner shuts down, this in-flight read only stops when `r.interval` elapses. Treat every `context.TODO()` at a deadline/RPC boundary as debt to repay by adding a `ctx` parameter.

## Deriving cancellable children — always `defer cancel()`

`WithCancel`/`WithTimeout`/`WithDeadline` each return a derived context and a `context.CancelFunc`. Calling the cancel func releases the resources the context holds (for timeouts, the internal timer goroutine). **Always call it**, even on the happy path, even after the timeout already fired — extra calls are no-ops. Idiom: `defer cancel()` on the very next line:

```go
ctx, cancel := context.WithTimeout(parent, 5*time.Second)
defer cancel() // releases the timer when this function returns, regardless of why
result, err := doRPC(ctx)
```

The repo does exactly this before every consensus RPC, using a named timeout constant:

```go title="internal/orchestrator/consensus/rule_change.go" {1-2}
rpcCtx, cancel := context.WithTimeout(ctx, timeouts.RuleWriteTimeout)
defer cancel()
resp, err := r.coordinator.rpcClient.Recruit(rpcCtx, p.Pooler, &consensusdatapb.RecruitRequest{
    TermRevocation: revocation,
})
```

Note the naming: the derived context is `rpcCtx`, distinct from the incoming `ctx` — the function logs against `ctx` (the broader request) but passes `rpcCtx` (the narrower deadline) to the RPC.

:::caution[Gotcha]
Forgetting `defer cancel()` is the single most common context bug: with `WithTimeout` it leaks a timer until the *parent* is cancelled — which for a long-lived parent can be the process lifetime. `go vet`'s `lostcancel` check catches some cases but not all. Make `defer cancel()` muscle memory, on the line immediately after the `With...` call.
:::

### The no-op cancel trick

To conditionally apply a deadline while still letting the caller `defer cancel()` unconditionally, return a do-nothing cancel func in the "no deadline" branch:

```go title="internal/gateway/handler/handler.go" {6-9}
func (h *GatewayHandler) statementTimeoutCtx(ctx context.Context, state *GatewayConnectionState, query ast.Stmt) (context.Context, context.CancelFunc) {
    timeout := ResolveStatementTimeout(
        ParseStatementTimeoutDirective(query),
        state.GetStatementTimeout(),
    )
    if timeout > 0 {
        return context.WithTimeout(ctx, timeout)
    }
    return ctx, func() {} // no deadline: return ctx unchanged + a harmless cancel
}
```

Either way the caller writes the same two lines — `ctx, cancel := h.statementTimeoutCtx(...); defer cancel()` — with no special-casing.

## Reacting to cancellation: `Done()`, `Err()`, and `select`

`ctx.Done()` returns a channel *closed* when the context is cancelled or its deadline passes. `<-ctx.Done()` is the "wake me when it's time to stop" primitive. After it closes, `ctx.Err()` says why: `context.Canceled` (someone called cancel) or `context.DeadlineExceeded` (timeout fired).

The canonical pattern is a `select` racing your real work against `ctx.Done()` — this makes *any* blocking wait cancellable:

```go
ticker := time.NewTicker(100 * time.Millisecond)
defer ticker.Stop()
for {
    select {
    case <-ctx.Done():
        return ctx.Err()
    case <-ticker.C:
        if done() {
            return nil
        }
    }
}
```

`WaitForLSN` is exactly this — poll PostgreSQL every 100ms until a standby has replayed WAL to a target position, but bail the instant the caller's context expires:

```go title="internal/pooler/manager/rpc_manager.go" {3-7}
for {
    select {
    case <-ctx.Done():
        pm.logger.ErrorContext(ctx, "WaitForLSN context cancelled or timed out",
            "target_lsn", targetLsn,
            "error", ctx.Err())
        return errx.Wrap(ctx.Err(), "context cancelled or timed out while waiting for LSN")
    case <-ticker.C:
        reachedTarget, err := pm.checkLSNReached(ctx, targetLsn)
        if err != nil {
            return err
        }
        if reachedTarget {
            return nil
        }
    }
}
```

Two things to notice: `ctx.Err()` is wrapped with `errx.Wrap` so the chain still satisfies `errors.Is(err, context.DeadlineExceeded)` while carrying extra context; and `ctx` is *also* passed into `checkLSNReached`, so the inner query inherits the same deadline — cancellation propagates all the way down.

A subtler variant selects over *two* done-like channels when there are two independent reasons to stop — a connection-pool waitlist races the pool closing against the caller's deadline:

```go title="internal/pooler/pools/connpool/waitlist.go"
select {
case <-closeChan:
    // Pool was closed while we were waiting. Remove ourselves from the waitlist...
case <-ctx.Done():
    // Context expired. Remove ourselves from the waitlist to prevent another
    // goroutine from trying to hand us a connection later on.
    if removed {
        return nil, context.Cause(ctx)
    }
}
```

:::caution[Gotcha]
Cancellation does not undo side effects — it just unblocks you. This waitlist goroutine had registered itself in a shared list; when its `ctx.Done()` fires it must *remove itself* under the mutex, or a peer will later hand a connection to a goroutine that already gave up. A naive `case <-ctx.Done(): return ctx.Err()` here leaks a stranded waiter. Whenever you `select` on `ctx.Done()`, ask "what shared state did I register that I now have to unregister?"
:::

:::note
That branch returns `context.Cause(ctx)` rather than `ctx.Err()`. `context.Cause` (Go 1.20+) returns the specific cause if the context was cancelled via `WithCancelCause`, otherwise falls back to what `ctx.Err()` would give.
:::

## "ctx is the first parameter" convention

Any method that does I/O, blocks, or makes an RPC takes `ctx context.Context` as its **first** parameter, named `ctx`. An entire client interface follows it:

```go title="internal/rpcclient/client.go"
type PoolerClient interface {
    Recruit(ctx context.Context, pooler *clustermetadatapb.Pooler, request *consensusdatapb.RecruitRequest) (*consensusdatapb.RecruitResponse, error)
    Promote(ctx context.Context, pooler *clustermetadatapb.Pooler, request *consensusdatapb.PromoteRequest) (*consensusdatapb.PromoteResponse, error)
    SetPrimary(ctx context.Context, pooler *clustermetadatapb.Pooler, request *consensusdatapb.SetPrimaryRequest) (*consensusdatapb.SetPrimaryResponse, error)
    // ...
}
```

Corollary: **do not store a `Context` in a struct field** as a general habit. A context models a single call tree's lifetime; stashing one means later method calls silently reuse a possibly-stale deadline. Pass it, don't park it.

### The deliberate exception: self-owned background watchers

One legitimate reason to store a context in a struct: an object that owns a long-lived background goroutine with a `Start()`/`Stop()` lifecycle. It derives a cancellable context once at construction, keeps it *and its cancel func*, loops on it, and calls cancel from `Stop()`:

```go title="internal/gateway/discovery.go" {12,21-24}
type CellPoolerDiscovery struct {
    // ...
    ctx        context.Context
    cancelFunc context.CancelFunc
    wg         sync.WaitGroup
}

func NewCellPoolerDiscovery(ctx context.Context, topoStore topo.Store, cell string, logger *slog.Logger) *CellPoolerDiscovery {
    discoveryCtx, cancel := context.WithCancel(ctx)
    return &CellPoolerDiscovery{
        ctx:        discoveryCtx,
        cancelFunc: cancel,
    }
}

// inside the goroutine launched by Start()
for {
    select {
    case <-pd.ctx.Done():
        return
    case watchData, ok := <-changes:
        // ...
    }
}

func (pd *CellPoolerDiscovery) Stop() {
    pd.cancelFunc()
    pd.wg.Wait()
}
```

The stored context belongs to the *watcher itself*, not to any inbound request. Rule: store a context in a struct only when the struct owns the goroutine that uses it.

## Cancellation across gRPC boundaries

A context's cancellation and deadline travel over the wire automatically: pass a `ctx` to a generated gRPC client stub and gRPC encodes its deadline as request metadata; the server materializes a context with the same deadline, and if the client cancels, the server's `ctx.Done()` fires. That's how a gateway `statement_timeout` actually stops work inside the pooler.

The `rpcclient` here is a deliberately thin pass-through — it adds *no timeout of its own*, just forwards the caller's `ctx` to the stub. Bounding the call is the caller's job (which is why `rule_change.go` wraps with `WithTimeout(ctx, timeouts.RuleWriteTimeout)` first):

```go title="internal/rpcclient/grpc_client.go" {2,6}
func (c *Client) Recruit(ctx context.Context, pooler *clustermetadatapb.Pooler, request *consensusdatapb.RecruitRequest) (*consensusdatapb.RecruitResponse, error) {
    conn, closer, err := c.dialPersistent(ctx, pooler) // ctx also bounds connection acquisition
    if err != nil {
        return nil, err
    }
    defer func() { _ = closer() }()
    return conn.consensusClient.Recruit(ctx, request) // ctx flows over the wire as the gRPC deadline
}
```

`ctx` does double duty: it bounds *acquiring* the connection and then propagates as the *call's* deadline. Connection acquisition itself respects the context — when the pool is at capacity and must wait, it polls in a loop that bails on `ctx.Done()`:

```go title="internal/rpcclient/conn_cache.go"
for {
    select {
    case <-ctx.Done():
        cc.metrics.AddDialTimeout(ctx)
        return nil, nil, ctx.Err()
    default:
        if client, closer, found, err := cc.pollOnce(ctx, addr, poolerID); found {
            return client, closer, err
        }
    }
}
```

Long-lived streams use the context as the stream's lifetime: a stream stays open until its context is cancelled — cancelling the context is *how* you close the stream.

### Shaving the inbound deadline at the server

A handler can ask whether the caller imposed a deadline via `ctx.Deadline()`. `TriggerRecoveryNow` does this and, when a deadline exists, derives a *slightly shorter* child deadline so it leaves headroom to serialize and send the response:

```go title="internal/orchestrator/grpcserver/server.go" {6}
deadline, hasDeadline := ctx.Deadline()
if !hasDeadline {
    var cancel context.CancelFunc
    ctx, cancel = context.WithTimeout(ctx, 30*time.Second)
    defer cancel()
} else {
    // Subtract 200ms from deadline to allow time for response overhead.
    timeout := time.Until(deadline) - 200*time.Millisecond
    if timeout > 0 {
        var cancel context.CancelFunc
        ctx, cancel = context.WithTimeout(ctx, timeout)
        defer cancel()
    }
}
```

:::caution[Gotcha]
If a server forwards work using the *exact* inbound deadline, the inner operation can run right up to the moment the client gives up, so the client times out before it can read the reply — you lose the answer and the error looks like a network failure. Shaving a little budget (200ms here) means the server finishes early enough to respond *before* the client's clock runs out.
:::

### Distinguishing "deadline hit" from "real failure"

When an RPC's deadline fires, gRPC surfaces it on the *client* as a status error (`DeadlineExceeded`), not a bare `context.DeadlineExceeded`. Within a server, an operation that watched its own `ctx` returns the Go sentinel. A recovery handler treats deadline/cancellation as an *expected* outcome and only maps genuine errors to `Internal`:

```go title="internal/orchestrator/grpcserver/server.go"
remainingProblems, err := s.engine.TriggerRecoveryNow(ctx, req.MaxCycles)
if err != nil && !errors.Is(err, context.DeadlineExceeded) && !errors.Is(err, context.Canceled) {
    return nil, status.Error(codes.Internal, fmt.Sprintf("recovery trigger failed: %v", err))
}
```

Use `errors.Is` against the sentinels — never string-match `"context deadline exceeded"`. Wrapping with `errx.Wrap(ctx.Err(), ...)` preserves `errors.Is` reachability through several wrap layers.

## `context.WithValue` — request-scoped data, used sparingly

`WithValue` attaches a key/value to a derived context. Right tool for narrow, request-scoped data crossing API boundaries where adding a parameter is impractical (a trace span, an auth principal, a proof-of-something). Wrong tool for optional arguments or smuggling dependencies.

Keys must be an **unexported custom type** (typically zero-size `struct{}`) — never a bare `string`/`int`. String keys from different packages can silently collide; an unexported struct type is unforgeable and costs zero bytes:

```go
type ctxKey struct{}                       // unexported, zero-size, collision-proof
ctx = context.WithValue(ctx, ctxKey{}, v)  // store
v, ok := ctx.Value(ctxKey{}).(*MyType)     // retrieve + type-assert
```

An "action lock" is the textbook good use — it threads *proof that the caller holds the lock* through a call chain:

```go title="internal/pooler/manager/actionlock/action_lock.go"
type actionLockKey struct{}

type actionLockValue struct {
    lockID    uint64
    operation string
    released  *atomic.Bool
}

// Acquire returns a NEW context carrying the proof:
return context.WithValue(ctx, actionLockKey{}, val), nil

// AssertActionLockHeld reads it back via type assertion:
func AssertActionLockHeld(ctx context.Context) error {
    val, ok := ctx.Value(actionLockKey{}).(*actionLockValue)
    if !ok {
        return errors.New("context does not hold an action lock")
    }
    if val.released.Load() {
        return errors.New("context's action lock has been released")
    }
    return nil
}
```

The stored value is a pointer to a struct with an `atomic.Bool` released-flag, so `Release` can flip the flag and every context that captured that pointer immediately sees the lock as released. If a value could be a parameter, make it a parameter — the action lock qualifies precisely because the lock-ownership proof must flow transparently through intermediate functions that have no business taking a lock argument. Retrieval uses the comma-ok assertion, so a missing/wrong-typed value returns `ok == false` cleanly rather than panicking.

## Detached contexts: work that must outlive the request

Sometimes a background task is *triggered by* a request but must *outlive* it (graceful shutdown, a post-response health check). Reusing the request's context means its cancellation aborts the very cleanup you need. Fix: **detach** — build a fresh context that keeps the telemetry baggage but drops the cancellation linkage. `ctxutil.Detach` starts from `Background()` and copies over OTel baggage and the parent span (stored separately, so background work *links to* rather than *nests under* the originating trace):

```go title="internal/ctxutil/ctxutil.go"
func Detach(parent context.Context) context.Context {
    ctx := context.Background() // start fresh - no cancellation inheritance
    if bag := baggage.FromContext(parent); bag.Len() > 0 {
        ctx = baggage.ContextWithBaggage(ctx, bag)
    }
    if span := trace.SpanFromContext(parent); span.SpanContext().IsValid() {
        ctx = context.WithValue(ctx, parentSpanContextKey{}, span.SpanContext())
    }
    return ctx
}
```

Contrast with stdlib `context.WithoutCancel` (Go 1.21+): it keeps the parent span so background work appears as a *child*; `Detach` demotes it to a *linked* span for its own trace. The graceful-shutdown hook uses `Detach`, then re-imposes a bound:

```go title="internal/pooler/init.go"
mp.senv.OnClose(func() {
    // Detach from startCtx so a cancelled startup ctx doesn't block
    // the shutdown write, while preserving any trace/telemetry values.
    ctx, cancel := context.WithTimeout(ctxutil.Detach(startCtx), 10*time.Second)
    defer cancel()
    mp.Shutdown(ctx)
})
```

:::caution[Gotcha]
Detaching breaks cancellation *on purpose* — the detached context won't be cancelled when its origin is — so you must add your own bound. `Detach` + bound always travel together; forget the `WithTimeout` wrap and your "graceful shutdown" becomes a "hang forever during shutdown".
:::

## Centralized timeout constants

Don't hardcode magic `30 * time.Second` at RPC sites. Durations live in a `timeouts` package, each constant carrying a comment justifying its value from operational experience:

```go title="internal/timeouts/rpc.go"
// RemoteOperationTimeout is the default timeout for remote operations such as
// RPC calls, etcd data fetches, and synchronous replication health checks.
const RemoteOperationTimeout = 15 * time.Second

// RuleWriteTimeout is the timeout for rule writes and the election-flow RPCs
// (Recruit, Promote, SetPrimary).
const RuleWriteTimeout = 30 * time.Second

// ReadyTopoCheckTimeout bounds the etcd connectivity probe in /ready handlers.
const ReadyTopoCheckTimeout = 4 * time.Second
```

Callers reference the named constant: `context.WithTimeout(ctx, timeouts.RuleWriteTimeout)`. When you need a deadline on the latency path, look here first before inventing a number.

## ctx-aware logging

Log with slog's `*Context` methods — `logger.ErrorContext(ctx, ...)`, `InfoContext`, `DebugContext` — rather than the context-free variants. Passing `ctx` lets the logging backend extract trace/baggage data from the context so a log line correlates with the request that produced it. When you add logging on a path that has a `ctx`, prefer the `*Context` variant.

## Checkpoints

<details><summary>Why must you call the <code>CancelFunc</code> returned by <code>context.WithTimeout</code> even if the timeout has already fired or the operation succeeded?</summary>
The cancel func releases the context's internal resources — for <code>WithTimeout</code>/<code>WithDeadline</code> that includes a timer goroutine. If you never call it, those resources live until the *parent* context is cancelled, which for a long-lived parent can be the entire process lifetime: a slow leak. Calling it is idempotent, so the safe universal habit is <code>defer cancel()</code> on the line right after creation. <code>go vet</code>'s <code>lostcancel</code> catches some omissions but not all.</details>

<details><summary>The rule says "never store a <code>Context</code> in a struct", yet <code>CellPoolerDiscovery</code> has a <code>ctx</code> field. Why is that not a contradiction?</summary>
The rule targets objects that act on *behalf of a caller* per method call — a request handler must receive a fresh <code>ctx</code> each call because the caller owns the request's lifetime. <code>CellPoolerDiscovery</code> is the opposite: it *owns* a long-lived background goroutine with a <code>Start()</code>/<code>Stop()</code> lifecycle. It derives one cancellable context at construction, the goroutine loops on it, and <code>Stop()</code> calls the stored <code>cancelFunc</code>. The stored context belongs to the watcher's own subtree, so caching it is correct. The distinction is ownership: store a context only when the struct owns the goroutine that consumes it.</details>

<details><summary>Why must a <code>WithValue</code> key be an unexported custom type like <code>type actionLockKey struct&#123;&#125;</code> rather than a string constant?</summary>
Context keys are compared by equality across the whole program. Two packages that both use the string <code>"lock"</code> would silently collide and overwrite each other's values. An unexported, zero-size struct type is unique to its package (nothing outside can name it), costs zero bytes, and is collision-proof. Retrieval uses the comma-ok assertion (`val, ok := ctx.Value(actionLockKey{}).(*actionLockValue)`), so a missing or wrong-typed value returns cleanly as <code>ok == false</code> rather than panicking — which is how <code>AssertActionLockHeld</code> distinguishes "no lock" from "lock present".</details>

<details><summary><code>TriggerRecoveryNow</code> subtracts 200ms from the inbound deadline before forwarding work. What goes wrong without that shave?</summary>
If the server runs the inner operation up to the *exact* inbound deadline, it finishes at the same instant the client gives up. The client's RPC then times out before it can receive the server's response, so the (possibly successful) answer is lost and the caller sees a deadline/network error instead. Reserving a small budget (200ms here) ensures the server completes early enough to serialize and send the reply before the client's clock expires.</details>
