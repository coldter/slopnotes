## Goroutines and the `go` statement

Start a goroutine by prefixing a call with `go`. It returns immediately and **its return value is discarded** — there is no handle, no join. If you want a result, completion, or an error back, arrange a channel, a `WaitGroup`, or a context yourself:

```go title="Starting goroutines"
func work(id int) int { return id * 2 }

go work(1)            // launched; the returned int is thrown away
go func() {           // common form: an anonymous closure
    fmt.Println("hi")
}()
fmt.Println("main continues immediately")
```

### The cost model

A goroutine is **not** an OS thread. It starts with a tiny (few KB) stack that grows/shrinks, multiplexed onto `GOMAXPROCS` OS threads. Spawning is cheap — one goroutine per cohort member or per RPC is normal. But cheap-to-spawn is not free-to-*leak*: a goroutine blocked forever on a channel nobody will send to sits in memory until process exit. Most of this page is about giving every goroutine a guaranteed exit path.

### Loop-variable capture (Go 1.22+)

One goroutine per cohort member, capturing `p` directly:

```go title="consensus/rule_change.go — dispatchRecruit"
recruited := make(chan recruitResult, len(cohort))
for _, p := range cohort {
    go func() {
        recruited <- recruitResult{pooler: p, cs: r.recruit(ctx, p, revocation)}
    }()
}
return recruited
```

Since Go 1.22 each `for ... range` iteration creates a fresh loop variable, so each goroutine gets the right `p`. Pre-1.22 all goroutines captured the *same* `p` and mostly saw the final value; you had to write `p := p`. Don't "fix" missing shadows on Go 1.25 — check the module's Go version first. (Passing the value as an argument — `go func(problems []types.Problem){ ... }(shardProblems)` — is also correct; pick one per package.)

## Channels

A channel is a typed, thread-safe conduit. Sends (`ch <- v`) and receives (`v := <-ch`) synchronize the two goroutines and establish a happens-before edge (see [sync & the memory model](/go-guide/language/09-sync-and-memory-model/)).

### Unbuffered vs buffered

```go title="Channel capacity"
unbuf := make(chan int)      // capacity 0: send blocks until a receiver is ready
buf   := make(chan int, 3)   // capacity 3: send blocks only when 3 are queued
```

**Sizing rule for this repo: buffer a results channel to the number of producers** so producers never block on send, even if the collector stops reading early:

```go title="consensus/rule_change.go"
recruited := make(chan recruitResult, len(cohort))
```

The collector may **return early** the moment it can build a valid proposal:

```go title="consensus/rule_change.go — collectRecruitsAndBuildProposal" {7-9}
for range len(cohort) {
    rr := <-recruited
    if rr.cs == nil {
        continue
    }
    statuses = append(statuses, rr.cs)
    p, err = r.tryBuildProposal(revocation, statuses)
    if err == nil {
        return propReq, leaderKey, nil   // <-- early return, stops reading
    }
}
```

If `recruited` were unbuffered, the recruit goroutines whose results are never read would block forever on send and leak. Because the buffer holds exactly `len(cohort)` slots, **every** producer can deposit its result and exit even if the collector walked away. Buffer to guarantee producer non-blocking or decouple a known-bounded burst — not just "to go faster" (over-buffering hides backpressure).

### Channel direction

Restrict in a signature: send-only `chan<- T`, receive-only `<-chan T`. The compiler enforces it — a function taking `<-chan Event` physically cannot send or close:

```go title="Directional channel parameters"
func consume(in <-chan int)  { for v := range in { _ = v } }  // can only receive
func produce(out chan<- int) { out <- 1; close(out) }         // can only send/close
```

### The empty-struct signal channel

`chan struct{}` carries no data, only the *event* of a send/close — the idiom for stop signals and wakeups:

```go title="buffer/timeout_thread.go"
type timeoutThread struct {
    buf      *Buffer
    notifyCh chan struct{} // signaled when the queue changes (enqueue or eviction)
    stopCh   chan struct{} // closed to stop the goroutine
}
```

`notifyCh <- struct{}{}` means "something changed, wake up"; `close(stopCh)` means "stop". No bytes cross the channel — the synchronization *is* the message.

### Closing a channel

`close(ch)` marks a channel done. Three load-bearing behaviors:

1. A receive on a closed channel returns the zero value **forever** — a one-shot broadcast: `close(stopCh)` unblocks every goroutine waiting on it at once.
2. The two-value receive `v, ok := <-ch` reports `ok == false` when closed and drained — distinguishes a real zero from "closed".
3. `for v := range ch` receives until closed+drained, then ends the loop.

```go title="close as broadcast"
done := make(chan struct{})
go func() {
    <-done            // blocks until close(done); zero value, ignored
    fmt.Println("stopped")
}()
close(done)           // broadcasts to every receiver waiting on done
```

:::caution[Gotcha — only the owner closes, exactly once]
Closing an already-closed channel **panics**, and sending on a closed channel **panics**. Exactly one goroutine owns the close — in `timeout_thread.go`, `stop()` is the only place `stopCh` is ever closed, and the buffer's lifecycle guarantees a single call:

```go title="buffer/timeout_thread.go — stop"
func (tt *timeoutThread) stop() {
    close(tt.stopCh)
}
```
:::

### The nil channel

A `nil` channel blocks **forever** on send and receive. Inside a `select`, a case on a nil channel is effectively *disabled* — never selected. That's occasionally a deliberate tool (set a channel var to `nil` to switch off one `select` branch), but more often it's an accidental silent deadlock: you forgot to `make` it. If a goroutine seems stuck on a channel op, check whether the channel was initialized.

## `select`: multiplexing channel operations

`select` waits on multiple channel operations and proceeds with whichever is ready (random among several ready). With `default`, it's non-blocking:

```go title="select with a non-blocking default"
select {
case v := <-ch1:
    use(v)
case ch2 <- x:
    // sent
case <-ctx.Done():
    return ctx.Err()
default:
    // nothing ready right now — don't block
}
```

### The watch loop: ctx + closed-detection receive

A discovery loop selects over the context (shutdown) and a topology watch stream, using the two-value receive to notice the upstream watch closing:

```go title="gateway/discovery.go"
for {
    select {
    case <-gd.ctx.Done():
        return
    case event, ok := <-changes:
        if !ok {
            gd.logger.Info("Cell watch channel closed, will reconnect")
            return
        }
        gd.processCellChange(event)
    }
}
```

Two clean exit paths: the owner cancels `gd.ctx` (graceful shutdown), or the upstream closes `changes` (`ok == false`, reconnect). No third path where this goroutine blocks indefinitely — that's what makes it leak-free.

### The non-blocking "try-send" wakeup (coalescing)

The most reusable idiom here: a **buffered(1) channel plus a non-blocking send** to wake a worker *at most once*, coalescing a burst into one wakeup:

```go title="buffer/timeout_thread.go — notify"
// notify signals the timeout thread to re-check the queue head.
// Non-blocking: if a notification is already pending, this is a no-op.
func (tt *timeoutThread) notify() {
    select {
    case tt.notifyCh <- struct{}{}:
    default:
    }
}
```

Cap 1: the first `notify()` deposits a token; a second before the worker drains finds the buffer full, so `default` runs and the call returns. *N* notifications collapse into *one* pending wakeup. The worker re-reads the real queue under a lock, so dropping redundant signals is correct, not lossy. A non-blocking send **silently drops** when full — safe only when the receiver derives real state from elsewhere (queue/counter/snapshot) and the channel is a pure "go look again" nudge. Discovery uses the same idiom with a mutex-guarded notification queue (`queueNotification` appends under `notificationsMu`, then non-blocking-sends on `notifySignal`).

### Timeouts with `time.Timer` and the reset dance

`time.NewTimer(d)` returns a `*time.Timer` whose `C` field fires once after `d`. The timeout thread waits on the head entry's deadline, a notification, or a stop, all at once:

```go title="buffer/timeout_thread.go"
select {
case <-timer.C:
    // head entry's deadline reached — evict it
    tt.evictHead()
case <-tt.notifyCh:
    // queue changed — re-check head
    continue
case <-tt.stopCh:
    return
}
```

Reusing a timer across iterations needs the canonical **Stop-then-drain** dance — a stale tick can be sitting in `timer.C` and would fire spuriously next time:

```go title="buffer/timeout_thread.go — timer reset"
// Reset the timer. We drain it first to avoid races.
if !timer.Stop() {
    select {
    case <-timer.C:
    default:
    }
}
timer.Reset(delay)
```

`Stop()` returns false if the timer already fired/stopped; then a pending value may sit in `timer.C`, so the inner non-blocking receive drains it. Only after the channel is known-empty is `Reset` safe. Keep this dance even on Go 1.23+ (where `Stop`/`Reset` are less prone to stale ticks) — it's the portable, race-detector-clean pattern, used verbatim in both the timeout thread and the health-stream watchdog. `defer timer.Stop()` releases the timer's runtime resources on exit.

## Fan-out / fan-in

**Fan-out** spawns N goroutines to work in parallel; **fan-in** collects their N results. Two variants differ in *how the collector knows it's done*:

<Mermaid title="Fan-out / fan-in" height={360} code={`
flowchart LR
  C["Caller"] --> D{"fan-out"}
  D --> W1["goroutine 1"]
  D --> W2["goroutine 2"]
  D --> W3["goroutine N"]
  W1 -->|send| R[("results channel")]
  W2 -->|send| R
  W3 -->|send| R
  R --> F{"fan-in / collect"}
  F --> C
`} />

### Variant A: count the results (no closer goroutine)

When the producer count is known, the collector reads exactly that many times — the recruit/promote dispatch in consensus:

```go title="consensus/rule_change.go"
// dispatch: one goroutine per cohort member, buffered to len(cohort)
recruited := make(chan recruitResult, len(cohort))
for _, p := range cohort {
    go func() {
        recruited <- recruitResult{pooler: p, cs: r.recruit(ctx, p, revocation)}
    }()
}

// collect: read exactly len(cohort) results
for range len(cohort) {
    rr := <-recruited
    // ...
}
```

No `close`, no `WaitGroup`: the collector reads precisely `len(cohort)` values, the buffer guarantees no producer blocks, and closing is unnecessary when the consumer counts. `for range len(cohort)` is the Go 1.22 range-over-int form.

### Variant B: drain until close (the closer goroutine)

When the consumer wants to `range` the channel — or doesn't know how many values arrive — *someone* must `close` it, and no single producer can (double-close panics). A dedicated **closer goroutine** waits on a `WaitGroup`, then closes:

<Mermaid title="Closer goroutine drains the WaitGroup" height={360} code={`
flowchart LR
  subgraph Producers
    G1["go fn()"]
    G2["go fn()"]
    G3["go fn()"]
  end
  G1 -->|wg.Done| WG[("WaitGroup")]
  G2 -->|wg.Done| WG
  G3 -->|wg.Done| WG
  G1 -.->|err only| EC[("errCh (buffered)")]
  G2 -.->|err only| EC
  G3 -.->|err only| EC
  WG -->|wg.Wait| CL["closer goroutine"]
  CL -->|close| EC
  EC --> RX["return &lt;-errCh"]
`} />

```go title="tools/event/hooks.go — ErrorHooks.Fire" {12-15}
errCh := make(chan error, len(h.funcs))
var wg sync.WaitGroup

for _, f := range h.funcs {
    wg.Add(1)
    go func(fn func() error) {
        defer wg.Done()
        if err := fn(); err != nil {
            errCh <- err
        }
    }(f)
}

// Close the channel once every goroutine completes.
go func() {
    wg.Wait()
    close(errCh)
}()

// Return the first error, or nil if the channel closes without one.
return <-errCh
```

This is fail-fast fan-in: the single `<-errCh` returns the first error, or — if all succeed — blocks until the closer runs `close(errCh)`, yielding `nil`. **Buffer `errCh` to `len(h.funcs)` too**: the caller reads once and returns, so later failing goroutines must be able to deposit and exit without a reader (unbuffered would block them forever). Why does `hooks.go` need a closer but `rule_change.go` doesn't? Different termination contracts: `rule_change.go` *counts*; `hooks.go` resolves via a *single* receive that must mean "first error or nil-on-completion", which requires a close. The no-error sibling `Hooks.Fire()` uses the Go 1.25 `WaitGroup.Go` form and no channel at all:

```go title="tools/event/hooks.go — Hooks.Fire"
wg := sync.WaitGroup{}
for _, f := range h.funcs {
    wg.Go(f)
}
wg.Wait()
```

## `sync.WaitGroup` and the Go 1.25 `Go` method

A `WaitGroup` is a counter: `Add(n)` increments, `Done()` decrements (usually deferred), `Wait()` blocks until zero — the standard way to **join** goroutines.

Classic form (still everywhere):

```go title="recovery/recovery_loop.go"
var wg sync.WaitGroup
for _, shardProblems := range problemsByShard {
    wg.Add(1)
    go func(problems []types.Problem) {
        defer wg.Done()
        re.processShardProblems(ctx, problems[0].ShardKey, problems)
    }(shardProblems)
}
wg.Wait()
```

Go 1.25's `WaitGroup.Go` fuses `Add(1)`/`go`/`defer Done()` into one call — still a goroutine, not synchronous:

```go title="consensus/rule_change_certified.go"
var (
    mu sync.Mutex
    wg sync.WaitGroup
)
for _, p := range poolers {
    wg.Go(func() {
        rpcCtx, cancel := context.WithTimeout(ctx, timeouts.RemoteOperationTimeout)
        defer cancel()
        resp, err := c.rpcClient.Status(rpcCtx, p, &poolermanagerdatapb.StatusRequest{})
        // ... guarded by mu when writing shared results
    })
}
```

`wg.Go(fn)` is exactly `wg.Add(1); go func(){ defer wg.Done(); fn() }()`. You can pass a method value directly — discovery does `gd.wg.Go(gd.processNotifications)`.

:::caution[Gotcha — WaitGroup joins, it doesn't share data]
It's for **joining**, not sharing data. The goroutines above coordinate writes through a `sync.Mutex` (`mu`) and a per-call timeout context; `Wait()` only tells you *when they're all done*. Reading shared results without that mutex would be a data race even though `Wait()` establishes happens-before for the final read after it returns.
:::

## `errgroup`: fan-out with first-error propagation

`golang.org/x/sync/errgroup` is a `WaitGroup` that also collects errors and (optionally) cancels a shared context on the first failure. `g.Go(func() error {...})` runs a task; `g.Wait()` blocks until all return and yields the **first** non-nil error. `errgroup.WithContext(parent)` derives a child context cancelled the instant any task errors:

```go title="pooler/internal/manager/state_manager.go" {1}
g, ctx := errgroup.WithContext(ctx)
for _, c := range ssm.components {
    g.Go(func() error {
        return c.OnStateChange(ctx, poolerType, servingStatus)
    })
}
if err := g.Wait(); err != nil {
    return err
}
```

The first line *shadows* `ctx` with the derived one, then passes it into each `OnStateChange` — so if component A fails, the derived `ctx` is cancelled and B/C (if they honor `ctx`) abort in-flight work. That only helps **cooperative** tasks: a task that ignores `ctx` gets no benefit, and `Wait()` returns only the first error (collect others yourself if you need them all).

Sometimes you want parallel-with-combined-error but not cancellation — a topology client's `Close()` discards the derived context with `_`:

```go title="internal/topo/store.go — Close" {1}
g, _ := errgroup.WithContext(context.TODO())

g.Go(func() error {
    if ts.globalTopo != nil {
        if err := ts.globalTopo.Close(); err != nil {
            return fmt.Errorf("failed to close global topo: %w", err)
        }
        ts.globalTopo = nil
    }
    return nil
})

g.Go(func() error {
    // ... close all cell connections ...
    return nil
})
err := g.Wait()
```

Discarding the context is right here because closing topology connections is short, must run to completion regardless (you want every connection closed even if one errors), and there's no in-flight operation worth cancelling — cancelling siblings would be actively wrong.

## Goroutine lifecycle and leak avoidance

Every long-lived goroutine needs an **owner** and an **exit path**. The contract here: a long-lived goroutine selects on a cancellable context (or stop channel), and the owner, on shutdown, **cancels and then waits**. Cancelling alone tells the goroutine to stop; only `Wait()` confirms it has.

A `HealthStream` is the textbook example — it owns a parent context, its cancel func, and a `WaitGroup`:

```go title="recovery/health_stream.go"
mu      sync.Mutex
streams map[topo.ComponentID]*streamEntry

// Parent context; cancelled by Stop().
ctx    context.Context
cancel context.CancelFunc
wg     sync.WaitGroup
```

`Start` launches one goroutine per pooler with `wg.Go`; the goroutine removes its own map entry via `defer` before returning:

```go title="recovery/health_stream.go — Start"
ctx, cancel := context.WithCancel(hs.ctx)   // per-pooler child context
entry := &streamEntry{cancel: cancel}
hs.streams[poolerID] = entry

hs.wg.Go(func() {
    defer func() {
        hs.mu.Lock()
        delete(hs.streams, poolerID)
        hs.mu.Unlock()
    }()
    hs.runStream(ctx, poolerID, entry)
})
```

Two layers of context: a parent `hs.ctx` (cancelled to stop everything) and a per-pooler child (cancelled to stop just one stream). The defer-driven self-deletion means the goroutine cleans up its own bookkeeping no matter how it exits, under the same mutex `Stop()` uses. Shutdown is the canonical cancel-then-wait:

```go title="recovery/health_stream.go — Shutdown"
func (hs *HealthStream) Shutdown() {
    hs.cancel()
    hs.wg.Wait()
}
```

:::caution[Gotcha — cancel requests, Wait confirms]
`hs.cancel()` *requests* stop; `hs.wg.Wait()` *confirms* it. Returning after only `cancel()` could tear down resources (close connections, free the store) while a stream goroutine is still mid-`runStream`, racing with the cleanup. Cancel-then-wait is *the* shutdown idiom here — every owner of background goroutines does it. Also: confine the map `delete` to exactly one place (the goroutine's own defer); `Stop()` deliberately does not delete — it only calls `entry.cancel()` and lets the goroutine remove its entry.
:::

### A self-contained watchdog goroutine

Inside `runStream`, an inner goroutine implements a **staleness watchdog**: if no health message arrives within a timeout, it cancels the stream's context, which makes the blocking `stream.Recv()` return an error and triggers a reconnect. It combines a buffered(1) reset channel, the timer drain dance, and a three-way `select`:

```go title="recovery/health_stream.go — watchdog"
resetCh := make(chan time.Duration, 1)
go func() {
    current := initialStaleness
    timer := time.NewTimer(current)
    defer timer.Stop()
    for {
        select {
        case d := <-resetCh:
            current = d
            if !timer.Stop() {
                select {
                case <-timer.C:
                default:
                }
            }
            timer.Reset(current)
        case <-timer.C:
            hs.logger.WarnContext(ctx, "health stream stale", "pooler_id", poolerID)
            cancelWatchdog()
            return
        case <-watchdogCtx.Done():
            return
        }
    }
}()
```

The recv loop feeds it via the same non-blocking buffered(1) send — *resetting the watchdog cannot block the recv loop*:

```go title="recovery/health_stream.go — feed the watchdog"
select {
case resetCh <- timeout:
default:
    // a reset is already pending; the watchdog will pick it up
}
```

The "cancel a context to unblock a blocking `Recv`" trick generalizes: many blocking I/O calls in Go (gRPC streams, DB queries, HTTP requests) take a context, and cancelling it is how you interrupt them from another goroutine.

## Worker / event-loop serialization: share memory by communicating

Instead of "share state under a mutex", give the state to one goroutine and send it requests over a channel. A LISTEN/NOTIFY `Listener` is built this way — one reader goroutine and one event-loop writer share a single TCP connection without locking it, because only the event loop ever touches it:

<Mermaid title="One owner serializes a shared resource" height={360} code={`
flowchart LR
  C1["caller A"] -->|request + done| RQ[("requests channel")]
  C2["caller B"] -->|request + done| RQ
  RQ --> EL["event-loop goroutine<br/>(sole owner)"]
  EL -->|exclusive access| RES["TCP conn + subscription state"]
  EL -.->|close(req.done)| C1
  EL -.->|close(req.done)| C2
`} />

```go title="pooler/internal/pubsub/listener.go"
type request struct {
    typ     requestType
    channel string
    subCh   chan *sqltypes.Notification
    done    chan struct{} // closed when the request is processed
}
```

Callers submit a `request` on the serialized `requests` channel and block on its `done` channel until the single event-loop goroutine has processed it:

```go title="pooler/internal/pubsub/listener.go — Unsubscribe"
req := request{typ: reqUnsubscribe, channel: channel, subCh: subCh, done: make(chan struct{})}
select {
case l.requests <- req:
    <-req.done            // wait for the event loop to process & close(req.done)
case <-l.stopped:         // listener is shutting down — give up
}
```

The `done chan struct{}` is a per-request completion signal: the event loop runs `close(req.done)` after applying the command, unblocking this caller. The outer `select` against `l.stopped` is a second clean exit path. State lives entirely inside the event-loop goroutine, so there's no mutex around it — the channel handoff *is* the synchronization. Use this when a single resource (connection, file, mutable state) needs serialized access and a lock would force lock-ordering reasoning.

## Bounding concurrency: `semaphore.Weighted` vs a buffered channel

A buffered channel of capacity N is the simplest counting semaphore (acquire = send, release = receive). The repo uses the more explicit `golang.org/x/sync/semaphore.Weighted` when it wants a *global resource limit* with a non-blocking try-acquire on a hot path. The buffer service caps total in-flight buffered requests:

```go title="buffer/buffer.go"
// bufferSizeSema limits the total number of buffered requests globally.
bufferSizeSema *semaphore.Weighted
// ...
bufferSizeSema: semaphore.NewWeighted(int64(config.Size.Get())),
```

On the latency-sensitive admit path it uses `TryAcquire` — returns `false` immediately instead of blocking when full (so it can evict the oldest entry to make room rather than stall the caller):

```go title="buffer/buffer.go — admit path"
if !b.bufferSizeSema.TryAcquire(1) {
    // Buffer is full. Evict the oldest entry globally to make room.
    // ...
}
```

Slots are returned with `b.bufferSizeSema.Release(1)` when an entry drains or is evicted. `Weighted` also supports `Acquire(ctx, n)` (blocking, context-aware) and weighted acquisitions (`n > 1`). Reach for a buffered channel when the permits are simple and you're already passing values through a channel; reach for `semaphore.Weighted` when you want `TryAcquire`, weighted permits, context-aware blocking, or a limiter conceptually separate from any data flow.

## Capstone: a channel hand-off race (the connection-pool waitlist)

The waitlist shows why a naive timeout path can *lose a connection*. A waiter `select`s over three things: the pool closing, its context expiring, and an unbuffered channel on which a returner will hand it a connection:

```go title="connpool/waitlist.go — waiter"
select {
case <-closeChan:
    // ... try to remove ourselves from the list ...
    if removed {
        return nil, ErrPoolClosed
    }
    // if we couldn't remove ourselves, another goroutine is handing us a connection
    return <-elem.Value.conn, nil

case <-ctx.Done():
    // ... try to remove ourselves from the list ...
    if removed {
        return nil, context.Cause(ctx)
    }
    // another goroutine is handing us a connection
    return <-elem.Value.conn, nil

case conn := <-elem.Value.conn:
    return conn, nil
}
```

The race: a waiter's context can expire at the *same instant* a returner picks this waiter and sends a connection on `elem.Value.conn`:

```go title="connpool/waitlist.go — returner"
target.Value.conn <- conn
runtime.Gosched()
```

The send is on an **unbuffered** channel, so it blocks until someone receives. If the timed-out waiter just returned an error and walked away, that returner would block forever (leak) *and* the connection would be lost (never returned to the pool). So the waiter must `return <-elem.Value.conn` — receive the in-flight connection it's being handed, even though it timed out. The `runtime.Gosched()` after the send yields the returner so the just-woken waiter can run and complete the receive promptly.

:::caution[Gotcha — always give every send a receiver]
The signal is "did I successfully remove myself from the shared list?" — decided under `wl.mu`. If you *don't* receive on the channel in the `removed == false` branch, you leak the returner goroutine and lose a pooled connection. An orphaned unbuffered send is a permanent block.
:::

## Checkpoints

<details><summary>Why is the results channel in <code>dispatchRecruit</code> <code>make(chan recruitResult, len(cohort))</code> rather than unbuffered?</summary>
The collector can return early as soon as it builds a valid proposal, abandoning the channel. With a buffer sized to the number of producers, every recruit goroutine can deposit its result and exit without a waiting receiver. An unbuffered channel would block — and leak — every producer whose result is never read.</details>

<details><summary>After <code>close(stopCh)</code>, what happens to ten goroutines blocked on a receive from it, and why must <code>stop()</code> be the only caller of <code>close(stopCh)</code>?</summary>
All ten unblock at once — a receive on a closed channel returns the zero value immediately and forever, so <code>close</code> is a one-shot broadcast. <code>stop()</code> must be the sole closer because closing an already-closed channel panics; the buffer's lifecycle guarantees <code>stop()</code> runs once.</details>

<details><summary><code>HealthStream.Shutdown()</code> calls <code>hs.cancel()</code> then <code>hs.wg.Wait()</code>. Why isn't <code>cancel()</code> alone enough?</summary>
<code>cancel()</code> only *requests* that the stream goroutines stop; it returns immediately while they may still be mid-execution. <code>wg.Wait()</code> blocks until they have actually exited, so the caller can safely tear down shared resources without racing live goroutines.</details>

<details><summary>Why does <code>ErrorHooks.Fire()</code> need a <code>wg.Wait(); close(errCh)</code> goroutine, but <code>collectRecruitsAndBuildProposal</code> does not?</summary>
<code>Fire()</code> resolves to a single receive on <code>errCh</code> that must mean "first error, or nil when everyone finished". The only way one receive can detect "all done, no error" is for the channel to be closed — and no individual producer can close it (double-close panics), so a closer goroutine waits on the <code>WaitGroup</code> and closes. <code>collectRecruits...</code> instead *counts* (<code>for range len(cohort)</code>), reading exactly as many values as it sent, so the channel never needs a close signal.</details>
