Two ways to coordinate goroutines: **channels** (hand off ownership) and **shared memory protected by synchronization** (mutexes, atomics). No `synchronized`, no implicit monitor — nothing protects a field unless you write the protection.

## The data race, and why it is undefined behavior

A **data race** is: two goroutines access the same memory location, at least one writes, and no synchronization orders the accesses. That's the whole definition — "at the same time" in any wall-clock sense is not required.

```go title="A data race"
// RACE: two goroutines, one writes, no synchronization.
var counter int
go func() { counter++ }() // read-modify-write
go func() { counter++ }() // read-modify-write
```

A data race is **undefined behavior**, not just "a lost increment": the compiler and CPU may reorder, cache, and *tear* a write (split a multi-word write so another goroutine sees half-old, half-new bytes). A racing program can observe values no sequential interleaving could produce, or crash. Don't reason about racy code as "eventually consistent" — reason about it as "broken". Even a single `bool` flag read in one goroutine and written in another is a race; there is no "small enough to be safe" access.

The practical tool is the **race detector**:

```bash title="Run tests with race detection"
go test -short -v -race ./...
```

`-race` instruments every memory access and reports the two stacks when an unsynchronized access pair occurs. It only catches races on code paths that actually execute — necessary but not sufficient; it cannot prove the *absence* of races.

## Happens-before: the only thing the memory model guarantees

A write `W` is guaranteed visible to a read `R` only if there's a chain of happens-before edges from `W` to `R`:

| Primitive | The edge it creates |
|---|---|
| **Mutex** | An `Unlock` happens-before any subsequent `Lock` of the same mutex. |
| **Atomics** | An atomic `Store` happens-before any atomic `Load` that *observes* that stored value. |
| **Channels** | A send happens-before the corresponding receive completes; a close happens-before a receive that returns zero because the channel is closed. |
| **Once** | The function passed to `once.Do(f)` completes happens-before any `once.Do(...)` call *returns*. |
| **WaitGroup** | The `Done` calls happen-before the `Wait` that they release. |
| **Goroutine start** | The `go` statement happens-before the goroutine begins. |

Everything else is unordered. Two writes with no connecting edge can be seen in either order, or not at all — so you cannot "just" set a flag in one goroutine and spin-read it in another.

Every primitive below exists to create one of these edges.

## `sync.Mutex`: embed it, protect named fields

The dominant pattern: an **unexported** `mu sync.Mutex` field, a comment naming what it guards, and every method `Lock`/`defer Unlock` around them. The zero value is ready to use — no constructor:

```go title="A counter safe for concurrent use"
type Counter struct {
	mu sync.Mutex // guards n
	n  int
}

func (c *Counter) Inc()       { c.mu.Lock(); defer c.mu.Unlock(); c.n++ }
func (c *Counter) Value() int { c.mu.Lock(); defer c.mu.Unlock(); return c.n }
```

`defer c.mu.Unlock()` right after `Lock()` is the idiom — the unlock survives early returns and panics. The receiver is `*Counter`, not `Counter`: a value receiver would lock a *copy* of the mutex, protecting nothing.

### The real thing

```go title="connection_state.go"
// All methods are thread-safe.
type ConnectionState struct {
	// mu protects all mutable fields in this struct.
	mu sync.Mutex

	User               string
	Settings           *Settings
	PreparedStatements map[string]*query.PreparedStatement
}

func (s *ConnectionState) GetUser() string {
	if s == nil {
		return ""
	}
	s.mu.Lock()
	defer s.mu.Unlock()
	return s.User
}
```

Three things to absorb:

1. **The comment names what `mu` guards** — "mu protects all mutable fields in this struct" is the contract that says touching `User`/`Settings`/`PreparedStatements` without holding `mu` is a bug. Go won't check it for you.
2. **The nil-receiver guard comes *before* the lock** — `if s == nil { return "" }` first; reversed, `s.mu.Lock()` would dereference nil and panic.
3. **Map mutation is protected too** — concurrent map writes crash the process with `fatal error: concurrent map writes` (no `-race` needed).

:::tip[Idiom]
A returned pointer escapes the lock. Returning `s.Settings` (a `*Settings`) under `mu` then unlocking is a safe pointer read, but the caller must not mutate the pointed-to `Settings` afterward — that's why a `Clone` method does `clone.Settings = s.Settings.Clone()` under the lock: it hands back an independent copy the caller owns.
:::

## Narrow the critical section

`defer Unlock` is the safe default, but hold the lock only around the shared-memory mutation, then release before slow/blocking work. An action-lock helper takes the semaphore (potentially blocking) *outside* the mutex and holds the mutex only to bump two counters:

```go title="action_lock.go — blocking work outside the lock" {2-4,7-11}
// Try to acquire the semaphore (may block).
if err := al.sema.Acquire(ctx, 1); err != nil {
	return ctx, errx.Wrap(err, "failed to acquire action lock")
}

// Generate a unique ID for this acquisition.
al.mu.Lock()
lockID := al.nextID
al.nextID++
al.currentID = lockID
al.mu.Unlock()
```

:::caution[Gotcha]
Never hold a mutex while doing slow or blocking work — I/O, channel sends, semaphore waits, or calls that might re-enter and lock again. It serializes everything behind the lock and invites deadlock. Hold the lock only around the shared-memory mutation; do the blocking part outside. (`al.sema` is a `*semaphore.Weighted` from `golang.org/x/sync/semaphore` — an external module, not stdlib. There is no `sync.Semaphore`.)
:::

## `sync.RWMutex`: only when reads vastly dominate

`RWMutex` adds `RLock`/`RUnlock` for readers that may proceed concurrently, while `Lock`/`Unlock` give a writer exclusive access. Use it only for read-mostly state. A server-environment struct keeps a plain `Mutex` for one-shot init and a separate `RWMutex` only for the ready-check slice:

```go title="servenv.go" {4-5}
mu           sync.Mutex
inited       bool
listeningURL url.URL
readyMu      sync.RWMutex
readyChecks  []func() error
```

The `/ready` HTTP endpoint is polled frequently by many load balancers and only *reads* the slice; the reader copies the slice header out under `RLock`, then runs the (potentially slow) checks with the lock released:

```go title="pages.go — read side"
sv.readyMu.RLock()
checks := sv.readyChecks
sv.readyMu.RUnlock()
for _, check := range checks {
	// ... call each check without holding the lock
}
```

:::caution[Gotcha]
`RWMutex` is not free — more bookkeeping than a plain `Mutex`, so under heavy writes a plain `Mutex` is simpler and often faster. And Go's `RWMutex` is **not reentrant**: taking `RLock` while you hold `Lock` deadlocks. The naming convention (`readyMu` next to `readyChecks`) makes the pairing obvious.
:::

## `sync.Once`: run something exactly once

`Once.Do(f)` runs `f` exactly once across all goroutines, ever; concurrent callers block until the first `f` returns, then return without re-running. The zero value is ready:

```go title="Lazy singleton"
var (
	once     sync.Once
	instance *Client
)

func Get() *Client {
	once.Do(func() { instance = newClient() })
	return instance
}
```

A pooler record uses a `Once` to start a background publisher goroutine exactly once even if `Register` is called repeatedly:

```go title="pooler_record.go"
func (r *poolerRecord) Register(parent context.Context, alarm func(string)) {
	r.registerOnce.Do(func() {
		ctx, cancel := context.WithCancel(parent)
		r.publisherMu.Lock()
		r.publisherCancel = cancel
		r.publisherMu.Unlock()
		r.publisherWG.Go(func() {
			r.runPublisher(ctx)
		})
		// ... kick off initial registration retry loop
	})
}
```

The doc comment says "Idempotent." — the `Once` is what makes that true. Happens-before matters too: everything the `Do` body did is visible to any later caller whose `Do` returns immediately.

:::caution[Gotcha]
A `Once` cannot be reset — once `Do` has fired, every future `Do` is a no-op forever. If `f` panics, the `Once` still counts as "done"; it will not retry. Design `f` to be genuinely one-shot.
:::

## `sync.WaitGroup`: fan out, then join

`Add(n)` raises the counter, each goroutine calls `Done()` (usually deferred), `Wait()` blocks until zero.

### Classic form

```go title="recovery_loop.go"
var wg sync.WaitGroup
for _, shardProblems := range problemsByShard {
	wg.Add(1)
	go func(problems []types.Problem) {
		defer wg.Done()
		re.processShardProblems(ctx, problems[0].ShardKey, problems)
	}(shardProblems)
}
wg.Wait()
```

:::caution[Gotcha]
`Add` must happen on the launching goroutine *before* the `go` statement, never inside the spawned goroutine — otherwise `Wait()` can observe a zero counter and return before the goroutine has even registered. (The loop-var-as-argument form above is belt-and-suspenders since Go 1.22's per-iteration variables, but still perfectly readable.)
:::

### Modern form: `wg.Go` (Go 1.25)

`WaitGroup.Go` fuses `Add(1)`, `go`, and `Done()`:

```go title="The fused form"
r.publisherWG.Go(func() {
	r.runPublisher(ctx)
})
```

Equivalent to `wg.Add(1); go func() { defer wg.Done(); r.runPublisher(ctx) }()` but impossible to misuse — you can't forget the `Done`, and the `Add` is guaranteed to precede the goroutine. Prefer `wg.Go` for new code; recognize the classic form because it's still everywhere. Don't reuse a `WaitGroup` for a new batch until a previous `Wait()` has returned, and never copy a `WaitGroup` after first use.

## `sync/atomic`: lock-free single-word access

Modern Go gives typed wrappers — `atomic.Int64`, `atomic.Int32`, `atomic.Uint64`, `atomic.Bool`, `atomic.Pointer[T]` — with `.Load`, `.Store`, `.Add`, `.Swap`, `.CompareAndSwap`. The zero value reads as zero.

```go title="A lock-free hit counter"
type Stats struct {
	hits atomic.Int64
}

func (s *Stats) Hit()         { s.hits.Add(1) }
func (s *Stats) Count() int64 { return s.hits.Load() }
```

:::tip[Idiom]
Prefer the typed struct (`atomic.Int64`) over the old free functions (`atomic.AddInt64(&n, 1)` on a bare `int64`). The wrapper self-documents as atomic and structurally prevents an accidental non-atomic `n++` — you literally cannot write `n++` on an `atomic.Int64`, only `n.Add(1)`.
:::

### Expose atomics through methods, never the field

A connection pool makes its whole metrics struct out of atomic counters, unexported and reachable only through `Load()` accessors:

```go title="pool.go — metrics"
type Metrics struct {
	maxLifetimeClosed atomic.Int64
	getCount          atomic.Int64
	waitCount         atomic.Int64
	waitTime          atomic.Int64
	// ...
}

func (m *Metrics) GetCount() int64         { return m.getCount.Load() }
func (m *Metrics) WaitTime() time.Duration { return time.Duration(m.waitTime.Load()) }
// ... one Load() accessor per field
```

`WaitTime` stores nanoseconds as an `int64` and wraps the load in `time.Duration` (a `time.Duration` *is* an `int64`). Each counter is independent, so atomics are the right tool: no two need to change as a unit.

### Mutex for grouped invariants, atomics for independent counters

The contrast is sharp in a heartbeat reader:

```go title="reader.go"
lagMu          sync.Mutex
lastKnownLag   time.Duration
lastKnownTime  time.Time
lastKnownError error

reads      atomic.Int64
readErrors atomic.Int64
```

`reads`/`readErrors` are standalone counters → atomics. But `lastKnownLag`/`lastKnownTime`/`lastKnownError` form a *triple that must be consistent together* (the lag, the time it was measured, and any error must all reflect the same heartbeat read) → one `Mutex`.

:::caution[Gotcha]
Two separate atomics are *not* atomic *together*. Replacing `lagMu` with three independent atomics lets a reader `Load` `lastKnownLag` from read #5, get descheduled, and `Load` `lastKnownTime` from read #6 — observing a triple that never coexisted. When several values must change as one unit, use a mutex (or a single atomic pointer to an immutable struct holding all three), never N separate atomics.
:::

### Compare-and-swap loops

`CompareAndSwap(old, new)` writes `new` only if the current value still equals `old`, returning whether it succeeded — the building block for lock-free read-modify-write. A demand tracker keeps a concurrent maximum with no mutex at all:

```go title="demand_tracker.go — CAS loop"
for {
	old := d.buckets[currentIdx].Load()
	if sampled <= old {
		break
	}
	if d.buckets[currentIdx].CompareAndSwap(old, sampled) {
		break
	}
}
```

Why not just `if sampled > old { Store(sampled) }`? Between the `Load` and the `Store`, another goroutine could store a *larger* value, which our `Store` would then clobber — losing the higher max. The CAS loop closes that window: only write if the bucket is still `old`, else retry.

:::caution[Gotcha]
`atomic` types must never be copied. That's why `buckets` is a `[]atomic.Int64` and the code indexes it in place (`d.buckets[currentIdx].Load()`) rather than ranging with a value copy (`for _, b := range d.buckets { b.Load() }` would copy each `atomic.Int64` — `go vet`'s `copylocks` flags it). Read-side code uses index loops: `for i := range d.buckets { d.buckets[i].Load() }`.
:::

### `atomic.Pointer[T]`: lock-free read-mostly snapshots (copy-on-write)

`atomic.Pointer[T]` swaps a whole pointer atomically. Treat the pointed-to value as **immutable after publication** and you get a read-lock-free alternative to `RWMutex`: readers `Load()` with no lock; a writer builds a brand-new value and `Store`s the new pointer (copy-on-write). Nobody mutates in place. A cancel manager shows this next to a `Mutex` doing the opposite, in the *same* struct:

```go title="cancel.go"
// prefixCache maps PID prefix to gateway gRPC address. Replaced atomically
// on cache miss or periodic refresh; reads are lock-free.
prefixCache atomic.Pointer[map[uint32]string]

// clientsMu protects clients.
clientsMu sync.Mutex
clients   map[string]*gatewayConn
```

- `prefixCache` is a swap-whole-snapshot cache: readers `Load()` without locking; the map is never mutated after being stored — a refresh builds a fresh map and stores its pointer.
- `clients` is mutated in place (entries added on demand), so it needs the mutex.

The same technique drives the lock-free accessors on the pooler record's `desired atomic.Pointer[...]` field — `Type()`/`Hostname()` just `r.desired.Load().Type`; mutation goes through a `Mutate` method that clones the proto, applies changes to the clone, then stores the new pointer.

:::caution[Gotcha]
`atomic.Pointer` is only safe if the pointed-to value is *immutable after `Store`*. Calling `p.Load()` and then mutating the map/struct it returns is still a data race — you made only the *pointer* read atomic, not the data behind it. The "build new, then `Store`" copy-on-write discipline is mandatory. This is the single most common way to misuse `atomic.Pointer`.
:::

### `CompareAndSwap(nil, ...)` as a do-this-once guard

A pool uses a `close atomic.Pointer[chan struct{}]` both as an open/closed flag and a one-shot guard:

```go title="pool.go — one-shot open guard"
func (pool *Pool[C]) open() {
	closeChan := make(chan struct{})
	if !pool.close.CompareAndSwap(nil, &closeChan) {
		// already open
		return
	}
	// ... first opener proceeds
}
```

If `close` is still `nil`, atomically install our close channel and proceed; if another goroutine got there first, the CAS fails and we bail. A `sync.Once`-like guard from a single atomic, with the bonus that the stored value (the channel) is what the rest of the code uses to signal shutdown. `atomic.Bool` is the right type for a one-shot flag read from many goroutines without a lock: `released.Store(true)` then `released.Load()` elsewhere creates the happens-before edge. (In the action lock, that flag rides inside a `context.Value`, tying it to [context](/go-guide/language/08-context/).)

## Never copy a struct that contains a sync or atomic type

The most common Go concurrency bug after the bare data race:

```go title="The copy bug"
type Counter struct {
	mu sync.Mutex
	n  int
}

func bad(c Counter) { c.mu.Lock() } // c is a COPY: this locks a different mutex
```

Copying a `sync.Mutex`, `RWMutex`, `WaitGroup`, `Once`, or any `atomic.*` duplicates its internal state and silently breaks it — two copies of a mutex protect nothing, a copied `WaitGroup` loses its counter, a copied atomic is a separate variable. `go vet`'s **copylocks** analyzer flags this at build time (golangci-lint runs it). This is *why* these structs almost always travel by pointer: every connection-state method has a pointer receiver; the demand tracker, pooler record, pool, reader, and cancel manager are all passed/stored as pointers. Mental rule: if a struct contains a lock or atomic, it is a *pointer-only* type — give it a `New...` constructor returning `*T` and never expose value copies.

## Lock ordering: preventing the AB/BA deadlock

When one goroutine holds lock A and waits for B while another holds B and waits for A, both block forever. The defense is discipline: always acquire nested locks in the *same* documented order everywhere. A discovery struct writes the hierarchy straight into the comments:

```go title="discovery.go" {2,7}
// State (protected by mu)
// Lock order: acquire this BEFORE CellPoolerDiscovery.mu
mu              sync.Mutex
cellWatchers    map[string]*CellPoolerDiscovery
lastCellRefresh time.Time

// Listeners for pooler changes (protected by listenersMu)
listenersMu sync.Mutex
listeners   []PoolerChangeListener
```

The parent's `mu` must be taken before any child's `mu`. Because every code path obeys the same order, the deadlock cycle can never form. There is no language feature enforcing this — the comment *is* the enforcement. When a struct holds more than one lock, document the acquisition order next to the fields; better still, structure code so you only ever hold one lock at a time.

## Channels vs. mutexes: which to reach for

Go's slogan — "do not communicate by sharing memory; share memory by communicating" — is guidance, not law. Both tools are first-class, and real code uses both, often in the same struct.

| Access pattern | Reach for |
|---|---|
| One owner producing values for others to consume | channel |
| Many goroutines updating one independent counter | atomic |
| Many goroutines reading/writing a shared map or a group of fields with an invariant | mutex |
| Many readers, rare writers, value treatable as immutable | `atomic.Pointer` copy-on-write |
| "Do this exactly once" | `sync.Once` (or `CompareAndSwap(nil, ...)`) |

Use **channels** when handing off ownership, building a pipeline, or signaling an event (the publisher in the pooler record uses a size-1 buffered `wakeup chan struct{}` to signal "work to publish" without accumulating duplicates — the *signal* is a channel and the *state* is an `atomic.Pointer`, side by side). Use a **mutex (or atomic) + fields** when protecting shared mutable state with a simple invariant. The skill is matching the primitive to the access pattern — exactly what a single struct combining `Once` + `WaitGroup` + `atomic.Pointer` + `Mutex` demonstrates.

## Checkpoints

1. Why is a Go data race "undefined behavior" rather than just a possibly-stale read?
   <details><summary>Answer</summary>Because the compiler and CPU may reorder, cache, and tear (split) memory operations when no happens-before edge constrains them. A racing program can observe values no sequential interleaving could produce, or crash. Only `-race` and proper synchronization make it safe — don't reason about it as "eventually consistent".</details>

2. In the connection-state struct, why must `if s == nil { return ... }` come before `s.mu.Lock()`?
   <details><summary>Answer</summary>`s.mu` is a field on the pointer `s`. If `s` is nil, evaluating `s.mu.Lock()` dereferences a nil pointer and panics. The nil guard lets callers invoke methods on a possibly-nil pointer uniformly, so it must run before any field access including the lock.</details>

3. Why does the demand tracker use a CAS loop instead of `if sampled > old { bucket.Store(sampled) }`?
   <details><summary>Answer</summary>Between the `Load` of `old` and the `Store`, another goroutine could store an even larger value; a plain `Store` would clobber it and lose the higher max. `CompareAndSwap(old, sampled)` only writes if the bucket is still `old`, retrying otherwise, so concurrent updates cannot lose the maximum.</details>

4. When is a single `atomic.Pointer` the right choice over three separate atomics for a lag/time/error triple?
   <details><summary>Answer</summary>Never with three separate atomics — they are not atomic *together*, so a reader could mix fields from different reads. Either use one mutex, or store all three inside one immutable struct behind a single `atomic.Pointer` and swap the whole struct copy-on-write. Both make the triple change as one unit.</details>

## Exercises

1. In a thread-safe struct of your own, list every method that takes the lock and confirm each uses a pointer receiver. Then explain why returning a `*Settings` pointer is *not* sufficient to safely mutate that `Settings` afterward, and how a `Clone` under the lock avoids the problem.

2. Take the CAS loop above. On paper, trace two concurrent callers where a naive `if sampled > old { Store }` loses the higher value, then explain why the bucket slice is `[]atomic.Int64` indexed in place rather than ranged over.

3. Find two uses of `atomic.Pointer[T]` in any concurrent codebase. For each, decide whether the pointed-to value is treated as immutable after `Store`, and describe the bug that appears if a reader mutated the loaded value in place.

4. Compare the two `WaitGroup` styles: classic `Add(1)`/`go`/`defer Done()`/`Wait()` versus `wg.Go(...)`. State in one sentence what `wg.Go` fuses, and one footgun it removes.

5. Explain why a lag/time/error triple shares one mutex while independent counters are `atomic.Int64`. Construct a concrete interleaving where replacing the mutex with three atomics lets a reader observe an inconsistent triple.
