## Value semantics: every assignment is a copy

No hidden references. Every assignment and argument is a **copy**. For a struct, "the value" is all its fields contiguously.

```go title="value-semantics.go"
type Point struct{ X, Y int }

func move(p Point) { p.X = 99 } // mutates a COPY

func main() {
	a := Point{1, 2}
	b := a   // b is an independent copy
	b.X = 5  // a.X is still 1
	move(a)  // a.X is still 1
}
```

To mutate the caller's value or avoid copying a large struct, pass a **pointer**:

```go title="value-semantics.go"
func move(p *Point) { p.X = 99 } // p.X is shorthand for (*p).X

a := Point{1, 2}
move(&a) // a.X is now 99
```

:::tip[Idiom]
Go auto-dereferences through pointers for field/method access: `p.X` works whether `p` is `Point` or `*Point`. You almost never write `(*p).X`.
:::

### Why this matters for receivers

A **value receiver** operates on a copy; a **pointer receiver** on the original. In `internal/sqltypes/sqltypes.go`, `Value` (a 3-word slice header) uses value receivers; `Result`/`Row` (larger structs needing nil-checks) use pointer receivers:

```go title="internal/sqltypes/sqltypes.go"
// Value represents a nullable column value.
// nil means NULL, []byte{} means empty string.
type Value []byte

func (v Value) IsNull() bool {
	return v == nil
}
```

```go title="internal/sqltypes/sqltypes.go"
func (r *Result) ToProto() *query.QueryResult { if r == nil { return nil } /* ... */ }
func (r *Row) ToProto() *query.Row            { if r == nil { return nil } /* ... */ }
```

`Value` copies cheaply (the header, not the bytes) and behaves like a primitive → value receiver. `*Result`/`*Row` are larger (don't copy per call) and nil-check (`if r == nil { return nil }` only works on a pointer receiver). Don't mix receiver kinds on one type — if any needs a pointer, make them all pointers.

## Reference-like headers: slices, maps, channels, strings

Some builtins are **headers** — small structs containing a pointer to backing storage. Copying the header copies the pointer, so the copy shares the backing data.

**A slice variable is not the array; it is a `(ptr, len, cap)` triple pointing at an array.**

```go title="header-aliasing.go"
s := []int{1, 2, 3}
t := s    // copies the 3-word header; t and s share the backing array
t[0] = 99 // s[0] is now 99 too
```

## Slice internals: ptr, len, cap

Notice: `ptr` points at the first element; `len` is how many you can index; `cap` is how many from `ptr` to the array's end.

- **ptr** — points at the first element of the backing array.
- **len** — number of elements you can index (`s[0]`..`s[len-1]`).
- **cap** — elements from `ptr` to the end of the backing array.

Sublicing creates a new header pointing into the **same** backing array:

```go title="subslice-aliasing.go"
s := []byte("hello world")
sub := s[6:11] // sub == "world", shares s's backing array
sub[0] = 'W'   // s is now "hello World" — aliasing!
```

`len(sub)` is 5; `cap(sub)` is 5 (offset 6 to the end of the 11-byte array). No bytes copied.

### The lexer's scan buffer (high-perf subslicing)

The SQL lexer scans by indexing/subslicing one buffer, never copying per token. `ParseContext` holds the source as a `[]byte` built once:

```go title="internal/parser/context.go"
scanBuf    []byte // the string being scanned (for lexer)
// ...
scanBuf:    []byte(input),
scanBufLen: len(input),
```

The lexer reads `scanBuf[pos]` and takes subslices like `scanBuf[startPos:scanPos]` for tokens — header arithmetic, zero allocation on the hot path.

### Wire-codec subslicing — the retention gotcha

`RowFromProto` carves each column out of one big buffer as a subslice:

```go title="internal/sqltypes/sqltypes.go" {11}
func RowFromProto(pr *query.Row) *Row {
	if pr == nil {
		return nil
	}
	values := make([]Value, len(pr.Lengths))
	offset := 0
	for i, length := range pr.Lengths {
		switch length {
		case -1:
			values[i] = nil // NULL
		case 0:
			values[i] = []byte{} // empty string, not NULL
		default:
			values[i] = pr.Values[offset : offset+int(length)]
			offset += int(length)
		}
	}
	return &Row{Values: values}
}
```

Two consequences:

1. Every `Value` aliases the one `pr.Values` backing array — mutating one column's bytes corrupts its neighbors, and retaining one tiny `Value` keeps the **entire** buffer alive for the GC.
2. It's fast on purpose: one `make([]Value, N)`, zero per-column byte copies.

:::caution[Gotcha]
A subslice keeps its whole backing array alive. Slice 8 bytes out of an 8 MB buffer and keep it forever → the 8 MB can't be collected. When retaining a small piece long-term, copy it out.
:::

### The defensive copy at API boundaries

When the lexer exposes its internal buffer, it `make`+`copy`s so a caller can't mutate lexer state:

```go title="internal/parser/context.go"
func (ctx *ParseContext) GetScanBuf() []byte {
	// Return copy for safety
	buf := make([]byte, len(ctx.scanBuf))
	copy(buf, ctx.scanBuf)
	return buf
}
```

## append: growth, reallocation, aliasing

If `len < cap`, `append` writes into the existing array (mutating shared storage). If `len == cap`, it allocates a new larger array, copies, and returns a header pointing at the new one — old aliases stop seeing new writes:

```go title="append-aliasing.go"
a := make([]int, 2, 4) // len 2, cap 4
b := append(a, 7)      // fits in cap: b shares a's array, b[2]==7
a = a[:3]              // a now also sees the 7 — same backing array

c := append(b, 1, 2, 3) // overflows cap 4: c gets a NEW array
c[0] = 99               // a/b are UNAFFECTED
```

:::caution[Gotcha]
`append` may or may not reallocate — never assume either way. Always assign back: `s = append(s, x)`.
:::

### Preallocate with `make` to avoid growth churn

`ToProto` knows the final size, so it allocates once with `make([]byte, 0, totalLen)` (len 0, cap totalLen) and appends without reallocating:

```go title="internal/sqltypes/sqltypes.go" {12}
lengths := make([]int64, len(r.Values))
var totalLen int
for i, v := range r.Values {
	if v == nil {
		lengths[i] = -1
	} else {
		lengths[i] = int64(len(v))
		totalLen += len(v)
	}
}

values := make([]byte, 0, totalLen)
for _, v := range r.Values {
	if v != nil {
		values = append(values, v...) // spread one slice into another
	}
}
```

Two `make` shapes side by side: `make([]int64, len(r.Values))` (len == N, for index assignment `lengths[i] = ...`) vs `make([]byte, 0, totalLen)` (len 0, cap N, for append). And `append(values, v...)` — the `...` spreads `v`'s elements; `append(values, v)` would be a type error. When the exact size is unknown, the lexer uses cap as an upper bound (a Unicode escape can't outgrow the input): `result := make([]byte, 0, len(input))`.

## copy() and the deep-clone idiom

`copy(dst, src)` copies `min(len(dst), len(src))` and does **not** grow `dst`. Clone = `make` to the right length, then `copy`:

```go title="clone.go"
src := []int{1, 2, 3}
dst := make([]int, len(src))
copy(dst, src) // dst is independent
```

The generated AST cloner preserves the nil/non-nil distinction:

```go title="internal/parser/ast/ast_clone.go"
func CloneSliceOfOid(n []Oid) []Oid {
	if n == nil {
		return nil
	}
	res := make([]Oid, len(n))
	copy(res, n)
	return res
}
```

`copy` is **shallow**: for a slice of pointers it duplicates the pointers, not the pointees. The cloner handles that with a per-element deep clone:

```go title="internal/parser/ast/ast_clone.go" {6-7}
func CloneSliceOfRefOfDefElem(n []*DefElem) []*DefElem {
	if n == nil {
		return nil
	}
	res := make([]*DefElem, len(n))
	for i, x := range n {
		res[i] = CloneRefOfDefElem(x) // recurse into each pointed-at node
	}
	return res
}
```

:::caution[Gotcha]
`copy` stops at the shorter length: `dst := make([]int, 2); copy(dst, src)` from a 5-element `src` copies only 2 and silently drops the rest. Size `dst` to `len(src)`.
:::

## nil slice vs empty slice — load-bearing

`nil` slice: `ptr == nil, len == 0, cap == 0`. Empty slice (`[]byte{}` / `make([]byte, 0)`): non-nil ptr, len 0, cap 0. Ranging/appending works on both, so the difference is invisible to most code — but in `sqltypes` it's **semantic**: `nil` `Value` = SQL `NULL`; `[]byte{}` = empty string. `RowFromProto` keeps `-1` and `0` distinct on purpose:

```go title="internal/sqltypes/sqltypes.go"
case -1:
	values[i] = nil      // NULL
case 0:
	values[i] = []byte{} // empty string, not NULL
```

`Value.IsNull()` is literally `v == nil`. Normalizing nil → `[]byte{}` anywhere in this path turns every SQL NULL into an empty string — a correctness bug.

:::caution[Gotcha]
Protobuf flattens nil and empty *repeated* fields to "absent" on the wire, losing the distinction across gRPC. The codebase restores it with an explicit flag — `HasFields` tells "no fields" from "empty fields list": `if pr.HasFields && fields == nil { fields = []*query.Field{} }`. When a serialization format can't carry nil-vs-empty, carry it yourself.
:::

## Maps: reference-like, must be made, comma-ok, no order

A map value is a pointer to a runtime hash table — copying the variable copies the pointer (both names see the same table). The zero value is `nil`: **readable** (lookups return zero), **not writable** (write panics):

```go title="nil-map.go"
var m map[string]int // nil map
_ = m["missing"]     // ok: returns 0
m["x"] = 1           // PANIC: assignment to entry in nil map

m = make(map[string]int) // now writable
m["x"] = 1               // ok
```

The keyword table is built in `init()` with a **capacity hint**:

```go title="internal/parser/keywords.go"
var keywordLookupMap map[string]*KeywordInfo
// ...
func init() {
	keywordLookupMap = make(map[string]*KeywordInfo, len(Keywords))
	for i := range Keywords {
		keywordLookupMap[Keywords[i].Name] = &Keywords[i]
	}
}
```

The `len(Keywords)` hint sizes the buckets once instead of rehashing as it grows (a hint, not a cap).

### Address of a slice element, not the loop variable

`&Keywords[i]` takes the address of element `i` **in the slice's backing array** — a stable pointer into the real records. The tempting `for _, k := range Keywords { ... &k }` points at a copy. (Pre-Go-1.22 the same `k` was reused across iterations, so every pointer aliased the last value; Go 1.22+ makes `k` per-iteration, but `&Keywords[i]` is still the intention-revealing form.)

### The comma-ok lookup

A missing key returns the zero value, so you can't distinguish "absent" from "present but zero" by value alone — the two-result form does:

```go title="comma-ok.go"
v, ok := m["k"] // ok is false if absent
```

```go title="internal/pooler/internal/connstate/settings_cache.go"
if elem, ok := c.cache[key]; ok {
	// Move to front (most recently used)
	c.lru.MoveToFront(elem)
	c.hits++
	return elem.Value.(*cacheEntry).settings
}
```

`GetOrCreate` returns the *same* `*Settings` pointer for identical inputs — that contract works because maps are reference-like and pointers carry identity.

:::caution[Gotcha]
Map values are **not addressable**: no `&m[k]`, no `m[k].Field = x` for struct values. Store a pointer (`map[K]*V`) or read-modify-write the whole value. Map iteration order is **randomized** by the runtime — never rely on it; collect keys and `sort` if you need order.
:::

## Strings vs []byte: immutability and conversion cost

A `string` is a 2-word header (ptr, len) over **immutable** bytes; `[]byte` is the 3-word mutable slice:

<Mermaid title="string header vs []byte header" height={360} code={`
flowchart LR
  subgraph S["string header (2 words)"]
    sptr["ptr"]
    slen["len"]
  end
  subgraph B["[]byte header (3 words)"]
    bptr["ptr"]
    blen["len"]
    bcap["cap"]
  end
  imm["immutable bytes"]
  mut["mutable backing array"]
  sptr --> imm
  bptr --> mut
`} />

Converting between them **allocates and copies** in the general case:

```go title="string-bytes-conversion.go"
s := "hello"
b := []byte(s)  // allocates len(s) bytes, copies them
s2 := string(b) // allocates again, copies back
```

The lexer pays this **exactly once** — `scanBuf: []byte(input)` at setup — then scans by index over the mutable buffer. `GetCurrentText` does the reverse at a controlled point: subslice (cheap, aliases) then `string(...)` (one copy, safe to retain):

```go title="internal/parser/context.go"
func (ctx *ParseContext) GetCurrentText(startPos int) string {
	if startPos < 0 || startPos > ctx.scanPos {
		return ""
	}
	return string(ctx.scanBuf[startPos:ctx.scanPos])
}
```

### The zero-allocation `string(b) == "literal" optimization

The compiler recognizes `string(byteSlice) == stringValue` consumed directly by a comparison and lowers it to a **memcmp with no allocation**. The lexer relies on this in its hot loop:

```go title="internal/parser/context.go" {8}
// HasPrefixAtScanPos reports whether scanBuf at the current scan position
// starts with needle. needle is taken as a string so callers don't have to
// allocate a []byte: `string(byteSlice) == stringLit` lowers to a direct
// memcmp in the Go compiler with no heap allocation.
func (ctx *ParseContext) HasPrefixAtScanPos(needle string) bool {
	pos := ctx.scanPos
	if len(ctx.scanBuf)-pos < len(needle) {
		return false
	}
	return string(ctx.scanBuf[pos:pos+len(needle)]) == needle
}
```

:::caution[Gotcha]
The optimization fires only when the conversion is consumed *directly* by the comparison. Hoist it into a variable — `s := string(...); return s == needle` — and the compiler must materialize `s`, forcing the heap allocation back. Keep `string(b) == ...` inline in hot loops.
:::

### Avoid the conversion when nothing changes

`normalizeKeywordCase` returns the **original** string untouched when there's nothing to lowercase (zero allocations on the common path), and only allocates when it must rewrite bytes:

```go title="internal/parser/keywords.go" {10}
func normalizeKeywordCase(s string) string {
	hasUpper := false
	for i := 0; i < len(s); i++ {
		if s[i] >= 'A' && s[i] <= 'Z' {
			hasUpper = true
			break
		}
	}
	// If no uppercase, return original string (avoid allocation)
	if !hasUpper {
		return s
	}
	// Need to convert case - create new string
	result := make([]byte, len(s))
	for i := 0; i < len(s); i++ {
		ch := s[i]
		if ch >= 'A' && ch <= 'Z' {
			ch += 'a' - 'A' // PostgreSQL ASCII-only conversion
		}
		result[i] = ch
	}
	return string(result)
}
```

### byte vs rune

Indexing a string (`s[i]`) gives a **byte** (`uint8`); ranging decodes **runes** (`int32` codepoints), with `i` the byte offset. `string(someRune)` UTF-8-encodes that codepoint (the lexer's `[]byte(string(cp))`); `string(someByteSlice)` reinterprets bytes; `string(65)` is `"A"`.

:::caution[Gotcha]
`len(s)` is the **byte** count, not character count. For ASCII (SQL keywords) they coincide, which is why `normalizeKeywordCase` can iterate bytes. For arbitrary UTF-8, iterate with `range` or use `utf8.RuneCountInString`.
:::

## strings.Builder: never copy it

`+` in a loop reallocates every iteration. `strings.Builder` accumulates into a growable buffer and produces the final string once:

```go title="builder.go"
var b strings.Builder
for i := 0; i < 3; i++ {
	b.WriteString("x")
}
return b.String() // "xxx", one final allocation
```

The SQL-rendering code threads a `*strings.Builder` through helpers (pointer, so writes accumulate in the caller's builder — and a value would trip `go vet`'s copylocks, since `Builder` contains a `noCopy` marker):

```go title="internal/parser/ast/json_parse_nodes.go"
func appendJsonReturning(b *strings.Builder, output *JsonOutput) {
	// ...
	b.WriteString(" RETURNING ")
	// ...
}
```

`ParseContext` embeds a `strings.Builder` **as a value field**, which is why `ParseContext` is *only ever* used as `*ParseContext` — copying it would copy `literalBuf` and trip copylocks.

## Arrays vs slices

An **array** has a fixed length that's part of its type (`[3]int` ≠ `[4]int`) and is a genuine **value** — assigning/passing copies all elements:

```go title="array-vs-slice.go"
var a [3]int
b := a    // copies all 3 ints
b[0] = 9  // a[0] is still 0

// A slice over an array does NOT copy:
s := a[:] // s is a slice header pointing into a's storage
s[0] = 9  // a[0] is now 9
```

`[]byte(input)` builds a **slice over a fresh backing array** (that's the allocation); a `string` is an immutable byte sequence, conceptually array-backed — which is why mutating one requires the `[]byte` copy. Fixed-size things like `[16]byte` digests show up implicitly; the API you touch is almost always the slice.

## make vs new

| | `make(T, ...)` | `new(T)` |
|---|---|---|
| For | slices, maps, channels only | any type |
| Returns | an initialized **value** `T` | a `*T` to a zeroed `T` |

```go title="make-vs-new.go"
s := make([]int, 0, 8)    // usable empty slice, cap 8
m := make(map[string]int) // usable writable map
p := new(int)             // p is *int, *p == 0
```

`new` on a reference type is usually a mistake: `bad := new([]byte)` is a `*[]byte` pointing at a **nil** slice — you wanted `make([]byte, 0, n)`. For a zeroed struct you'll fill in, prefer `&T{}` over `new(T)` (lets you set fields inline).

## Escape analysis: stack vs heap

The compiler decides automatically whether each value lives on the stack (freed on return) or the heap (GC-managed). If a value's address can be reached after the function returns, it **escapes to the heap**. Common triggers:

- returning a pointer to a local (`func f() *T { var x T; return &x }` — safe in Go, but a heap allocation);
- storing a value in an interface (boxing);
- closures capturing a variable by reference that outlives the function;
- slices/maps whose size isn't known at compile time.

The alloc-avoidance code above (`normalizeKeywordCase` returning the original string, `HasPrefixAtScanPos` keeping `string(b) == ...` inline) is written against this model. You can't tell from source whether a value escapes — ask the compiler:

```bash title="observe escape decisions"
go build -gcflags=-m ./internal/parser/...
```

This prints lines like `([]byte)(input) escapes to heap` and `moved to heap: x`, each with a source position. `-gcflags='-m -m'` explains why. For allocation counts in benchmarks: `go test -bench=. -benchmem` reports `allocs/op`.

:::note
Don't micro-optimize for the stack blindly — escape analysis is an optimization, not a contract, and can change across Go versions. Verify a real hot path with `-gcflags=-m` and `-benchmem` before contorting it. The places this repo optimizes (the lexer, the wire codec) are exactly the latency-sensitive query path.
:::

## Defined types vs aliases (memory-relevant recap)

`type Value []byte` is a **new named type** with its own method set — not `[]byte` for method/interface purposes, same layout though. `type TokenType = int` is a pure **alias** — `TokenType` and `int` are the same type, fully interchangeable:

```go title="internal/parser/tokens.go"
// This is now just an alias for int to maintain compatibility during transition
type TokenType = int
```

```go title="internal/sqltypes/sqltypes.go"
type Value []byte
```

Pass a `TokenType` anywhere an `int` is wanted and vice versa. You **cannot** call `Value`'s methods on a bare `[]byte` without an explicit conversion. Full treatment: [Types, Structs & Methods](/go-guide/language/02-types-structs-methods/).

## Checkpoints

1. After `RowFromProto` returns, you keep a 4-byte `Value` from a result whose `pr.Values` was 2 MB. How much memory stays reachable, and why?
   <details><summary>Answer</summary>All 2 MB. The 4-byte <code>Value</code> is a subslice whose <code>ptr</code> points into the 2 MB backing array; the GC keeps the whole array alive while any slice references it. Copy the 4 bytes out with <code>make</code>+<code>copy</code> to release the rest.</details>

2. Why does `Value` use value receivers while `Result`/`Row` use pointer receivers?
   <details><summary>Answer</summary><code>Value</code> is a 3-word header — cheap to copy, primitive-like → value receivers. <code>Result</code>/<code>Row</code> are larger structs, nil-checked (<code>if r == nil</code> only works on a pointer receiver), and pointer receivers avoid per-call copies.</details>

3. Why is `string(ctx.scanBuf[pos:pos+len(needle)]) == needle` allocation-free, but `s := string(...); return s == needle` not?
   <details><summary>Answer</summary>The compiler special-cases <code>string(b) == stringValue</code> consumed directly by a comparison and lowers it to a memcmp without materializing the string. Assigning to a variable forces the string onto the heap, defeating the optimization.</details>

4. `var m map[string]int` then `m["x"] = 1` — what happens, and the fix?
   <details><summary>Answer</summary>Panics: "assignment to entry in nil map". A nil map is readable but not writable. Initialize with <code>m = make(map[string]int)</code> (optionally with a capacity hint).</details>
