Go ships its test framework in the stdlib — no JUnit, no separate runner. A test is a `func TestXxx(t *testing.T)` in a file ending `_test.go`. This repo has ~485 `_test.go` files and leans on exactly one external assertion library, `github.com/stretchr/testify`:

```go title="go.mod"
module github.com/example/platform

go 1.25.1

require github.com/stretchr/testify v1.11.1
```

The `go 1.25` line matters: the Go 1.24+ benchmark loop `for b.Loop()` is available and the code uses it. (This page covers what tests *look like*; the full command reference for *running* them is [tooling/testing workflow](/go-guide/tooling/02-testing-workflow/).)

## The `_test.go` convention and test functions

Exact signature: `func TestXxx(t *testing.T)` — capital `T` after `Test`, one `*testing.T`, no return value. The `t` is your handle for failures (`t.Errorf`, `t.Fatalf`), logging (`t.Logf`), and lifecycle (`t.Cleanup`, `t.Helper`, `t.Run`).

```go title="math_test.go"
package mymath

import "testing"

func TestAdd(t *testing.T) {
	got := Add(2, 3)
	if got != 5 {
		t.Errorf("Add(2,3) = %d, want 5", got)
	}
}
```

`t.Errorf` records a failure and **keeps running**; `t.Fatalf` records a failure and **stops** the current test (`runtime.Goexit()`).

### Two package styles: white-box vs black-box

A `_test.go` file can declare the same package (`package parser`) or an external one (`package parser_test`). Same-package tests are *white-box* (can call unexported helpers); `_test` tests are *black-box* (see only the exported API). The parser tests are white-box (`internal/parser/parse_test.go` declares `package parser`); a config example test is black-box (`package funcs_test`). Reach for `_test` when you want to prove the public surface is usable on its own.

## Table-driven tests and `t.Run` subtests

The dominant unit-test shape: a slice of structs, one per case, iterated with `for...range`, each case wrapped in a `t.Run` subtest:

```go title="classify_test.go"
func TestClassify(t *testing.T) {
	tests := []struct {
		name string
		in   int
		want string
	}{
		{name: "negative", in: -1, want: "neg"},
		{name: "zero", in: 0, want: "zero"},
		{name: "positive", in: 7, want: "pos"},
	}
	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			if got := Classify(tt.in); got != tt.want {
				t.Errorf("Classify(%d) = %q, want %q", tt.in, got, tt.want)
			}
		})
	}
}
```

Each `t.Run(name, fn)` is an isolated subtest shown as `TestClassify/negative`; run one with `go test -run 'TestClassify/zero'`. Each case is independently reported and selectable, a failure names the case, and adding a case is one struct literal. The `name` field is load-bearing — it becomes the subtest path. A clean real example is `internal/retry/backoff_test.go`. (Go replaces spaces with underscores in subtest names for `-run`; the match is a regex per `/` level. And since Go 1.22 loop variables are per-iteration, so the old `tt := tt` shadow is obsolete — don't add it back.)

## testify: `assert` vs `require`

| | `assert.Equal(t, want, got)` | `require.Equal(t, want, got)` |
|---|---|---|
| On mismatch | records failure, **continues** (built on `t.Errorf`) | records failure, **stops the test** (`t.FailNow()` → `runtime.Goexit()`) |

Rule of thumb: use `require` for **preconditions** whose failure makes everything after noise (a constructor error, a temp dir that couldn't be made); use `assert` when you want **multiple independent results** in one run. `require.NoError` right after a setup call is the most common pattern in the tree:

```go title="thing_test.go"
func TestThing(t *testing.T) {
	obj, err := New()
	require.NoError(t, err) // if construction failed, nothing below is meaningful — bail now
	assert.Equal(t, "ready", obj.State()) // independent checks: keep going to report all
	assert.Equal(t, 0, obj.Count())
}
```

The parser corpus loop makes the opposite choice on purpose — tens of thousands of statements in a *single* subtest use non-fatal `assert` so the first bad statement doesn't abort the whole pass:

```go title="internal/parser/parse_test.go"
// Assertions are made with assert (non-fatal) inside the single
// per-file subtest rather than a t.Run per statement: the corpora
// hold tens of thousands of statements, and one subtest each
// overwhelms the CI test reporter. Each message names the query so
// failures are still identifiable.
if tcase.Error != "" {
	assert.ErrorContainsf(t, err, tcase.Error, "case: %s", testName)
} else {
	if assert.NoErrorf(t, err, "case: %s", testName) {
		assert.EqualValuesf(t, expectedQuery, parsedOutput, "case: %s", testName)
		// ...
	}
}
```

The `f`-suffixed variants (`assert.NoErrorf`, `assert.ErrorContainsf`) take a printf-style message, and the nested `if assert.NoErrorf(...) { ... }` works because testify assertions return a `bool` (did it pass?) — the manual version of "require, but scoped to this one case."

:::caution[Gotcha — require in a spawned goroutine]
`require.*` stops the test via `runtime.Goexit()`, which only unwinds the **current goroutine**. Calling `require.NoError` from a goroutine you spawned leaves the test goroutine running — you can get a hang or a misleading pass. In spawned goroutines, prefer `assert.*`, or send the error back over a channel and assert on the main test goroutine. testify mirrors the stdlib: `require.ErrorIs(t, err, context.DeadlineExceeded)` is the testify form of `errors.Is`; `assert.ErrorContains` checks substrings.
:::

## testify suites — used exactly once

`suite.Suite` is an xUnit-style fixture with setup/teardown hooks where each method becomes a test — embed it, write `TestFoo()` methods, optionally implement `SetupSuite`/`SetupTest`/`TearDownTest`/`TearDownSuite`, and wire it with one normal `TestXxx` calling `suite.Run`. There is exactly **one** suite in this repo — the parser tests:

```go title="internal/parser/parse_test.go"
type parseTestSuite struct {
	suite.Suite
	outputDir string
}

func (s *parseTestSuite) SetupSuite() {
	dir := getTestExpectationDir()
	err := os.RemoveAll(dir)
	require.NoError(s.T(), err)
	err = os.Mkdir(dir, 0o755)
	require.NoError(s.T(), err)
	s.outputDir = dir
}

func TestParseTestSuite(t *testing.T) {
	suite.Run(t, new(parseTestSuite))
}
```

Inside suite methods, `s.T()` returns the underlying `*testing.T`. The suite earns its place because the parser tests need one-time setup — clearing and recreating `testdata/expected` before any test file runs. Don't over-reach for suites: the repo-wide convention is plain top-level `TestXxx` + testify + table-driven `t.Run`; ~398 files import `require`, 344 import `assert`, exactly one uses `suite`. When a per-test setup helper plus `t.Cleanup` will do, prefer that.

## `t.Helper()` and `t.Cleanup()`

`t.Helper()` marks the calling function as a test helper — a failure inside it reports the **caller's** file:line, not the helper's. `t.Cleanup(fn)` registers a teardown closure to run when the test **and all its subtests** finish, in **LIFO** order — strictly better than `defer` for shared setup (a `defer` lives only in the function where it's written; a `t.Cleanup` registered inside a helper still fires when the *test* ends, even after `require.*` aborts via `Goexit`):

```go title="test/utils/poolserver/server_test.go" {2,5,10}
func startTestServer(t *testing.T) (socketPath string, stop func()) {
	t.Helper()
	dir, err := os.MkdirTemp("", "pooltest")
	require.NoError(t, err)
	t.Cleanup(func() { os.RemoveAll(dir) })
	socketPath = filepath.Join(dir, "pool.sock")
	srv, err := poolserver.NewServer(socketPath)
	require.NoError(t, err)
	go srv.Serve()
	t.Cleanup(func() { srv.Stop() })
	return socketPath, srv.Stop
}
```

Two cleanups registered: remove the temp dir, then stop the server. LIFO means `srv.Stop()` runs first (registered last), then `os.RemoveAll(dir)` — stop the thing using the directory before deleting it. Prefer `t.Cleanup` over a returned `stop func`: the cleanup fires no matter what the caller does, including when a later `require` aborts the test.

## `t.Setenv` and `testing.Short()` / `t.Skip`

`t.Setenv(key, value)` sets an env var for the duration of the test and restores it automatically; it also marks the test as cannot-be-parallel (`t.Parallel()` after `t.Setenv` panics). This tree has zero `t.Parallel()` usage, so subtests run sequentially by default. `testing.Short()` returns true under `-short`; combined with `t.Skip`, expensive/integration tests opt out of the fast pass:

```go title="expensive_test.go"
func TestExpensive(t *testing.T) {
	if testing.Short() {
		t.Skip("skipping in -short mode")
	}
	// slow work...
}
```

The end-to-end tests use both — they skip under `-short`, and their setup helpers `t.Setenv` vars that get restored automatically:

```go title="test/endtoend/dbctld/dbctld_grpc_test.go" {6-7}
func createTestGRPCServer(t *testing.T, dataDir, binDir string) (net.Listener, func()) {
	t.Helper()
	lis, err := net.Listen("tcp", "localhost:0")
	require.NoError(t, err)
	grpcServer := grpc.NewServer()
	t.Setenv(constants.PgDataDirEnvVar, filepath.Join(dataDir, "pg_data"))
	t.Setenv("PATH", binDir+":"+os.Getenv("PATH"))
	// ...
}
```

The parser property test inverts the usual pattern: instead of skipping the whole test under `-short`, it always runs the curated cases and skips only the giant ~240-file PostgreSQL regression corpus (`if !testing.Short() { entries, err := os.ReadDir("testdata/postgres") ... }`).

## Golden / fixture files

A "golden file" test stores expected output as a checked-in artifact under `testdata/` (a directory `go test` automatically excludes from package compilation) and compares actual output against it. Here the fixtures are **JSON** under `testdata/`. The parser corpus lives in `internal/parser/testdata/`: curated case files (`ddl_cases.json`, `dml_cases.json`, `select_cases.json`) plus a `postgres/` subdirectory of 240 JSON files. Each case is a small struct:

```go title="internal/parser/parse_test.go"
type ParseTest struct {
	Comment  string `json:"comment,omitempty"`
	Query    string `json:"query,omitempty"`
	Expected string `json:"expected,omitempty"` // If empty, defaults to Query
	Error    string `json:"error,omitempty"`
}
```

The update workflow is **hand-rolled write-on-failure**, not a `-update` flag: when a corpus file produces any failure, the suite re-encodes the *actual* parser output into `testdata/expected/<name>.json` so you can diff and promote it:

```go title="internal/parser/parse_test.go" {9}
// Write updated test file if there were failures
if s.outputDir != "" && failed {
	name := strings.TrimSuffix(filepath.Base(filename), filepath.Ext(filename))
	name = filepath.Join(s.outputDir, name+".json")
	file, err := os.Create(name)
	require.NoError(t, err)
	defer file.Close()

	enc := json.NewEncoder(file)
	enc.SetIndent("", "  ")
	enc.SetEscapeHTML(false) // keep SQL readable: don't escape < > &
	err = enc.Encode(expected)
	require.NoError(t, err)
	t.Logf("Updated test expectations written to: %s", name)
}
```

:::caution[Gotcha]
There's no `-update` flag. Promoting a new golden means running the suite, reviewing the diff that lands in `testdata/expected/`, and copying the reviewed result back over `testdata/*.json`. Note `enc.SetEscapeHTML(false)`: without it the encoder would rewrite `<`, `>`, `&` in SQL into `&lt;` etc., making fixtures unreadable.
:::

## Benchmarks: `b.N`, `b.Loop()`, `-bench`, `-benchmem`

A benchmark is `func BenchmarkXxx(b *testing.B)`. Two loop idioms coexist:

**Classic** — `for i := 0; i < b.N; i++`. The framework picks `b.N` adaptively; if you do setup before the loop, call `b.ResetTimer()` to exclude it:

```go title="internal/parser/numeric_test.go"
func BenchmarkNumericLexing(b *testing.B) {
	benchmarks := []struct {
		name  string
		input string
	}{
		{"simple integer", "12345"},
		{"scientific notation", "1.23E-10"},
		{"hex integer", "0xDEADBEEF"},
		// ...
	}
	for _, bm := range benchmarks {
		b.Run(bm.name, func(b *testing.B) {
			b.ReportAllocs()
			for i := 0; i < b.N; i++ {
				lexer := NewLexer(bm.input)
				_ = lexer.NextToken()
			}
		})
	}
}
```

**Modern (Go 1.24+)** — `for b.Loop()`. It manages the iteration count internally, automatically excludes pre-loop setup from the timer (no `ResetTimer` needed), and prevents the compiler from eliminating the body as dead code:

```go title="internal/parser/parse_benchmark_test.go" {6}
func BenchmarkParser(b *testing.B) {
	queries := loadPostgresTestQueries(b) // setup, excluded from timing automatically
	var totalStatements int
	var parseErrors int
	b.ReportAllocs()
	for b.Loop() {
		for _, query := range queries {
			asts, err := ParseSQL(query)
			if err != nil {
				parseErrors++
				continue
			}
			totalStatements += len(asts)
		}
	}
	b.Logf("Parsed %d total statements with %d errors", totalStatements, parseErrors)
}
```

`b.ReportAllocs()` adds `allocs/op` and `B/op` to the output (the per-benchmark equivalent of `-benchmem`); `b.Run(name, fn)` makes named sub-benchmarks like `t.Run`. Run with `go test -bench=. -benchmem` (the `-bench` value is a regex; `.` matches all). The compiler may delete a call whose result is unused, so accumulate into a variable and consume it after the loop (a *sink*) — the classic form assigns to `_`, the modern one logs via `b.Logf`. On Go 1.25, prefer `for b.Loop()`.

## Example tests — and the `// Output:` gotcha

`func ExampleXxx()` serves double duty: it appears in generated docs, and if it ends in an `// Output:` comment, `go test` **captures stdout and asserts it matches**. Without that comment, the example is **compiled but never executed**:

```go title="internal/config/funcs/get_test.go" {10-11}
func ExampleGetPath() {
	reg := config.NewRegistry()
	v := viper.New()
	val := config.Configure(reg, "path", config.Options[[]string]{
		GetFunc: funcs.GetPath,
	})
	stub(val, v)
	v.Set(val.Key(), []string{"/var/www", "/usr:/usr/bin", "/vt"})
	fmt.Println(val.Get())
	// Output: [/var/www /usr /usr/bin /vt]
}
```

This one runs: the `// Output:` line makes the framework compare stdout against `[/var/www /usr /usr/bin /vt]` and fail on mismatch. Compile-only examples have **no** `// Output:` line (e.g. `Example` in `internal/retry/retry_test.go`) — they never fail no matter how broken their runtime behavior. Use `// Unordered output:` for order-insensitive output like map iteration. Naming (`Example`, `ExampleFoo`, `ExampleFoo_bar`) attaches the example to a symbol for docs.

## The race detector

`go test -race` instruments memory accesses and reports data races — concurrent unsynchronized access where at least one is a write. It catches concurrent map writes, unguarded shared variables, and similar bugs that are otherwise nondeterministic. It slows tests significantly and isn't run on every pass; it's available as a pass-through flag on the dev wrapper and via a `make` target. It only finds races that *actually occur during the run*, so combine with `-count=N` to re-execute flaky scenarios.

## Fuzzing — what Go offers, and what this codebase actually does

Native Go fuzzing uses `func FuzzXxx(f *testing.F)`: seed a corpus with `f.Add(...)`, then `f.Fuzz(func(t *testing.T, in ...) { ... })`; the engine mutates inputs, persists interesting ones under `testdata/fuzz/`, run with `go test -fuzz=FuzzXxx`:

```go title="fuzz_example_test.go"
func FuzzParse(f *testing.F) {
	f.Add("SELECT 1")          // seed corpus
	f.Fuzz(func(t *testing.T, s string) {
		_, _ = Parse(s)        // must not panic on any input
	})
}
// run continuously:  go test -fuzz=FuzzParse
```

:::caution[Gotcha — there's no engine fuzzing here]
Despite the name, this repo has **no** native Go fuzzing: zero `func FuzzXxx` targets, zero `f.Add`/`f.Fuzz` calls, no `testdata/fuzz/` seed corpus. The file literally named `internal/parser/identifier_quoting_fuzz_test.go` is **not** an engine fuzzer — it's a plain `func TestIdentifierQuotingFuzz(t *testing.T)` doing reflection-driven property/corpus testing:

```go title="internal/parser/identifier_quoting_fuzz_test.go"
func TestIdentifierQuotingFuzz(t *testing.T) {
	queries := loadFuzzCorpus(t)
	if len(queries) == 0 {
		t.Fatal("no fuzz corpus loaded — check testdata paths")
	}
	var findings []fuzzFinding
	// ...
	for _, q := range queries {
		asts, err := ParseSQL(q)
		if err != nil {
			continue
		}
		for _, stmt := range asts {
			fuzzStmt(stmt, q, report)
		}
	}
	// ...
}
```

The property under test: for every statement in the corpus, parse to an AST, walk it via `reflect`, and for each string field that looks like a SQL identifier, replace its value with `"weird " + original` (a value that *requires* double-quoting on emit), deparse, and re-parse. If the re-parse fails, the deparser emitted that field unquoted — a missed quoting site. The corpus is the same JSON fixtures the benchmarks consume. This is property-based testing over a curated corpus with a deterministic, structured mutation — not coverage-guided random input generation.
:::

## `TestMain` — package-level setup

`func TestMain(m *testing.M)`, if present, runs *instead of* the tests: do package-wide setup, call `m.Run()` to run all tests, then `os.Exit` with its return code. This is how the end-to-end packages spin up a cluster once per package instead of per test:

```go title="test/endtoend/queryserving/main_test.go"
func TestMain(m *testing.M) {
	exitCode := shardsetup.RunTestMain(m)
	if exitCode != 0 {
		setupManager.DumpLogs()
		// ... dump logs for each shared setup
	}
	setupManager.Cleanup()
	// ... cleanup each shared setup
	os.Exit(exitCode) //nolint:forbidigo // TestMain() is allowed to call os.Exit
}
```

:::caution[Gotcha]
You **must** call `m.Run()` and propagate its exit code; if you forget, no tests run. `os.Exit` skips deferred functions, so any teardown must happen *before* the `os.Exit` call — which is why cleanup runs first here. The `//nolint:forbidigo` exists because the linter normally forbids `os.Exit` (it bypasses defers), but `TestMain` is the sanctioned exception.
:::

## Putting a test together

<Steps>

1. Create a file ending in `_test.go` and pick the package: `package foo` for white-box access to internals, or `package foo_test` to test only the exported API.

2. Write `func TestXxx(t *testing.T)`. Use `require` for setup preconditions (`require.NoError` after a constructor) and `assert` for the independent checks you want all reported in one run.

3. If you have several cases, make it a table: a slice of structs with a `name` field, iterated with `t.Run(tt.name, ...)` so each case is named and individually selectable.

4. Factor shared setup into a helper that calls `t.Helper()` and registers teardown with `t.Cleanup` (LIFO) rather than returning a `stop func`.

5. Gate slow paths behind `if testing.Short() { t.Skip() }` so they stay out of the fast pass.

</Steps>

## Checkpoints

<details><summary>What is the difference between <code>assert.Equal</code> and <code>require.Equal</code>, and which goroutine does the difference apply to?</summary>`assert.Equal` records a failure and continues; `require.Equal` records a failure and stops the test immediately via `t.FailNow()` → `runtime.Goexit()`. The stop applies only to the **current goroutine**. Calling `require.*` from a spawned goroutine will not stop the test goroutine and can cause a hang or a misleading result — use `assert` or channel the result back in that case.</details>

<details><summary>You wrote an <code>Example()</code> with a few <code>fmt.Println</code> calls but it never fails even when the output is wrong. Why, and how do you fix it?</summary>An example is only executed-and-asserted if it ends with an `// Output:` (or `// Unordered output:`) comment. Without it, the example is compiled and shown in docs but never run. Add an `// Output:` comment listing the expected stdout. Confirmed by `ExampleGetPath` (has `// Output:`, runs) vs `Example` / `Example_withTimeout` in `retry_test.go` (no `// Output:`, compile-only).</details>

<details><summary>Why does the parser corpus loop use <code>assert</code> (non-fatal) instead of <code>require</code>?</summary>The corpus holds tens of thousands of statements in a single subtest. `require` would abort the whole pass on the first failing statement via `Goexit`, hiding every other failure. `assert` records each failure (with a message naming the query) and keeps going, so one run surfaces all problems. It still uses `require` for setup preconditions like `os.Create` succeeding — there, fatal-stop is correct because nothing after a failed setup is meaningful.</details>

<details><summary>What does <code>t.Helper()</code> change, and in what order do two <code>t.Cleanup</code> closures run?</summary>`t.Helper()` makes failures inside the helper report the **caller's** file:line instead of the helper's, so you can tell which call site failed. `t.Cleanup` closures run in **LIFO** order (last registered first) when the test and all its subtests finish — in `startTestServer`, `srv.Stop()` (registered last) runs before `os.RemoveAll(dir)` (registered first), correctly stopping the server before deleting its directory. They also run even after a `require` abort.</details>
