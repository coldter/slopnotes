**What you will learn:** the five long-running services (plus a test binary) and what each one is responsible for, how cells and the topology store organize the cluster, how gRPC connects the services, and the exact path a client query takes from the wire to PostgreSQL and back.

**Prerequisites:** you've read the language track. This page leans on [interfaces & composition](/go-guide/language/03-interfaces-composition/) (the request path is glued together with interfaces), [context](/go-guide/language/08-context/) (a `ctx` is threaded through every hop), and [concurrency](/go-guide/language/07-concurrency/) (results stream back through callbacks and gRPC server streams). New to the whole guide? Start at the [orientation](/go-guide/orientation/).

## The one-paragraph mental model

The example system is a **distributed SQL proxy**: a set of small Go services that sit in front of real PostgreSQL servers and add routing, connection pooling, and automated failover. A client speaks the ordinary PostgreSQL wire protocol to a **gateway**; the gateway is a stateless proxy that turns each query into a **gRPC** call to a **pooler**; the pooler runs the query on a pooled SQL connection to a real **PostgreSQL** process. Everything else — lifecycle management, consensus/failover, admin — happens off to the side and is *not* on the query path.

:::note[The single most important sentence on this page]
The latency-sensitive path is `gateway -> pooler -> postgres`, and only the first hop is gRPC. The second hop is a real pooled SQL connection.
:::

## The five services (plus a test binary)

Each service is a separate binary under `cmd/<svc>/main.go`. The descriptions below are taken from the package doc-comments and cobra `Short` strings in those files — the system's own words for what each one does.

| Service | Binary location | On the query path? | One-line responsibility |
| --- | --- | --- | --- |
| **gateway** | `cmd/gateway/main.go` | **Yes (hop 1)** | "a stateless proxy responsible for accepting requests from applications and routing them to the appropriate pooler server(s) ... It speaks both the PostgreSQL Protocol and a gRPC protocol." |
| **pooler** | `cmd/pooler/main.go` | **Yes (hop 2)** | "provides connection pooling and communicates with dbctld via gRPC to serve queries from gateway instances." |
| **dbctld** | `cmd/dbctld/main.go` | No (control plane) | "manages PostgreSQL server instances ... providing lifecycle management and configuration control." |
| **orchestrator** | `services/orchestrator/init.go` | No (control plane) | Consensus + failover: builds a `consensus.NewCoordinator` and a `recovery.NewEngine`, watches topology, and drives recovery. |
| **admin** | `cmd/admin/main.go` | No (admin/observability) | "provides administrative services for the cluster, exposing both HTTP and gRPC endpoints" + an HTTP reverse proxy to per-cell status pages. |
| **portpoolserver** | `cmd/portpoolserver/main.go` | No (tests only) | "a cross-process port allocation service for integration tests." |

The operator CLI `platformctl` handles cluster management; it is not a long-running service.

:::caution[Gotcha — dbctld is NOT a query relay]
It's tempting to read a flat data-flow list ("dbctld → handles starting and stopping PostgreSQL") and assume queries pass through dbctld. They do not. The dbctld service surface is entirely lifecycle: `Start`, `Stop`, `Restart`, plus `ReloadConfig`/`Status`/`Version`/`InitDataDir`/`PgRewind`. The pooler keeps a *separate* gRPC link to dbctld (a `DBCtldAddr` in its config) used only to start/stop/configure Postgres — never to run a `SELECT`.
:::

:::caution[Gotcha — gateways barely talk to each other]
The cross-gateway contract (`proto/gatewayservice.proto`) defines exactly one RPC: `CancelQuery`. PostgreSQL cancel requests arrive on a fresh connection carrying a PID; the system encodes a gateway prefix into that PID, so a cancel that lands on the wrong gateway is *forwarded* to the owner. Gateways never route normal queries to each other.
:::

## Cells and the topology store

A **cell** is an availability zone. Each cell runs its own full stack of services (gateway, pooler, orch, dbctld + postgres). The cluster's metadata lives in a **topology store** — etcd in production (`etcdtopo`), an in-process fake (`memorytopo`) in tests. The Go package that reads and writes it is `internal/topo`.

The store is split into two logically separate connections:

<Mermaid title="Global vs cell topology" height={360} code={`
flowchart TB
  Global["Global Topology (static metadata)<br/>- Databases<br/>- Cell locations"]
  CellA["Cell Topo A (dynamic data)<br/>- Gateways<br/>- Poolers<br/>- Orch state"]
  CellB["Cell Topo B (dynamic data)<br/>- Gateways<br/>- Poolers<br/>- Orch state"]
  Global --> CellA
  Global --> CellB
`} />

- **Global topology** holds *static* cluster-level metadata: `Database` records and `Cell` locations. A `Cell` is just `` `{ name, server_addresses, root }` `` — how to connect to that cell's topology service.
- **Cell topology** holds *dynamic* per-cell catalogs: the `Pooler`, `Gateway`, and `Orch` records for components living in that cell.

The global and cell topologies may run on the same etcd cluster, but they remain separate in terms of naming and client management: the topology client keeps one connection to the global topology service and one connection to each cell topology service.

:::caution[Gotcha — `Cell` records are essentially static]
Cell records are not meant to be changed while the system is running, and a cell cannot be removed while a shard still references it. Cells are added during provisioning, not reshuffled at runtime.
:::

Every component is uniquely named by an `` `ID{component, cell, name}` ``. That is how the gateway, given a routing decision, names the exact pooler it must reach.

:::caution[Gotcha — minimum two cells]
A shard bootstraps with an `` `AtLeastN(2)` `` durability policy, so a single pooler can never elect a leader. The `PLATFORM_NUM_CELLS` minimum is 2. Any tutorial that says "spin up one of everything" is wrong for failover-capable clusters.
:::

Three different things are labelled with words derived from "primary"; keep them distinct:

- **leader / follower** — consensus roles owned by the orchestrator.
- **primary / standby / replica** — PostgreSQL recovery-mode state (`pg_is_in_recovery()`).
- **PoolerType PRIMARY / REPLICA** — a *topology routing label* (writes vs. reads) set by the gateway.

:::caution[Gotcha — do not conflate `PoolerType_PRIMARY` with the consensus leader]
They are different concepts that happen to share a word. The routing label is set in the gateway's `scatterconn.buildTarget`, far from the consensus code.
:::

## How gRPC wires the services together

The inter-service contract is protobuf. Each service has a `*.proto` in `proto/` that generates Go into `` `internal/pb/<name>` ``. The contracts that matter for the big picture:

- `PoolerService` (`proto/poolerservice.proto`) — the gateway-to-pooler contract: `ExecuteQuery`, `StreamExecute`, `PortalStreamExecute`, plus `Describe`, `GetAuthCredentials`, `CopyBidiExecute`, `ConcludeTransaction`, etc.
- `DBCtld` (`proto/dbctldservice.proto`) — pooler-to-dbctld lifecycle control.
- `OrchService` (`proto/orchservice.proto`) — recovery/failover control RPCs.
- `GatewayService` (`proto/gatewayservice.proto`) — cross-gateway `CancelQuery` only.

:::caution[Gotcha — `ExecuteQuery` vs `StreamExecute`]
The proto comment is blunt: `ExecuteQuery` "should be used sparingly only when we know the result set is small, otherwise StreamExecute should be used." The simple-query hot path uses `StreamExecute`, so streaming is the default.
:::

:::note[Generated code is read-only]
Everything under `internal/pb/` carries `// Code generated` and must not be hand-edited. Trace bugs to the `.proto` source and regenerate with `make proto`. Treat `internal/pb` as the *contract*, not as logic. For the full story see [gRPC & protobuf](/go-guide/project/04-grpc-and-protobuf/).
:::

## Tracing a query end-to-end

Let's follow a single `SELECT 1` from the client socket to Postgres and back. Each step names the real file and what the request *looks like* at that boundary.

<Mermaid title="SELECT 1 end-to-end" height={460} code={`
sequenceDiagram
  autonumber
  participant Client
  participant Gateway as gateway
  participant Pooler as pooler
  participant Postgres
  Client->>Gateway: PG 'Q' message (raw SQL)
  Note over Gateway: handler.HandleQuery
  Note over Gateway: executor.StreamExecute (plan)
  Note over Gateway: scatterconn.StreamExecute (buildTarget)
  Gateway->>Pooler: gRPC StreamExecuteRequest{Query, Target}
  Note over Pooler: grpcpoolerservice + executor
  Pooler->>Postgres: pooled SQL (QueryStreaming)
  Postgres-->>Pooler: rows

  Gateway-->>Client: PG DataRow / CommandComplete
`} />

### Step 1 — PG wire arrives at the gateway handler

In `services/gateway/handler/handler.go`, `HandleQuery` receives a simple-protocol `Q` message carrying the raw SQL string. The handler parses it (syntactic only) and runs the executor under a statement-timeout context:

```go title="services/gateway/handler/handler.go"
func (h *GatewayHandler) HandleQuery(ctx context.Context, conn *server.Conn, queryStr string, callback func(ctx context.Context, result *sqltypes.Result) error) error {
	// ...
	asts, err := parser.ParseSQL(queryStr)
	// ...
	result, err = h.executor.StreamExecute(ctx, conn, st, queryStr, asts[0], countingCallback)
```

Notice the `callback` parameter: results are *pushed* back, not collected then returned. The handler wraps the caller's callback in a `countingCallback` that tallies rows. The extended query protocol (`Parse`/`Bind`/`Execute`/`Describe`/`Close`/`Sync`) has sibling handlers in the same file that ultimately funnel into the same executor.

:::note
A parse failure is turned into `errx.NewParseError(...)` so the client sees the same `42601` SQLSTATE PostgreSQL would. See [structured errors & observability](/go-guide/project/09-errors-and-observability/).
:::

### Step 2 — the gateway executor plans

In `services/gateway/executor/executor.go`, `StreamExecute` consults the plan cache + planner, then routes through an interface, not a concrete type:

```go title="services/gateway/executor/executor.go"
type Executor struct {
	planner   *planner.Planner
	exec      engine.IExecute
	logger    *slog.Logger
	planCache *plancache.PlanCache
}
```

`exec` is the `engine.IExecute` interface; the concrete implementation injected at startup is `ScatterConn`. This interface seam is classic Go decoupling — see [interfaces & composition](/go-guide/language/03-interfaces-composition/).

### Step 3 — scatterconn decides read vs write

In `services/gateway/scatterconn/scatter_conn.go`, `buildTarget` converts the connection state into a `query.Target`:

```go title="services/gateway/scatterconn/scatter_conn.go"
func (sc *ScatterConn) buildTarget(tableGroup, shard string, state *handler.GatewayConnectionState) *querypb.Target {
	poolerType := clustermetadatapb.PoolerType_PRIMARY
	if state.TargetReplica() {
		poolerType = clustermetadatapb.PoolerType_REPLICA
	}
	return &querypb.Target{
		TableGroup: tableGroup,
		Shard:      shard,
		PoolerType: poolerType,
	}
}
```

This is *the* place read-vs-write routing is decided. `Target` (`proto/query.proto`) is `` `{ table_group, shard, pooler_type }` ``, and `PoolerType` is `PRIMARY` / `REPLICA` / `DRAINED`.

:::caution[Gotcha — reads vs writes are split by TCP port, not by parsing the SQL]
The gateway optionally starts a *second* listener for replica reads. In `services/gateway/init.go` it only builds the replica listener when `pgReplicaPort > 0`, and on that listener calls `replicaHandler.SetTargetReplica(true)`. That flag is exactly what flips `buildTarget` to `REPLICA`. Connect to the primary port → `PRIMARY`; connect to the replica port → `REPLICA`.
:::

### Step 4 — poolergateway resolves a concrete pooler

In `services/gateway/poolergateway/pooler_gateway.go`, `PoolerGateway` implements `queryservice.QueryService`. `QueryServiceByID` resolves a `Target`/`ID` to a live pooler connection; `StreamExecute` forwards the call. The actual gRPC client is created in `services/gateway/poolergateway/pooler_connection.go` via `grpccommon.NewClient(addr, ...)` then:

```go title="services/gateway/poolergateway/pooler_connection.go"
client: poolerservice.NewPoolerServiceClient(conn),
```

That single line is the proof the gateway-to-pooler hop is gRPC. *Which* pooler gets picked is driven by service discovery: `services/gateway/discovery.go` watches the cell topology for `Pooler` records and feeds a `poolergateway.LoadBalancer`.

### Step 5 — the wire call

In `services/gateway/poolergateway/grpc_query_service.go`, `StreamExecute` builds the proto request and pumps the server stream into the callback:

```go title="services/gateway/poolergateway/grpc_query_service.go"
req := &poolerservice.StreamExecuteRequest{
	Query:              sql,
	Target:             target,
	Options:            options,
	ReservationOptions: reservationOptions,
}
stream, err := g.client.StreamExecute(ctx, req)
// ... for { response, err := stream.Recv(); ... }
```

This is the boundary where in-process Go calls become bytes on the network. `ctx` (carrying the statement timeout from Step 1) rides along — see [context](/go-guide/language/08-context/).

### Step 6 — pooler server side

In `services/pooler/grpcpoolerservice/service.go`, `StreamExecute` runs *admission control* (`StartRequest`, which lets a graceful drain keep serving single queries while rejecting new transactions), fetches its executor, and streams results back via `stream.Send`:

```go title="services/pooler/grpcpoolerservice/service.go"
func (s *poolerService) StreamExecute(req *poolerpb.StreamExecuteRequest, stream poolerpb.PoolerService_StreamExecuteServer) error {
	if err := s.pooler.StartRequest(req.Target, admissionKind(...)); err != nil {
		return errx.ToGRPC(err)
	}
	executor, err := s.pooler.Executor()
	// ...
	reservedState, err := executor.StreamExecute(stream.Context(), req.Target, req.Query, req.Options, ...)
```

### Step 7 — the pooler runs real SQL

In `services/pooler/internal/executor/executor.go`, the pooler pulls a pooled Postgres connection, stamps a virtual PID, and runs the query with retry:

```go title="services/pooler/internal/executor/executor.go"
conn, err := e.poolManager.GetRegularConnWithSettings(ctx, settings, user, clientKey, serverKey)
// ...
if err := conn.Conn.QueryStreamingWithRetry(ctx, sql, callback); err != nil {
	return nil, wrapQueryError(err)
}
```

This is the `pooler -> postgres` hop. It is a real pooled SQL connection (pgx/libpq-style), *not* gRPC and *not* via dbctld. Rows stream back up the same chain — pooler stream → gateway callback → PG `DataRow`/`CommandComplete` to the client.

## Why it is built this way

- **Stateless gateway, stateful pooler.** Pooling and per-connection reservation state live in the pooler (close to Postgres), so gateways can be scaled and replaced freely. The gateway only holds routing + plan caches.
- **Interface seams at every hop** (`engine.IExecute`, `queryservice.QueryService`) make each layer unit-testable in isolation and let the gateway swap a real gRPC client for a fake. See [interfaces & composition](/go-guide/language/03-interfaces-composition/).
- **Topology in etcd, not config files.** The sample `config/*.yaml` files are tiny (mostly `http-port`, `log-level`). Real cell/pooler wiring is discovered from the topology store at runtime, which is what makes failover and live rebalancing possible.
- **Strict dependency direction** keeps it all decoupled: `cmd/` may depend on anything; `services/` may not depend on `cmd/` or *other* services; shared `internal/` packages may not depend on `cmd/` or `services/`; the lowest-level tooling packages may not depend on any repo code outside themselves. This is enforced by package layout, and it is why the gateway reaches the pooler over a generated gRPC client (a shared `internal`/`pb` boundary) rather than importing the pooler package.

## Checkpoints

<details><summary>Which hops in the latency-sensitive query path are gRPC, and which is not?</summary>
Only `gateway -> pooler` is gRPC (`PoolerService`, via `poolerservice.NewPoolerServiceClient`). The `pooler -> postgres` hop is a real pooled SQL connection (`conn.Conn.QueryStreamingWithRetry`). dbctld is not on the path at all.</details>

<details><summary>You connect to the gateway's replica-reads port. Trace how that becomes <code>PoolerType_REPLICA</code> in the gRPC request.</summary>
`init.go` builds a second listener whose handler has `SetTargetReplica(true)`. That makes `state.TargetReplica()` true, so `scatterconn.buildTarget` sets `poolerType = REPLICA`, which is placed in the `query.Target` carried by the `StreamExecuteRequest`. The decision is made by *which TCP port* you connected to, not by inspecting the SQL.</details>

<details><summary>What is the difference between global topology and cell topology, and where is each stored?</summary>
Global topology holds static metadata (`Database` records, `Cell` locations); cell topology holds dynamic per-cell catalogs (`Pooler`/`Gateway`/`Orch` records). The topology client keeps one connection to global and one per cell; both may live on the same etcd cluster but are separate connections/namespaces (`internal/topo/store.go`).</details>

<details><summary>Why can't this cluster run with a single cell?</summary>
The shard bootstraps with an `AtLeastN(2)` durability policy, so a single pooler can never form a quorum to elect a leader. The `PLATFORM_NUM_CELLS` minimum is 2.</details>
