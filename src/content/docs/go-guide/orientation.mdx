The running example is a **distributed SQL proxy**: small Go services in front of PostgreSQL adding scaling, pooling, and failover. Learn Go by reading this real codebase, not toy examples.

## The example system

A single Go module, `github.com/example/platform` (Go 1.25), in the standard `cmd/` + `internal/` layout. Clients speak the plain PostgreSQL wire protocol; behind the proxy, the system picks a Postgres, reuses connections, and elects a new leader when one dies — the client never notices.

## Request path

The latency-sensitive path is two hops. Only the first is gRPC; the second is a real pooled SQL connection:

<Mermaid title="Request path" height={360} code={`
flowchart LR
  Client["psql / app"] -->|"PostgreSQL wire protocol"| GW["gateway<br/>(stateless proxy, PG wire in)"]
  GW -->|"gRPC: PoolerService"| PL["pooler<br/>(connection pool, serves queries)"]
  PL -->|"pooled SQL"| PG["PostgreSQL<br/>(real PG process)"]
`} />

Notice: the client talks PG wire the whole way; gRPC is internal between gateway and pooler.

| Service | Role | On the query path? |
| --- | --- | --- |
| **gateway** | Stateless proxy: PG wire + gRPC, routes queries | Yes (hop 1) |
| **pooler** | Connection pool; serves queries; talks to dbctld via gRPC | Yes (hop 2) |
| **dbctld** | PostgreSQL lifecycle only (start/stop/restart) | No (control plane) |
| **orchestrator** | Consensus + failover | No (control plane) |
| **admin** | Admin HTTP + gRPC endpoints | No (admin) |

`cmd/platformctl` is the operator CLI; `cmd/portpoolserver` is a test-only port allocator. Neither is a service.

:::caution[Gotcha — dbctld is not a query relay]
Queries never pass through dbctld. Its whole RPC surface (`proto/dbctldservice.proto`: `Start`, `Stop`, `Restart`, `Status`, `Version`, `InitDataDir`, …) is lifecycle. The pooler keeps a *separate* gRPC link to dbctld only to manage Postgres.
:::

The cluster is organized into **cells** (availability zones) with metadata in a **topology store** (etcd in production). Full topology and the query trace: [Architecture & Request Flow](/go-guide/project/01-architecture-request-flow/).

## Repo map

| Path | What lives here |
| --- | --- |
| `proto/` | gRPC/protobuf contracts (`.proto`); generate into `pb/`. Key files: `poolerservice.proto`, `dbctldservice.proto`, `orchservice.proto`, `gatewayservice.proto`, `clustermetadata.proto`, `query.proto`. |
| `config/` | Per-component YAMLs (`gateway.yaml`, `pooler.yaml`, …). One source in a precedence chain: flags > env > config file > defaults. |
| `Makefile` | Self-documenting build/dev driver (`make help`). |
| `cmd/` / `internal/` / … | All Go source — see below. |

The Go tree and its dependency direction:

| Path | What lives here | Dependency rule |
| --- | --- | --- |
| `cmd/` | 7 binaries (5 services + `platformctl` + `portpoolserver`), each a tiny `main.go` | **Can depend on anything** |
| `internal/` (services) | The 5 services (`admin`, `gateway`, `orch`, `pooler`, `dbctld`) | **Cannot** depend on `cmd/` or other services |
| `internal/` (shared) | `errx`, `pgprotocol`, `sqltypes`, `parser`, `queryservice`, `topo`, `consensus`, `constants`, … | **Cannot** depend on `cmd/` or the services |
| `tools/` | Project-agnostic helpers (timers, retry, …) | **Cannot** depend on any repo code outside `tools/` |
| `pb/` | Generated protobuf Go (`// Code generated`). Read-only | — |
| `observability/` | Metric catalog | — |
| `provisioner/` | Cluster provisioning | — |
| `test/` | End-to-end tests + utilities | — |

<Mermaid title="Allowed dependency directions" height={320} code={`
flowchart TB
  cmd["cmd/<br/>(can depend on anything)"]
  services["services (internal/)"]
  common["shared libs (internal/)"]
  tools["tools/"]
  cmd --> services
  cmd --> common
  cmd --> tools
  services --> common
  services --> tools
  common --> tools
`} />

In words: `cmd/` → anything; services → shared + tools only; shared → tools only; `tools/` → nothing in-repo.

:::caution[Gotcha — generated code is read-only]
Files under `pb/` carry `// Code generated`. Never hand-edit them; trace the bug to the `.proto` and run `make proto`. The SQL parser (`postgres.go` from `goyacc`) and AST clone/rewrite helpers regenerate the same way via `make parser` / `make build-all`.
:::

## Reading unfamiliar Go fast

Go has almost no metaprogramming — the code says what it does. The leverage is where to start.

### Import path == directory

`github.com/example/platform/internal/gateway` *is* the directory `internal/gateway`. Strip the module prefix (`github.com/example/platform`) and you have the repo-relative path. Exact, always.

:::note
The **package name** is whatever the `package` clause says — it need not match the last path segment. Always read the `package` line (e.g. `package main`, aliased imports).
:::

### Start at the entry points

Every binary is a tiny `cmd/<svc>/main.go` that delegates immediately. Two shapes:

**Service binaries** build a [cobra](/go-guide/project/02-cmd-and-cobra/) command, then run `Init` / `RunDefault`:

```go title="cmd/gateway/main.go"
func run(ctx context.Context, gw *gateway.Gateway) error {
	if err := gw.Init(ctx); err != nil {
		return err
	}
	return gw.RunDefault()
}
```

Read the package doc-comment and the cobra `Short` string first — they are the project's own one-liners (the gateway's `Short`: *"gateway is a stateless proxy responsible for accepting requests from applications and routing them to the appropriate pooler server(s) for query execution. It speaks both the PostgreSQL Protocol and a gRPC protocol."*).

**The operator CLI** dispatches to subcommands under `cmd/platformctl/command/`:

```go title="cmd/platformctl/main.go"
func main() {
	root := command.GetRootCommand()
	if err := root.Execute(); err != nil {
		os.Exit(1)
	}
}
```

### Follow an interface seam

The request path is glued by interfaces, not concrete types. When you hit one — `engine.IExecute`, `queryservice.QueryService` — grep for its name to find the definition and the concrete implementations:

```bash
grep -rn 'IExecute' .
```

An interface defines the seam; the implementation lives in another package you find by grepping the name. See [Interfaces & composition](/go-guide/language/03-interfaces-composition/).

### Read doc-comments without opening files

- `go doc <import-path>` prints a package's doc-comment and exported symbols; `go doc <import-path>.Symbol` drills into one. Faster than opening the file for the contract.
- `gopls` (the Go language server) powers jump-to-definition and find-references in any Go-aware editor.
