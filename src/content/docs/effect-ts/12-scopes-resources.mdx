Long-lived processes accumulate things that must be closed: sockets, file handles, DB connections, subscriptions, locks, temp dirs. `try/finally` and `Symbol.dispose`/`using` work for *synchronous, lexical* lifetimes — open and close inside one function body. They fall apart when lifetimes become **dynamic**: a connection opened in one function but used until an HTTP request finishes, a pool shared by N tasks and torn down when the last user leaves. Effect's answer is the `Scope`.

## The problem with manual cleanup

The canonical TS pattern for "use this thing while this request runs":

```ts
async function handleRequest(req: Request): Promise<Response> {
  const controller = new AbortController()
  req.signal.addEventListener("abort", () => controller.abort())
  const conn = await pool.acquire()
  try {
    return await query(conn, req, controller.signal)
  } finally {
    pool.release(conn)
  }
}
```

Three failure modes in eight lines:

1. **Early returns/throws between `acquire` and `try`** — move one line and `finally` no longer covers acquisition.
2. **Cancellation has no story** — `AbortController` gives a *signal*, not a lifecycle; every resource gets ad-hoc listener wiring.
3. **Composition doesn't scale** — two resources means two nested try/finally blocks; a resource outliving the function needs a callback parameter or a "things to close later" registry someone must remember to drain.

Root issue: **the lifetime is implicit**. Nothing in the type system says "this value requires a surrounding cleanup boundary."

## `Scope`: a lifetime as a value

A `Scope` is a container of finalizers. Register cleanup effects on it; closing runs them, handing each the `Exit` that ended the work:

```ts
import { Effect, Exit, Scope } from "effect"

const program = Effect.gen(function* () {
  const scope = yield* Scope.make() // closeable scope, not yet in context

  yield* Scope.addFinalizer(scope, Effect.sync(() => console.log("cleanup")))
  console.log("work")

  yield* Scope.close(scope, Exit.succeed("done"))
})

Effect.runSync(program)
// work
// cleanup
```

Three properties:

- **LIFO order** — last registered, first run. Mirrors nested destructors; dependent resources compose correctly (acquired second → released first).
- **Exit-aware** — `Scope.close(scope, exit)` records the exit; each finalizer can inspect success/failure/interruption.
- **Add-after-close is safe** — a `Closed` scope runs the finalizer immediately with the stored exit. No register-after-close race.

Finalization strategy is chosen at construction:

```ts
const seq = yield* Scope.make()           // "sequential" (default): one at a time, reverse order
const par = yield* Scope.make("parallel") // forks concurrently — teardown I/O-bound and independent
```

Failures from finalizers are aggregated into the close result either way. A scope also exposes `scope.state`: `"Empty"` / `"Open"` / `"Closed"` (with its exit) — handy for debugging lifecycle bugs.

### The `Scope` service

Most code shouldn't construct scopes by hand. A scope travels in the **context** like any service, and effects that register cleanup simply require it:

```ts
import { Effect, Scope } from "effect"

// R = Scope — visible in the type
const useResource = Effect.gen(function* () {
  const scope = yield* Scope.Scope          // or: yield* Effect.scope
  yield* Scope.addFinalizer(scope, Effect.sync(() => console.log("released")))
  return "value"
})
```

Requiring `Scope` in `R` is the *type-level declaration of dynamic lifetime*: "this effect creates resources that need cleanup from whoever runs it." The program won't type-check until someone provides a scope boundary.

## Opening boundaries: `Effect.scoped` and friends

`Effect.scoped` is the workhorse: open a fresh scope, run the effect inside, close the scope when it exits — with the same `Exit`, so finalizers observe the outcome:

```ts
import { Effect } from "effect"

const result = yield* Effect.scoped(useResource)
// R no longer contains Scope — the requirement was discharged
```

When you need the scope itself (hand to `forkIn`, register extra finalizers, build child scopes), `scopedWith` passes it as a value without putting it in context:

```ts
import { Effect, Scope } from "effect"

const program = Effect.scopedWith((scope) =>
  Effect.gen(function* () {
    yield* Scope.addFinalizer(scope, Effect.sync(() => console.log("bye")))
    return 42
  })
)
```

| Function | Behavior |
|---|---|
| `Effect.scoped(effect)` | Fresh scope opened + closed around `effect`; removes `Scope` from `R` |
| `Effect.scopedWith((scope) => eff)` | Same, but hands you the scope instead of placing it in context |
| `Scope.provide(scope)(effect)` | Runs `effect` inside an *existing*, caller-managed scope; removes `Scope` from `R` but does **not** close it |
| `Scope.use(closeable)(effect)` | Like `Scope.provide` but closes the scope when `effect` exits |
| `Scope.fork(scope, strategy?)` | Creates a child scope registered with the parent; closing parent closes child, closing child detaches it |

The `Effect.scoped` vs `Scope.provide` distinction is the ownership boundary: `Effect.scoped` says "resources die when this block ends"; `Scope.provide` says "run inside *my* lifetime" — attaching resources to a long-lived scope you control elsewhere (request scope, session scope):

```ts
import { Effect, Exit, Scope } from "effect"

const attachToRequest = Effect.gen(function* () {
  const requestScope = yield* Scope.make()

  // resource lives exactly as long as requestScope
  yield* Scope.provide(requestScope)(openSubscription)

  // ...serve requests...

  yield* Scope.close(requestScope, Exit.void)
})
```

:::caution[provide ≠ scoped]
`Scope.provide` deliberately does not close anything. If you use it and never close the scope yourself, you've built a leak with excellent types. Reach for `Scope.use` when you want auto-close with a scope you created.
:::

## `acquireRelease`: the bracket, done right

`Effect.acquireRelease(acquire, release)` pairs acquisition with a release function and registers the release on the current scope:

```ts
import { Cause, Effect, Schema } from "effect"

class ConnectionError extends Schema.TaggedError<ConnectionError>()(
  "ConnectionError",
  { reason: Schema.String }
) {}

interface Conn { readonly id: number }

const connect = Effect.gen(function* () {
  yield* Effect.log("opening")
  return { id: 1 } satisfies Conn
}).pipe(
  Effect.timeout("5 seconds"),
  // timeouts surface as Cause.TimeoutError — map to your domain error here
  Effect.catchIf(Cause.isTimeoutError, () =>
    new ConnectionError({ reason: "connect timeout" }))
)

const conn = Effect.acquireRelease(
  connect,
  (conn, exit) => Effect.sync(() => console.log(`closed ${conn.id}`))
)
```

v4 changed the signature in a way that matters:

```ts
Effect.acquireRelease<A, E, R, R2>(
  acquire: Effect<A, E, R>,
  release: (a: A, exit: Exit<unknown, unknown>) => Effect<unknown, never, R2>,
  options?: { readonly interruptible?: boolean }
): Effect<A, E, R | R2 | Scope>
```

The release function receives **both** the acquired resource *and* the `Exit` the scope closed with — replacing a whole category of "was I cancelled?" plumbing: send a graceful `BYE` on success, an `RST` on failure, nothing on interruption.

Three guarantees make this safe under concurrency — what plain `try/finally` *cannot* give you:

1. **Acquisition runs uninterruptibly by default.** Once `acquireRelease` starts the acquire effect, it can't be interrupted halfway — the resource is fully obtained, or acquisition never began. Without this, an interrupt between "socket opened" and "registered in scope" leaks the socket.
2. **Release runs only if acquisition succeeded, and then *always*** — success, failure of subsequent code, interruption of the whole fiber all funnel into scope close.
3. **Release itself runs uninterruptibly.** Cleanup is never abandoned halfway. (If release needs interruptible work — e.g. wait on another service with a timeout — wrap that part explicitly.)

If acquisition is genuinely long and you accept partial-state cleanup on interrupt, opt in:

```ts
const lease = Effect.acquireRelease(
  acquireLease,                       // may be interrupted mid-flight
  releaseLease,
  { interruptible: true }             // allow interrupts during acquisition
)
```

:::tip[Disposable resources]
For values already implementing `Symbol.dispose` / `Symbol.asyncDispose`, v4 adds `Effect.acquireDisposable(acquire)` — same scoping behavior, disposal protocol instead of an explicit release function. Handy when bridging to libraries built around `using`.
:::

## Custom resources with `addFinalizer`

`acquireRelease` covers the common shape. When the "resource" is really a set of cleanups, or acquisition interleaves with usage, drop to `addFinalizer`, which registers directly on the ambient scope:

```ts
import { Cause, Effect, Exit, Schema } from "effect"

class TempDirError extends Schema.TaggedError<TempDirError>()(
  "TempDirError",
  { path: Schema.String }
) {}

const withTempDir = Effect.gen(function* () {
  const dir = `/tmp/job-${Date.now()}`
  yield* Effect.tryPromise({
    try: () => fs.mkdir(dir, { recursive: true }),
    catch: () => new TempDirError({ path: dir })
  })

  // exit-aware: knows whether the job finished, failed, or got cancelled
  yield* Effect.addFinalizer((exit) =>
    Effect.sync(() => {
      if (Exit.isFailure(exit) && Cause.hasInterruptsOnly(exit.failure)) {
        console.log(`preserving ${dir} for post-mortem`)
      } else {
        fs.rmSync(dir, { recursive: true })
      }
    })
  )

  return dir
})
```

`Effect.addFinalizer` requires `Scope` — the type system now insists whoever runs `withTempDir` provides a cleanup boundary. Wrap it: `yield* Effect.scoped(withTempDir)`.

The `(exit) => ...` shape unlocks behavior impossible with `finally`: distinguish interruption (`Exit.isInterrupted`) to preserve debug state on cancel; inspect failures to log the cause; compensate differently per outcome (commit a marker row on success, roll back on failure). Sibling combinators for attaching behavior to a specific effect rather than the surrounding scope: `Effect.onExit` (runs with the `Exit`), `Effect.onError` (failures only, gets the `Cause`), `Effect.onInterrupt` (interruption only), `Effect.ensuring` (unconditional). Use `addFinalizer`/`acquireRelease` for resources; these for logging and metrics hooks.

## Ordering: why LIFO is load-bearing

Real systems acquire *graphs* of resources: a pool depends on a config service; a consumer depends on the pool. LIFO finalization tears down in exact reverse order of construction — the consumer's finalizer still has a working pool to flush into:

```ts
import { Effect } from "effect"

const events: Array<string> = []

const program = Effect.scoped(Effect.gen(function* () {
  yield* Effect.acquireRelease(
    Effect.sync(() => events.push("acquire config")),
    () => Effect.sync(() => events.push("release config"))
  )
  yield* Effect.acquireRelease(
    Effect.sync(() => events.push("acquire pool")),
    () => Effect.sync(() => events.push("release pool"))
  )
  yield* Effect.acquireRelease(
    Effect.sync(() => events.push("acquire consumer")),
    () => Effect.sync(() => events.push("release consumer"))
  )
  return "ready"
}))

Effect.runSync(program)
// acquire config -> acquire pool -> acquire consumer
// release consumer -> release pool -> release config
```

Manual cleanup makes you maintain that ordering by hand across every call site. Scopes make it structural — and because each layer's resources registered on the same scope, an interruption at any point unwinds exactly what was acquired so far.

## Scopes inside Layers

Layers (chapter 10) are scopes wearing a dependency-injection hat. `Layer.effect(Service, buildEffect)` runs `buildEffect` inside the layer's own scope — the signature shows it:

```ts
Layer.effect<Service, E, R>(service, effect): Layer<Service, E, Exclude<R, Scope>>
```

That `Exclude<R, Scope>` is the tell: any `Scope` requirement the build effect had is satisfied by the layer and removed from what users need. Resources acquired during construction finalize automatically when the layer's memoized lifetime ends (`Layer.launch`, MemoMap teardown at shutdown, or `Effect.scoped(Layer.build(layer))`):

```ts
import { Context, Effect, Layer } from "effect"

class Pool extends Context.Service<
  Pool,
  { readonly query: (sql: string) => Effect.Effect<string> }
>()("Pool") {}

const connect = Effect.sync(() => ({ id: 1 }))
const disconnect = () => Effect.sync(() => console.log("pool: disconnected"))

export const PoolLive = Layer.effect(
  Pool,
  Effect.gen(function* () {
    const conn = yield* Effect.acquireRelease(connect, disconnect)
    return {
      query: (sql) => Effect.succeed(`result of ${sql} via ${conn.id}`)
    }
  })
)
// PoolLive: Layer<Pool, never> — no Scope leaked to consumers
```

Layers built from other layers acquire dependencies' resources first, and everything tears down in reverse construction order when the memo map closes — dependency-ordered startup and shutdown for free, because underneath it's one big LIFO scope.

## Leak-freedom: comparing the models

| Concern | `try/finally` | `AsyncDisposable` / `using` | `AbortController` | Effect `Scope` |
|---|---|---|---|---|
| Cleanup on early return/throw | Yes (if block entered correctly) | Yes | No | Yes, structurally |
| Cleanup on cancellation | Not guaranteed to run | Not guaranteed | Signal only, no lifecycle | Guaranteed, finalizers uninterruptible |
| Dynamic lifetime (outlives function) | Manual callbacks | Manual (pass the disposable around) | Manual listeners | `Scope.provide` / `forkIn`, typed in `R` |
| Resource acquired after guard begins | Leaks | Leaks | Leaks | Impossible — registration is part of acquisition |
| Knows why it ended (success/fail/cancel) | No | No | Partially (signal reason) | Yes — finalizers receive the `Exit` |
| Ordering across dependencies | Hand-maintained nesting | Hand-maintained | None | LIFO, automatic |
| Type-level proof a boundary exists | No | No | No | Yes — `R` contains `Scope` until discharged |

The last row is the quiet revolution: in vanilla TS, "does this leak if misused?" is a code-review question. With scopes it's a compile error — an effect with `Scope` in `R` cannot run without a boundary.

:::caution[Scopes don't fix blocking]
This machinery coordinates *when* cleanup effects run. It cannot make a synchronous blocking call cancellable, nor conjure a release for a native handle that lacks one. Wrap blocking work with `Effect.try` and give the underlying library its own shutdown hook if it has one.
:::

## A complete resource graph

Three dependent resources, exit-aware releases, composed into a layer, consumed in a scoped block:

```ts
import { Context, Effect, Layer, Schema } from "effect"

class Bus extends Context.Service<
  Bus,
  { readonly publish: (msg: string) => Effect.Effect<void> }
>()("Bus") {}
class Cache extends Context.Service<
  Cache,
  { readonly get: (k: string) => Effect.Effect<string | undefined> }
>()("Cache") {}

const BusLive = Layer.effect(
  Bus,
  Effect.gen(function* () {
    yield* Effect.acquireRelease(
      Effect.sync(() => console.log("bus: connected")),
      (_conn, exit) =>
        Effect.sync(() =>
          console.log(`bus: closed (${exit._tag})`)
        )
    )
    return { publish: (msg) => Effect.sync(() => console.log(`bus: ${msg}`)) }
  })
)

const CacheLive = Layer.effect(
  Cache,
  Effect.gen(function* () {
    const bus = yield* Bus
    const store = new Map<string, string>()

    const flush = Effect.sync(() => {
      // runs while the bus is still open — LIFO guarantees it
      for (const [k, v] of store) console.log(`bus: flush ${k}=${v}`)
      console.log(`cache: flushed ${store.size} entries`)
    })

    yield* Effect.addFinalizer(() => flush)

    return {
      get: (k) =>
        Effect.sync(() => {
          store.set(k, `value:${k}`)   // pretend this was a cache miss fill
          return store.get(k)
        })
    }
  })
).pipe(Layer.provide(BusLive))

const program = Effect.gen(function* () {
  const cache = yield* Cache
  yield* cache.get("user:42")
}).pipe(Effect.provide([BusLive, CacheLive]))

await Effect.runPromise(program.pipe(Effect.scoped))
// bus: connected
// bus: flush user:42=value:user:42
// cache: flushed 1 entries
// bus: closed (Success)
```

Note what did *not* appear anywhere: try/finally blocks, cleanup registries, abort listeners, shutdown flags. The lifetimes are declared once, in the right order, and the runtime enforces them on every exit path — including the ones nobody tested. When hunting a suspected leak, remember the invariant: **every registration happens on some scope, and every scope closes exactly once** — leaks almost always turn out to be a scope nobody closes (a `Scope.provide` without `close`, or fibers detached via `forkDetach`, next chapter).
