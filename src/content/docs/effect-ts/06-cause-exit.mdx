Typed errors (chapter 05) are what your program *expects* to go wrong. A `Cause` records what *actually* went wrong — including defects and interruption, possibly several at once. Every failed execution produces one; every `run*` surfaces one; every `catchCause` handler receives one.

## The shape

```ts
interface Cause<out E> {
  readonly [TypeId]: typeof TypeId
  readonly reasons: ReadonlyArray<Reason<E>>
}

type Reason<E> = Fail<E> | Die | Interrupt
```

No nesting:

- **`Fail<E>`** — typed error from the error channel. `.error: E`
- **`Die`** — untyped defect. `.defect: unknown`
- **`Interrupt`** — fiber interrupted. `.fiberId: number | undefined`

Every reason also carries an `annotations` map (stack frames, spans, anything you add via `Effect.annotateLogs`) plus an `annotate()` method returning a copy with more metadata.

```ts title="src/reasons.ts"
import { Cause } from "effect"

const c1 = Cause.fail("boom")
c1.reasons[0] // { _tag: "Fail", error: "boom", annotations: {} }

const c2 = Cause.die(new Error("bug"))
if (Cause.isDieReason(c2.reasons[0])) {
  c2.reasons[0].defect // Error("bug")
}

const c3 = Cause.interrupt(42)
if (Cause.isInterruptReason(c3.reasons[0])) {
  c3.reasons[0].fiberId // 42
}
```

### Annotations: where the failure site lives

Each reason's `annotations` holds the captured stack frame under `Cause.StackTrace`:

```ts
import { Cause, Context } from "effect"

declare const reason: Cause.Fail<string>

const frame = Context.getOption(Cause.reasonAnnotations(reason), Cause.StackTrace)
```

Attach your own annotations to every reason in a cause — request-scoped facts survive into crash logs without threading a logger through everything:

```ts
import { Cause, Context } from "effect"

class RequestId extends Context.Service<RequestId, string>()("RequestId") {}

declare const cause: Cause.Cause<string>
declare const requestId: string

const enriched = Cause.annotate(cause, Context.make(RequestId, requestId))
```

## Why v4 flattened the tree

v3's `Cause` was a recursive ADT — `Sequential([Cause])` / `Parallel([Cause])` — elegant on paper, miserable in practice: deeply nested values, recursive helpers for simple questions, and a Sequential/Parallel distinction nobody branched on. v4 keeps exactly what handlers use; combining is concatenation:

```ts title="src/combine.ts"
import { Cause } from "effect"

const combined = Cause.combine(Cause.fail("a"), Cause.die(new Error("b")))
combined.reasons.map((r) => r._tag) // ["Fail", "Die"]

Cause.combine(Cause.empty, Cause.fail("x")).reasons.length // 1 — empty is the identity
```

Need ordering metadata? Annotations carry it. What you lose in topology you gain in trivially serialisable, diffable, loggable values.

:::note[Equality]
`Cause` implements structural equality: two causes with equal reason arrays compare equal, so tests can assert on entire failure shapes.
:::

## How multiple reasons arise

A single sequential failure yields a single-reason cause. Multiplicity comes from:

1. **Concurrent composition** — effects side by side under `all` / `race` / `forEach({ concurrency })` can several fail before siblings notice; their causes merge into one multi-reason value:

```ts
import { Cause, Effect } from "effect"

const program = Effect.all(
  [Effect.fail("a"), Effect.fail("b"), Effect.die(new Error("c"))],
  { concurrency: "unbounded" }
)
```

2. **Explicit combination** via `Cause.combine` (e.g. in `catchCause` handlers, or `Fiber.join` merging child causes into yours).
3. **Collection APIs with aggregate payloads** — subtlety: `Effect.validate` runs every element, but its failure is a *single* `Fail` whose `.error` is the `NonEmptyArray<E>` of collected errors, not one reason per element:

```ts
const checked = Effect.validate(["a", "", "c"], (s) =>
  s.length > 0 ? Effect.succeed(s) : Effect.fail(`empty:${s}`)
)
// fails once; cause.reasons.length === 1; cause.reasons[0].error === ["empty:", ...]
```

Never assume `cause.reasons.length === 1`, and never assume a `Fail`'s error isn't itself a collection. Loop, narrow, inspect.

## Inspecting a cause

| Layer | Functions | Question answered |
|---|---|---|
| Predicates | `hasFails` `hasDies` `hasInterrupts` `hasInterruptsOnly` | does any reason of kind X exist? |
| Guards | `isFailReason` `isDieReason` `isInterruptReason` | narrowing while iterating |
| Extractors | `findError` `findErrorOption` `findDefect` `findFail` `findDie` `findInterrupt` | give me the first X |

```ts title="src/inspect.ts"
import { Cause, Result } from "effect"

declare const cause: Cause.Cause<string>

if (Cause.hasDies(cause)) {
  console.error("at least one defect present")
}

for (const reason of cause.reasons) {
  switch (reason._tag) {
    case "Fail":
      console.log("typed:", reason.error)
      break
    case "Die":
      console.log("defect:", reason.defect)
      break
    case "Interrupt":
      console.log("interrupted by fiber:", reason.fiberId)
      break
  }
}

// extractors return Result (success-first! chapter 07)
const first: Result.Result<string, Cause.Cause<never>> = Cause.findError(cause)
const defect: Result.Result<unknown, Cause.Cause<string>> = Cause.findDefect(cause)
const asOption = Cause.findErrorOption(cause) // Option<string>
```

`findErrorOption` is the workhorse for "just tell me the error if there is one"; the `Result` variants preserve the remaining cause when nothing matches, so chained extraction doesn't lose information. Also: `interruptors(cause)` collects defined fiber IDs into a `ReadonlySet<number>`, and `Cause.map(cause, f)` transforms only `Fail` payloads, passing `Die`/`Interrupt` through untouched.

## Exit: the completed-fiber envelope

An effect *executing* can fail in flight; a fiber that has *finished* reports an `Exit`:

```ts
type Exit<A, E> = Success<A, E> | Failure<A, E>

interface Success<A, E> { /* .value: A */ }
interface Failure<A, E> { /* .cause: Cause.Cause<E> */ }
```

Constructors mirror the failure modes: `Exit.succeed(a)`, `Exit.fail(e)` (sugar for a single-Fail cause), `Exit.die(defect)`, `Exit.failCause(cause)`, `Exit.interrupt(fiberId?)`. `Exit.fail(e)` exists but the canonical carrier is the cause — `Failure.cause` may hold any number of mixed reasons.

### Where Exits appear

**`Effect.runPromiseExit`** — the never-rejecting runner:

```ts
import { Effect, Exit } from "effect"

declare const program: Effect.Effect<number, string>

const exit = await Effect.runPromiseExit(program)
if (Exit.isSuccess(exit)) {
  exit.value // number
} else {
  exit.cause // Cause.Cause<string>
}
```

Contrast `Effect.runPromise`, which resolves only on success and on failure throws the *squashed* cause (`Cause.squash`: first Fail error, else first Die defect, else an interrupt placeholder). Squashing is deliberately lossy — prefer `runPromiseExit` whenever "failed" vs "died" matters.

**`Fiber.await`** — observing a forked fiber returns its Exit instead of propagating its failure:

```ts
import { Cause, Effect, Fiber } from "effect"

declare const task: Effect.Effect<number, string>

const supervised = Effect.gen(function* () {
  const fiber = yield* Effect.forkChild(task)
  const exit = yield* Fiber.await(fiber) // Effect<Exit<number, string>>
  if (Exit.isFailure(exit) && Cause.hasInterruptsOnly(exit.cause)) {
    yield* Effect.log("child was cancelled")
  }
})
```

(`Fiber.join` is the counterpart that re-raises: it merges the child's cause into yours.)

**Fiber observers / `runFork`** — `fiber.addObserver(cb)` delivers the final Exit; this is what ManagedRuntime and test harnesses build on.

**Request resolvers (preview)** — batching infrastructure completes individual requests with exits directly: `entry.completeUnsafe(Exit.succeed(value))` or `Exit.failCause(cause)` per entry. Recognise the type when you see it with `RequestResolver`.

### Folding an Exit

```ts
import { Effect, Exit } from "effect"

declare const exit: Exit.Exit<number, string>

const rendered = Exit.match(exit, {
  onSuccess: (value) => `ok: ${value}`,
  onFailure: (cause) => `bad: ${Cause.pretty(cause)}`
})
```

Guards `Exit.isSuccess` / `Exit.isFailure` narrow directly; `hasFails`, `hasDies`, `hasInterrupts` exist on Exit too, delegating to the wrapped cause. The rest of the surface:

| Function | Behaviour |
|---|---|
| `Exit.getSuccess(exit)` | `Option<A>` — value if success |
| `Exit.getCause(exit)` | `Option<Cause<E>>` — cause if failure |
| `Exit.findErrorOption(exit)` | first typed error, or `None` |
| `Exit.map` / `mapError` / `mapBoth` | channel transforms |
| `Exit.asVoid` | erase the payload |

### A worked pass through a failure

Run something that fails three ways at once, then dissect it:

```ts title="src/dissect.ts"
import { Cause, Effect, Exit } from "effect"

declare const flaky: Effect.Effect<number, string>

const exit = await Effect.runPromiseExit(
  Effect.all([flaky, Effect.die(new Error("boom"))], { concurrency: "unbounded" })
)

if (Exit.isFailure(exit)) {
  const { reasons } = exit.cause

  const counts = {
    fail: reasons.filter(Cause.isFailReason).length,
    die: reasons.filter(Cause.isDieReason).length,
    interrupt: reasons.filter(Cause.isInterruptReason).length
  }

  const headline = Cause.squash(exit.cause)   // what runPromise would throw
  const report = Cause.pretty(exit.cause)     // everything, human-readable

  console.log(counts, headline, report)
}
```

This is the shape of every crash-reporting hook, HTTP 500 handler, and job-runner error path: take an Exit, split its reasons, render.

## Interruption is a reason, not an exception

v3 represented cancellation as an `InterruptedException` in the error channel — so every interruptible signature carried it, and every catch-all risked swallowing cancellation. v4 makes interruption an `Interrupt` **reason**, structurally distinct from failures:

- Typed-error combinators (`catch`, `catchTag`, ...) never see interrupts. Cancellation can't be accidentally swallowed by business logic.
- To react specifically to cancellation, use `Effect.onInterrupt` or check `Cause.hasInterruptsOnly` — the latter distinguishes "cancelled" from "cancelled *and also* something failed".
- Cleanup runs during unwinding regardless (finalizers, `acquireRelease`); chapter 13 covers fiber-level semantics.

## Defect strategy

Working rules:

- **Prefer fail over die whenever recovery is conceivable.** A defect skips every `catchTag` table and surfaces only to `catchCause`/`catchDefect`/crash reporting.
- **Let defects crash.** The runtime logs them with full pretty-printed causes and kills the owning fiber — the correct default for bugs.
- **Capture defects only where you add value:**

```ts title="src/report.ts"
import { Cause, Effect } from "effect"

declare const pluginTask: Effect.Effect<void>

// observe without swallowing
const observed = pluginTask.pipe(
  Effect.onError((cause) =>
    Cause.hasDies(cause)
      ? Effect.logError("plugin crashed", { cause: Cause.pretty(cause) })
      : Effect.void
  )
)

// recover, but only from defects, and say why
const sandboxed = pluginTask.pipe(
  Effect.catchDefect((defect) =>
    Effect.logWarning("disabling broken feature").pipe(Effect.asVoid)
  )
)
```

`Effect.onError` fires on any non-success exit (errors included) and cannot change the outcome — ideal for audit logging. `Effect.catchDefect` converts a defect into a typed error path, justified almost exclusively at integration boundaries: plugin hosts, worker pools, request handlers deciding between 500 and fallback content.

:::caution[Don't convert defects reflexively]
Every `catchDefect` weakens the signal that "a defect means a bug". Convert at the outermost boundary that must respond, and log the original cause there.
:::

## Pretty-printing

Three renderers, increasing fidelity:

```ts
import { Cause } from "effect"

declare const cause: Cause.Cause<unknown>

Cause.squash(cause)       // unknown — the single thrown value runPromise would raise
Cause.prettyErrors(cause) // Array<Error> — one Error per Fail/Die, stacks annotated with spans
Cause.pretty(cause)       // string — joined stack traces
```

`prettyErrors` preserves messages, names, stacks, and `cause` chains, and appends span annotations captured at the failure site — which is why `withSpan`/`Effect.fn` naming pays off in production logs. Ship `prettyErrors` to structured loggers; use `pretty` for humans. `squash` is lossy by design: first `Fail`, then first `Die`, then a generic interrupt marker.

### Causes in your logs

The default runtime already logs unhandled failures with pretty-printed causes. Two idioms for your own paths:

```ts
import { Cause, Effect } from "effect"

declare const task: Effect.Effect<number, string>

const logged = task.pipe(
  Effect.catch((error) =>
    Effect.logWarning("task failed", { tag: "TaskFailure", detail: error })
      .pipe(Effect.as(0))
  )
)

const audited = task.pipe(
  Effect.onError((cause) => Effect.logError(`exit cause: ${Cause.pretty(cause)}`))
)
```

`prettyErrors` returns plain `Array<Error>` with stacks and spans, so it drops straight into Sentry/Datadog-style reporters without custom serialisers.

## Cheat sheet

| Task | Code |
|---|---|
| Any typed failures? | `Cause.hasFails(cause)` |
| Any defects? | `Cause.hasDies(cause)` |
| Only cancellation? | `Cause.hasInterruptsOnly(cause)` |
| First typed error | `Cause.findErrorOption(cause)` |
| First defect | `Cause.findDefect(cause)` |
| Merge two causes | `Cause.combine(a, b)` |
| Build from reasons | `Cause.fromReasons([...])` |
| Never-rejecting run | `await Effect.runPromiseExit(eff)` |
| Observe a child fiber | `yield* Fiber.await(fiber)` |
| Fold success/failure | `Exit.match(exit, { onSuccess, onFailure })` |
| Log-on-any-exit | `Effect.onError(cb)` |
| Capture defects | `Effect.catchDefect(d => ...)` |
| Human-readable string | `Cause.pretty(cause)` |
