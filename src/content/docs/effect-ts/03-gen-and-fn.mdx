Sequence effects with generators (`Effect.gen`), attach behavior with combinators around them. Combinator-only style survives in small pipelines; business logic lives in generators.

## How `Effect.gen` works

```ts
// simplified from packages/effect/src/internal/effect.ts
export const gen = (...args) =>
  suspend(() =>
    fromIteratorUnsafe(args.length === 1 ? args[0]() : args[1].call(args[0].self))
  )
```

Each execution calls the generator function (fresh iterator); the runtime drives `iterator.next(value)` — execute the yielded Effect, feed `A` back on success, resume so `yield*` raises the typed error on failure. The body runs per execution, so `gen` effects are re-runnable, and delegation flattens at the iterator level (no nesting).

What you may yield (`Y` channel):

| Yieldable | Behavior when yielded |
|---|---|
| `Effect` | run it; success feeds back; `E` joins the error channel |
| `Option<T>` | `Some(t)` yields `t`; `None` fails with `NoSuchElementError` |
| `Result<E, A>` | success yields `A`; failure fails with its `E` |
| `Config<T>` | reads config; failure is `ConfigError` |
| `Context.Service` class | retrieves the service from context |

v3-yieldable handle types (`Ref`, `Deferred`, `Fiber`, `Queue`) are plain values now — call accessors explicitly:

```ts
const ref = yield* Ref.make(0)
const value = yield* Ref.get(ref)        // NOT `yield* ref`

const deferred = yield* Deferred.make<string>()
yield* Deferred.done(deferred, Exit.succeed("done"))
const msg = yield* Deferred.await(deferred)

const fiber = yield* Effect.forkChild(task)
const result = yield* Fiber.join(fiber)
```

Why: in v3 those types were structurally assignable to `Effect`, so `Effect.all([refA, refB])` silently *read* refs. v4's split (Yieldable ≠ assignable) turns that bug into a type error.

## Body style

```ts
import { Effect } from "effect"

class FileProcessingError extends Schema.TaggedError<FileProcessingError>()(
  "FileProcessingError",
  { message: Schema.String }
) {}

const processFile = Effect.gen(function* () {
  yield* Effect.log("Starting the file processing...")
  yield* Effect.log("Reading file...")
  return yield* new FileProcessingError({ message: "Failed to read the file" })
}).pipe(
  Effect.catch((error) => Effect.logError(`An error occurred: ${error}`)),
  Effect.withSpan("fileProcessing")
)
```

Two conventions: raise errors with `return yield* new SomeError(...)` (the `return` ends control flow so narrowing works and `R` stays accurate); attach cross-cutting behavior via `.pipe` around the gen block, not inline conditionals.

## `Effect.fn` — functions returning effects

```ts
import { Effect } from "effect"

export const getUser = Effect.fn("getUser")(
  function* (id: string): Effect.fn.Return<User, UserNotFound, Database> {
    yield* Effect.annotateCurrentSpan({ userId: id })
    return yield* (yield* Database).findById(id)
  },
  // combinators as extra arguments — NOT .pipe
  Effect.retry({ times: 3 }),
  Effect.timeout("5 seconds"),
  Effect.catchTag("UserNotFound", () => Effect.succeed(User.guest))
)
```

Over a plain arrow around `Effect.gen`, `Effect.fn("name")` gives:

- **A tracing span per invocation** named `"getUser"`, plus synthetic stack frames pairing definition and call site.
- **Combinators applied per call**: trailing args receive `(effect, ...originalArgs)`, so retry/timeout wrap every invocation with the right args in scope.
- **Correct arity**, and a body that can be a generator *or* a bare Effect.

Without a name, `Effect.fn(body)` still adds a frame boundary but creates no span. Use the named form across service boundaries.

### `Effect.fn.Return`

```ts
function* (id: string): Effect.fn.Return<User, UserNotFound, Database> {
```

`Effect.fn.Return<A, E, R>` = `Generator<Effect<any, E, R>, A, any>` — annotates what the generator body returns while the produced function's full `Effect<User, UserNotFound, Database>` is inferred. Use it when inference is ambiguous or for explicit exported signatures.

:::tip
`Effect.fnUntraced(body, ...combinators)` — same shape without span/frame machinery, for hot inner helpers.
:::

## `this` binding

```ts
import { Effect } from "effect"

class Cart {
  items: Array<string> = []

  add = Effect.gen({ self: this }, function* () {
    self.items.push("apple")
    return self.items.length
  })
}
```

v3's bare `Effect.gen(this, ...)` is gone. Idiomatic v4 stateful components are services in layers (later parts), closing over private state — not classes with generator methods.

## Control flow is plain JavaScript

```ts
const checkout = Effect.fn("checkout")(function* (cartId: string) {
  const cart = yield* store.get(cartId)
  if (cart.items.length === 0) {
    return yield* new EmptyCartError({ cartId })
  }
  for (const item of cart.items) {
    yield* inventory.reserve(item.sku, item.qty)
  }
  try {
    return yield* payments.charge(cart.total)
  } catch {
    return yield* new PaymentDeclinedError({ cartId })
  }
})
```

v3 loop helpers (`Effect.loop`, `Effect.iterate`, `while`-style combinators) are **removed** — write the loop yourself. The generator *is* the loop construct.

## Style checklist

1. Prefer `Effect.gen`; use `Effect.fn("name")` for exported effect-returning functions.
2. Always `return` when raising an error inside a gen body.
3. Attach behavior with `.pipe` (standalone) or trailing args (inside `Effect.fn`) — don't `.pipe` onto `Effect.fn` results.
4. Name spans after functions; annotate with request-scoped facts (`annotateCurrentSpan`).
5. Define domain errors with `Schema.TaggedError` — decodable, loggable, HTTP-mappable, catchable by `_tag`.
