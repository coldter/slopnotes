Every `Effect<A, E, R>` carries `R` — the requirements channel. Effect's opinionated idea: **dependencies are part of the return type**. A function claiming `Effect<User, UserNotFound, Database>` is confessing "I cannot run unless something hands me a working `Database`." The requirement travels with the value, flows through every combinator, and lands on whichever boundary provides it. Arguments stay the right tool for data; services are for *capabilities* — connections, clients, clocks, feature flags — threaded through many layers unchanged.

This chapter covers the *what*: declaring services, accessing them, and the `Context` they live in. The *who builds them* question is [Chapter 10](/effect-ts/10-layers/).

## What `R` actually is

At runtime every fiber carries a `Context` — an immutable hash-array-mapped map from identifier strings to implementations. Yielding a service asks the fiber's context for its entry:

| Channel | Promise equivalent | Checked by |
|---|---|---|
| `A` | resolve value | types |
| `E` | *(nothing — rejects with `any`)* | types |
| `R` | *(nothing — closures capture whatever)* | types |

Adding a dependency to a leaf changes its inferred signature; every caller up the chain satisfies it, passes it through, or pushes the requirement outward.

## Declaring a service: `Context.Service`

v4 has exactly one way to declare a required service. Class-style form:

```ts
import { Context, Effect, Layer, Schema } from "effect"

export class DatabaseError extends Schema.TaggedError<DatabaseError>()(
  "DatabaseError",
  { message: Schema.String }
) {}

export class Database extends Context.Service<Database, {
  query(sql: string): Effect.Effect<Array<unknown>, DatabaseError>
  transaction<A>(
    body: Effect.Effect<A, DatabaseError>,
  ): Effect.Effect<A, DatabaseError>
}>("myapp/db/Database") {
  static readonly layer = Layer.effect(
    Database,
    Effect.gen(function* () {
      const query = Effect.fn("Database.query")(function* (sql: string) {
        // real driver calls go here — see Chapter 10
        return []
      })
      const transaction = Effect.fn("Database.transaction")(
        function* <A>(body: Effect.Effect<A, DatabaseError>) {
          return yield* body
        },
      )
      return Database.of({ query, transaction })
    }),
  )
}

export type DatabaseService = Database["Service"]
```

Anatomy:

1. **`extends Context.Service<Database, Shape>()`** — the two-stage call. `Context.Service<Database, Shape>` captures the class (`Self`) and the service interface (`Shape`); calling it with `()` returns a class factory; the second call takes the identifier string. This lets the class be named `Database` and act as *both type and runtime key*.
2. **`"myapp/db/Database"`** — the identifier string, the key under which the implementation lives in a `Context`. It's the service's runtime identity: same string = same slot regardless of type. Namespacing (`myapp/db/`) is convention — dependencies from multiple libraries share one context namespace.
3. **The shape type** — the interface consumers call. Methods returning `Effect<...>` keep errors and further requirements flowing through the channels.
4. **`static readonly layer`** — a default construction recipe. v4 generates **no** layers for you; attaching a `layer` static is the house convention so consumers write `Effect.provide(program, Database.layer)`.
5. **`Database.of({ ... })`** — an identity function typed against the shape, for autocomplete and excess-property checking.
6. **`export type DatabaseService = Database["Service"]`** — extracts the shape for signatures like `function migrate(db: DatabaseService)`. (`Context.Service.Shape<typeof Database>` also works.)

:::caution[The identifier string is load-bearing]
Two unrelated services sharing a string overwrite each other in a merged context with no type error — `Context.make` stores by string key. Give every service a namespaced unique id; treat renaming as a breaking change.
:::

### Function-style keys

When you don't need a class (tests, scripts):

```ts
import { Context } from "effect"

export const ClockPort = Context.Service<{
  now(): Effect.Effect<number>
}>("myapp/time/ClockPort")

// same operations on the returned value:
// ClockPort.of, ClockPort.use, ClockPort.useSync, ClockPort.context
```

The value is both key and accessor. Classes win when you want a place to attach the `layer` static and a nominal name in error messages.

## Accessing services

| Accessor | Callback returns | Adds to `E` | Adds to `R` | Use when |
|---|---|---|---|---|
| `yield* Service` | — (unwraps in place) | per method called | `Identifier` | inside any gen/fn body — the default |
| `Service.use(f)` | `Effect<A, E, R>` | `E` from callback | `R \| Identifier` | composing without a whole gen block |
| `Service.useSync(f)` | plain `A` | nothing | `Identifier` | pure reads of the service object |

### `yield*` inside generator bodies (default)

A `Key` *is* an `Effect<Shape, never, Identifier>`, so you yield it:

```ts
import { Effect } from "effect"
import { Database } from "./database.ts"

export const getUser = Effect.fn("getUser")(function* (id: string) {
  const db = yield* Database
  return yield* db.query(`SELECT * FROM users WHERE id = '${id}'`)
})
// getUser: (id: string) => Effect<User, DatabaseError, Database>
```

The value binds once per invocation; the requirement propagates into the signature automatically. Yielding the class directly means one import gives you key, shape, and layer.

### `use` / `useSync` for one-liners outside generators

```ts
import { Effect } from "effect"
import { Database } from "./database.ts"

export const countUsers: Effect.Effect<number, DatabaseError, Database> =
  Database.use((db) => db.query("SELECT count(*) FROM users"))

export const hasPool: Effect.Effect<boolean, never, Database> =
  Database.useSync((db) => "query" in db)
```

`useSync`'s callback can't suspend, so it adds no `E`/`R` — the escape hatch for using services inside combinator pipelines that expect pure transforms.

### Combinator style: `Effect.service` family

```ts
import { Effect, Option } from "effect"
import { Database } from "./database.ts"

const dbEffect = Effect.service(Database)                 // explicit retrieval mid-pipe
const maybeDb: Effect.Effect<Option.Option<Database>> =    // did anyone provide it?
  Effect.serviceOption(Database)

const grabContext = Effect.gen(function* () {
  const ctx = yield* Effect.context<never>()               // the whole context
  return ctx
})
```

`Effect.context<R>()` materializes the entire map — how generic middleware forwards "whatever the caller provided" downward. Use these when writing combinators, not business logic.

## `Context.Reference` — services with defaults

For knobs that deserve sane defaults but allow overrides (log levels, timeouts, feature flags), use `Context.Reference`: a key that resolves to a lazily-computed, cached default when nobody provided a value:

```ts
import { Context, Effect } from "effect"

export const LogLevelRef = Context.Reference<"info" | "warn" | "error">(
  "myapp/LogLevel",
  { defaultValue: () => "info" },
)

export const audit = Effect.fn("audit")(function* (event: string) {
  const level = yield* LogLevelRef
  if (level !== "error") {
    yield* Effect.log(`[audit] ${event}`)
  }
})

await Effect.runPromise(audit("user.signup")) // runs with "info" — no provision needed

await Effect.runPromise(
  audit("user.signup").pipe(
    Effect.provideService(LogLevelRef, "error"),
  ),
)
```

- `defaultValue` is invoked lazily on first miss and cached on the reference.
- References are fully yieldable and **never appear in `R`**: their type is `Service<never, Shape>` — the default guarantees resolution. Overrides narrow behavior, they don't change types.
- Overriding is ordinary service provision: `Effect.provideService`, `Context.add`, or `Layer.succeed(LogLevelRef, "debug")` all work.

This one mechanism replaced two v3 concepts at once: `Context.Reference<Self>()` and **all of `FiberRef`**. v4's runtime settings are just references read by the engine — the built-ins live in the `References` module (`References.MinimumLogLevel`, `References.CurrentLogAnnotations`, `References.Scheduler`, `References.MaxOpsBeforeYield`, ...), overridden identically:

```ts
import { Effect, References } from "effect"

const noisy = Effect.gen(function* () {
  yield* Effect.logDebug("visible here")
})

await Effect.runPromise(
  noisy.pipe(Effect.provideService(References.MinimumLogLevel, "Warning")),
)
```

No `FiberRef.make`/`local`/`get`/`set` exists anymore. State that was a `FiberRef` becomes a `Context.Reference` holding an immutable value (or a small interface with methods); for *mutable* per-fiber state, hold a `Ref` inside the reference's value. Feature flags are the classic case:

```ts
export const Features = Context.Reference<{
  readonly newCheckout: boolean
  readonly aiSummaries: boolean
}>("myapp/Features", {
  defaultValue: () => ({ newCheckout: false, aiSummaries: true }),
})

export const withBetaCheckout = <A, E, R>(
  self: Effect.Effect<A, E, R>,
): Effect.Effect<A, E, R> =>
  Effect.provideService(self, Features, {
    newCheckout: true,
    aiSummaries: true,
  })
```

## `Context` as a typed immutable map

Beneath the surface, a `Context<R>` is a persistent map from identifier strings to implementations:

```ts
import { Context, Option } from "effect"
import { Database } from "./database.ts"
import { Cache } from "./cache.ts"

const impl = { query: () => Effect.succeed([]) }

const ctx1 = Context.make(Database, impl)                          // one-service context
const ctx2 = ctx1.pipe(Context.add(Cache, { get: () => Option.none() })) // extend immutably
const db: typeof impl = Context.get(ctx2, Database)                // throws if missing (References safe)
const maybeCache = Context.getOption(ctx2, Cache)                  // Option.some({...})
const missing = Context.getOption(Context.empty(), Cache)          // Option.none()

const otherImpl = { query: () => Effect.succeed([{ fallback: true }]) }
const ctx3 = Context.merge(ctx2, Context.make(Database, otherImpl)) // right side wins on conflicts
const justDb = ctx2.pipe(Context.pick(Database))                  // project
const noCache = ctx2.pipe(Context.omit(Cache))                     // subtract
```

| Operation | Signature sketch | Failure mode |
|---|---|---|
| `Context.empty()` | `Context<never>` | — |
| `Context.make(k, v)` | one-service context | — |
| `Context.add(ctx, k, v)` | extended context | — |
| `Context.get(ctx, k)` | `Shape` | dies if missing (safe for References) |
| `Context.getOption(ctx, k)` | `Option<Shape>` | never fails |
| `Context.getOrElse(ctx, k, f)` | `Shape` with fallback | never fails |
| `Context.merge(a, b)` / `mergeAll(...)` | union of services | right wins on key clash |
| `Context.pick(k...)` / `omit(k...)` | narrowed context | — |

Two facts: `Effect.provide(effect, context)` accepts a raw `Context` — hand-built maps are clearer than layers when everything is already in memory (`Effect.provide(handler, Context.make(Database, fakeDb))`). And services build contexts: `Database.context(impl)` = `Context.make(Database, impl)`; `Layer.succeedContext(context)` turns any context into a layer. `add`/`merge`/`pick`/`omit` return new contexts and leave operands untouched — safe to snapshot in middleware. Equality is structural; `Context.hasSameCache` exists for framework code needing identity checks.

## The v3 collapse

Five v3 spellings, one survivor:

| v3 mechanism | v4 replacement |
|---|---|
| `Context.Tag<"id", Shape>()` | `Context.Service<Shape>("id")` (function style) |
| `GenericTag<Shape>("id")` | same — the id is just a string now |
| `class X extends Effect.Tag<X>()("id", {...})` | `class X extends Context.Service<X, Shape>()("id")` — attach your own `layer` static |
| `Effect.Service` (auto-generated `.Default` layer) | deleted; same replacement as above |
| `Context.Reference<Self>()("id", { defaultValue })` | `Context.Reference<Shape>("id", { defaultValue })` |
| `FiberRef` | `Context.Reference` + `References.*` builtins |

Migration heuristics: every `Tag`/`GenericTag` becomes a function-style `Context.Service` — `yield* Tag` call sites stay valid verbatim. Every `Effect.Tag`/`Effect.Service` class loses its auto-generated `.Default`/`.live` layers — write the layer yourself as a static (v3's magic layers hid construction requirements from the type system). `tag.use(...)` → `Service.use(...)` unchanged. `FiberRef.make(default)` → `Context.Reference(id, { defaultValue })`; `FiberRef.get` → `yield* ref`; `local`/`set` → scoped `Effect.provideService`.

## Swapping implementations: the testing payoff

Given the `Database` class, a test stub is just another layer satisfying the same key:

```ts
import { Effect, Layer } from "effect"
import { Database, DatabaseError } from "./database.ts"

const rows = [{ id: "u_1" }, { id: "u_2" }]

export const DatabaseTest = Layer.succeed(
  Database,
  Database.of({
    query: () => Effect.succeed(rows),
    transaction: (body) => body,
  }),
)
```

Business code never changes — `getUser` still declares `Effect<User, DatabaseError, Database>`. Only the edge picks the implementation:

```ts
Effect.provide(program, Database.layer)  // production
Effect.provide(program, DatabaseTest)    // tests — see Chapter 28
```

`Layer.succeed` stubs share nothing with production machinery and start instantly. Pattern: **declare requirements deep, decide implementations at the edge**. Layers memoize within a run, so providing `DatabaseTest` once around the whole runner means every call site providing that *same layer value* resolves to one shared stub. How memoization works is the centerpiece of the next chapter.
