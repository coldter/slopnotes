Auther is configured entirely through environment variables, validated at startup by a Zod schema in `env.ts`. **Required** vars block boot if missing; **optional** ones have defaults or are environment-specific. The Docker stack below supplies them all for local dev.

## Required environment variables

| Variable | Description | Example |
| --- | --- | --- |
| `BETTER_AUTH_SECRET` | Encryption key (min 32 chars). Session encryption, JWKS private-key encryption, webhook-secret encryption. | `a-very-long-random-secret-string-here` |
| `BETTER_AUTH_DATABASE_URL` | Turso/libSQL connection URL | `libsql://your-db.turso.io` |
| `JWT_ISSUER` | JWT issuer URL (must match deployment URL) | `https://auth.example.com` |
| `JWT_AUDIENCE` | Comma-separated JWT audiences | `payload-admin,my-app,my-spa` |
| `PAYLOAD_CLIENT_ID` | Confidential client ID | `my-confidential-client` |
| `PAYLOAD_CLIENT_SECRET` | Confidential client secret (also the signup restriction secret) | `secret-at-least-32-chars` |
| `PAYLOAD_REDIRECT_URI` | Confidential client redirect URL | `https://myapp.com/auth/callback` |
| `PAYLOAD_SPA_CLIENT_ID` | Public PKCE client ID | `my-spa-client` |
| `PAYLOAD_SPA_REDIRECT_URIS` | Comma-separated SPA redirect URLs | `https://spa.example.com/callback` |
| `CRON_SECRET` | Secret for internal cron endpoints (JWKS rotation, trace cleanup) | `cron-secret-value` |
| `QSTASH_TOKEN` | Upstash QStash token for the webhook queue | `eyJ...` |
| `QSTASH_CURRENT_SIGNING_KEY` | QStash signature verification key | `sig_xxxxx` |
| `UPSTASH_REDIS_REST_URL` | Upstash Redis URL for idempotency/rate limiting | `https://your-redis.upstash.io` |
| `UPSTASH_REDIS_REST_TOKEN` | Upstash Redis auth token | `AxxxxxxxxxxxxxxxxxxxQ==` |
| `PAYLOAD_WEBHOOK_URL` | Default outbound webhook destination | `https://myapp.com/api/webhooks` |
| `PAYLOAD_OUTBOUND_WEBHOOK_SECRET` | HMAC secret for outbound webhooks (min 32 chars) | `outbound-webhook-secret-32chars` |
| `PAYLOAD_INBOUND_WEBHOOK_SECRET` | HMAC secret for inbound webhooks (min 32 chars) | `inbound-webhook-secret-32chars` |
| `RESEND_API_KEY` | Resend API key | `re_xxxxxxxxxxxxx` |
| `EMAIL_FROM` | Sender email address | `noreply@example.com` |
| `EMAIL_FROM_NAME` | Sender display name | `Auther` |

:::caution[Secrets must be long enough]
`BETTER_AUTH_SECRET` and both webhook HMAC secrets require at least 32 characters — startup validation rejects shorter values. Generate them with a real random source, not a memorable phrase.
:::

## Optional environment variables

| Variable | Description | Default |
| --- | --- | --- |
| `BETTER_AUTH_DATABASE_AUTH_TOKEN` | Turso auth token | (none) |
| `PRODUCTION_URL` | Production deployment URL | Falls back to `NEXT_PUBLIC_APP_URL` |
| `NEXT_PUBLIC_APP_URL` | Current deployment URL (CORS, trusted origins) | `http://localhost:3000` |
| `PAYLOAD_SPA_LOGOUT_URIS` | Comma-separated post-logout redirect URLs | (none) |
| `PAYLOAD_PREVIEW_ORIGIN_PATTERNS` | Wildcard patterns for preview deploys (e.g. `https://*.vercel.app`) | (none) |
| `QSTASH_URL` | QStash API URL (local dev) | Default QStash cloud URL |
| `QSTASH_NEXT_SIGNING_KEY` | Next QStash signing key (rotation) | (none) |
| `QUEUE_TARGET_BASE_URL` | Base URL for queue worker targets (Docker networking) | (none) |
| `VERCEL_URL` | Auto-set by Vercel | (none) |
| `SKIP_EMAIL_SENDING` | Set to any value to skip email delivery (testing) | (none) |

## Local development with Docker

`docker-compose.yml` stands up the whole system — including local replacements for each managed dependency — so a fresh checkout runs end to end with one command.

| Service | Port | Purpose |
| --- | --- | --- |
| `app` (Next.js) | 3000 | The Auther application |
| `libsql` | 8080 | Turso-compatible SQLite database |
| `redis` | 6379 | Upstash Redis replacement |
| `qstash` | 8081 | Upstash QStash local server |
| `mailhog` | 8025 (UI), 1025 (SMTP) | Email testing (catches all outbound email) |
| `webhook-tester` | 8082 | Webhook request inspector |

### Quick start

<Steps>

1. Bring the stack up. Development mode hot-reloads the app; production mode builds the image first.

   <Tabs syncKey="docker-mode">
     <TabItem label="Development (hot-reload)">
       ```bash
       pnpm d:up-dev
       ```
     </TabItem>
     <TabItem label="Production (build first)">
       ```bash
       pnpm d:up
       ```
     </TabItem>
   </Tabs>

2. Wait for supporting services. On startup `db-migrate` runs the Drizzle schema push; `db-seed` creates a test admin and seeds OAuth clients.

3. Sign in at `http://localhost:3000` with the seeded admin:

   ```text
   email:    admin@test.local
   password: admin123
   ```

4. Inspect captured email in the Mailhog UI at `http://localhost:8025`, and watch outbound webhooks in the webhook-tester on port 8082.

</Steps>

:::tip[Seeded test data]
The seed step gives you a working account and pre-registered OAuth clients out of the box, so you can exercise the full sign-in and authorization flow immediately.
:::

### Useful scripts

Run the Next.js server directly against your own services (outside Docker, needs a populated `.env.local`):

```bash
pnpm dev              # Local dev server (requires .env.local)
pnpm db:push          # Push schema changes to the database
pnpm db:generate      # Generate Drizzle migrations
pnpm user:create      # Create a user via CLI
pnpm auth:test        # Test the auth flow
pnpm clients:seed     # Seed OAuth clients
pnpm lint             # ESLint + TypeScript type checking
```
