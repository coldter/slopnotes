Auther proves *who* a request is from via OIDC on top of OAuth2, wired through one `betterAuth()` instance. Sign in, exchange a code for a token, and the token is signed by a key the world can trust.

## Better-auth configuration

All auth behavior is assembled in one file by composing better-auth plugins:

```ts title="src/lib/auth.ts"
betterAuth({
  // ...plugins listed below
});
```

| Plugin | Purpose |
| --- | --- |
| `emailAndPassword` | Email/password sign-in with email verification |
| `username` | Username field on user accounts |
| `admin` | Admin role management (role field on user table) |
| `apiKey` | API key management (create, verify, revoke, rate-limit) |
| `jwt` | JWT issuance with configurable issuer and audience |
| `oidcProvider` | Full OIDC provider surface (authorize, token, userinfo, jwks) |
| `oAuthProxy` | URL differences between dev/staging/production |
| `nextCookies` | Cookie sessions for the Next.js admin UI |

Every auth endpoint is served through one catch-all route at `src/app/api/auth/[...betterAuth]/route.ts`. That route also wraps each request with CORS headers from the configured trusted origins and records per-OIDC-route metrics (`authorize`, `token`, `userinfo`, `jwks`, `sign-in`, `sign-up`, `sign-out`).

## OIDC provider surface

The `oidcProvider` plugin exposes the standard endpoints any conforming client already speaks:

| Endpoint | Method | Purpose |
| --- | --- | --- |
| `/api/auth/oauth2/authorize` | GET | Redirects to sign-in if unauthenticated, then back to the client with a code. |
| `/api/auth/oauth2/token` | POST | Exchanges codes (optional PKCE verifier) for access + ID tokens (JWTs). |
| `/api/auth/oauth2/userinfo` | GET | Authenticated user profile. Requires a valid access token. |
| `/api/auth/jwks` | GET | Public keys for offline JWT signature verification. |
| `/api/auth/oauth2/register` | POST | Dynamic client registration. Protected by the internal signup secret. |

These cooperate in the **authorization-code flow**: the user signs in on Auther, Auther hands the client a short-lived *code* via redirect, and the client swaps it for tokens over a back channel. The code is useless alone, so it can travel through the browser URL safely.

Provider config lives in the same central file:

```ts title="src/lib/auth.ts"
oidcProvider({
  loginPage: "/sign-in",
  allowDynamicClientRegistration: true,
  useJWTPlugin: true,
  metadata: {
    issuer: env.JWT_ISSUER, // e.g., "https://auth.example.com"
  },
  trustedClients: [payloadAdminClient, payloadSPAClient],
}),
```

Three options carry the meaning: `loginPage: "/sign-in"` is where an unauthenticated authorize request lands; `allowDynamicClientRegistration: true` lets clients self-register, guarded by the signup secret; `useJWTPlugin: true` routes ID-token signing through the JWT plugin — RS256 with JWKS-managed keys, not a shared secret.

## Session management

Two session models run at once: cookie sessions for the admin UI, JWTs for external clients.

### Cookie sessions (admin UI)

Built on `auth.api.getSession()`, which reads the session cookie from request headers:

```ts title="src/lib/session.ts"
// Get current session (returns null if not authenticated)
const session = await getSession();

// Require authentication (throws if not logged in)
const session = await requireAuth();

// Require admin role (throws if not admin)
const session = await requireAdmin();
```

### Route protection middleware

`src/proxy.ts` runs as Next.js edge middleware and intercepts `/admin/*` and `/dashboard/*`. No session cookie on a protected route → redirect to sign-in with the original path in `redirectTo`:

```ts title="src/proxy.ts"
const AUTH_ROUTES = ["/admin", "/dashboard"];

// If no session cookie and route is protected, redirect to sign-in
if (!sessionCookie && isProtected) {
  const signInUrl = new URL("/sign-in", request.url);
  signInUrl.searchParams.set("redirectTo", pathname);
  return NextResponse.redirect(signInUrl);
}
```

:::note[Why it doesn't bounce logged-in users away from `/sign-in`]
A stale-but-present cookie would trigger an infinite redirect loop (cookie says logged in, page says go away). Leaving `/sign-in` reachable lets an expired session resolve cleanly.
:::

### JWT / token sessions (external clients)

External apps never get a cookie. They receive RS256 JWTs with rotating JWKS keys, carrying embedded permissions so most requests authorize without calling back to Auther. How those permissions are computed is [ReBAC & the Permission Engine](/auther/server/rebac/).

## JWKS key rotation

A **JWKS** is the public-key directory clients fetch from `/api/auth/jwks`. A client looks up the key once, caches it, and verifies signatures offline — no round-trip per request, no shared secret.

A stolen private key can forge tokens for every client, so Auther **rotates** RS256 keys on a schedule. Rotation logic lives in `src/lib/jwks-rotation.ts`:

| Parameter | Value | Constant |
| --- | --- | --- |
| Rotation interval | 30 days | `JWKS_ROTATION_INTERVAL_MS` |
| Retention window | 60 days | `JWKS_RETENTION_WINDOW_MS` |

<Steps>

1. A cron job calls `POST /api/internal/rotate-jwks`, protected by `CRON_SECRET`.

2. `rotateJwksIfNeeded()` checks the age of the latest key.

3. If older than 30 days (or none exists), a fresh RS256 key pair is generated.

4. Keys older than 60 days are pruned from the database.

5. Private keys are encrypted at rest with AES-256-GCM, using `BETTER_AUTH_SECRET` as the key.

6. The `jwks` table stores both the encrypted private key and the public key.

</Steps>

The 60-day retention window is why rotation doesn't break live clients: a token signed by the previous key stays verifiable through the overlap.

:::tip[Cache JWKS, but below the rotation interval]
Cache the JWKS endpoint, but keep the TTL under 30 days — otherwise a client can keep trusting a key that has aged out.
:::

The JWKS repository (`src/lib/repositories/jwks-repository.ts`) is read-only from app code: `findAll()`, `findAllWithStatus()` (age + "ok"/"breached"), and `findLatest()`. Minting keys is handled internally by better-auth's `createJwk()` during rotation.

## Pre-registered OAuth clients

Most clients register dynamically, but two reference clients ship pre-configured from env vars in `src/lib/auth.ts`. They illustrate the two ends of the client spectrum: **confidential** (server-side, can keep a secret) and **public** (browser, any shipped "secret" is no secret).

Confidential client — server-side app with a secret:

```ts title="src/lib/auth.ts"
const payloadAdminClient = {
  clientId: env.PAYLOAD_CLIENT_ID,
  clientSecret: env.PAYLOAD_CLIENT_SECRET,
  type: "web",
  name: "Payload Admin (Confidential)",
  redirectURLs: [env.PAYLOAD_REDIRECT_URI],
  metadata: {
    tokenEndpointAuthMethod: "client_secret_basic",
    grantTypes: ["authorization_code"],
  },
  skipConsent: true,
};
```

It authenticates with `client_secret_basic` — Base64 `client_id:client_secret` in the `Authorization: Basic ...` header — over the authorization-code flow. `skipConsent: true` skips the approval prompt.

Public client — SPA / browser, no secret:

```ts title="src/lib/auth.ts"
const payloadSPAClient = {
  clientId: env.PAYLOAD_SPA_CLIENT_ID,
  type: "public",
  name: "Payload SPA (PKCE)",
  redirectURLs: env.PAYLOAD_SPA_REDIRECT_URIS,
  metadata: {
    tokenEndpointAuthMethod: "none",
    grantTypes: ["authorization_code"],
    postLogoutRedirectUris: env.PAYLOAD_SPA_LOGOUT_URIS,
  },
  skipConsent: true,
};
```

No secret → it enforces **PKCE**: the browser generates a `code_verifier`/`code_challenge` pair, sends the challenge at authorize, and proves possession of the verifier at token exchange. That binding stops an attacker who intercepts the code from redeeming it.

Additional clients register at runtime via `/api/auth/oauth2/register` or the admin UI at `/admin/clients/register`.

## Signup restrictions

Auther is an IdP for known applications, not a public sign-up service. A `createAuthMiddleware` before-hook in `src/lib/auth.ts` gates registration paths:

```ts title="src/lib/auth.ts"
validateInternalSignupAccess(
  request,
  relativePath,
  restrictedSignupPaths,  // Set(["/sign-up/email", "/oauth2/register"])
  env.PAYLOAD_CLIENT_SECRET
);
```

`validateInternalSignupAccess()` in `src/lib/utils/auth-middleware.ts` requires an `x-internal-signup-secret` header matching `PAYLOAD_CLIENT_SECRET` on `/sign-up/email` and `/oauth2/register`; missing or wrong → 403. Users are created via the admin UI, invite links, or an authorized backend.

:::caution[The signup secret is the client secret]
The internal signup secret *is* the confidential client secret. Any app that can authenticate as a client can also create users — treat and rotate it accordingly.
:::

## Email verification and password reset

Both transactional emails go through Resend (`src/lib/email/send.ts`) using React Email templates in `src/lib/email/templates/`:

- **Verification email** — `sendVerificationEmail()` on sign-up, from `email-verification.tsx`.
- **Password reset email** — `sendPasswordResetEmail()`, from `password-reset.tsx`.

Both render the template to HTML with `render()`, send via the Resend API, and record metrics (duration, success/error, rate-limit). `SKIP_EMAIL_SENDING` short-circuits delivery in tests.

Config: `RESEND_API_KEY`, `EMAIL_FROM` (e.g. `noreply@example.com`), `EMAIL_FROM_NAME` (e.g. `"Auther"`).
