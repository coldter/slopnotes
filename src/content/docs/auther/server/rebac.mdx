**ReBAC** asks *who is related to what* (Carol owns invoice 789). **ABAC** adds a runtime rule (but only if the amount is under $1,000). Auther runs ReBAC for structure and layers ABAC on top — this chapter covers the ReBAC half; the [ABAC layer](/auther/server/abac-groups/) covers context-aware policies.

## Relationship tuples

The core primitive is the **access tuple** — one row in `access_tuples` (`src/db/rebac-schema.ts`):

```text
(entityType, entityId, relation, subjectType, subjectId)
```

Read it as "the subject has this relation to the entity":

| entityType | entityId | relation | subjectType | subjectId | Meaning |
| --- | --- | --- | --- | --- | --- |
| `platform` | `*` | `admin` | `user` | `alice_id` | Alice is a platform admin |
| `users` | `*` | `viewer` | `user` | `bob_id` | Bob can view all users |
| `oauth_client` | `client_123` | `use` | `group` | `eng_group` | The engineering group can use `client_123` |
| `client_abc:invoice` | `*` | `editor` | `apikey` | `key_456` | API key 456 can edit all invoices in `client_abc` |
| `client_abc:invoice` | `inv_789` | `owner` | `user` | `carol_id` | Carol owns invoice `inv_789` in `client_abc` |

What makes the shape expressive:

- **Wildcard `entityId` `*`** — "all entities of this type."
- **Subject relations** — `group:admins#member` means "all members of the admins group," so a group grant flows to members without a tuple per person.
- **Optional Lua condition** on a single tuple — tuple-level ABAC for one grant.
- **`entityTypeId`** FK into `authorization_models.id` — a stable reference that survives renaming an entity type.

All reads/writes go through `TupleRepository` (`src/lib/repositories/tuple-repository.ts`), 18 methods. The resolver leans on the lookup side — `findExact`, `findBySubject`, `findBySubjects`, `findByEntity`, `findByEntityType` — plus the write side (`createIfNotExists`) and bookkeeping (`countByRelation`, `updateEntityTypeString`).

## Authorization models

Tuples say *who relates to what*. An **authorization model** says which relations and permissions exist and how they connect — stored as JSON in `authorization_models`, validated by the Zod schema in `src/schemas/rebac.ts`:

```json
{
  "relations": {
    "owner": { "union": ["admin"] },
    "admin": { "union": ["editor"] },
    "editor": { "union": ["viewer"] },
    "viewer": []
  },
  "permissions": {
    "read":   { "relation": "viewer" },
    "write":  { "relation": "editor" },
    "delete": { "relation": "owner" },
    "refund": {
      "relation": "admin",
      "policyEngine": "lua",
      "policy": "if context.resource.amount < 1000 then return true else return false end"
    }
  }
}
```

- **Relations form a hierarchy via `union`.** `"admin": { "union": ["editor"] }` means admin implies editor; since editor implies viewer, admin transitively gets viewer.
- **Permissions map an action to a required relation.** `"read": { "relation": "viewer" }` — anyone with `viewer` or any relation implying it can `read`.
- **ABAC attaches to a permission** via `policyEngine: "lua"` + a `policy` script run against runtime context. The `refund` above only allows sub-$1,000.
- **`subjectParams: { hierarchy: true }`** turns on recursive subject expansion for nested groups.

`AuthorizationModelService` (`src/lib/auth/authorization-model-service.ts`) enforces **dependency safety**: before removing a relation it checks no active tuples or registration-context grants still reference it, and rejects with a descriptive error instead of leaving dangling grants.

## The permission resolver

`PermissionService.checkPermission()` in `src/lib/auth/permission-service.ts` answers *can subject S do action A on entity E?* — a fixed pipeline that short-circuits on admin, expands subjects and relations breadth-first, matches tuples, then consults ABAC before allowing:

  Start(["checkPermission(S, A, E)"]) --> Admin{"subjectType is user<br/>and user.role === admin?"}
  Admin -->|"yes"| Allow1(["ALLOW (admin bypass)"])

  Model -->|"no"| Deny1(["DENY"])
  Model -->|"yes"| Perm{"permission A defined<br/>in the model?"}
  Perm -->|"no"| Deny2(["DENY"])
  Perm -->|"yes"| ExpandS["Expand subjects (BFS)<br/>user → groups → nested groups"]
  ExpandS --> ExpandR["Expand relations (BFS)<br/>required relation + relations that imply it"]
  ExpandR --> Match{"tuple matches?<br/>direct, or wildcard entityId *"}
  Match -->|"no match"| Deny3(["DENY"])
  Match -->|"match"| Policy{"ABAC policy?<br/>tuple condition > permission policy"}
  Policy -->|"no policy"| Allow2(["ALLOW"])
  Policy -->|"policy passes"| Allow3(["ALLOW"])
  Policy -->|"policy fails"| Deny4(["DENY"])
`} />

The pipeline, step by step:

| Step | Action |
| --- | --- |
| 0 — Admin bypass | `user` with `role === "admin"` → allow immediately. |
| 1 — Load model | No model for the entity type → deny. |
| 2 — Required relation | Permission not in the model → deny. |
| 3 — Expand subjects (BFS) | user → user-groups (legacy table) → nested groups via hierarchy tuples → list of `(subjectType, subjectId)` pairs. |
| 4 — Expand relations (BFS) | From the required relation, every relation that implies it (if `viewer` needed, also `editor`, `admin`, `owner`). |
| 5 — Check tuples | Each expanded subject × each expanded relation: direct match or wildcard `(entityType, "*", ...)`. |
| 6 — ABAC policy | Tuple-level condition first, then permission-level policy, then no policy (allow). Runs via `LuaPolicyEngine` with the runtime context. |
| 7 — No tuple → deny | The default answer is always no. |

:::note[Everything is measured]
Each check emits `authz.check.duration_ms`, `authz.decision.count` (tagged result + source), `authz.rebac.traversal_depth`, and `authz.rebac.subjects_expanded`. Watch the BFS expansions — deep group nesting is what grows traversal cost.
:::

## Two permission layers

### Layer A — Platform permissions

Who can manage Auther itself. Defined by **9 system models** in `src/lib/auth/system-models.ts`:

| Entity Type | Relations | Key Permissions |
| --- | --- | --- |
| `platform` | `super_admin > admin > member` | `manage_platform` |
| `users` | `admin > viewer` | view, create, update, delete, ban, impersonate |
| `groups` | `admin > editor > viewer` | view, create, update, delete, manage_members |
| `clients` | `admin > viewer` | view, create, update, delete, manage_access |
| `webhooks` | `editor > viewer` | view, create, update, delete, test |
| `pipelines` | `editor > viewer` | view, create, update, delete, execute |
| `api_keys` | `admin` | view_all, revoke |
| `keys` | `admin` | view, rotate |
| `sessions` | `admin` | view_all, revoke_all |

These are hardcoded fallbacks: if no DB record exists for an entity type, the system model is used — the platform works on a fresh install before any models are created.

### Layer B — Client-scoped permissions

What users can do *within* a specific client app. Custom models with entity types prefixed by client ID so they can't collide across clients:

```text
client_abc:invoice
client_abc:report
client_abc:payment
```

These are embedded in the JWTs Auther issues, so the consuming app enforces fine-grained access on its own resources without calling back per request.
