Four subsystems cover extending and operating Auther: **pipelines** run your Lua at auth events without a redeploy, **webhooks** notify other systems, **metrics** show what's happening, and the **admin UI** ties them together.

## The pipeline system

Attach custom Lua scripts to 16 auth lifecycle hooks; they run sandboxed when the event fires — geo-block a signup, enrich a token, fan out a side effect. Scripts form a **DAG** (directed acyclic graph): nodes are scripts, edges are "runs after," no cycles.

### Lifecycle hooks

Defined in `src/lib/pipelines/definitions.ts`, in three families. Each hook's *type* sets what a script can do: **blocking** aborts the operation, **async** runs side effects after, **enrichment** contributes data back into the flow.

Auth lifecycle:

| Hook | Type | Purpose |
| --- | --- | --- |
| `before_signup` | Blocking | Abort registration (geo-block, email-domain filter) |
| `after_signup` | Async | Post-registration side effects |
| `before_signin` | Blocking | Abort sign-in (ban check, suspicious IP) |
| `after_signin` | Async | Post-login side effects |
| `before_signout` | Blocking | Abort sign-out (rarely used) |
| `token_build` | Enrichment | Inject custom claims into JWTs |

API-key lifecycle (mirrors [API Keys](/auther/server/api-keys/)):

| Hook | Type | Purpose |
| --- | --- | --- |
| `apikey_before_create` | Blocking | Abort key creation |
| `apikey_after_create` | Async | Post-creation side effects |
| `apikey_before_exchange` | Blocking | Abort key→JWT exchange |
| `apikey_after_exchange` | Async | Post-exchange side effects |
| `apikey_before_revoke` | Blocking | Abort key revocation |

OAuth client lifecycle:

| Hook | Type | Purpose |
| --- | --- | --- |
| `client_before_register` | Blocking | Abort client registration |
| `client_after_register` | Async | Post-registration side effects |
| `client_before_authorize` | Blocking | Abort authorization |
| `client_after_authorize` | Async | Post-authorization side effects |
| `client_access_change` | Async | Access level changes |

### Execution model

`PipelineEngine` (`src/lib/auth/pipeline-engine.ts`) walks the DAG one layer at a time — scripts in the same layer are independent and run in parallel, later layers depend on earlier outputs:

<Mermaid title="DAG layer execution" height={420} code={`
flowchart TB
  Start["Hook fires<br/>(e.g. before_signup)"] --> L1
  subgraph L1["Layer 1 — parallel via Promise.all"]
    A["script A"]
    B["script B"]
  end
  L1 -->|"outputs become next layer's prev"| L2
  subgraph L2["Layer 2 — parallel"]
    C["script C"]
    D["script D"]
  end
  L2 --> L3["Layer 3 …"]
  L3 --> Done["Aggregate result"]
  Done --> Decision{"any script<br/>returned allowed: false?"}
  Decision -->|"yes (blocking hook)"| Block["Abort the auth flow"]
  Decision -->|"no / error / timeout"| Pass["Continue (fail-open)"]
`} />

- **DAG execution.** Layers sequential; scripts within a layer parallel via `Promise.all`.
- **Context propagation.** Each layer's output becomes the next layer's `prev`; an `outputs` map reaches back to a named node's result.
- **Safety limits.** `MAX_CHAIN_DEPTH = 10` layers, `MAX_PARALLEL_NODES = 5` scripts per layer.
- **Fail-open.** Errors and timeouts do *not* block the flow — only an explicit `allowed: false` from a blocking hook stops it.

:::tip[Why fail-open]
A buggy script must never lock users out. Only an explicit `allowed: false` blocks; crashes and timeouts carry on — a misbehaving script degrades the *extension*, not the core auth flow.
:::

### The script sandbox

Scripts are user-authored and run on the hot path, so each runs in `wasmoon` (Lua-in-WASM) with hard protections:

| Protection | Detail |
| --- | --- |
| Disabled globals | `os`, `io`, `package`, `require`, `loadfile`, `dofile` |
| Instruction limit | 50,000 operations via `debug.sethook` |
| Execution timeout | 10 seconds |
| SSRF protection | `helpers.fetch()` blocks private IPs, enforces HTTPS, 3s timeout, 1MB response cap |
| Secret encryption | Pipeline secrets encrypted at rest with AES-256-GCM |

Instead of raw Lua libraries, scripts get a curated `helpers` table:

```lua
helpers.log(message)              -- Log to trace
helpers.now()                     -- Current Unix timestamp
helpers.hash(value)               -- SHA-256 hash
helpers.env(key)                  -- Read env var (restricted)
helpers.secret(key)               -- Read encrypted secret
helpers.fetch(url, options)       -- HTTPS-only HTTP client
helpers.matches(value, pattern)   -- Pattern matching
helpers.trace(name, fn)           -- Create nested span
helpers.metrics.count(name, val)  -- Emit counter metric
helpers.metrics.gauge(name, val)  -- Emit gauge metric
```

An **enrichment** hook on `token_build` tagging every token with a plan tier:

```lua
-- token_build (Enrichment): tag every token with a plan tier
local tier = helpers.fetch("https://billing.internal.example/tier").body
helpers.metrics.count("token.enriched", 1)
return { claims = { tier = tier } }
```

A **blocking** hook on `before_signin` — returning `allowed: false` is the *only* thing that stops the flow:

```lua
-- before_signin (Blocking): block sign-in when an external check says so
local banned = helpers.fetch("https://risk.internal.example/check").body
if helpers.matches(banned, "true") then
  helpers.metrics.count("auth.signin.blocked", 1)
  return { allowed = false, reason = "blocked by risk check" }
end
return { allowed = true }
```

### Pipeline observability

Every run produces OpenTelemetry-compatible traces (`pipeline_traces`) and spans (`pipeline_spans`); `helpers.trace(name, fn)` carves nested spans. The admin UI renders a waterfall trace viewer showing which layer/script spent the time.

## The webhook system

Webhooks are the outbound counterpart to pipelines: external apps receive real-time notifications about auth events (e.g. your billing service subscribes to `user.created` and provisions an account on signup — no polling, no shared DB).

### Architecture

Four tables split configuration from intent from record from delivery attempt:

| Table | Role |
| --- | --- |
| `webhook_endpoint` | Destination URL + config: retry policy, format, encrypted signing secret. |
| `webhook_subscription` | Which event types each endpoint wants. |
| `webhook_event` | A record that something happened, with a JSON payload snapshot. |
| `webhook_delivery` | One delivery attempt, with status tracking. |

### Event types

```text
user.created, user.updated, user.deleted, user.verified
session.created, session.deleted
account.linked, account.unlinked
verification.sent, verification.completed
client.created, client.updated, client.deleted
access.granted, access.revoked
```

### Delivery flow

Delivery is async — an auth event records what happened and hands the HTTP delivery to a queue, so a slow recipient never slows the auth flow:

<Steps>

1. An auth event occurs (e.g. a user signs up).
2. `emitWebhookEvent()` in `src/lib/webhooks/delivery-service.ts` creates an event record.
3. For each subscribed active endpoint, a `pending` delivery record is created.
4. A `WebhookDeliveryJob` is enqueued to Upstash QStash.
5. The QStash worker at `/api/internal/queues/webhook-delivery` verifies the QStash signature and calls `deliverWebhook()`.
6. The delivery service loads the event + endpoint, decrypts the signing secret, builds an HMAC-SHA256 signed payload, and makes the HTTP request.
7. The delivery record is updated with response status, body, and duration.

</Steps>

Retries follow the endpoint's policy: `none` = zero retries; `standard` = three retries with QStash exponential backoff.

:::caution[Make your receiver idempotent]
Retried deliveries may arrive more than once. Dedupe on the `x-webhook-id` header so a duplicate is a no-op — no double-charged invoice, no second welcome email.
:::

### Webhook signatures

Payloads are HMAC-SHA256 signed (`src/lib/webhooks/signature.ts`); recipients verify with a constant-time compare. Each request carries:

```text
x-webhook-id: <event_id>
x-webhook-signature: <hmac_sha256_hex>
x-webhook-timestamp: <unix_ms>
x-webhook-origin: better-auth
```

## Metrics and observability

`src/lib/services/metrics-service.ts` records counters, gauges, and histograms to the `metrics` table in the project's own SQLite DB — telemetry lives alongside the data it describes:

| Metric type | Method | Example |
| --- | --- | --- |
| Counter | `count(name, value, tags)` | `auth.login.attempt` with `{ method: "email", status: "success" }` |
| Gauge | `gauge(name, value, tags)` | `jwks.active_key.age_ms` |
| Histogram | `histogram(name, value, tags)` | `authz.check.duration_ms` with `{ result: "allowed" }` |
| Measured | `measure(name, fn, tags)` | Wraps an async fn and records duration |

:::caution[Metrics must not leak PII]
Tags are an easy place to store sensitive data. Auther sanitizes tags — blocking `user_id`, `email`, `ip`, `user_agent`, `authorization` — caps at 10 tag keys, and truncates values to 128 chars.
:::

Key metrics across the IdP:

- `auth.login.attempt`, `auth.register.success`, `auth.session.created.count`
- `oidc.{route}.request.count`, `oidc.{route}.latency_ms`
- `authz.check.duration_ms`, `authz.decision.count`, `authz.rebac.traversal_depth`
- `jwks.rotate.triggered.count`, `apikey.resolve.duration_ms`
- `webhook.delivery.duration_ms`, `lua.pool.active`, `email.send.duration_ms`

The admin dashboard at `/admin` visualizes these with Recharts.

## The admin UI

Each section maps to a subsystem and is gated by the matching platform guard — the admin UI is not a privileged bypass:

| Section | Path | Purpose |
| --- | --- | --- |
| Dashboard | `/admin` | Metrics visualization, system overview |
| Users | `/admin/users` | User management (create, edit, ban, impersonate) |
| Groups | `/admin/groups` | User-group management, member and permission tabs |
| Clients | `/admin/clients` | OAuth client management |
| Keys | `/admin/keys` | JWKS signing-key management and rotation |
| Sessions | `/admin/sessions` | Active session monitoring and revocation |
| Webhooks | `/admin/webhooks` | Endpoint config and delivery logs |
| Pipelines | `/admin/pipelines` | DAG editor, secret management, trace viewer |
| Access | `/admin/access` | Platform-level access-control management |
| Requests | `/admin/requests` | Permission-escalation review |
| Settings | `/admin/settings` | Platform configuration |
| Profile | `/admin/profile` | Current user's profile and sessions |

`/admin/users` requires `users:view`, for example — the same ABAC engine from [ABAC, Guards, Groups & Invites](/auther/server/abac-groups/) gates the console itself.
