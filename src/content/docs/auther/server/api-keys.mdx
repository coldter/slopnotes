A cron job has no human to log in. It carries an API key — and Auther treats that key as a **first-class subject**: its own rows in `access_tuples` with `subjectType: "apikey"`, resolving through the same machinery as a user. One authorization story for machines and people.

## The key lifecycle

<Steps>

1. **Creation.** Minted via better-auth's API key plugin; stored in the `apikey` table with the value hashed, an optional expiration, and rate-limit config.

2. **Permission assignment.** The key gets its own tuples in `access_tuples` with `subjectType: "apikey"` — any relation on any entity, and it can even inherit through [group membership](/auther/server/rebac/).

3. **JWT exchange.** `POST /api/auth/api-key/exchange` trades the key once for a 15-minute JWT carrying the key's resolved permissions inline. The hot path never touches the `apikey` table.

4. **Runtime permission check.** For ABAC-gated permissions, `POST /api/auth/check-permission` evaluates the policy and returns allow/deny.

</Steps>

## Exchanging a key for a JWT

```http title="POST /api/auth/api-key/exchange"
POST /api/auth/api-key/exchange
Content-Type: application/json

{ "apiKey": "ak_live_xxxxxxxxxxxx" }
```

Response — a standard bearer envelope. `expiresIn` is seconds (900 = 15 min); `expiresAt` is the absolute expiry:

```json
{
  "token": "eyJhbGciOiJSUzI1NiIs...",
  "tokenType": "Bearer",
  "expiresIn": 900,
  "expiresAt": "2025-01-15T11:00:00.000Z"
}
```

The JWT embeds the resolved authorization state, shaped roughly `{ sub, iss, aud, scope, permissions, abac_required, apiKeyId }`:

```json
{
  "sub": "user_id",
  "iss": "https://auth.example.com",
  "aud": "payload-admin",
  "scope": "api_key_exchange",
  "permissions": { "client_abc:invoice": ["read", "write", "refund"] },
  "abac_required": { "client_abc:invoice": ["refund"] },
  "apiKeyId": "key_id"
}
```

Two claims do the work: `permissions` maps each entity to the relations the key holds (a verifier answers most questions from the token alone), and `abac_required` flags the subset whose final decision still depends on resource attributes — the key may `refund` in principle, but whether a *specific* invoice is refundable is an ABAC question.

:::tip[Why the token is short-lived]
15 minutes keeps verification off the database while bounding the blast radius of a leaked token. Permissions are baked in at exchange time, so a revoked or re-scoped key takes at most one token lifetime to propagate.
:::

## The runtime permission check

A permission in `abac_required` is necessary but not sufficient — the resource's attributes decide. Authenticate with the key via `x-api-key` and describe the entity, permission, and resource attributes:

```http title="POST /api/auth/check-permission"
POST /api/auth/check-permission
x-api-key: ak_live_xxxxxxxxxxxx

{
  "entityType": "client_abc:invoice",
  "entityId": "inv_123",
  "permission": "refund",
  "resource": {
    "attributes": { "amount": 500, "status": "paid" }
  }
}
```

```json
{
  "allowed": true,
  "entityType": "client_abc:invoice",
  "entityId": "inv_123",
  "permission": "refund",
  "subjectType": "apikey",
  "subjectId": "key_id"
}
```

`subjectType: "apikey"` confirms the key was treated as the principal in its own right.

## Unified resolution

`ApiKeyPermissionResolver` (`src/lib/services/api-key-permission-resolver.ts`) resolves a key's permissions with the same tuple, model, and transitivity logic the [permission engine](/auther/server/rebac/) applies to users — including group membership, since keys can be group members. One code path, so a key's permissions are as expressive and auditable as any human's.
