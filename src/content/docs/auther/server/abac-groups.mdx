ReBAC answers "is Alice an editor of this invoice?" from stored relationships. ABAC adds the request-time rule — the amount, the time, the owner. Everything here creates, scopes, or evaluates an access tuple on top of [ReBAC](/auther/server/rebac/).

## ABAC: Lua policies at request time

A relationship match must exist first; ABAC then runs a short **Lua policy** against live request context for a second opinion. Policies attach at two levels, and tuple-level wins:

**Permission-level** (in the model, applies to every check):

```json
{
  "refund": {
    "relation": "admin",
    "policyEngine": "lua",
    "policy": "if context.resource.amount < 1000 then return true else return false end"
  }
}
```

**Tuple-level** (on one specific tuple, overrides permission-level):

```sql
-- Bob can edit invoices, but only while they are in draft status
INSERT INTO access_tuples (entityType, entityId, relation, subjectType, subjectId, condition)
VALUES ('client_abc:invoice', '*', 'editor', 'user', 'bob_id',
        'return context.resource.status == "draft"');
```

### The Lua policy context

Every policy runs against a `context` object built in `src/lib/auth/abac-context.ts`:

```lua
-- context.resource: the resource being accessed
context.resource.id         -- "invoice_123"
context.resource.type       -- "invoice"
context.resource.amount     -- 500
context.resource.status     -- "draft"
context.resource.owner_id   -- "user_456"
context.resource.department -- "sales"

-- context.user: the actor
context.user.id             -- "user_789"
context.user.name           -- "Alice"
context.user.email          -- "alice@example.com"
context.user.role           -- "admin"
context.user.department     -- "finance"

-- context.action: the permission being checked
context.action              -- "refund"

-- context.timestamp: current time (ISO string)
context.timestamp           -- "2025-01-15T10:30:00.000Z"
```

Representative policies:

```lua
-- Only allow refunds under $1000
if context.resource.amount < 1000 then return true else return false end

-- Only allow editing your own resources
return context.resource.owner_id == context.user.id

-- Time-based: only during business hours (UTC)
local hour = tonumber(os.date("!%H"))
return hour >= 9 and hour < 17

-- Department-based: finance can refund anything, others capped at $500
if context.user.department == "finance" then return true end
return context.resource.amount < 500
```

Trace the refund policy: Alice (an `admin`) refunds a $500 invoice. ReBAC confirms `admin`; ABAC builds context and runs the policy — `500 < 1000` → `true` → ALLOW. Swap in a $5,000 invoice and the same script returns `false` → denied, with the decision and context snapshot in the audit log.

### Keeping user-authored Lua safe

The policy engine (`src/lib/auth/policy-engine.ts`) and pooled runtime (`lua-engine-pool.ts`) enforce hard limits so a slow or oversized script can't stall a check:

| Safety measure | Value |
| --- | --- |
| Execution timeout | 1 second |
| Max script size | 10 KB |
| Engine pool size | 20 engines |
| Engine TTL | 5 minutes |
| Max concurrent | 20 |
| Burst support | Yes (extra engines not reused) |

:::note[Auditing every decision]
Every ABAC evaluation lands in `abac_audit_logs` (entity, permission, subject, policy source, result, context snapshot, execution time). Policy changes are tracked in `policy_versions` — so you can answer both "what did we decide" and "what rule was in force."
:::

## The platform guard

`src/lib/auth/platform-guard.ts` wraps the permission engine for Auther's admin surface. Throwing guards for server actions:

```ts title="src/app/admin/actions/create-user.ts"
import { guards } from "@/lib/auth/platform-guard";

export async function createUser(data: CreateUserInput) {
  await guards.users.create(); // throws "Permission denied" if unauthorized
  // ... create user logic
}
```

Non-throwing checks return a boolean for conditional UI:

```ts title="src/app/admin/users/page.tsx"
import { canUser } from "@/lib/auth/platform-guard";

const showCreateButton = await canUser.users.create(); // boolean
```

Guard namespaces: `platform`, `users`, `webhooks`, `pipelines`, `clients`, `keys`, `groups`, `sessions`, `apiKeys`.

## Groups and hierarchies

Granting one user at a time doesn't scale. Groups (`user_group` + `group_membership`) are **first-class subjects in ReBAC** — a tuple names a group in the same slot as a user, so you grant the group once and add members freely:

```text
-- The Engineering group can use client_123
(oauth_client, client_123, use, group, eng_group_id)

-- Alice is a member of Engineering
group_membership: (alice_id, eng_group_id)
```

`expandSubjects()` in `PermissionService` walks outward breadth-first:

<Steps>

1. Start with Alice (the `user` subject).

2. Find Alice's groups through `group_membership` (legacy table).

3. Find hierarchical memberships through `hierarchy: true` tuples.

4. Repeat for each newly discovered group — this is what makes nested groups work.

</Steps>

Payoff: if Engineering is a subgroup of Product, and Product has access to a client, every Engineering member inherits it with no extra tuple.

## Registration contexts and invites

Registration contexts (`registration_contexts` table) auto-grant tuples to a sign-up flow so new users don't arrive with zero permissions:

```json
{
  "slug": "blog-commenter",
  "name": "Blog Commenter",
  "clientId": "blog_client_id",
  "grants": [
    { "entityTypeId": "model_123", "relation": "commenter" }
  ],
  "allowedOrigins": ["https://blog.example.com"],
  "allowedDomains": ["example.com"],
  "enabled": true
}
```

Wired by `applyRegistrationContextGrants()` in `src/lib/pipelines/registration-grants.ts`, backed by `RegistrationContextService` (`src/lib/services/registration-context-service.ts`). Two kinds: **client contexts** (`clientId` set — apply when a user authorizes through that client) and **platform contexts** (`clientId` null — apply to every new user).

### HMAC-signed invites

Platform invites (`platform_invites` table) issue one-time, HMAC-signed tokens, redeemed at:

```http
POST /api/auth/verify-invite
Content-Type: application/json

{ "token": "signed_token_here", "email": "alice@example.com" }
```

<Steps>

1. Validate the HMAC-SHA256 signature.

2. Confirm the invite is unconsumed and unexpired.

3. Optionally check the supplied email matches the invite's locked email.

4. Queue the associated registration-context grants for after the user is created.

5. Also queue every enabled global platform context.

</Steps>

Once the user creates their account, the queued grants apply automatically — an invited user lands fully provisioned.

## Permission request escalation

Users can *request* access they don't have. `PermissionRequestService` (`src/lib/services/permission-request-service.ts`) runs the gates:

- Duplicate pending request? → skip.
- `selfRequestable` in `permission_rules`? No → reject.
- Auto-reject Lua condition matches? → reject.
- Auto-approve Lua condition matches? → approve + create the tuple.
- Otherwise → `require_approval`, awaiting an admin.

An admin then approves (creates the granting tuple) or rejects with a note. Per-relation behavior lives in `permission_rules` — this rule makes `viewer` self-requestable and auto-approves `@example.com` emails:

```json
{
  "clientId": null,
  "relation": "viewer",
  "selfRequestable": true,
  "autoApproveCondition": "return context.user.email:match('@example.com$')",
  "defaultAction": "require_approval",
  "approverRelation": "admin"
}
```

:::note[Lua here too]
Auto-approve/reject conditions are the same Lua policies ABAC uses, evaluated against the same `context` — "anyone with `@example.com` gets `viewer` automatically" is a one-line rule.
:::

## Policy templates

`PolicyTemplateService` (`src/lib/services/policy-template-service.ts`) ships seven built-in templates in `policy_templates`:

| Template | Permissions granted |
| --- | --- |
| Super Administrator | `platform:super_admin` plus all admin relations |
| Platform Administrator | `platform:admin` plus all admin/editor relations |
| User Manager | `users:admin` only |
| Webhook Operator | `webhooks:editor` only |
| Pipeline Developer | `pipelines:editor` only |
| Read-Only Access | all viewer relations |
| API Key Self-Service | `api_keys` viewer plus create permissions |

`applyTemplateToUser(templateId, userId)` creates all the corresponding tuples in one step. Admins can define custom templates when the built-ins don't fit.
