Your app no longer owns the user record, but other tables still point at a `users` table by FK. The shadow-user pattern keeps a **local mirror** of Auther's user, populated and kept current automatically — every existing FK and `INNER JOIN users` keeps working while identity lives in Auther.

- A **shadow user** is a local cache row of the IdP's user, keyed by their ID — a read-mostly copy you join against.
- **JIT provisioning** creates that row lazily on the first valid token you see, instead of pre-syncing everyone.

This page is the mechanism, framework-agnostic. [Hono Walkthrough — Schema](/auther/integration/hono-schema/) applies it to a concrete Drizzle/Hono codebase.

## The four moving parts

1. **Auth middleware** — verifies JWTs on every request, attaches the user principal.
2. **JIT provisioner** — inserts a shadow row from the claims on first sight.
3. **Webhook receiver** — applies Auther's lifecycle events, keeps the row current, cascades deletes.
4. **Reconciliation job** (optional) — nightly safety net for missed webhooks.

Identity flows one direction: Auther is the source of truth; webhooks and JIT push changes *down* into the shadow copy; everything downstream hangs off the shadow row's PK by FK. Nothing writes identity back *up* to Auther.

## ID strategy: use Auther's `sub` verbatim

:::tip[No mapping table]
Use the JWT's `sub` claim *verbatim* as the shadow row's primary key. No local CUID, no `external_id` column, no lookup table. The most boring decision here — and the one that quietly removes a whole class of bugs.
:::

- **Joins stay trivial.** `notifications.user_id` points straight at the shadow row and matches `jwt.sub` in one step.
- **No dual-write problem.** Using `sub` directly makes ID disagreement impossible to express.
- **Bulk operations stay simple.** `DELETE FROM users WHERE id = ?` keyed on `sub` is the same operation as handling a `user.deleted` webhook.

## JIT provisioning

The first valid JWT for a user not yet in the shadow table → insert them, so a brand-new user is serviceable on their very first request:

```ts title="apps/server/src/modules/auth/shadow.ts"
import { eq } from "drizzle-orm";
import { db } from "@/db";
import { users } from "@repo/db/schema";

export interface AutherClaims {
  sub: string;
  iss: string;
  aud: string | string[];
  exp: number;
  iat: number;
  email?: string;
  email_verified?: boolean;
  name?: string;
  picture?: string;
  permissions?: Record<string, string[]>;
  abac_required?: Record<string, string[]>;
  sid?: string;
}

export async function ensureShadowUser(claims: AutherClaims) {
  const existing = await db.query.users.findFirst({
    where: eq(users.id, claims.sub),
  });
  if (existing) return existing;

  const [inserted] = await db
    .insert(users)
    .values({
      id: claims.sub,                                     // ← Auther's ID
      email: claims.email ?? `${claims.sub}@unknown.local`,
      name: claims.name ?? claims.email ?? claims.sub,
      emailVerified: claims.email_verified ?? false,
      image: claims.picture ?? null,
    })
    .onConflictDoNothing()
    .returning();

  return inserted ?? (await db.query.users.findFirst({
    where: eq(users.id, claims.sub),
  }))!;
}
```

Three details carry the design:

- **`onConflictDoNothing()`** handles the race where two concurrent first-requests both insert — one wins, the other re-selects.
- **Fallback values** keep a request serviceable even if a claim is missing (`${claims.sub}@unknown.local`); the next webhook corrects the row.
- **Insert-only** keeps the hot path fast — JIT never updates an existing row; updates belong to webhooks.

## The webhook receiver: three invariants, in order

Auther delivers `user.created`, `user.updated`, `user.deleted` to a receiver endpoint. It's internet-exposed, so validate every payload in a strict order:

<Steps>

1. **Signature** — verify the HMAC-SHA256 signature with a constant-time compare. Never parse JSON out of an unverified payload.
2. **Timestamp** — reject anything more than five minutes old. Blocks replay of a captured payload.
3. **Idempotency** — `SETNX` the `x-webhook-id` in Redis. QStash retries on any 5xx, so deduping prevents a retried event from double-applying.

</Steps>

:::caution[Order matters]
Each check assumes the previous passed. Parsing before the signature check trusts attacker-controlled bytes; skipping the timestamp reopens replay; skipping idempotency double-applies retries. The concrete receiver is in the [Hono walkthrough](/auther/integration/hono-auth-core/).
:::

## Reconciliation

Webhooks drop occasionally — deploys, transient DB errors, a wiped idempotency cache. A nightly reconciliation job (or a manual "resync" button) pulls current state from Auther and fixes silent drift. Cheap insurance, not something the request path depends on.

## Permission sync: read-at-request vs. webhook-sync

- **Read from the JWT at request time** (recommended). The token carries a `permissions` claim; middleware attaches it, routes read it. No local permissions table needed.
- **Webhook-sync into a local table** like `auth_relations` — only when you need admin-style queries ("list every user with `admin` on org X") that a per-request JWT can't answer. Add it *in addition to* the JWT, not instead of it.

Most apps start with read-at-request and add the local table only when the first admin feature needs it.
