Decide this once, early, before writing integration code. Every integration is one of four shapes, from answering two independent questions:

- **Where does the user row live?** — Shadow-User (local `users` table) vs. Federated-IDs (no local table).
- **Where do permissions live?** — Identity-Only (your app decides) vs. Full-Delegation (Auther decides).

Any combination is valid. Answer them separately and the rest is mechanical.

## A. Shadow-User — a local table that mirrors Auther

*Choose when `users.id` is referenced by foreign keys from several tables, or joins on the user row are common.*

A local `users` table still exists, but its primary key is literally Auther's user ID (the JWT `sub`), populated two ways:

1. **Just-In-Time (JIT)** — on the first valid JWT with an unseen `sub`, insert a shadow row from the claims.
2. **Webhooks** — Auther's `user.created`/`user.updated`/`user.deleted` keep the row current and cascade deletes.

All existing FKs keep working, `INNER JOIN users` still works, cascade deletes still work. You just stop *writing* the identity columns yourself.

The Hono template hits exactly this case: `users.id` is referenced by `sessions`, `accounts`, `two_factors`, `notifications`, `push_tokens`, `notification_preferences`, `members`, and `audit_logs`.

## B. Federated-IDs — no local users table

*Choose when your service is stateless and never joins on a user — it just carries an opaque ID through.*

Drop the `users` table. Downstream tables keep a `user_id` column as plain text with no FK. When you need profile data, fetch it from Auther's `/userinfo` and cache.

You gain a single source of truth and no sync logic; you lose FK integrity, `INNER JOIN users`, and every display query needs an external lookup. Right for stateless microservices and event processors; wrong for the Hono template.

## C. Identity-Only — Auther for authN, your own authZ

*Choose when you already have a working authorization system — Auther tells you who the user is, you decide what they can do.*

Auther issues tokens you trust for *authentication* (extract `sub`, `email`), but every permission decision runs through your app's own authorization. Almost always paired with Shadow-User. The Hono template's `packages/authorization` (`createAuthorize`, `registry.can()`, principals, resource loaders) kept as-is is precisely Identity-Only.

## D. Full-Delegation — Auther runs authN and authZ

*Choose when centralized authorization is the explicit goal — typically a multi-app SaaS sharing one permission model.*

The JWT carries a `permissions` claim with pre-resolved permissions per entity type; your app reads those claims. ABAC-gated permissions (runtime context) go through `/api/auth/check-permission`. Works for the Hono template too if you want to retire `packages/authorization` — but that's deleting working code, not a default.

## The two-axis decision matrix

| Situation | Users table | Authorization |
| --- | --- | --- |
| **Hono template (this guide's main example)** | **Shadow** | **Identity-Only** (keep the package) |
| Monolith with deep FK user dependencies | Shadow | Identity-Only |
| Stateless API microservice | Federated | Full-Delegation |
| Multi-tenant SaaS with per-tenant models | Shadow | Full-Delegation |
| Microservice mesh, each service owns its domain | Federated | Full-Delegation + local hot cache |
| Existing app with complex custom authz | Shadow | Identity-Only |
| Greenfield app, minimum code | Shadow | Full-Delegation |

:::tip[The default: Shadow-User + Identity-Only]
When in doubt, pick **Shadow + Identity-Only** — the least-disruptive choice: keep your `users` table (every FK and join keeps working) and keep your authorization code (delete nothing). You give up exactly one thing — ownership of identity. The other shapes ask you to throw away something that works.
:::
