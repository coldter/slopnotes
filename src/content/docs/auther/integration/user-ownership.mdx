You have a `users` table. Foreign keys point at it, queries `JOIN` against it, your auth middleware turns its rows into principals. Adopting Auther means a third party now owns identity — so who owns the row?

You stop owning *authentication*: Auther runs sign-up, sign-in, password hashes, 2FA, session tokens, key rotation. Your app gets a signed JWT. But your database isn't a blank slate — the fix is deciding, for every column on the user row, a single source of truth.

## What you already have

In the `hono-node-template-2026` monorepo, the starting schema:

```sql title="packages/db/src/schema/auth.ts"
users              (id, email, name, emailVerified, image, status, roleSlugs, ...)
sessions           (user_id → users.id  ON DELETE CASCADE, platform, activeOrganizationId, ...)
accounts           (user_id → users.id  ON DELETE CASCADE, password, providerId, ...)
verifications      (identifier, value, expiresAt)
two_factors        (user_id → users.id  ON DELETE CASCADE)
jwks               (public_key, private_key, ...)
```

```sql title="packages/db/src/schema/*"
notifications              (user_id → users.id  ON DELETE CASCADE)
push_tokens                (user_id → users.id  ON DELETE CASCADE)
notification_preferences   (user_id → users.id  ON DELETE CASCADE)
audit_logs                 (actor_id → users.id)
organizations              (owner_id → users.id)
members                    (user_id, org_id)
auth_relations             (subject_id, object_id, relation)  -- plain text
```

Application code assumes the row exists locally:

```ts
// apps/server/src/modules/notifications/service.ts
const conditions: SQL[] = [eq(notifications.userId, userId)];

// apps/server/src/modules/users/service.ts
db.query.users.findFirst({ where: eq(users.id, id) });

// apps/server/src/modules/auth/instance.ts
await db.delete(schema.sessions).where(eq(schema.sessions.userId, session.userId));

// apps/server/src/auth/middleware.ts
const principal = principalFromUser(c.get("user"));
```

## The two tempting shortcuts (both wrong)

:::caution[Shortcut 1: "Drop the local `users` table."]
Every FK cascade dangles, every `INNER JOIN users` has nothing to join to, and every `user.name` you display becomes a network call to Auther. The "delete one table" change metastasizes into a weeks-long refactor — plus orphaned rows pointing at users your DB no longer knows.
:::

:::caution[Shortcut 2: "Bolt Auther on the side, leave the database alone."]
Two identity stores drift the moment one changes. A user updates their email in Auther — your app shows the old one. An admin bans a user in Auther — your app still lets them in on a cached JWT. No rule for which store wins.
:::

## Ownership, column by column

Neither "all Auther" nor "all local" — both, decided per column. Some fields are pure identity (Auther's); some are product state (yours); a few are split. This table is the contract everything else builds on:

| Column | Authoritative in | Notes |
| --- | --- | --- |
| `id` | Auther | Local row uses Auther's ID verbatim as PK |
| `email`, `emailVerified` | Auther | Your app mirrors for joins/display |
| `name`, `image` | Auther | Your app mirrors |
| password / argon2id hash | Auther | Your app never stores |
| 2FA secret / backup codes | Auther | Your app never stores |
| `status` (active/inactive) | Auther | Auther's admin plugin (`banned` + `banReason`) |
| `failedLoginAttempts` | Auther | Auther's login-security plugin |
| `lockedUntil` | Auther | Same |
| `twoFactorEnabled` | Auther | Inferable from Auther's userinfo endpoint |
| `onboardingCompletedAt` | **Your app** | Pure product state |
| `notificationPreferences` | **Your app** | Your app |
| `roleSlugs` | Split | Platform roles → Auther; app-domain roles → your app |
| `activeOrganizationId` | **Your app** | Tenant selection is an app concern (see [Edge Cases](/auther/integration/edge-cases/)) |

Mirrored columns (`email`, `name`, `image`) keep joins and display lookups local while Auther stays the authority — you just keep the mirror fresh. "Your app" columns are data Auther has no opinion about, so nothing syncs. Once every column has exactly one owner, schema, sync, and failure modes follow mechanically.
