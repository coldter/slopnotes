Schema, auth core, and server internals are in place — now watch the system run. Each trace follows one real request end-to-end. Where a flow surfaces a failure mode, it links to the [Edge Cases Catalog](/auther/integration/edge-cases/).

**BFF** = backend-for-frontend (owns the web app's session cookie, holds the real OAuth tokens). **JIT** = just-in-time shadow-row insertion on the first valid token for an unseen user.

## Alice signs up on the web

The webhook and the JIT shadow-row insert converge on the *same* `users` row no matter which arrives first.

<Mermaid title="Web signup — confidential client + webhook fan-out" height={560} code={`
sequenceDiagram
  participant B as Browser
  participant BFF as Web BFF
  participant Auth as Auther
  participant H as Hono server
  B->>BFF: clicks "Sign up"
  BFF->>Auth: redirect to /oauth2/authorize (state, code_challenge)
  Note over Auth: Alice not logged in → renders /sign-in (→ /sign-up)
  Auth->>Auth: create account (email + password)<br/>hash, write user row, send verify email via Resend
  Auth->>Auth: fire after_signup pipeline hook<br/>emit user.created webhook
  Auth->>H: POST /api/auth/webhooks/auther<br/>x-webhook-{id,signature,timestamp}
  Note over H: verify sig → dedup → INSERT INTO users (id usr_xyz)
  Auth->>BFF: redirect to /auth/callback (code)
  BFF->>Auth: POST /oauth2/token (client_secret_basic)
  Auth-->>BFF: access_token + id_token + refresh_token
  Note over BFF: set httpOnly session cookie, store tokens server-side
  B->>H: API call (Authorization: Bearer token via BFF)
  Note over H: authContextMiddleware verifies JWT<br/>lookup users.id usr_xyz → found → attach user + session
`} />

The webhook body is `{ type: "user.created", payload: { id: "usr_xyz", email, ... } }`, signed with the `x-webhook-{id,signature,timestamp}` headers. Once verified and de-duplicated, the handler inserts the shadow row keyed on the Auther user id.

:::note[The race is already handled]
Alice might reach the Hono server *before* the webhook. The middleware lookup misses, JIT fires, and the row is inserted with `ON CONFLICT DO NOTHING`. The webhook arrives later, tries the same `INSERT`, conflicts, and no-ops. Either ordering is safe — see the [first-login race](/auther/integration/edge-cases/).
:::

## Alice logs in on mobile

A mobile public client runs the same PKCE handshake as an SPA; the shadow row from signup already exists, so the first API call needs no insert.

<Steps>

1. The mobile app opens an `ASWebAuthenticationSession` (iOS) pointed at `auth.example.com/api/auth/oauth2/authorize` with `client_id=hono-mobile`, `redirect_uri=com.myapp://auth/callback`, `response_type=code`, a `code_challenge`, and `scope=openid email profile offline_access`.
2. Auther shows the sign-in screen; Alice enters her password (plus 2FA if enabled).
3. Auther redirects to `com.myapp://auth/callback?code=...`.
4. The system browser returns control to the app, which extracts the `code`.
5. The app exchanges it: `POST /api/auth/oauth2/token` with `grant_type=authorization_code`, the `code`, the `code_verifier`, and `client_id=hono-mobile` — no client secret, it's a public client.
6. Auther returns `access_token` (1h), `refresh_token` (7d), and `id_token` (1h).
7. The app stores the `refresh_token` in the OS Keychain and keeps the `access_token` in memory.
8. The app calls the Hono API with `Authorization: Bearer <access_token>`. The middleware validates the token, finds Alice already in the shadow table, attaches her, and the request proceeds.
9. When the access token expires, the app calls `POST /token` with `grant_type=refresh_token` for a new access token — and a rotated refresh token, which it must store in place of the old one.

</Steps>

## Alice sends a notification

Adopting Auther changes only the *source* of a principal's roles — authorization reads JWT `permissions` instead of a local `users.roleSlugs` column.

<Mermaid title="Domain request — POST /api/notifications/send" height={460} code={`
sequenceDiagram
  participant B as Browser
  participant BFF as Web BFF
  participant H as Hono server
  participant DB as Postgres
  B->>BFF: POST /api/notifications/send (Bearer jwt)
  BFF->>H: forward request
  Note over H: authContextMiddleware<br/>jwtVerify vs JWKS → claims { sub usr_alice, permissions }
  Note over H: ensureShadowUser → found Alice → attach user + session
  Note over H: authorize("notifications", "send")<br/>resolvePrincipal → registry.can → allowed → next()
  Note over H: handler validates body (zod) → notificationService.send
  H->>DB: insert notifications (FK to users.id)
  Note over H: enqueue delivery job
  H-->>B: { id: "ntf_abc", status: "pending" }
`} />

Structurally nothing changed: the route still resolves a principal, runs `authorize("notifications", "send")`, validates the body with zod, and writes a `notifications` row whose FK to `users.id` still resolves. The only shift is the principal's roles now come from the JWT `permissions` claim.

## An admin bans Alice

Revocation is two-stage: Auther bans upstream, your webhook syncs locally, and Alice's in-flight token only dies when it expires or you deny-list it.

<Mermaid title="Admin ban — POST /api/users/:userId/deactivate" height={520} code={`
sequenceDiagram
  participant Adm as Admin
  participant H as Hono server
  participant Auth as Auther
  Adm->>H: POST /api/users/usr_alice/deactivate (admin_jwt)
  Note over H: authContextMiddleware validates, attaches admin
  Note over H: authorize("user", "deactivate") → JWT claim allows → next()
  Note over H: userService.deactivate → autherAdmin.banUser(...)
  H->>Auth: POST /api/admin/users/usr_alice/ban<br/>(exchange AUTHER_ADMIN_API_KEY for cached JWT)
  Note over Auth: set banned=true, invalidate sessions in Auther DB
  Auth->>H: user.updated webhook (+ possible access.revoked)
  Note over H: UPDATE users SET ... (shadow stays; she's banned upstream)
`} />

Alice's in-flight JWT stays valid for its remaining TTL (roughly 5–60 minutes). Two levers, alone or together:

- **Short access-token TTL** plus refusing refresh for banned users — Auther rejects the refresh, so the token simply expires.
- **`jti` deny-list** — the unique token id in each JWT. On ban, put Alice's active session `jti`s on a Redis block-list keyed by `jti` that the auth middleware checks and rejects on the next request.

:::caution[Revocation is not instant]
The two-stage flow — Auther bans, your webhook syncs, the token expires — is normal. Pick a TTL-versus-deny-list combination deliberately; tradeoffs are in the [Edge Cases Catalog](/auther/integration/edge-cases/).
:::

## Alice is deleted (GDPR request)

A hard delete upstream can let a still-valid token re-create the very row you just deleted — a "zombie user" — unless you tombstone the id so JIT refuses to re-insert it.

<Mermaid title="GDPR delete — autherAdmin.deleteUser('usr_alice')" height={520} code={`
sequenceDiagram
  participant Adm as Admin
  participant H as Hono server
  participant Auth as Auther
  participant B as Alice's client
  Adm->>H: "Delete Alice"
  H->>Auth: autherAdmin.deleteUser("usr_alice")
  Note over Auth: DELETE auther.user → cascade to session, etc.
  Auth->>H: user.deleted webhook
  Note over H: tx: scrub audit_logs actor_email = <deleted><br/>DELETE FROM users WHERE id usr_alice<br/>FK cascade: notifications, push_tokens, prefs, members
  B->>H: first request after webhook (still-valid JWT)
  Note over H: jwtVerify succeeds<br/>ensureShadowUser → not found → JIT INSERT → ZOMBIE
`} />

The delete webhook handler runs in one transaction: scrub denormalized identity fields (`UPDATE audit_logs SET actor_email = '<deleted>'`), delete the `users` row, and let FK cascades clean up `notifications`, `push_tokens`, `notification_preferences`, and `members`.

:::danger[Zombie user]
Alice's remaining JWT is still signature-valid for a few minutes after the delete. The first request she makes passes `jwtVerify`, misses the deleted shadow row, and JIT re-inserts it — resurrecting the account you just erased. Recipe: a short access token (5 min for sensitive routes, 15 min otherwise), a tombstone table, and a rule refusing JIT inserts for tombstoned ids within 24 hours. See the [Edge Cases Catalog](/auther/integration/edge-cases/).
:::

## Cron job: nightly notification digest

A browserless service authenticates with the same Bearer-token machinery — the API key's JWT carries a service-user `sub` and tuple-granted permissions, so the digest route needs no special-casing.

<Steps>

1. The cron service fires at 2am.
2. The job calls `getJobToken()`: if the cache is warm it reuses the token, otherwise it exchanges `AUTHER_API_KEY` for a JWT (valid 15 minutes).
3. For each user to notify, the job calls the digest endpoint with the job token:

   ```ts title="jobs/digest.ts"
   await fetch(`${HONO_URL}/api/notifications/digest`, {
     method: "POST",
     headers: { Authorization: `Bearer ${jobToken}` },
     body: JSON.stringify({ userId, payload }),
   });
   ```

4. The Hono server treats it like any other request: the JWT validates (its `sub` is the service user for the API key), JIT may create a shadow row for that service user the first time, and `authorize("notifications", "send")` passes because the key holds `(notifications, *, editor, apikey, <id>)`.
5. The notification is delivered exactly as in the domain-request flow.

</Steps>

Have your audit-log writer record a `principal.apiKeyId` — the JWT already carries it, so a digest run is traceable to the specific key that authorized it.
