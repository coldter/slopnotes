Once the happy path works, the real cost lives in the corners. Skim the group headings to find your phase, then the case whose first line matches your symptom. Each entry leads with the trigger, then the fix.

## Races & sync

### First-login race

Two simultaneous requests for Alice, whose shadow row doesn't exist yet, both run JIT and both `INSERT`. `ON CONFLICT DO NOTHING` + re-SELECT resolves it: one writer wins, the other reads the winner's row. No deadlock, no 500.

### Webhook arrives before JIT

`user.created` fires at signup, possibly before Alice hits the Hono server. The handler INSERTs with `ON CONFLICT DO NOTHING` — idempotent against JIT. Whichever runs first wins; both produce the same row.

### JIT inserts before the webhook

The common ordering: Alice signs in, JIT creates her row from JWT claims, then `user.created` arrives and its UPDATE fills in fields JIT couldn't derive (the webhook payload may carry fields that never appear in the JWT).

### Webhook never arrives

Lost outright — endpoint down during a deploy, QStash queue exhausted, idempotency cache wiped mid-retry, receiver 500'd through its retries. Defend in layers: QStash already retries ~3× with exponential backoff; manually replay one event (`DEL webhook:auther:<id>` in Redis, then re-trigger from Auther's admin UI); and run a nightly reconciliation sweep:

```ts title="apps/server/src/workers/reconcile-users.ts"
// run via cron service
export async function reconcileUsers() {
  const localUsers = await db.select().from(users);
  for (const local of localUsers) {
    const remote = await fetchAutherUser(local.id); // /api/admin/users/:id
    if (!remote) {
      await db.delete(users).where(eq(users.id, local.id));
      continue;
    }
    if (remote.email !== local.email || remote.name !== local.name || remote.emailVerified !== local.emailVerified || (remote.image ?? null) !== local.image) {
      await db.update(users).set({
        email: remote.email, name: remote.name, emailVerified: remote.emailVerified, image: remote.image,
      }).where(eq(users.id, local.id));
    }
  }
}
```

An admin "resync" button can trigger the same routine for one user on demand.

### Email change propagation

Alice changes her email in Auther; on verify a `user.updated` webhook fires with the new email and `emailVerified: true`. The shadow row updates; invalidate any local user-profile cache (Redis). The old JWT in her browser still carries the old email — harmless for identity (`sub` is stable), but always read `c.get("user").email` (the shadow row) for display, not `session.claims.email`.

### Audit correlation across systems

Pass `x-request-id` end-to-end and include `user_id` on every log line. Webhook events carry their own IDs — log them on receipt. Dashboards join on a `(user_id, 5-minute window)` key.

## Revocation & deletion

### User deletion cascade surprises

Default FK `CASCADE` removes notifications *and* audit logs with the user. For compliance, break the audit FK, keep the rows, scrub PII on delete. For notifications, cascade is usually fine.

### User deletion with in-flight tokens

Alice is deleted at t=0, but her JWT stays valid until t=900s — fifteen minutes of access without mitigation. Pick a recipe:

- **Short TTL** — 5 min for admin/sensitive routes, 15–60 min for normal traffic. More refreshes, faster revocation.
- **`jti` deny-list** — push her session `jti`s to Redis with `TTL = remaining JWT lifetime`; the middleware checks `if (await redis.exists('denylist:' + claims.jti)) return 401`.
- **Tombstone table** — record the deletion and refuse to re-provision from a stale JWT:

  ```ts title="tombstone.ts"
  await db.insert(deletedUsers).values({ id: userId, deletedAt: new Date() });
  // In ensureShadowUser:
  const tomb = await db.query.deletedUsers.findFirst({ where: and(eq(deletedUsers.id, sub), gt(deletedUsers.deletedAt, sub24h)) });
  if (tomb) throw new Error("user recently deleted");
  ```

- **Fail-closed on sensitive ops** — for money-moving actions, synchronously call `GET ${AUTHER_URL}/api/admin/users/:id`; on 404, reject.

Most apps are fine with a short TTL. Banking-grade flows want short TTL + deny-list + fail-closed on high-risk routes.

### Permission demotion mid-session

An admin revokes Alice's `users:admin`, but her in-flight JWT still claims it — up to fifteen minutes of over-permission. Same options as deletion: short TTL, a `permissions_rev` counter (a custom claim set via an Auther pipeline), or a forced `/check-permission` call for sensitive operations.

### Sign-out

A JWT is stateless — you can't invalidate one without a deny-list. On sign-out: clear client-side storage (drop the BFF cookie, drop mobile tokens), redirect to Auther's `/api/auth/sign-out` (ends Auther's session cookie), revoke the refresh token via `/revoke` if issued, and rely on the short access-token TTL for the residual window.

:::caution[Don't overpromise revocation]
Don't promise "instant global revocation" unless you've built the deny-list. A stateless token stays valid until it expires.
:::

## Tokens & keys

### JWKS cache staleness during rotation

Auther rotates signing keys every 30 days and keeps old keys for 60. `createRemoteJWKSet` with `cacheMaxAge: 12h` handles the overlap. If `/jwks` is unreachable, jose keeps the stale cache rather than rejecting every token — the correct fail-mode.

### Clock skew

Container clocks drift, producing `"exp" claim timestamp check failed` or `"iat" claim in the future`. jose's `clockTolerance: 30` grants 30 seconds of slack. Don't widen it beyond a small value — it directly weakens expiration enforcement. Persistent skew is an NTP problem; fix that instead.

### Impersonation

An admin logs in "as" Alice. Auther's admin plugin issues a token with `sub = usr_alice` while the session records `impersonatedBy = usr_admin`, and a `token_build` pipeline node can inject an `impersonator` claim. Your audit logger must honor it:

```ts title="apps/server/src/modules/audit-logs/service.ts"
async function log(principal: Principal, action: string, subject: string) {
  await db.insert(auditLogs).values({
    actorId: principal.userId,                      // Alice
    impersonatorId: principal.impersonator ?? null, // admin (if set)
    action, subject, createdAt: new Date(),
  });
}
```

Without `impersonatorId`, post-incident you can't answer "who actually did this?"

### 2FA step-up for sensitive ops

Re-challenge before money-moving actions — redirect to Auther with `prompt=login&acr_values=mfa`; Auther forces 2FA and returns a fresh token with `acr: "mfa"` and a new `auth_time`. The route checks both method and recency:

```ts
function requireRecentMfa(maxAgeSec: number) {
  return async (c: Context<Env>, next: Next) => {
    const session = c.get("session");
    const claims = /* extracted */;
    if (claims?.acr !== "mfa" || (Date.now() / 1000 - claims.auth_time) > maxAgeSec) {
      return c.json({ error: "mfa_required", redirectTo: "/step-up" }, 403);
    }
    return next();
  };
}
```

### Offline mobile

Cached access token unexpired → use as-is. Cached but expired with network → silent refresh via the refresh token. No network → show "reconnect to continue" rather than pretending the user is authenticated. Never extend the access-token TTL to infinity to paper over offline mode — that defeats expiration entirely.

### OIDC discovery

Auther exposes `/.well-known/openid-configuration` via better-auth; mobile SDKs (AppAuth) and server libraries use it to auto-configure endpoints. Point them at `${AUTHER_URL}/api/auth/.well-known/openid-configuration` (confirm the exact path against Auther's current better-auth config).

### Webhook versioning

Add fields, never remove them. If a removal is unavoidable, version the event type — `user.updated.v2`.

### Secret rotation

Rotate every shared secret with an overlap window: **webhook signing secret** — add the new secret to Auther, have your receiver accept both for a window, then remove the old one; **client secret** — rotate in Auther's admin UI, then redeploy Hono with the new value; **admin API key** — create the new key, migrate cron jobs onto it, then revoke the old one.

### Custom JWT claims

Need `department`, `tenant`, or a feature-flag bucket in the token? Write an Auther pipeline `token_build` node:

```lua
-- Auther pipeline: token_build node
local user = context.user
return {
  custom_claims = {
    department = user.department,        -- if stored in Auther user profile
    tenant = context.outputs.active_tenant or nil,
  }
}
```

Keep claims small — every request carries them as header bytes.

## Migration & onboarding

### Backfill on day one

Bulk-import existing Hono users via `POST ${AUTHER_URL}/api/auth/sign-up/email` with an `x-internal-signup-secret`, one user at a time (or batched via Auther's admin bulk endpoint). Preserve IDs if Auther accepts `id` — the Hono template already uses `usr_*` CUIDs, which Auther can adopt. For passwords:

- **Exact-hash import** — if Auther's better-auth config matches Hono's argon2id params, dump `accounts.password` into Auther's account table directly (through Auther's DB, not its API).
- **Force reset** (recommended for most) — bulk-invite all existing users with a password-reset link via Auther.
- **Dual-read transition** — accept both old local auth and new Auther auth for a window; users migrate as they log in.

### Email verification divergence

Import pre-migration verified users with `emailVerified: true` in Auther. Don't re-send verification emails to thousands of already-verified accounts.

## Ops & compliance

### Multi-tenant with active org

On stateless infrastructure, path-based tenancy (`/api/orgs/:slug/...`) beats session-based: no server-side org state, survives across instances.

### Background jobs, cron, and CI

Give each job its own API key with scoped tuples, and cache the `exchange` result for ~14 minutes. Never reuse a human's JWT for a cron job — when that person leaves or their permissions change, the job breaks silently.

### Rate limits

Auther owns sign-in rate limiting via its better-auth config, so remove `rateLimit` and `loginSecurityPlugin` from the local auth module (going away regardless). Your app-endpoint rate limits in `apps/server/src/middlewares/rate-limit.ts` stay — they're unrelated to auth.

### Local dev

Both projects ship a docker-compose. Run Auther on its default ports and Hono on different ports, sharing a docker network so Hono reaches Auther without `host.docker.internal` tricks:

```yaml title="docker-compose.dev.yaml"
# Hono project, fragment
services:
  auther:
    image: ghcr.io/you/auther:local
    ports: ["4000:3000"]
    environment:
      BETTER_AUTH_DATABASE_URL: http://auther-db:8080
      # ...
    networks: [app]
  auther-db:
    image: ghcr.io/tursodatabase/libsql-server:latest
    networks: [app]
networks:
  app: {}
```

Seed test users in Auther (`pnpm user:create` in its scripts) and use them from Hono in dev.

### CORS

Only relevant on direct browser-to-Auther fetches. A browser *redirect* to Auther is navigation, not CORS; a BFF's token exchange is server-side. Only a SPA fetching Auther directly triggers CORS — add the SPA origin to Auther's `CORS_ORIGIN`. Your Hono server's CORS origins are just the origins that call *it*.

### Admin UIs that manage users

Either redirect admins to Auther's `/admin` UI (simplest), or proxy through your Hono app's admin UI using `autherAdmin`. Don't maintain a second, parallel user-management surface — it will drift from Auther.

### PII in logs

Sanitize `Authorization` headers, full emails, and IPs. For OpenTelemetry export, add a redaction processor — Auther's metrics service already sanitizes tags, so follow suit in your Hono OpenTelemetry config (`apps/server/src/middlewares/otel.ts`).

### GDPR right-to-erasure

Erasure flows as a chain: Auther delete → webhook → Hono cascade → internal event → downstream services. Document the chain for auditors, and state the backup policy explicitly: removed from live within X days, from backups within Y per retention.

### Consent and ToS

Set `skipConsent: true` for B2B or trusted-client setups. Turn on per-client consent for B2C GDPR flows.
