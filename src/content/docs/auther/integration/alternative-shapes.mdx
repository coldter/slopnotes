The Hono walkthrough is one concrete shape — an FK-heavy monolith that owns its `users` table. Most other apps are variations. Find the closest shape below, pick the matching row of the [archetype matrix](/auther/integration/archetypes/), and reuse the mechanisms from the [core flows](/auther/integration/flows/) — JWT verification, Shadow-User sync, API-key exchange — in the proportions it demands.

## Pure-API backend (stateless microservice)

*No `users` table to mirror, so Shadow-User disappears entirely.*

A service called only by other services, never rendering UI, with no reason to keep a `users` table.

- **Archetype:** Federated-IDs + Full-Delegation.
- **Middleware:** verify the JWT, attach `userId` and `permissions` to the request context.
- **JOINs against users:** never happen. When a display name is needed, a BFF higher up fetches it from Auther's `/userinfo`.
- **Code you write:** a single middleware, ~100 lines. That's the whole integration.

```go
// Works with chi, gin, or echo.
func JWT(next http.Handler) http.Handler {
  return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
    token := strings.TrimPrefix(r.Header.Get("Authorization"), "Bearer ")
    claims, err := verifyToken(token) // uses go-jose JWKS auto-refresh
    if err != nil {
      http.Error(w, "unauthorized", 401)
      return
    }
    ctx := context.WithValue(r.Context(), "claims", claims)
    next.ServeHTTP(w, r.WithContext(ctx))
  })
}
```

## SPA with no backend

*No confidential server, so the browser itself runs the public PKCE flow.*

A pure-browser Vue/React app calling third-party APIs directly.

- **Archetype:** public PKCE client.
- **Tokens:** access token in memory; a refresh token only if Auther issues one for public clients.
- **Silent refresh:** a hidden iframe hitting `/authorize` with `prompt=none` and `response_mode=query`, or the refresh-token flow.
- **Code you write:** ~150-line `authClient.ts` exposing `login`, `logout`, `getToken`, `isAuthenticated`. Reach for `oidc-client-ts` rather than hand-rolling it.

## Monolith with FK-heavy user dependencies

*This is the full case — you already own a `users` table threaded with foreign keys.*

This is the shape the rest of Part 2 covers in full: [Hono walkthrough](/auther/integration/hono-schema/) from shrinking the schema through safe cutover. Shadow-User + Full-Delegation is the answer; nothing new to add here.

## Microservice mesh

*No service owns user rows — the question is verifying tokens cheaply as requests fan out.*

Billing, inventory, notifications sharing one Auther, all on federated IDs:

- **Archetype:** Federated-IDs in each service + Full-Delegation, backed by a shared verification library.
- **Shared package:** an `@company/auth-middleware` package bundling the JWKS cache, verify step, and context attach. Every service imports the same one.
- **API gateway:** an edge gateway (Envoy, Traefik, or managed) validates the JWT once and forwards trusted headers like `x-user-id` and `x-permissions`. Downstream services trust those headers because the gateway is the only ingress — saves a JWT verification per hop.
- **Cross-service calls:** relay the user's existing JWT rather than inventing a service-to-service scheme. For system-to-system calls with no user context, use the API-key exchange flow.
- **Hot-path authorization:** read permissions straight from the JWT claims locally. ABAC decisions go through `/check-permission`, but a well-designed hot path avoids ABAC-gated permissions on principle.

:::caution[Cache-stampede on `/jwks`]
If every service refreshes JWKS independently, they can stampede Auther's `/jwks` endpoint. Set a sensible `cacheMaxAge` and prefer gateway-only verification so the fleet shares one cache.
:::

## Multi-tenant SaaS

*Each tenant has its own users and permission model — isolation matters while the JWT stays small.*

A B2B SaaS where each customer is a tenant with its own resources and permission model. Auther's client-scoped entity types and per-tenant models do most of the work:

- **Archetype:** Shadow-User + Full-Delegation, with a separate authorization model per tenant inside Auther.
- **Per-tenant entity types:** scope them to the client — `tenant_acme:project`, `tenant_acme:invoice`, `tenant_acme:report`.
- **Per-tenant client:** one OAuth client per tenant for stronger isolation, or one shared client with tenant-routed JWT claims for simplicity.
- **Users in multiple tenants:** the JWT `permissions` claim reflects only the *active* tenant (injected by an Auther pipeline), so switching tenants re-issues the token. Keeps the token small.
- **Registration contexts:** one per tenant, keyed to an email domain — an `@acme.com` address authorizing through the acme client auto-gets `tenant_acme:project:viewer` across all projects.
- **Invites:** Auther's platform invite table, HMAC-signed and email-locked.
- **Shadow sync:** the ordinary lifecycle webhooks, unchanged.

:::note[A different multi-tenant guide]
This is multi-tenancy *as a client of Auther*. For multi-tenant infrastructure on the edge from scratch, see [Multi-Tenant SaaS on Cloudflare](/multi-tenant/overview/).
:::

## Mobile app with a backend

*The monolith shape plus device-specific token handling — PKCE and secure on-device storage.*

- **Archetype:** same as the FK-heavy monolith, plus on-device PKCE and refresh tokens.
- **Client:** a public PKCE client with a custom-scheme redirect such as `myapp://auth/callback`.
- **Tokens:** access token in memory or the Keychain; refresh token in the Keychain or EncryptedSharedPreferences.
- **Rotation:** Auther may rotate the refresh token on each use — persist the new one every time it refreshes.
- **Offline mode:** cache the last token; if expired and no network, fall back to a "reconnect" UX.
- **Biometric gate:** gate reading the refresh token from the Keychain behind a local FaceID/TouchID check. Entirely on-device — Auther never sees it.

## Background jobs, cron, and CI

*No interactive user — machines authenticate via the API-key-to-JWT exchange.*

- **Archetype:** API key exchanged for a JWT.
- **One key per job:** name each key for what it does — `cron:weekly-summary`, `ci:deploy-pipeline` — so the audit trail reads clearly.
- **Minimum tuples:** grant only what the job needs, e.g. `(notifications, *, sender, apikey, <id>)`.
- **In the job code:** exchange the key for a JWT, cache it ~14 minutes, refresh on demand.
- **Audit:** Auther records the API-key activity, and your app's audit log carries `principal.apiKeyId` alongside it.

## Legacy migration with gradual cutover

*An existing auth system keeps working while you cut over — the middleware runs dual-path.*

A Rails+Devise monolith with 500k users moving onto Auther with zero downtime:

<Steps>

1. **Stand up Auther and bulk-import users.** No user-facing change yet; the new IdP runs alongside the old one.

2. **Deploy dual-path middleware.** Accepts both a Devise session and an Auther JWT; flip the login button to point at Auther.

3. **Monitor and drain.** Let old Devise sessions expire naturally over the following days while watching the metrics.

4. **Remove the old path.** Delete the Devise middleware, drop the Devise gems, drop the legacy auth tables.

</Steps>

```ruby
# Phase 2: middleware accepts either credential.
def authenticate
  if (jwt = bearer_token(request))
    @principal = verify_auther_jwt(jwt) # new path
  elsif (session = devise_session)
    @principal = principal_from(session) # legacy path, drained in phase 3
  else
    head :unauthorized
  end
end
```

:::tip[Password migration]
Forcing a password reset by email is the cleanest way to migrate credentials: one-time UX hit, then done forever.
:::
