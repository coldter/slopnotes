With the schema reshaped and [auth core](/auther/integration/hono-auth-core/) verifying Auther's JWTs, the rest of the server follows. Most of it barely moves — keep your route guards, services, and notification code intact and change only where their inputs come from. The arc: **re-wire identity** (principal from the JWT) → **keep your authorization** (registry stays, input swaps) → **adjust call sites** that talked to better-auth → **roll out behind dual-mode middleware**.

## Re-wiring the principal

Everything downstream consumes a single `Principal` derived from the request context — the input to `packages/authorization`'s `authorize(...)` middleware. Getting its shape right lets every guarded route keep working unchanged.

Before — `roleSlugs` off the local user row:

```ts title="apps/server/src/auth/principal.ts (before)"
import type { Context } from "hono";

export function principalFromContext(c: Context) {
  const user = c.get("user");
  if (!user) return null;
  return {
    userId: user.id,
    email: user.email,
    roleSlugs: user.roleSlugs,       // from local user table
    sessionPlatform: c.get("session")?.platform,
  };
}

export function isValidRole(r: string): boolean {
  return ALL_ROLES.includes(r);
}
```

After — permission maps from the verifier on the context:

```ts title="apps/server/src/auth/principal.ts (after)"
import type { Context } from "hono";
import type { Env } from "@/lib/context";

export interface Principal {
  userId: string;
  email: string;
  permissions: Record<string, string[]>;   // from JWT
  abacRequired: Record<string, string[]>;  // from JWT
  impersonator?: string;                   // if present in JWT
}

export function principalFromContext(c: Context<Env>): Principal | null {
  const user = c.get("user");
  const session = c.get("session");
  if (!user || !session) return null;
  return {
    userId: user.id,
    email: user.email,
    permissions: session.permissions,
    abacRequired: session.abacRequired,
  };
}
```

The optional `impersonator` carries through when an admin acts as another user; it lines up with the audit-log `impersonatorId` column below.

## Keep `packages/authorization`, register an Auther-aware principal

`packages/authorization/src/hono.ts` exposes a `resolvePrincipal: (c) => Principal | null` hook. Today it wires to the local user's `roleSlugs`; after integration it wires to the JWT permissions. The registry only ever sees the resolved principal, so the swap happens in one place and no route file changes:

```ts title="apps/server/src/auth/registry.ts" {7,12-15}
import { createAuthorize } from "@repo/authorization";
import { principalFromContext } from "./principal";
import { registry } from "./capabilities";      // your existing app-domain resources

export const authorize = createAuthorize(registry, {
  resolvePrincipal: (c) => {
    const p = principalFromContext(c);
    if (!p) return null;

    // Map JWT permissions → the shape your registry's `can()` expects.
    // e.g. permissions["notifications"] = ["read","write"]
    //   →  ["notifications:read", "notifications:write"]
    return {
      id: p.userId,
      email: p.email,
      roles: Object.entries(p.permissions).flatMap(([entity, perms]) =>
        perms.map((perm) => `${entity}:${perm}`),
      ),
    };
  },
});
```

:::note[Zero route-file changes]
Every route that declares `guard: [authorize("user", "list")]` keeps working untouched — the entire identity swap happens in this one `resolvePrincipal` function.
:::

## Admin flows: ban, unban, update

Before — deactivating a user was a local write:

```ts title="apps/server/src/modules/users/service.ts (before)"
async function deactivate(userId: string, actorId: string, reason: string) {
  await db.update(users).set({
    status: "inactive",
    deactivatedAt: new Date(),
    deactivatedBy: actorId,
    deactivatedReason: reason,
  }).where(eq(users.id, userId));
}
```

After — the mutation goes to Auther, the source of truth for account status:

```ts title="apps/server/src/modules/users/service.ts (after)"
import { autherAdmin } from "@/modules/auth/admin-client";

async function deactivate(userId: string, actorId: string, reason: string) {
  await autherAdmin.banUser(userId, reason, actorId);
  // No local write. The user.updated webhook reflects Auther's banned flag.
  // If you need banned-ness locally for query performance, add a local
  // `deactivatedAt` column and update it from the webhook handler — but
  // treat Auther as the source of truth.
}
```

The route declaration is untouched — the guard still gates on the same capability:

```ts title="apps/server/src/modules/users/routes.ts"
deactivateUser: createRouteConfig({
  operationId: "deactivateUser",
  method: "post",
  path: "/{userId}/deactivate",
  guard: [authorize("user", "deactivate")],
  tags: ["users"],
  request: {
    params: userParamsSchema,
    body: { content: { "application/json": { schema: deactivateUserBodySchema } } },
  },
  responses: { 200: {/* … */}, /* …commonErrorResponses */ },
}),
```

## Sign-up and sign-in: delete local, defer to Auther

Delete `apps/server/src/modules/users/handler.ts`'s `createUser` endpoint. Account creation now happens in one of two places. Self-signup (e.g. mobile onboarding) — the client calls Auther's sign-up endpoint with the internal-signup-secret header (Auther's `PAYLOAD_CLIENT_SECRET`):

```ts title="client (mobile/web) — direct sign-up"
await fetch(`${AUTHER_URL}/api/auth/sign-up/email`, {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    // only for trusted clients
    "x-internal-signup-secret": process.env.AUTHER_SIGNUP_SECRET,
  },
  body: JSON.stringify({ email, password, name }),
});
```

For mobile this is safe because the secret lives on the app's *backend*, not the binary. The mobile app talks to your Hono server, which proxies the sign-up:

```ts title="apps/server/src/modules/users/service.ts (proxy helper)"
async function proxySignUp(input: { email: string; password: string; name: string }) {
  const r = await fetch(`${env.AUTHER_URL}/api/auth/sign-up/email`, {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "x-internal-signup-secret": env.AUTHER_SIGNUP_SECRET,
    },
    body: JSON.stringify(input),
  });
  if (!r.ok) throw new Error(`signup failed: ${r.status}`);
  // Auther emits a user.created webhook; the shadow row is created automatically.
  return r.json() as Promise<{ userId: string }>;
}
```

For web OIDC sign-up, redirect to Auther's sign-in page (which carries a "Sign up" link) — no Hono proxy. Sign-in follows the standard authorization-code flow ([Client Integration](/auther/server/client-integration/), scenarios A and B). The Hono server never sees a password.

## Notifications: same data flow, new call site

The `notificationService` over `notifications`, `push_tokens`, `notification_preferences` doesn't change — queries key on `userId`, and the shadow row carries the same ID. Only the *trigger* for auth-lifecycle notifications moves.

Before, the new-device notification fired from a local better-auth database hook (`auth-notifications.ts`, called from `databaseHooks.session.create`). After, delete that file — the same `notificationService.send(...)` fires from an Auther pipeline `after_signin` hook emitting a webhook, or from your webhook receiver's `security.new_device_login` branch. The emission code is unchanged; only the trigger moved from a local hook to a remote webhook.

## Organizations and the active org

The template stored `sessions.activeOrganizationId` / `activeOrgRole`, populated in `databaseHooks.session.create`. JWTs have no session table, so "which org am I acting in" lives elsewhere. Pick one:

<Tabs syncKey="tenancy">
  <TabItem label="URL-path tenancy (recommended)">

  The org slug lives in the path — no session state, bookmarkable, shareable, stateless: `/api/orgs/acme/notifications`. A middleware extracts `:orgSlug`, checks membership, attaches the result:

  ```ts title="apps/server/src/middlewares/org-context.ts"
  import { createMiddleware } from "hono/factory";
  import { and, eq } from "drizzle-orm";
  import { db } from "@/db";
  import { members, organizations } from "@repo/db/schema";

  export const orgContextMiddleware = createMiddleware(async (c, next) => {
    const slug = c.req.param("orgSlug");
    if (!slug) return c.json({ error: "org required" }, 400);
    const user = c.get("user");
    if (!user) return c.json({ error: "unauthenticated" }, 401);

    const [membership] = await db
      .select({ orgId: organizations.id, role: members.role })
      .from(members)
      .innerJoin(organizations, eq(organizations.id, members.organizationId))
      .where(and(eq(members.userId, user.id), eq(organizations.slug, slug)))
      .limit(1);

    if (!membership) return c.json({ error: "not a member" }, 403);

    c.set("activeOrg", { id: membership.orgId, slug, role: membership.role });
    return next();
  });

  // mount per org-scoped router
  app.use("/api/orgs/:orgSlug/*", authContextMiddleware, orgContextMiddleware);
  ```

  </TabItem>
  <TabItem label="JWT-claim tenancy">

  Auther's `token_build` pipeline hook injects an `active_org` claim into the JWT. This binds the tenant into the token, but switching orgs requires re-issuing the token — a round trip through Auther. Reach for it only when you genuinely need the tenant bound inside the token.

  </TabItem>
</Tabs>

Either way, delete the old `additionalFields.activeOrgRole` from `instance.ts` — that field, and the file, are gone.

## Audit logs: break the FK, keep the history

The template's `audit_logs.actor_id` references `users.id` — a liability once Auther owns users: a `CASCADE` on delete quietly removes the user's audit history, almost always wrong for compliance. Drop the FK, keep the column, scrub PII on delete:

```ts title="packages/db/src/schema/audit-logs.ts" {3}
export const auditLogs = pgTable("audit_logs", {
  id: varchar("id", { length: 255 }).primaryKey().$defaultFn(/* … */),
  actorId: varchar("actor_id", { length: 255 }).notNull(),       // no .references()
  impersonatorId: varchar("impersonator_id", { length: 255 }),   // new column
  action: text("action").notNull(),
  subject: text("subject"),
  createdAt: timestamp(/* … */).defaultNow().notNull(),
  // … existing columns
});
```

In the webhook dispatcher's `user.deleted` branch, scrub the actor's PII-like fields but keep the rows:

```ts title="apps/server/src/modules/auth/webhook.ts (user.deleted branch)"
await db.transaction(async (tx) => {
  // Keep audit rows; scrub PII-like fields on the actor's rows
  await tx.update(auditLogs)
    .set({ actorEmail: "<deleted>", actorName: "<deleted>" })   // if you have these
    .where(eq(auditLogs.actorId, evt.payload.id));
  await tx.delete(users).where(eq(users.id, evt.payload.id));
});
```

:::caution[Cascading deletes erase compliance history]
A `references()` with default cascade on `actor_id` means a user deletion in Auther can wipe their entire audit trail. Drop the FK, retain the rows, scrub only the PII columns.
:::

## Environment variables

Add the Auther-related variables to the Zod env schema; remove the dead better-auth ones (`BETTER_AUTH_SECRET`, rate-limit configs, anything that only ran the local instance):

```ts title="apps/server/src/env.ts"
const envSchema = z.object({
  // …existing
  AUTHER_URL: z.string().url(),                    // e.g. https://auth.example.com
  AUTHER_ISSUER: z.string().url(),                 // usually same as AUTHER_URL
  AUTHER_AUDIENCE: z.string(),                     // matches your OAuth client audience
  AUTHER_INBOUND_WEBHOOK_SECRET: z.string().min(32),
  AUTHER_SIGNUP_SECRET: z.string().min(32),        // proxy sign-up endpoint
  AUTHER_ADMIN_API_KEY: z.string(),                // service API key for admin ops
});
```

## The `apps/web` OIDC client

Your web app becomes an OAuth client. The Hono server doesn't care which token-holding model you pick; it only validates JWTs. Pick one by threat model:

<Tabs syncKey="webclient">
  <TabItem label="BFF (recommended)">

  Backend-For-Frontend: a small server between the browser and your API holds the tokens server-side; the browser never touches them.

  - The web app's backend (Next.js route handlers or a dedicated BFF) is a confidential OAuth client.
  - On login: browser redirects to Auther → BFF callback → BFF exchanges the code for tokens → sets an `httpOnly` cookie holding a session reference that maps to the JWT stored in Redis (or encrypted in the cookie).
  - Every browser→BFF→Hono call: the BFF adds `Authorization: Bearer`.
  - XSS-safe — no token in browser-accessible storage — and transparent token refresh works.

  </TabItem>
  <TabItem label="Direct token">

  Simpler, weaker. The browser is a public PKCE client holding the token itself:

  - Access token in memory; a refresh token in an `httpOnly` cookie if Auther issues one.
  - Every call goes browser→Hono directly with `Authorization: Bearer`.
  - Vulnerable to XSS theft of the token. Use only with a strict CSP and zero third-party scripts.

  </TabItem>
</Tabs>

## The `rpc-client.ts` contract

The template's `rpc-client.ts` generates a typed client from the OpenAPI spec. Nothing about the contract changes — the generated client just needs to pass `Authorization: Bearer <token>` on every call. Its consumers (web, mobile) obtain the token from their respective auth flows.

## The ordered migration sequence

Run old and new systems side by side and converge gradually — a dual-mode middleware accepting both the legacy cookie and the new JWT makes that possible.

:::caution[Never big-bang an auth system]
Flipping every client at once leaves no safe rollback and risks locking out your entire user base on one bad deploy. Migrate behind dual-mode middleware and drain old traffic over time.
:::

<Steps>

1. **Stand up Auther in production**, but point no one at it yet. Seed a test admin.

2. **Create the OAuth clients in Auther**: `hono-web` (confidential or PKCE per the web-client choice), `hono-mobile` (public PKCE), `hono-admin` (an API key for server-to-server admin calls).

3. **Bulk-import users** into Auther via the admin signup endpoint, preserving existing IDs so shadow rows line up.

4. **Deploy dual-mode middleware** to Hono — accepts both old better-auth cookies and Auther JWTs; JWT wins when present:

   ```ts title="apps/server/src/middlewares/auth-context.ts (dual mode)"
   export const authContextMiddleware = createMiddleware<Env>(async (c, next) => {
     const authHeader = c.req.header("Authorization");
     if (authHeader?.startsWith("Bearer ")) {
       // Auther path
       return autherPath(c, next, authHeader.slice(7));
     }
     // Legacy better-auth cookie path
     return legacyPath(c, next);
   });
   ```

5. **Flip the web app's login button** to Auther. New logins issue JWTs; old cookies keep working.

6. **Watch the metrics**: `auth.jwt.verify.result.count`, `auth.shadow.jit.count`, webhook delivery counts, error rates.

7. **Drain.** Over your longest session TTL (7 days for mobile), cookie traffic converges to zero.

8. **Remove dual-mode**: delete `legacyPath`, delete `apps/server/src/modules/auth/instance.ts`, and run the Drizzle migration to drop the now-unused tables.

</Steps>

Rollback for steps 1–7 is reverting the deployment. The Drizzle migration in step 8 is the one irreversible step — run it only after several days of clean, Auther-only traffic.
