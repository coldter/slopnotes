## Frequently asked questions

### Can I skip the shadow table and store the user ID as plain text everywhere?

Yes — that's the Federated-IDs archetype ([Four Integration Archetypes](/auther/integration/archetypes/)). The cost: losing DB JOINs and cascade deletes against a real user row. Worth it for microservices (no shared DB anyway), not for an FK-heavy monolith like the Hono template.

### My Hono app has eight tables with foreign keys to `users`. Do I rewrite all of them?

No. The shadow table's `id` is the same shape (`varchar(255)`) carrying Auther's ID, so existing FKs still resolve — nothing about the ID changed.

### What about social logins like Google or GitHub?

Configure the social providers in Auther's `auth.ts`. The OIDC flow handles the provider hop transparently; your Hono server only ever sees an ordinary Auther JWT. From the app's side, no difference between a password login and a social one.

### Can I keep my own custom signup form?

Yes. Proxy the sign-up through Hono to Auther's sign-up endpoint with the `x-internal-signup-secret` header. Auther's registration contexts then apply any post-signup permission grants.

### What happens if Auther is down?

Most of the system keeps working because verification is local:

- Existing JWTs keep validating (JWKS is cached — no live call needed).
- New logins fail (they need Auther's authorize endpoint).
- Token refresh fails once an access token expires.
- `/check-permission` fails — your app picks the posture: fail-closed (safe) or fail-open for static permissions (risky).
- Webhooks queue in QStash and deliver once Auther is back.

For higher availability, run multi-region Auther behind a load balancer with JWKS served from a CDN.

### Can I issue my own JWTs from Hono, signed with Auther's keys?

No. Private signing keys are encrypted at rest in Auther's database and never leave it — your app can only verify, never sign. For service-to-service tokens, use Auther's API key exchange flow.

### My JWT is too big because I belong to many tenants. How do I shrink it?

Include only the *active tenant's* permissions, built by Auther's `token_build` pipeline. Switching tenants becomes a token re-issue instead of one bloated token carrying every tenant's claims.

### Should I sync `access.granted` / `access.revoked` into `auth_relations`?

Only if you need local admin queries like "list every user with `admin` on org X." For enforcement you don't need the sync — the JWT claim is the source of truth at issuance time and cheaper to read than a mirrored table.

### When do I call `/check-permission` versus deciding locally?

Ask: does the permission depend on the resource's runtime attributes — amount, status, ownership? If yes, it's an ABAC decision → `/check-permission`. If no, a local check or JWT claim suffices. Most permissions are the latter.

### Can a user have multiple sessions on multiple devices?

Yes. Auther issues an independent token per session; your Hono server treats each request the same — a valid JWT from this user. Devices don't coordinate.

### How do I force logout everywhere?

Revoke all the user's sessions in Auther's admin UI. Already-issued JWTs remain valid until their `exp`, so revocation isn't instant by default. For immediate cutoff, maintain a `jti` deny-list and reject revoked token IDs at the edge.

### Do I really keep `packages/authorization`?

Yes — the recommended default. Your local authorization package handles app-domain permissions; Auther's handles identity-level concerns. Both run at request time; neither replaces the other.

### Can I fully delegate to Auther instead?

Yes, and it's valid. Move every resource and permission into Auther's authorization models, delete `packages/authorization`, and always resolve access through JWT claims plus `/check-permission`. Simpler, single place to manage policy — at the cost of more latency on ABAC paths.

## What to remember

1. **Decide ownership column by column.** The local `users` row is a cache of Auther's user plus your app-specific fields — not a second source of truth.
2. **Shadow-User + JIT provisioning + webhooks is the default** for FK-heavy apps like the Hono template.
3. **Use Auther's `sub` as the local `users.id`.** Never generate a local ID.
4. **Let `jose` handle JWKS.** Don't write your own key-rotation logic.
5. **Webhooks need a signature, a timestamp, and idempotency** — in that order.
6. **Short access-token TTLs plus refresh tokens** resolve most stale-permission and deleted-user cases on their own.
7. **Keep your local authorization if it works.** `packages/authorization` is for app-domain permissions; Auther's is for identity concerns.
8. **Migrate gradually via dual-mode middleware.** Never big-bang a cutover.
9. **Other system shapes are variations on the same themes** — pick the row in the [archetype matrix](/auther/integration/archetypes/), then apply the same mechanisms.
