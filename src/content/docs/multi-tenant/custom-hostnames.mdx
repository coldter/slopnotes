Tenants eventually want the product on a domain they own (`app.acme.com`). That means provisioning a TLS cert for a hostname you don't control, tracking issuance over minutes-to-days, and not letting one tenant burn the shared cert quota. Cloudflare for SaaS handles the hostname/cert machinery; the remaining work is a clean onboarding flow, an internal lifecycle state machine, and a reconciler that keeps the database honest about what Cloudflare actually did.

## What Cloudflare for SaaS gives you

Bundled into <Badge text="Pro" variant="note" /> and <Badge text="Business" variant="note" /> plans with no separate SKU. Each zone includes 100 custom hostnames, `$0.10`/hostname overage, hard ceiling 50,000 outside Enterprise. Provision with one API call — `POST /zones/{zone_id}/custom_hostnames` — and Cloudflare auto-issues the SSL cert via Domain Control Validation (DCV — how the CA confirms the domain is really under your control).

DCV flavors: **HTTP DCV** is simplest — Cloudflare validates the moment the tenant's CNAME goes live, no extra DNS record. That's the method this design uses.

:::caution[Two Enterprise-only fields to never send]
- **`certificate_authority`** is Enterprise-only. Setting it to `"google"` returns API error `1459` on Pro/Business. Cloudflare's default CA selection (Google Trust Services with Let's Encrypt fallback per CAA records) applies automatically.
- **`custom_metadata`** is not universally available (Enterprise / account-team-enabled). Don't depend on it — build reverse lookups on `cf_hostname_id` and `hostname`.
:::

## The onboarding flow

Never call Cloudflare the instant a tenant types a hostname — that's the abuse channel (see [Why TXT pre-verification](#why-txt-pre-verification)). Two phases: the tenant proves domain control platform-side via a TXT record; only then does the platform touch Cloudflare.

<Steps>

1. **Tenant adds a TXT record (platform-side verification).**

   ```http title="Add a pending hostname"
   POST /api/tenancy/hostnames
   Content-Type: application/json

   { "hostname": "app.acme.com" }
   ```

   Per-org rate limit: at most 10 pending hostnames at a time, 50/day. The server inserts a `tenant_custom_hostname` row with `lifecycle_status: "awaiting_txt"`, `verification_verified_at: NULL`, `cf_hostname_id: NULL`. **No Cloudflare API call yet.** The response carries a per-org `verification_token` (a cuid) and the record to add:

   ```text title="Verification instructions surfaced to the tenant"
   Add a DNS TXT record:
     _app-example-verify.app.acme.com  ->  <verification_token>
   Then click "Verify" to continue.
   ```

2. **The platform verifies the TXT.**

   ```http title="Verify the TXT record"
   POST /api/tenancy/hostnames/{id}/verify
   ```

   The server resolves the TXT over DNS-over-HTTPS (`https://cloudflare-dns.com/dns-query`). On a match it sets `verification_verified_at = now()` and writes a `hostname.verified` audit event (CRITICAL, dual-scope).

3. **The platform registers the hostname with Cloudflare.** Only after verification. HTTP DCV (`method: "http"`) makes the later CNAME-only flow work; `certificate_authority` is deliberately absent:

   ```ts title="apps/server — register the custom hostname" {3,7-8}
   await fetch(`https://api.cloudflare.com/client/v4/zones/${zoneId}/custom_hostnames`, {
     method: "POST",
     headers: { Authorization: `Bearer ${cfApiToken}`, "Content-Type": "application/json" },
     body: JSON.stringify({
       hostname: "app.acme.com",
       ssl: { method: "http", type: "dv", settings: { min_tls_version: "1.2" } },
     }),
   });
   ```

   The row is updated with the returned `cf_hostname_id`, `lifecycle_status: "pending_cloudflare"`, and the raw Cloudflare validation fields. The tenant is shown the CNAME to create:

   ```text title="CNAME instructions surfaced to the tenant"
   Create a CNAME record:
     app.acme.com  ->  customers.example.com

   Expect ~2-5 minutes of TLS errors during initial cert issuance after the
   CNAME is live. To eliminate downtime, you can pre-validate via the
   /.well-known/pki-validation/ token shown below.
   ```

4. **The reconciler tracks status.** A cron on `apps/server` runs every 60 seconds, polling non-terminal hostnames and storing raw Cloudflare validation state separately from the internal lifecycle status. See [The reconciler](#the-reconciler).

5. **Notification on activation.** When Cloudflare reports `status === "active"` and the row wasn't previously active, the reconciler emits a `hostname.activated` audit (CRITICAL, dual-scope) and sends a `HostnameVerifiedEmail` to the org's admins — exactly once.

</Steps>

### Why TXT pre-verification

HTTP DCV already protects the *certificate* — an attacker submitting `app.competitor.com` can never finish issuance, because the competitor's server never serves the validation challenge. But the *registration itself* is the resource being abused: every `POST /zones/{zone_id}/custom_hostnames` consumes a slot in the zone-wide hostname quota and counts toward Cloudflare's abuse heuristics, regardless of whether the cert issues. A script firing thousands of competitor hostnames could exhaust the quota or get the zone flagged. The TXT record is a cheaper proof of control on the platform's side, *before* a single Cloudflare slot is spent.

### The CNAME target

Tenants CNAME to `customers.example.com`, a proxied CNAME on the platform's zone pointing at the *fallback origin* — the single backend Cloudflare for SaaS routes every custom hostname to. Set once at zone level, so every tenant domain lands on the same Workers app.

:::caution[Don't point tenants at the wrong target]
The CNAME target is `customers.example.com`, *not* `<worker>.workers.dev` and *not* `app.example.com.cdn.cloudflare.net` (undocumented, not recommended).
:::

## The internal lifecycle

Cloudflare's own validation states are noisy and its timeouts aren't infinite — an unvalidated hostname moves through `Moved` and is eventually `Deleted` after a 7-day backoff. So the database keeps the raw Cloudflare state in `cf_status` / `cf_ssl_status` *and* maps it onto a small internal lifecycle enum. Decoupling the two lets the product survive Cloudflare renaming or adding states.

<Mermaid title="Custom-hostname lifecycle" height={460} code={`
stateDiagram-v2
  [*] --> awaiting_txt: row created (no CF call)
  awaiting_txt --> pending_cloudflare: TXT verified + registered with CF
  pending_cloudflare --> active: CF reports active
  pending_cloudflare --> error: caa_error / validation failure
  error --> active: tenant fixes DNS, CF revalidates
  pending_cloudflare --> moved: CF validation times out
  moved --> deleted: CF deletes after 7-day backoff
  active --> deleted: tenant DELETEs the hostname
  active --> moved: CF detaches the hostname
  deleted --> [*]
`} />

Terminal-ish states: `active` (working), `moved` (CF detached but not yet deleted), `deleted` (tombstoned in the DB — never hard-deleted, for audit), `error` (recoverable validation failure).

## The reconciler

Polling is the source of truth. A `scheduled` handler picks up every registered-but-not-terminal hostname, asks Cloudflare for its current state, and writes the mapped lifecycle status plus raw fields back in a transaction. A `null` response means Cloudflare deleted it after the backoff — tombstone the row.

```ts title="apps/server/src/workflows/hostname-reconciler.ts" {8-11,21,26}
// Phase A standalone; folded into customHostnameLifecycle.reconcileAll() in Phase C.
export default {
  async scheduled(event, env, ctx) {
    await withDrizzleClient(env, async (db) => {
      const rows = await db.select().from(tenantCustomHostnames)
        .where(and(
          isNotNull(tenantCustomHostnames.cfHostnameId),
          notInArray(tenantCustomHostnames.lifecycleStatus, ["active", "deleted"]),
        ))
        .limit(100);

      for (const row of rows) {
        const cfState = await cfApi.getCustomHostname(env, row.cfHostnameId);
        await db.transaction(async (tx) => {
          if (cfState === null) {
            // CF deleted after 7-day backoff — tombstone our row
            await tx.update(tenantCustomHostnames).set({ lifecycleStatus: "deleted" }).where(eq(tenantCustomHostnames.id, row.id));
            await auditLogService.create({
              event: AUDIT_EVENTS.HOSTNAME.DELETED.event,
              actorType: "system", targetType: "hostname", targetId: row.id,
              metadata: { hostname: row.hostname, reason: "cf_deleted_after_backoff" },
            }, tx);
            return;
          }
          await tx.update(tenantCustomHostnames).set({
            lifecycleStatus: mapCloudflareStatus(cfState.status),
            cfStatus: cfState.status,
            cfSslStatus: cfState.ssl.status,
            verificationErrors: [...(cfState.verification_errors ?? []), ...(cfState.ssl.validation_errors ?? [])],
            lastReconciledAt: new Date(),
          }).where(eq(tenantCustomHostnames.id, row.id));

          if (cfState.status === "active" && row.lifecycleStatus !== "active") {
            await auditLogService.create({
              event: AUDIT_EVENTS.HOSTNAME.ACTIVATED.event,
              actorType: "system", targetType: "hostname", targetId: row.id,
              metadata: { hostname: row.hostname },
            }, tx);
          }
        });
      }
    }, { waitUntil: (p) => ctx.waitUntil(p) });
  },
};
```

Operational details that aren't obvious from the code:

- **Cron and Hyperdrive.** Wrap the handler body in `withDrizzleClient(...)` exactly like a request handler. `placement.mode: "smart"` does *not* apply to scheduled handlers, so you accept latency to the Hyperdrive pool's region.
- **Trace sampling.** The server worker samples traces at 1% by default; bump the `scheduled` handler to 100% — cron runs are rare (1440/day) and traced runs are the only forensics you get. Add per-row structured logs as a second layer.

:::note[The scaling cliff at ~6,000 pending hostnames]
The reconciler processes 100 rows/min, so `100 × 60 = 6,000` is the maximum sustained backlog it can keep up with. Beyond that, switch to a Queue fan-out: the cron enqueues batches and a queue consumer (the same `apps/server` worker) processes them with concurrency. <Badge text="deferred to v2" variant="caution" /> — the 60-second cron suffices until well past 6,000 hostnames stuck in a non-terminal state at once.
:::

### Webhooks as a latency optimization

Cloudflare for SaaS offers webhooks for hostname/SSL state changes (validation, issuance, deployment, deletion, renewal). v1 stays on polling as the source of truth; webhooks are a low-risk latency optimization if faster activation notifications matter. Either way, the reconciler remains the durability backstop.

## The Cloudflare API token

One token, stored as a Cloudflare Secret (`CLOUDFLARE_API_TOKEN`), drives all of this. Scopes deliberately narrow: `Zone:Read`, `SSL and Certificates:Edit`, `Custom Hostnames:Edit` — on the SaaS zone only, never account-wide. The runbook rotates it quarterly.

:::tip[v2 hardening: split read and write tokens]
Split into a read token (reconciler) and a write token (admin actions) to narrow the blast radius if either leaks.
:::

## Failure modes worth designing for

### The TLS error window

When a tenant flips their CNAME, traffic reaches the platform while the cert is still issuing — the browser sees a TLS handshake error for ~2–5 minutes. Two mitigations, tenant chooses: accept the brief errors (warned up-front in the UI), or pre-validate via `/.well-known/pki-validation/{token}` served on the tenant's *existing* origin **before** flipping DNS, eliminating the window.

:::caution[The create response may omit validation records]
If the `POST` create response omits `ssl.validation_records[]`, fetch the hostname again with a delayed follow-up `GET` before surfacing the pre-validation token. Don't assume the create body contains it.
:::

### CAA records block issuance

If the tenant's apex zone has CAA records that don't permit `pki.goog` or `letsencrypt.org`, issuance silently fails and Cloudflare returns a `caa_error` in `verification_errors`. The UI surfaces the required records:

```text title="Required CAA records"
Add to your DNS:
  acme.com  CAA  0 issue "pki.goog"
  acme.com  CAA  0 issue "letsencrypt.org"
```

### Tenant on another CDN

A tenant already fronted by Fastly or Akamai may have DNS obfuscation that breaks DCV — the hostname won't validate. Document it so support recognizes it.

### Apex tenant domains

Apex domains like `acme.com` itself aren't supported in v1 — apex proxying for tenant-owned domains requires Cloudflare Enterprise BYOIP. Tenants must use a subdomain (`app.acme.com`, `acme-portal.acme.com`).

### API rate limit

The Cloudflare API rate limit is 1200 requests per 5 minutes globally. At 6,000 pending hostnames the reconciler stays within budget, but bursts could trip it — the API wrapper uses exponential backoff.

## Deletion

Never hard-deletes the row — history is kept for audit. Also guarded so a tenant can't lock themselves out:

```http title="Delete a custom hostname"
DELETE /api/tenancy/hostnames/{id}
```

The service guard refuses if removing this hostname would leave the org with no access path (no other custom hostname *and* `enforceSSO` configured for a host other than the default subdomain). Otherwise it: calls `DELETE` on the Cloudflare API; sets `lifecycle_status = 'deleted'` (tombstoned, not removed); writes a `hostname.deleted` audit event (CRITICAL, dual-scope); invalidates the cache via service-binding fan-out (see [Tenant Resolution](/multi-tenant/tenant-resolution/#cache-invalidation)).

## The schema

One table holds both views — the platform's (lifecycle status, verification token/timestamp) and Cloudflare's raw (`cf_status`, `cf_ssl_status`, `verification_errors`). The composite index on `(lifecycle_status, last_reconciled_at)` makes the reconciler's "oldest non-terminal rows first" query cheap.

```sql title="tenant_custom_hostnames (Drizzle definition)"
tenantCustomHostnames = pgTable("tenant_custom_hostnames", {
  id: varchar(255).primaryKey().$defaultFn(() => generatePrefixedCuid("tnh")),
  organizationId: text().notNull().references(organizations.id, { onDelete: "cascade" }),
  hostname: text().notNull().unique(),
  cfHostnameId: text().unique(),
  lifecycleStatus: text({ enum: ["awaiting_txt", "pending_cloudflare", "active", "moved", "deleted", "error"] }).notNull().default("awaiting_txt"),
  cfStatus: text(),
  cfSslStatus: text(),
  verificationErrors: jsonb<string[]>().notNull().default([]),
  verificationToken: text().notNull(),
  verificationVerifiedAt: timestamp({ withTimezone: true }),
  lastReconciledAt: timestamp({ withTimezone: true }),
  createdAt: createdAt(),
  updatedAt: updatedAt(),
}, (t) => [
  index("tch_organization_id_idx").on(t.organizationId),
  index("tch_status_reconciled_idx").on(t.lifecycleStatus, t.lastReconciledAt),
]);
```

## Gotchas worth remembering

- **The create response may not include `validation_records`** — do a delayed follow-up `GET` rather than assuming the `POST` body contains them.
- **Validation timeout is 7 days, not infinite** — Cloudflare moves a hostname through `Moved` then `Deleted`; keep the raw Cloudflare state and map it into a separate internal lifecycle.
- **Tenants on another CDN won't validate** — Fastly/Akamai DNS obfuscation breaks DCV.
- **API rate limit is 1200/5min globally** — fine at 6,000 pending, but bursts can trip it; use exponential backoff.
- **No `certificate_authority` field** — Enterprise-only. Let Cloudflare pick the CA.
- **No `custom_metadata` field** — treat as unavailable unless explicitly entitled; look up by `cf_hostname_id` or `hostname`.
- **Wildcard custom certs (`*.acme.com`) are Enterprise-only** — only single hostnames in v1.
- **The CNAME target is `customers.example.com`** (proxied on the platform zone), not the worker URL.
