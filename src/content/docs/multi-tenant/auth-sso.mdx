Identity is where multi-tenancy breaks subtly: a cookie scoped to the wrong domain, a forwarded header trusted blindly, or a default account-linking rule merging accounts across orgs — and a user in tenant A can act as a user in tenant B. All auth lives in one worker, `apps/auth`, running the **only** Better Auth instance in the system. One instance = exactly one place to get cookies, sessions, and JWT scoping right.

:::tip[Why one instance can serve every tenant]
Better Auth normally pins itself to a single base URL. Here it's configured with an **allowlist of app hosts** — so the same worker answers for `acme.app.example.com`, sibling subdomains, and custom domains like `app.acme.com`. Each request says which host it's serving; the allowlist just says "yes, that host is one of ours."
:::

## Part 1 — Better Auth config

The auth worker builds a fresh instance per request via `createAuth(db, env, ctx, options)`. The tenant arrives as a **typed parameter**, never as a spoofable header.

```ts title="apps/auth/src/lib/auth.ts"
betterAuth({
  appName: brand.appName,
  secret: env.BETTER_AUTH_SECRET,

  baseURL: {
    allowedHosts: authAllowedHosts,   // wildcard first-party hosts + active custom hosts snapshot
    protocol: "https",
  },
  basePath: "/api/auth",

  // Better Auth automatically adds allowedHosts to trustedOrigins.
  // Only add local-dev origins and short-lived validated IdP discovery origins here.
  trustedOrigins: async () => [...devTrustedOrigins, ...extraTrustedOrigins],

  emailAndPassword: {
    enabled: true,
    disableSignUp: true,                  // self-serve sign-up off; invitation-only
    requireEmailVerification: true,
  },

  account: {
    accountLinking: {
      enabled: true,
      allowDifferentEmails: false,
      trustedProviders: [],               // empty: provisionUser approves explicitly
    },
  },

  advanced: {
    useSecureCookies: true,
    defaultCookieAttributes: { sameSite: "lax", httpOnly: true, secure: true },
    cookies: {
      session_token: { name: "session_token_v1", attributes: { httpOnly: true, sameSite: "lax", secure: true } },
    },
  },

  databaseHooks: { /* see below */ },
  plugins: [ /* see below */ ],
});
```

### Why `baseURL` is an object, not a string

The object form with `allowedHosts` is what lets one instance serve every tenant. The key behavior is **OIDC callback URL derivation**: Better Auth builds the IdP callback address from the inbound request's host at runtime, so `https://acme.app.example.com/api/auth/sso/callback/{providerId}` resolves correctly even with one auth worker behind all hosts.

That runtime host resolution is the system's sharpest edge. In Better Auth v1.6, the dynamic host is read in this order: `x-forwarded-host`, then `host`, then the request URL. So before `apps/server` calls `AUTH.fetch(...)`, `AUTH.getSession(...)`, or `AUTH.getToken(...)`, it must reconstruct the request, pin `host` to the already-validated public host, and strip or overwrite `x-forwarded-host` / `x-forwarded-proto`.

:::caution[Dynamic `baseURL` trusts proxy headers unless you sanitize them]
The auth proxy must rebuild the request and its headers rather than forwarding the raw incoming object, or an attacker who can influence `x-forwarded-host` can steer callback URLs.
:::

Two more deliberate choices:

- **No `fallback`.** An unknown host should fail closed, not silently resolve to a first-party origin. Omitting `fallback` makes unrecognized hosts an error.
- **`allowedHosts` is a live snapshot, not a timer.** `@repo/tenancy` owns the active custom-hosts snapshot and its invalidation; a blind "refresh every five minutes" loop is too coarse for suspension, hostname deletion, or a freshly added domain.

### Why self-serve sign-up is off

Every tenant user arrives through invitation acceptance — see [operator-led onboarding](/multi-tenant/admin-panel/#operator-led-onboarding). `disableSignUp: true` is set globally. Invitation acceptance still creates users via the server-side `auth.api.createUser` admin path, which bypasses `disableSignUp`.

### Pinning the active org in `session.create.before`

The session-creation hook reads the typed RPC tenant parameter (not a header), enforces membership, sets `activeOrganizationId`, and rejects users with no membership in this tenant:

```ts title="apps/auth/src/lib/auth.ts" {6-13}
session: {
  create: {
    before: async (session, hookCtx) => {
      if (!tenant) return { data: session };  // apex / no tenant
      const [member] = await db.select().from(members)
        .where(and(
          eq(members.userId, session.userId),
          eq(members.organizationId, tenant.organizationId),
        )).limit(1);
      if (!member) {
        throw new APIError("FORBIDDEN", { message: "No membership in this tenant" });
      }
      return {
        data: {
          ...session,
          activeOrganizationId: tenant.organizationId,
          activeOrgRole: member.role,
          // ... existing platform / expiresAt logic ...
        },
      };
    },
  },
  update: {
    before: async (session) => {
      const updateData = session as Record<string, unknown>;
      if (updateData.activeOrganizationId !== undefined && tenant) {
        if (updateData.activeOrganizationId !== tenant.organizationId) {
          throw new APIError("FORBIDDEN", { message: "Cannot switch tenant via setActive" });
        }
      }
      return { data: session };
    },
  },
},
```

The `update.before` half closes a related hole: `setActive` can normally move a session to a different org, but the host pins org context, so any attempt to switch to a foreign tenant is rejected.

### Cookie isolation

Cookies are the actual isolation boundary:

- **No `Domain` attribute** means host-only by default. `crossSubDomainCookies` stays disabled.
- **`SameSite` is not the isolation mechanism.** Sibling tenant subdomains under the same registrable domain (eTLD+1) are same-site to the browser, so `SameSite=Strict` does not block tenant-to-tenant CSRF on its own.
- Auth/session cookies stay `SameSite=lax` to preserve OAuth/OIDC round-trips. Tenant and admin mutations are protected by explicit `Origin` checks, Better Auth's built-in CSRF protection on auth routes, and custom non-simple-request guards on the system's own mutation routes.
- Per-subdomain cookie isolation is automatic; custom-hostname isolation too — a custom domain is a different eTLD+1 entirely.

## Part 2 — SSO plugin

Per-tenant SSO comes from `@better-auth/sso` (OIDC, OAuth2, and SAML 2.0 in one plugin). OIDC ships day one; SAML is deferred to v2 (only the onboarding UI is deferred). Note: Better Auth's hosted self-service SSO dashboard is an enterprise feature — this template builds its own org-admin control plane on the OSS plugin endpoints.

:::tip[Generate the schema before you build]
Before any Phase A code, run `npx auth generate` with `sso()` enabled, then again with `domainVerification: { enabled: true }`. The generated schema diff is the source of truth for the Drizzle tables — don't hand-write them.
:::

### Plugin config

```ts title="apps/auth/src/lib/auth.ts"
sso({
  organizationProvisioning: { disabled: true },   // membership managed via org plugin
  provisionUser: async ({ user, userInfo, provider }) => {
    if (!userInfo.email_verified) {
      throw new APIError("FORBIDDEN", { message: "Email not verified by IdP" });
    }
    if (!provider.organizationId) {
      throw new APIError("INTERNAL_SERVER_ERROR", { message: "SSO provider missing org" });
    }
    if (!provider.domainVerified) {
      throw new APIError("FORBIDDEN", { message: "SSO domain not verified" });
    }
    // Account-takeover prevention: only link to an existing user if that user is
    // already a member of this org.
    const existing = await db.query.users.findFirst({ where: { email: { eq: userInfo.email } } });
    if (existing && existing.id !== user.id) {
      const [m] = await db.select().from(members)
        .where(and(eq(members.userId, existing.id), eq(members.organizationId, provider.organizationId)))
        .limit(1);
      if (!m) {
        throw new APIError("FORBIDDEN", {
          message: "Email belongs to a user without membership in this org",
        });
      }
    }
  },
  provisionUserOnEveryLogin: false,
  domainVerification: { enabled: true },
})
```

The `provisionUser` triple-gate is the most security-critical code on this page — the attack it stops is in [Account linking and cross-tenant takeover](#account-linking-and-cross-tenant-takeover) below.

### `ssoCallbackGuardPlugin` — runs *before* token exchange

Rejecting inside `provisionUser` is too late: by then the **authorization code exchange** has already happened (the code can only be spent once). A custom `before` hook guards the callback path first:

```ts title="apps/auth/src/plugins/sso-callback-guard.ts"
export const ssoCallbackGuardPlugin = (db, tenant: TenantContext) => ({
  id: "sso-callback-guard",
  hooks: {
    before: createAuthMiddleware(async (ctx) => {
      if (!ctx.path.startsWith("/sign-in/sso/callback/")) return;
      if (!tenant) throw new APIError("FORBIDDEN", { message: "Tenant required" });
      const providerId = ctx.path.split("/").pop();
      const provider = await db.query.ssoProviders.findFirst({
        where: { providerId: { eq: providerId } },
        columns: { organizationId: true },
      });
      if (!provider || provider.organizationId !== tenant.organizationId) {
        throw new APIError("FORBIDDEN", { message: "Provider does not belong to this tenant" });
      }
    }),
  },
});
```

### `ssoEnforcementPlugin` — blocks password sign-in when SSO is enforced

When an org turns on SSO enforcement, password sign-in must be refused at the API, not just hidden in the UI:

```ts title="apps/auth/src/plugins/sso-enforcement.ts"
export const ssoEnforcementPlugin = (db, tenant: TenantContext) => ({
  id: "sso-enforcement",
  hooks: {
    before: createAuthMiddleware(async (ctx) => {
      if (ctx.path !== "/sign-in/email") return;
      if (!tenant) return;
      const org = await db.query.organizations.findFirst({
        where: { id: { eq: tenant.organizationId } },
        columns: { enforceSSO: true },
      });
      if (org?.enforceSSO) {
        throw new APIError("FORBIDDEN", { message: "This organization requires SSO" });
      }
    }),
  },
});
```

Two API details the 2026 hooks surface enforces:

- The hooks API takes a single middleware function, not the older `{ matcher, handler }` array shape.
- `createAuthMiddleware` and `APIError` import from `better-auth/api`.

:::note[Match the path exactly]
The enforcement plugin uses `ctx.path === "/sign-in/email"`, not `startsWith` — an exact match avoids catching future endpoints sharing the prefix.
:::

### The SSO sign-in flow

With enforcement on, the two guards fire at different points: `ssoCallbackGuardPlugin` runs *before* the code exchange; `provisionUser` and `session.create.before` run *after*.

When `enforceSSO` is false, the flow is ordinary: `/api/tenancy/current` returns `{ enforceSSO: false }`, the UI shows the password form, the client calls `authClient.signIn.email(...)`, the enforcement hook is a no-op, and the standard email/password path still finishes in `session.create.before`. The enforcement plugin is defense in depth — the API refuses password sign-in regardless of what the UI renders.

### Registering an SSO provider

Org admins with the `manage_sso_config` permission register via `POST /api/sso-config/providers` with `{ providerId, issuer, clientId, clientSecret, domain }`. The server handler **overrides `organizationId` from `c.var.tenant.organizationId`** and never trusts the body, then normalizes the issuer, computes the discovery origins Better Auth must trust, encrypts `clientSecret` at rest (see [SSO client secrets](/multi-tenant/security/#sso-client-secret-encryption)), and calls a dedicated auth-worker registration path.

This is deliberately *not* a naive proxy to `/api/auth/sso/register`. Better Auth performs OIDC discovery during registration and checks those URLs against `trustedOrigins`; since `request` is `undefined` during direct `auth.api.*` calls, registration needs a request-scoped `createAuth(..., { extraTrustedOrigins })` path that injects the validated IdP origins for that one attempt.

Domain verification uses Better Auth's built-in token flow: registration returns a verification token, the tenant publishes a `_better-auth-token-{providerId}` DNS record, the token expires after one week. Even so, `provider.organizationId === tenant.organizationId` plus the membership checks remain the real admission gate; `domainVerified` is hardening, not the sole authorization primitive.

Enforcement toggles separately via `PATCH /api/sso-config/enforcement` with `{ enabled: true }`; the system requires at least one verified SSO provider before enforcement can be turned on.

## Part 3 — JWT and sessions

Downstream services authenticate with short-lived JWTs, which raises the question a single-tenant template never had: a token minted on tenant A must never be accepted by tenant B. Scope every claim to one host.

### Per-tenant JWT scoping

Better Auth's `jwt` plugin issues 15-minute JWTs. Here issuer, audience, and an `org` claim are all pinned to the current tenant's host:

```ts title="apps/auth/src/lib/auth.ts"
jwt({
  jwt: {
    issuer: tenant ? `https://${tenant.host}` : env.FALLBACK_APP_URL,
    audience: tenant ? `https://${tenant.host}` : env.FALLBACK_APP_URL,
    expirationTime: "15m",
    definePayload: ({ user, session }) => ({
      sub: user.id,
      email: (user as { email: string }).email,
      roleSlugs: (user as UserWithStatusFields).roleSlugs,
      platform: session.platform,
      org: tenant ? {
        id: tenant.organizationId,
        host: tenant.host,
        sessionVersion: tenant.sessionVersion,
      } : null,
    }),
  },
  jwks: { rotationInterval: 30 * 24 * 60 * 60 },
})
```

### The five verifier invariants

A verifier of a tenant JWT must confirm all five — the claim shapes are `{ aud, iss, org }` and `{ id, host, sessionVersion }`:

:::caution[Every consumer must check all five]
1. `aud === "https://${expectedHost}"` — tenant-host scoping.
2. `iss === "https://${expectedHost}"` — issuer pinning.
3. `org.host === expectedHost` — claim integrity.
4. `org.id === expectedOrgId` — org pinning.
5. `org.sessionVersion >= db.organization.session_version` — revocation check.
:::

Invariant 5 is `>=`, not `===`: several version bumps may be in flight, and a fresh JWT minted just after a bump shouldn't be rejected for trailing the database by a step.

Re-implementing these checks in every service is how they drift. Phase C consolidates them into `@repo/auth-tokens.verifyTenantJwt(token, opts)` — see the [auth-tokens package](/multi-tenant/deep-modules/#auth-tokens-package).

### Session model

Existing per-platform expiry is preserved: web sessions last one hour, mobile seven days. The revocation lever is a new `organization.session_version` column (integer, default `0`), bumped on suspension and restore. A JWT verifier rejects any token whose claimed version is stale, forcing re-authentication.

### Tenant suspension revokes sessions immediately

Suspending a tenant must cut live sessions at once, not wait for cookie expiry (1h–7d). In the same transaction that sets `suspended_at`, two statements run:

```sql
DELETE FROM session WHERE active_organization_id = orgId;
UPDATE organization SET session_version = session_version + 1 WHERE id = orgId;
```

Implemented by `tenantOperations.suspend` — see [tenant operations](/multi-tenant/deep-modules/#tenant-operations). It's the only correct call path: the same service handles the dual-scope audit and cache invalidation suspension requires.

## Account linking and cross-tenant takeover

Better Auth's default account linking merges users by email. Without a membership gate, a malicious org admin can take over a victim's account in *other* orgs:

:::danger[Account-takeover path without the gate]
1. The attacker configures an OIDC provider whose `id_token` returns `email = victim@bigcorp.com` — the IdP is fully attacker-controlled.
2. The attacker signs in via "their" SSO using the victim's email.
3. Default linking attaches the login to the existing `victim@bigcorp.com` user — the attacker now controls that account, including memberships in other orgs.
:::

The `provisionUser` hook blocks this with three conditions before any link:

- The IdP asserts `email_verified: true`.
- The existing user is **already a member of this org**.
- The SSO provider's domain is verified.

`account.accountLinking.trustedProviders: []` stays empty, so default linking only proceeds when `provisionUser` explicitly passes.

:::caution[`allowDifferentEmails: false` is load-bearing]
Keep `account.accountLinking.allowDifferentEmails` at `false`. The default is `true` in some Better Auth versions, which would let an SSO IdP attach a *different* email to an existing user — reopening the takeover path.
:::

## Things that bite

- **OIDC vs SAML callback handling.** With the object-form `baseURL`, the OIDC callback is derived from the inbound request. SAML stores absolute callbacks per provider — which is why SAML is deferred to v2.
- **`provisionUser` runs after the token exchange.** Any check that must happen before the IdP code is consumed belongs in `ssoCallbackGuardPlugin`.
- **Keep `trustedOrigins` small.** `allowedHosts` is added automatically; the extra list should stay purpose-specific (local dev, validated IdP discovery), not echo the inbound host.
- **Per-request, not a module-level singleton.** `createAuth(db, env, ctx, options)` per request; a singleton would force AsyncLocalStorage for no measurable gain.
- **MFA placement.** For SSO logins, MFA can only be enforced at the IdP layer — Better Auth doesn't layer MFA on SSO. For email/password, the existing `twoFactor` plugin handles it.
