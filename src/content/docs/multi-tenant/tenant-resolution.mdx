Every request to a tenant worker (`apps/server` or `apps/auth`) must turn `request.host` into an `organizationId` before any business logic. This is **the** critical path: get it slow and you tax every endpoint; get it wrong and you leak one tenant's data to another. The solution is three small pieces: a pure classifier, a thin middleware, a two-tier cache.

## Hostname shapes

Three valid host patterns, plus a hard rejection for everything else:

| Pattern | Example | Where the org lives |
| --- | --- | --- |
| Default subdomain | `acme.app.example.com` | `organization.slug = "acme"` |
| Tenant custom domain | `app.acme.com` | `tenant_custom_hostnames.hostname` (status `active`) |
| Apex (marketing) | `app.example.com` | No tenant — serves the marketing / find-your-team page |
| Admin host | `admin.example.com` | A different worker; `tenantMiddleware` rejects it with 404 |

Slugs are constrained at org-creation: a reserved-slug list, a Punycode (`xn--`) reject, and the regex `^[a-z0-9](?:[a-z0-9-]{1,61}[a-z0-9])?$`.

## The pure classifier

Classification lives in one pure function, `parseHostname`, in `packages/shared/src/tenant.ts` (or `@repo/tenancy` after Phase C — see [Deep Modules](/multi-tenant/deep-modules/#tenancy-package)). Pure = trivially testable, no I/O on the hot path.

```ts title="packages/shared/src/tenant.ts"
export const WILDCARD_SUFFIX = ".app.example.com"; // env-configurable
export const ADMIN_HOST = "admin.example.com";

export function parseHostname(host: string, suffix: string, adminHost: string):
  | { kind: "subdomain"; slug: string }
  | { kind: "apex" }
  | { kind: "custom"; hostname: string }
  | { kind: "admin" }
  | { kind: "invalid" } {
  const normalized = host.toLowerCase().normalize("NFC").replace(/\.$/, "");
  if (!/^[a-z0-9.-]+$/.test(normalized)) return { kind: "invalid" };
  if (normalized.includes("*") || normalized.includes(" ")) return { kind: "invalid" };
  if (normalized === adminHost) return { kind: "admin" };
  if (normalized === suffix.slice(1)) return { kind: "apex" };
  if (normalized.endsWith(suffix)) {
    const slug = normalized.slice(0, -suffix.length);
    return slug.includes(".") ? { kind: "invalid" } : { kind: "subdomain", slug };
  }
  return { kind: "custom", hostname: normalized };
}
```

The order of these checks is load-bearing. The admin host is matched first, before any wildcard or custom-host classification — otherwise `admin.example.com` would fall through to a `custom` lookup and leak a 404 timing oracle. Apex next, then the wildcard suffix, and only then does anything unrecognized become a `custom` hostname to look up in the database.

:::caution[Trust only the edge `Host` header]
Never read `X-Forwarded-Host` for tenant resolution — the Cloudflare-set `Host` header is the only trustworthy source; a forwarded header is attacker-controlled. On the server/auth proxy path, strip or overwrite forwarded host/proto headers before invoking Better Auth, whose dynamic `baseURL` logic can consult them.
:::

## Tenant middleware

Thin by design: classify the host, short-circuit the cases that need no database, otherwise resolve through the cache. Sets `tenant` on the request context.

```ts title="apps/server/src/middlewares/tenant-context.ts"
export const tenantMiddleware = createMiddleware<AppEnv>(async (c, next) => {
  const rawHost = c.req.header("host");
  if (!rawHost) return c.text("Bad Request", 400);

  const parsed = parseHostname(rawHost, c.env.WILDCARD_SUFFIX, c.env.ADMIN_HOST);
  if (parsed.kind === "invalid" || parsed.kind === "admin") return c.notFound();
  if (parsed.kind === "apex") {
    c.set("tenant", null);
    return next();
  }

  const tenant = await resolveCached(parsed, c);
  if (!tenant) return c.notFound();
  c.set("tenant", tenant);
  return next();
});
```

`apps/auth` runs the same middleware, before the Better Auth handler so SSO discovery and session hooks see the tenant context.

Two things about the `apex` branch are easy to get wrong:

1. **It's a legitimate request, not an error.** The marketing page on `app.example.com` hits `apps/server` with `tenant === null`.
2. **Tenant-scoped routes must default-deny when `c.var.tenant === null`.** The codebase keeps an explicit allowlist of routes valid on apex — the login picker and public marketing endpoints — and everything else rejects.

:::note[One consistent host source]
Use one derivation of the host throughout the request; don't mix `c.req.header("host")` with `c.req.url`'s `URL.host`, or the classifier and downstream code can disagree.
:::

## Cache strategy

A Postgres lookup on every API call would be wasteful, but this cache is security-sensitive: when a tenant is suspended or a slug renamed, stale entries must clear fast and everywhere. That rules out single-tier choices.

**Two tiers**, each playing to a Cloudflare strength:

- **Cache API** — per-colo cache (a *colo* is one Cloudflare data center). Sub-millisecond reads in-colo, strong same-colo consistency on invalidation. This is the fast read path.
- **KV** — eventually-consistent global key-value store. Holds one small, rarely-changing version counter.

Mental model: **Cache API answers fast; KV is the kill switch that expires every colo's cache at once.**

Why not KV as the lookup cache directly? Its cross-colo eventual-consistency window (~60s) is too long for security-sensitive ops like suspension. The Cache API has no such lag in-colo.

The cache key embeds the version prefix, which the admin worker bumps on a slug rename or suspension:

```ts
const version = (await c.env.CACHE.get("tenant_cache_version")) ?? "v0";
const cacheKey = new Request(
  `https://tenant-cache.internal/${version}/${parsed.kind}/${
    parsed.kind === "subdomain" ? parsed.slug : parsed.hostname
  }`
);
```

Bumping the version invalidates every entry under the old version, fleet-wide, on next read — one coarse lever for rare, broad invalidations.

Asymmetric TTLs are deliberate: positive results cache 60s, negative ("tenant not found") only 5s. A freshly-created tenant becomes visible within ~5s in any colo that had cached the negative; deletes and creations propagate fast without making the common positive case chatty.

## Cache invalidation

The Cache API is per-colo and per-worker. A `cache.delete()` in `apps/admin`'s isolate does nothing for `apps/server`'s isolate, let alone another colo. Targeted invalidation needs two cooperating mechanisms.

First, service-binding RPC fan-out to invalidate a specific tenant. Each tenant worker exposes it on its entrypoint:

```ts title="apps/server/src/entrypoint.ts"
// (apps/auth/src/entrypoint.ts is identical)
async invalidateTenant(spec: { kind: "subdomain" | "custom"; key: string }) {
  await caches.default.delete(`https://tenant-cache.internal/${currentVersion}/${spec.kind}/${spec.key}`);
}
async bumpTenantCacheVersion() {
  await this.env.CACHE.put("tenant_cache_version", String(Date.now()), { expirationTtl: 86400 });
}
```

Second, the admin worker orchestrates the fan-out across its peers:

```ts title="apps/admin/src/lib/cache-fanout.ts"
export async function invalidateTenant(env: AdminEnv, spec) {
  await Promise.all([
    env.API.invalidateTenant(spec),
    env.AUTH.invalidateTenant(spec),
  ]);
}
```

The fan-out is asymmetric on purpose: `apps/auth` has no binding back to `apps/admin`. When the auth worker itself triggers an invalidation (e.g. a session-version bump), it calls `apps/auth → apps/server.invalidateTenant(...)`; the admin worker remains the orchestrator for global invalidations. After Phase C this lives behind `@repo/tenancy`'s `Invalidator` / `FanOutInvalidator` — see [Deep Modules](/multi-tenant/deep-modules/#tenancy-package).

:::note[The per-colo limit is accepted, not solved]
Even with RPC fan-out, `cache.delete()` only purges the colo where the consumer ran. The 60-second positive TTL is the durability backstop for residual stale entries. For a security-critical revocation (a compromised tenant), bump the version counter instead — every colo's cache invalidates on its next read.
:::

:::caution[Don't reach for the version hammer routinely]
Bumping the version is right for slug renames and suspensions, but it's coarse — it invalidates the whole fleet's cache. Don't bump it on every routine update.
:::

## Local development

`localhost:3000` matches neither the wildcard suffix nor any custom host, so the middleware would 404. A dev-only header is the escape hatch, behind a strict two-factor gate:

```ts
if (c.env.NODE_ENV === "development" && c.env.ALLOW_DEV_TENANT_HEADER === "true") {
  const devSlug = c.req.header("x-dev-tenant-slug");
  if (devSlug) {
    // resolve as if host were `${devSlug}.app.example.com`
  }
}
```

Both conditions must hold: `NODE_ENV` (a wrangler `var`) and `ALLOW_DEV_TENANT_HEADER` (a Cloudflare Secret only in `.dev.vars`). A CI guard rejects any deploy to staging/production where `NODE_ENV !== "production"`. The tenant SPA sends `X-Dev-Tenant-Slug: acme` from `VITE_DEV_TENANT_SLUG=acme` in `.env.development`.

## Tombstoned slugs

A soft-deleted org's slug must never be reissued — a future tenant with the same slug would inherit confusion across links, cookies, JWTs, and audit logs. Soft-delete does two things in one transaction (D16, D37):

1. `UPDATE organization SET deleted_at = now(), deleted_by = ?, slug = NULL WHERE id = ?`
2. `INSERT INTO reserved_slugs (slug, reason: "deleted_org", organization_id)`

Tenant creation checks both the active `organization.slug` UNIQUE constraint and `reserved_slugs`.

## The soft-delete invariant

Orgs are never hard-deleted, so every query against `organization` must filter `deleted_at IS NULL`. Forgetting it resurrects a deleted tenant. Enforced by review (documented in `CLAUDE.md`); a future Drizzle `activeOrganizations` helper may make it the default.

## Performance targets

- **Cache hit, warm isolate:** cache lookup under 1ms; total middleware overhead under 2ms at p99.
- **Cache miss, cold path:** ~5–10ms for KV version lookup + Hyperdrive query + cache write.
- **Cache miss, cold isolate:** ~50–100ms, one-time per isolate boot.
