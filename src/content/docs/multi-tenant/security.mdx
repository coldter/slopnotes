Multi-tenancy is mostly a security problem. There are **two identity domains** — tenant users and operators — and nearly every threat reduces to one of two questions: *how could tenant A touch tenant B's data, or how could an ordinary user become an operator?* Each section below states the attack first, then the defense.

Threat statuses: <Badge text="closed" variant="success" /> = fully addressed, <Badge text="mitigated" variant="note" /> = risk reduced, <Badge text="accepted" variant="caution" /> = residual risk tolerated for v1.

## Two identity domains

- **Tenant users** — customers, in Better Auth's `users` table, managed by tenant admins.
- **Operators** — SaaS staff, in the `global_admins` table, gated by Cloudflare Access — never by a tenant session.

Attackers follow from those domains: a tenant admin escalating to global admin or reading another tenant's data; an unauthenticated attacker registering slugs/hostnames they don't own; a malicious tenant pointing an attacker-controlled OIDC provider at the system; a compromised CF Access IdP; a former operator with a still-valid Access session; an authenticated tenant user calling a global-admin endpoint; a compromised Postgres backup leaking SSO client secrets.

## Identity isolation invariants

Each is enforced by a concrete mechanism, not convention:

| Invariant | Mechanism |
| --- | --- |
| Operators are never in the `users` table | `global_admins` is a separate table; gates check it specifically |
| Tenant cookies never cross hosts | `Domain` attribute unset (host-only); `crossSubDomainCookies: false` |
| Cross-tenant CSRF is blocked | Host-only cookies + explicit `Origin`/CSRF enforcement on every state-changing route |
| A JWT minted for tenant A is never accepted by tenant B | Per-host `aud` + `iss`; `org.host`, `org.id`, `org.sessionVersion` claims |
| An operator session never shares state with a tenant session | The admin worker has no cookie session; the CF Access JWT is verified per request |
| An operator action is always visible to the affected tenant | `auditLogService.createDualScope` writes to both views |
| `audit_logs` is append-only | A Postgres trigger raises on UPDATE/DELETE |
| Self-serve sign-up is disabled | `disableSignUp: true` globally; users arrive only via invitation |
| Better Auth's `organization.create` always rejects | An unconditional `before` hook |
| Tenants are creatable only by operators | `AdminApiEntrypoint.createTenantOnBehalfOf` is the only public path |

## Cookie isolation

<Badge text="closed" variant="success" />

**The attack:** a user logged into `acme.app.example.com` visits a malicious tenant at `evil.app.example.com`; a script there fires a request riding Acme's session cookie into Acme's API. The model is *per-host cookies plus explicit CSRF/origin enforcement* — leaning on `SameSite` alone doesn't carry the weight:

- The session cookie carries no `Domain` attribute, so the browser scopes it to the exact host that set it.
- Sibling tenant subdomains share a registrable domain, so the browser treats them as *same-site* — `SameSite=strict` does **not** stop tenant-to-tenant CSRF on its own.
- Auth/session cookies stay `SameSite=lax` so OAuth/OIDC callback and state-cookie flows keep working. Tenant and admin mutations are protected by explicit `Origin` checks, Better Auth's built-in CSRF checks on its own endpoints, and custom non-simple-request guards on the system's mutation routes.
- `crossSubDomainCookies` stays off. Better Auth's `secondaryStorage` (KV) caches session state by token, not domain — no cross-host leakage through the cache.

:::caution[The isolation boundary]
Because sibling subdomains are same-site, the real defense is that every state-changing tenant or admin endpoint enforces `Origin` against the resolved public origin, and custom mutation endpoints require a non-simple request shape (e.g. JSON plus a custom header).
:::

## JWT scoping

<Badge text="closed" variant="success" />

**The attack:** an attacker replays a valid JWT minted for their own tenant against another tenant's host, hoping a consumer honors it and serves someone else's data. Every JWT is scoped to exactly one host and org; every consumer verifies all five scoping properties.

Mint side (Better Auth's `jwt` plugin):

```ts
{
  iss: "https://acme.app.example.com",
  aud: "https://acme.app.example.com",
  sub: user.id,
  email, roleSlugs, platform,
  org: { id: orgId, host: "acme.app.example.com", sessionVersion: 5 },
  exp: now + 15min,
}
```

Verifier side — every consumer checks all five:

1. `aud === "https://${expectedHost}"`
2. `iss === "https://${expectedHost}"`
3. `org.host === expectedHost`
4. `org.id === expectedOrgId`
5. `org.sessionVersion >= db.organization.session_version`

:::note[Why all five]
Omitting any one re-opens cross-tenant token forgery. `aud`/`iss` alone could in principle be spoofed by anyone controlling the mint side; the `org` claim ties the JWT to a specific organization, and `org.sessionVersion` enables immediate revocation on suspension. After the deep-module consolidation, all five live behind `verifyTenantJwt(token, opts)` — see [Deep Modules](/multi-tenant/deep-modules/#auth-tokens-package).
:::

## SSO callback validation before token exchange

<Badge text="closed" variant="success" />

**The attack:** a tenant self-registers its OIDC provider, then replays its IdP's callback response against *another* tenant's callback URL — a confused-deputy trick to get Better Auth to mint a session for the wrong tenant. `ssoCallbackGuardPlugin` runs on `/sign-in/sso/callback/*` *before* the code is exchanged:

```ts
hooks: {
  before: createAuthMiddleware(async (ctx) => {
    if (!ctx.path.startsWith("/sign-in/sso/callback/")) return;
    const providerId = ctx.path.split("/").pop();
    const provider = await db.query.ssoProviders.findFirst({
      where: { providerId: { eq: providerId } },
      columns: { organizationId: true },
    });
    if (!provider || provider.organizationId !== tenant.organizationId) {
      throw new APIError("FORBIDDEN", { message: "Provider does not belong to this tenant" });
    }
  }),
}
```

:::caution[Why it must run before]
Rejecting in `provisionUser` is too late: by then the authorization code has already been spent at the IdP. Without the guard, Better Auth exchanges the code and mints a session for the wrong tenant.
:::

## SSO email-link account takeover

<Badge text="closed" variant="success" />

:::danger[Account takeover]
A tenant admin (or a compromised one) configures a provider whose `id_token` returns `email = victim@bigcorp.com`. With default account linking, Better Auth attaches the session to the existing victim user — the attacker takes over the account, including memberships in *other* orgs.
:::

The `provisionUser` hook requires three conditions before any link: `userInfo.email_verified === true`, the existing user is already a member of *this* org, and the provider's `domainVerified === true`. `account.accountLinking.trustedProviders: []` stays empty, so default linking only proceeds when `provisionUser` passes.

## Operator account takeover via IdP race

<Badge text="closed" variant="success" />

:::danger[Operator takeover]
Suppose operator `alice@company.com` is provisioned with `cf_access_sub = NULL`, and the CF Access policy allows `@company.com` via OTP. An attacker registers a different IdP account asserting the same email and signs in *first* — email-fallback matching writes the attacker's `sub` to Alice's row. Silent takeover.
:::

Mitigation: **no email fallback**. `globalAdminMiddleware` matches only by `cf_access_sub`; first-login binding requires a one-time `enrollment_token` (24h TTL) issued out-of-band by a `super_admin`:

<Steps>

1. A super-admin POSTs `/api/admin/global-admins { email, name, role }`. The server returns the enrollment token (shown once).
2. The super-admin shares the token out-of-band (Slack, password manager).
3. The operator authenticates via CF Access and presents `x-admin-enrollment-token` on their first request.
4. The middleware atomically claims the row with `UPDATE ... WHERE cf_access_sub IS NULL` (race-safe).

</Steps>

An email cross-check at redemption catches an IdP returning a different email than expected.

## Custom hostname squatting

<Badge text="closed" variant="success" />

:::caution[Resource abuse]
Anyone with tenant-admin role could POST `/api/tenancy/hostnames { hostname: "app.competitor.com" }`. If the system registered that with Cloudflare immediately, it would burn quota and potentially trigger abuse-flagging on the zone.
:::

Two-step flow: the POST creates a `tenant_custom_hostnames` row with a `verification_token` and makes **no** Cloudflare API call. The tenant adds a TXT record (`_app-example-verify.<host>` = token); a verify endpoint resolves it via DNS-over-HTTPS; only then does the system call Cloudflare. Per-org rate limits back this up: at most 10 pending hostnames at a time, 50/day, plus a hard refusal on hostnames whose apex resolves to an IP the system doesn't control unless the TXT record is present.

## Slug squatting and tombstones

<Badge text="closed" variant="success" />

:::caution[Impersonation and inheritance]
An attacker could register slugs like `admin`, `api`, `oauth`, `support` — or register an org, delete it, and re-register the same slug to inherit links, cookies, and JWTs referencing the prior org's users.
:::

Mitigations at both ends: a reserved-slug denylist (~50 entries: system names, admin paths, marketing surfaces, DNS reserved labels, common subdomains); the DNS-label-safe regex `^[a-z0-9](?:[a-z0-9-]{1,61}[a-z0-9])?$`; `xn--` Punycode rejected (no IDN in v1); slugs lowercased and NFC-normalized before validation; on soft-delete the slug moves to `reserved_slugs` with `reason: "deleted_org"` and is never reissued. See [Tenant Resolution](/multi-tenant/tenant-resolution/).

## SSO client secret encryption

<Badge text="closed" variant="success" />

:::danger[Pivot into systems you don't own]
A Postgres backup leak would yield every tenant's IdP `client_secret`. The attacker could then act *as* the SaaS against every tenant's IdP, impersonating any user the IdP issues for the registered `client_id` — far more damaging than a normal DB leak.
:::

Secrets use `pgcrypto` column-level encryption. The decryption key lives in Cloudflare Secrets Store — not in the database, not in env vars. Better Auth reads from a `sso_providers_decrypted` view that decrypts on read, with `SET LOCAL app.sso_key = '...'` per session. Application code reads `sso_providers` (raw, encrypted) by default and uses `withDecryptedSecret(...)` scoped closures for plaintext. Defense in depth: the logger middleware redacts any field named `secret`, `clientSecret`, or `enrollmentToken` from structured logs.

## CF API token blast radius

<Badge text="mitigated" variant="note" />

**The attack:** if the worker leaks `CLOUDFLARE_API_TOKEN`, an attacker can do whatever it's authorized for — so scope it tightly. It's scoped to the SaaS zone only, with three permissions — `Zone:Read`, `SSL and Certificates:Edit`, `Custom Hostnames:Edit` — never account-wide. Stored as a Cloudflare Secret with quarterly rotation in the runbook. v2 hardening: split read and write tokens so the reconciler uses a read token and admin actions a write token.

## workers.dev bypass

<Badge text="closed" variant="success" />

:::caution[Perimeter bypass]
Cloudflare Access binds at the hostname level. The default `<name>.<account>.workers.dev` URL is not behind Access, so anyone who guesses it reaches the worker with no JWT validation.
:::

Every worker (`apps/admin`, `apps/auth`, `apps/server`, `apps/app`) sets `"workers_dev": false` and `"preview_urls": false`. Defense in depth: each worker's first middleware also rejects any request whose `Host` header isn't its configured public hostname.

## trustedOrigins echo abuse

<Badge text="closed" variant="success" />

:::caution[Trusting spoofable input]
A naive `trustedOrigins` callback returning `https://${new URL(request.url).host}` would trust whatever `Host` arrived. If `Host` were ever spoofable, an attacker could mark any URL as trusted.
:::

`allowedHosts` is explicit and automatically added to `trustedOrigins`. The extra `trustedOrigins` callback is reserved for local-dev origins and short-lived, validated IdP discovery origins during SSO provider registration.

## Forwarded-header confusion at the auth boundary

<Badge text="closed" variant="success" />

:::caution[Header spoofing across workers]
Better Auth's dynamic `baseURL` resolution consults `x-forwarded-host` and `x-forwarded-proto` before `host`. If `apps/server` forwarded the raw request into the auth worker, a spoofed forwarded header could distort callback-URL generation or trusted-origin checks.
:::

Every call from `apps/server` to `apps/auth` reconstructs the request and headers, sets `host` to the already-validated public host, and strips or overwrites `x-forwarded-host` / `x-forwarded-proto`. Tenant resolution itself trusts only the Cloudflare-delivered `Host` header.

## Tenant suspension revokes sessions

<Badge text="closed" variant="success" />

:::caution[Revocation lag]
When a tenant is suspended for a ToS violation, cookie expiry of 1h–7d would otherwise let suspended users keep operating on existing tokens.
:::

`tenantOperations.suspend(...)` closes the gap in one transaction:

```sql
UPDATE organization
   SET suspended_at = now(),
       session_version = session_version + 1
 WHERE id = $1;

DELETE FROM session WHERE active_organization_id = $1;
```

JWT verifiers then reject any claim where `org.sessionVersion < db.organization.session_version` — existing tokens stop working immediately.

## Operator privilege escalation

<Badge text="closed" variant="success" />

:::danger[Privilege escalation]
A `support` operator could try to promote themselves to `super_admin`, or cover their tracks by deleting audit-log rows.
:::

Controls that stack: the `OPERATOR_PERMISSIONS` matrix gates `platform.manage_global_admins` to `super_admin` only; only a `super_admin` can grant `super_admin` to another operator; `support` cannot read `admin.*` audit events (`security` role has read-only access); the `audit_logs` Postgres trigger blocks UPDATE/DELETE, so even a DB-credentialed engineer can't rewrite history; an operator cannot deactivate themselves, and the system never lets the active `super_admin` count drop to zero.

## Cross-tenant operator queries

<Badge text="mitigated" variant="note" />

:::caution[Data exfiltration]
A curious or malicious operator could scrape user data across all tenants.
:::

Cross-tenant reads are allowed but tightly controlled: `admin.support.query` is classified **CRITICAL** (transactional audit, not bufferable); a hard row cap of 100 per query (pagination beyond that requires separately audited calls); a per-operator rate limit via a RateLimiter Durable Object partition `(globalAdminId, "support_query")`, 60/hour. The audit row records the SQL predicate digest plus the row count.

## CSRF on tenancy and admin endpoints

<Badge text="closed" variant="success" />

**The attack:** the new tenancy and admin mutation routes are *not* Better Auth's own endpoints, so they don't inherit its CSRF protection. An attacker who gets a logged-in admin to load a hostile page could fire a state-changing request riding the admin's session.

All Better Auth endpoints have built-in CSRF protection (origin check plus custom header). New admin and tenancy mutation endpoints add the same `Origin` header check — the value must equal the configured public hostname. Host-only cookies plus explicit origin/CSRF enforcement are the primary defense; `SameSite` is additional hardening only.

## Open redirect

<Badge text="mitigated" variant="note" />

**The attack:** an attacker crafts a sign-in link with `callbackURL=https://evil.com`, so a successful login bounces the victim to an attacker-controlled site. `signIn.sso({ callbackURL })` and similar calls rely on Better Auth's `trustedOrigins` check, which restricts `callbackURL` to the dynamic per-host set — combined with the host validation above, `https://evil.com` can't be redirected to.

## Information disclosure on /api/tenancy/current

<Badge text="accepted" variant="caution" />

**The attack:** this endpoint is unauthenticated (the login page needs it), so an attacker can hammer it across hosts to enumerate tenants and their SSO config. It returns:

```ts
{ organizationId, slug, enforceSSO, providers: [{ providerId, label }], branding }
```

It's rate-limited aggressively per source IP (e.g. 60/min/IP across all hosts) and returns minimal info: `providerId` and `label` only, no internal IDs, no IdP issuer URL. Acceptable disclosure for v1.

## MFA gap

<Badge text="accepted" variant="caution" />

:::caution[Un-mitigatable in v1]
The Cloudflare Access JWT does not include an `amr` claim, so the worker can't verify a token was issued via MFA.
:::

v1 leans on two layers: a CF Access policy of `Require: Authentication Method ∈ {mfa, swk, hwk, otp}` (bypassable if misconfigured), and IdP-side MFA enforcement (Google Workspace 2SV, Okta MFA policy). v2 plan: call the CF Access Identity API server-side, verify the AMR value, cache by `identity_nonce`.

## Logout

<Badge text="closed" variant="success" />

- **Tenant**: Better Auth's `signOut` clears the session cookie and revokes the session row.
- **Operator**: `https://admin.example.com/cdn-cgi/access/logout` — Cloudflare-managed; per-app revocation propagates within ~30 seconds.

## CF Access logout CSRF

<Badge text="accepted" variant="caution" />

A malicious tenant could embed `<img src="https://admin.example.com/cdn-cgi/access/logout">` on a tenant page; an operator browsing it during support gets logged out — a nuisance, not exfiltration. The endpoint is Cloudflare-controlled, so CSRF tokens can't be added. The runbook recommends a separate browser profile for admin access.

## Local-dev surface hardening

<Badge text="closed" variant="success" />

Dev conveniences are double-gated so they can never leak into production:

- The dev tenant header (`X-Dev-Tenant-Slug`) requires `NODE_ENV === "development"` **and** `ALLOW_DEV_TENANT_HEADER === "true"` (a Cloudflare Secret). A CI guard rejects deploys to staging/prod where merged config has `NODE_ENV !== "production"`.
- The admin email fallback (`LOCAL_DEV_ADMIN_EMAIL`) uses the same pattern: `NODE_ENV === "development"` **and** `ALLOW_DEV_ADMIN_AUTH === "true"`. A misconfigured production deploy fails hard rather than silently authenticating.

## Audit log immutability

<Badge text="closed" variant="success" />

**The attack:** an operator (or DB-credentialed engineer) tampers with `audit_logs` to erase evidence — so the control can't live in application code alone. A Postgres trigger blocks UPDATE/DELETE on `audit_logs`, and application code never issues UPDATE/DELETE against the table. The DB role the workers use holds only `INSERT, SELECT` on `audit_logs`; the migration role separately holds the DDL permissions to install the trigger.

## Reserved-slug enforcement at the DB level

<Badge text="closed" variant="success" />

**The attack:** two requests race to claim the same slug; both pass the app's "is it free?" check; both try to insert — a TOCTOU window the app-level check can't close. UNIQUE constraints on `organization.slug` and `reserved_slugs.slug` make collisions impossible at the database level; the application also checks both before insert, and the UNIQUE constraint catches the second writer in a race.
