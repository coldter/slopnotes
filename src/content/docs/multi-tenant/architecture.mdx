The system is **three Workers plus two static SPAs**, sharing one Postgres via Hyperdrive (Cloudflare's Postgres connection pooler) and one Better Auth instance. Tenants and operators never share a session, a worker, or a cookie domain — the boundaries *are* the security model.

:::note[Cloudflare terms on this page]
A *Worker* is deployed code that runs at the edge. A *service binding* lets one Worker call another via typed RPC (`env.AUTH.getSession(...)`) instead of HTTP — the called Worker needs no public URL, so the binding doubles as a private security perimeter. *Hyperdrive* keeps warm Postgres connections at the edge.
:::

## What each worker owns

**`apps/auth`** holds the single Better Auth instance, built per request via `createAuth(db, env, ctx, options)`. It owns the identity tables — `users`, `sessions`, `accounts`, `organization`, `member`, `invitation`, `sso_providers`, `verifications`, `two_factors`, `jwks` — and exposes an `AuthEntrypoint` RPC (`getSession`, `handleAuthRequest`, `getToken`, `createUser`, `signInEmail`, `acceptInvitation`, `invalidateTenant`). It is **not publicly reachable**; only other workers reach it over a service binding.

**`apps/server`** is the public tenant-facing API on `.app.example.com` and tenant custom hostnames. It owns the tenancy module (custom-hostname CRUD), the org-admin SSO-config module, invitation-acceptance orchestration, and within-org reads. It holds the Cloudflare API token for hostname provisioning, runs the 60-second reconciler cron, and serves the tenant SPA by proxying non-API paths to `apps/app` via its `STATIC_ASSETS` binding.

**`apps/admin`** is the operator-facing API on `admin.example.com`. Every request is gated twice: Cloudflare Access verifies the operator's JWT at the perimeter, then a `global_admins` table lookup gates at the database. It owns the `global_admins` table, exposes tenant CRUD and cross-tenant queries, serves `apps/admin-ui`, and runs a daily inactivity-sweep cron.

**`apps/app`** and **`apps/admin-ui`** are Workers Static Assets — they serve a built SPA's files from the edge with no business logic. `apps/app` is reachable only through `apps/server`'s `STATIC_ASSETS` binding, with `not_found_handling: "single-page-application"` so client-side routes resolve to `index.html`. `apps/admin-ui` is built by Vite and served by `apps/admin`'s `ASSETS` binding; it has no separate deployable.

## Routing rules

A **fallback origin** is the one zone-level hostname that *every* tenant custom domain lands on once Cloudflare for SaaS verifies it. Instead of wiring a route per customer, point them all at one origin and let one Worker sort out the tenant per request.

Zone config (runbook): a proxied fallback origin (`fallback.example.com`) pointed at `apps/server`, a proxied wildcard (`*.app.example.com`) at `apps/server`, a published CNAME target (`customers.example.com`) that tenants point custom domains at, the Cloudflare for SaaS fallback origin set at zone level, and a Cloudflare Access application on `admin.example.com`.

The tenant worker matches its three hostnames explicitly:

```json title="apps/server/wrangler — routes"
"routes": [
  { "pattern": "*.app.example.com/*",    "zone_name": "example.com" },
  { "pattern": "app.example.com/*",       "zone_name": "example.com" },
  { "pattern": "fallback.example.com/*",  "zone_name": "example.com" }
]
```

Custom hostnames like `app.acme.com` need **no** per-tenant route entries — they land on the worker through the SaaS zone's fallback origin. The admin worker binds with `custom_domain: true` instead of a route pattern: a `route` matches traffic on a hostname the zone owns, while `custom_domain: true` tells Cloudflare to provision and manage the DNS record and certificate for that exact hostname:

```json title="apps/admin/wrangler — routes"
"routes": [{ "pattern": "admin.example.com", "custom_domain": true }]
```

`apps/app` has no public routes at all; it's reached only via the `STATIC_ASSETS` binding.

:::caution[Critical: `workers_dev: false` + `preview_urls: false` on every worker]
Cloudflare Access binds to *hostnames*, not workers. Without `workers_dev: false`, the admin worker would also be reachable at `admin.<account>.workers.dev` and bypass Access entirely. Same risk for `apps/auth` and `apps/server`. As defense in depth, each worker's first middleware also rejects any request whose `Host` header isn't its configured public hostname.
:::

## Service bindings

Workers talk over typed RPC, not HTTP — the binding *is* the internal security perimeter.

| From | To | Entrypoint | Purpose |
|------|----|-----------| --------|
| `apps/server` | `apps/auth` | `AuthEntrypoint` | Auth proxy + RPC for session/token/user operations |
| `apps/server` | `apps/app` | (default fetch) | `STATIC_ASSETS` for non-API paths |
| `apps/auth` | `apps/server` | `ApiEntrypoint` | Auth lifecycle hooks + `invalidateTenant` |
| `apps/admin` | `apps/server` | `AdminApiEntrypoint` | Tenant creation, cross-tenant queries, hostname lifecycle |
| `apps/admin` | `apps/auth` | `AuthEntrypoint` | Operator-initiated user creation + accept-invitation |

There is deliberately **no** binding from `apps/auth` to `apps/admin`. Auth-side cache invalidation flows the other way, through `apps/auth → apps/server.invalidateTenant(...)` on the existing binding.

Invitation acceptance is the one public route that creates a session — an ordered procedure where each step guards the next:

<Steps>

1. `tenantMiddleware` resolves the tenant from the host.
2. Load the invitation and guard it: pending, not expired, org matches the tenant.
3. `AUTH.createUser(...)` server-side — bypasses `disableSignUp`. Catching `USER_ALREADY_EXISTS` and looking up the existing user makes the step an idempotent retry.
4. `AUTH.signInEmail(...)` returns a session and its `Set-Cookie` headers.
5. `AUTH.acceptInvitation({ headers, invitationId })` writes the membership row.
6. Mark the invitation `accepted`, forward the `Set-Cookie` to the browser, return `{ redirectTo: "/dashboard" }`.

</Steps>

## What's intentionally left out

- **No queue for cache invalidation.** Cloudflare Queues are work-distribution (one consumer per queue), not pub/sub. The design uses service-binding RPC fan-out plus KV cache versioning — see [Tenant Resolution](/multi-tenant/tenant-resolution/#cache-invalidation).
- **No shared secret** between admin and auth workers to gate Better Auth's `organization.create`. That endpoint always rejects; the admin worker creates orgs via direct Drizzle inserts in `AdminApiEntrypoint`.
- **No HMAC-signed header** for tenant context between workers. The typed RPC parameter (`AuthEntrypoint.getSession(headers, tenant)`) is the carrier.
- **No JWT for the admin panel.** Cloudflare Access provides the durable session; every admin request re-validates the CF Access JWT plus the `global_admins` row.
- **No cross-subdomain cookies.** `crossSubDomainCookies` stays `false`; isolation comes from host-only cookies plus explicit CSRF/origin enforcement.

## Why three workers, not two or four

Splitting `apps/admin` from `apps/server` follows Cloudflare Access's grain — one Access application per hostname — and keeps operator bugs off tenant traffic. The admin surface doesn't belong in `apps/auth` either: that worker is binding-only with no public surface. And `apps/app` stays a pure static-assets worker — the tenant API lives in `apps/server` because that's where `tenantMiddleware` runs; splitting it out would duplicate auth middleware and complicate the cookie-domain story.

Package boundaries are a separate axis — covered in [Deep Modules](/multi-tenant/deep-modules/).
