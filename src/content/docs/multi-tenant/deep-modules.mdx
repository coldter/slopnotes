A **deep module** (John Ousterhout's term) is a small, simple interface that hides a lot of implementation — a narrow door into a big room. Callers work against a few well-named methods instead of re-deriving the same rules from prose. The opposite, a *shallow* module, exposes almost as much interface as implementation and barely earns its keep.

Six concepts in this system started shallow and scattered — the same idea spread across several files, each consumer re-implementing the rules. Each section below follows the same four beats: **the problem** (the concept lives in N files and drifts), **the module** (one small typed interface, the only way in), **what it hides**, **the test boundary** (test the small interface, not the internals).

`@repo/tenancy` is already a runtime boundary all workers depend on, so it lands early (Phase A). The other five consolidate once core multi-tenant behavior is stable (Phase C).

## Implementation order

Strict, because each step builds on the one before it — schema before the package that queries it, the token verifier before the service that reads `org.sessionVersion`:

<Steps>

1. The Phase 0 spike validates the Better Auth SSO schema and the Cloudflare hostname state model.
2. Phase A schema migrations land.
3. Phase A: `@repo/tenancy` — every worker uses it.
4. Phase C: `@repo/auth-tokens` — the verifier-side helper.
5. Phase C: `authenticateOperator` plus `@repo/authorization/operator`.
6. Phase C: the `customHostnameLifecycle` service in `apps/server`.
7. Phase C: `ssoProviderRepository`, with its Postgres view.
8. Phase C: the `tenantOperations` service.
9. Workers refactor: route handlers shrink to thin wrappers around the modules above.

</Steps>

## Tenancy package

Tenant context is the first thing every request needs and the easiest to fragment — spread across `parseHostname`, two tenant middlewares, `cache-fanout.ts`, and the `bumpTenantCacheVersion` RPC, it's five files for one concept, and the cache-key shape leaks into invalidation code in three workers. One package gives every worker a single way to turn a host into an organization.

```ts title="packages/tenancy/src/index.ts"
export type TenantContext = {
  organizationId: string;
  host: string;
  slug?: string;
  kind: "subdomain" | "custom";
  enforceSSO: boolean;
  sessionVersion: number;
};

export type ResolveDeps = {
  db: DrizzleClient;
  cache: Cache;
  kv: KVNamespace;
  wildcardSuffix: string;
  adminHost: string;
};

export async function resolveTenant(host: string, deps: ResolveDeps): Promise<TenantContext | null>;

// Asymmetric invalidator: workers that ONLY invalidate their own colo,
// vs the admin worker that fans out to peers.
export type Invalidator = {
  invalidateOwn(spec: { kind: "subdomain" | "custom"; key: string }): Promise<void>;
  bumpOwnVersion(): Promise<void>;
};

export type FanOutInvalidator = Invalidator & {
  fanOut(spec: { kind: "subdomain" | "custom"; key: string }): Promise<void>;
  fanOutBumpVersion(): Promise<void>;
};

// Workers create their own variant in their entrypoint:
export function createInvalidator(env: { CACHE: KVNamespace }): Invalidator;
export function createFanOutInvalidator(env: { CACHE: KVNamespace; API: AuthRpc; AUTH: AuthRpc }): FanOutInvalidator;
```

What it hides: the `parseHostname` rules (lowercase + NFC + regex + reserved names + tombstone check); the Cache API key shape (version prefix + kind/key segments); the KV version-bump TTL; the deleted-org filter (`WHERE deleted_at IS NULL`); the admin-host exclusion; the reverse-lookup join paths (subdomain via `organizations.slug`, custom hostname via the `tenant_custom_hostnames` join).

The invalidator is split in two on purpose. `apps/auth` has no binding back to `apps/admin`, so it gets the plain `Invalidator` (own-colo only) and reuses `apps/auth → apps/server.invalidateTenant(...)` for cross-server invalidation. The admin worker gets the `FanOutInvalidator`. The asymmetry of the binding graph is reflected in the type, so a worker can't accidentally call a fan-out method it has no binding for.

**Test boundary:** integration tests against in-process Postgres with a mocked Cache and KV — resolution by slug, resolution by custom hostname, soft-deleted orgs return `null`, cache-miss writes a positive entry, cache hit skips the DB, short negative TTL, version bump invalidates old-version entries. One suite replaces four separate test files.

## Auth tokens package

JWT verification started as a protocol written in prose: every consumer was told to check `aud`, `iss`, `org.host`, `org.id`, and `sessionVersion >= db`. No module owned it, so each consumer re-implemented the checks from an English description — exactly the duplication that drifts. The fix: make the protocol a module that returns a typed result.

```ts title="packages/auth-tokens/src/index.ts"
export type AuthorizedClaims = {
  sub: string;
  email: string;
  roleSlugs: string[];
  platform: "web" | "mobile";
  org: { id: string; host: string; sessionVersion: number };
};

export type VerifyError =
  | { kind: "expired" }
  | { kind: "wrong_aud"; actual: string; expected: string }
  | { kind: "wrong_iss"; actual: string; expected: string }
  | { kind: "wrong_org"; actual: string; expected: string }
  | { kind: "wrong_host"; actual: string; expected: string }
  | { kind: "stale_session"; claim: number; current: number }
  | { kind: "bad_signature" };

export type VerifyOpts = {
  expectedHost: string;
  expectedOrgId: string;
  jwks: JWKSResolver;
};

// Stateful variant — for internal verifiers with DB access (reads the live sessionVersion).
export async function verifyTenantJwt(
  token: string,
  opts: VerifyOpts & { db: DrizzleClient },
): Promise<AuthorizedClaims | VerifyError>;

// Stateless variant — for external verifiers (caller supplies the version they last saw).
export async function verifyTenantJwtStateless(
  token: string,
  opts: VerifyOpts & { expectedMinSessionVersion: number },
): Promise<AuthorizedClaims | VerifyError>;
```

Two variants because two kinds of verifier exist: an internal verifier in another worker has DB access and uses `verifyTenantJwt`; an external downstream service has no DB access and uses `verifyTenantJwtStateless` with the most recent version it saw.

Minting deliberately stays in Better Auth. Its `jwt` plugin keeps owning key management and JWKS distribution — replacing the mint side would break its session helpers and force you to manage JWKS by hand. This package only consumes tokens; the design just extends `definePayload` to add the `org` claim. All verifiers fetch JWKS from Better Auth's `/api/auth/jwks` and cache it with `createRemoteJWKSet`.

**Test boundary:** round-trip tests covering every claim combination and every failure mode — the coverage the prose protocol never had.

## Tenant operations

Every operator-on-tenant mutation — create, suspend, restore, delete — must coordinate four things in one transaction: DB writes, a dual-scope audit record, a session-version bump, and (post-commit) a cache invalidation. Spread across many endpoint handlers, nothing structurally guarantees the next endpoint remembers all four. A service that owns the coordination turns "remember four steps" into "call one method."

```ts title="apps/server/src/services/tenant-operations/index.ts"
type TenantOperator = { kind: "global_admin"; admin: GlobalAdmin } | { kind: "system"; reason: string };

export class TenantOperations {
  constructor(private deps: { db; auditLogService; invalidator: FanOutInvalidator }) {}

  async create(payload: { slug; name; primaryAdminEmail }, by: TenantOperator): Promise<{ orgId; invitationId; hostedAt }>;
  async suspend(orgId: string, by: TenantOperator, reason: string): Promise<void>;
  async restore(orgId: string, by: TenantOperator): Promise<void>;
  async delete(orgId: string, by: TenantOperator): Promise<void>;  // soft-delete + tombstone slug
}
```

Each method runs the same transaction shape, with the version bump, session deletes, and slug tombstone switched on only for the operations that need them:

```text
db.transaction([
  DB writes (insert/update),
  dual-scope audit (createDualScope inside the tx),
  session-version bump (suspend / restore / delete only),
  session deletes (suspend / delete only),
  slug tombstone (delete only),
])
post-commit: invalidator.fanOut(spec)   // + bump version on rename (rename deferred to v2)
```

The `by` parameter is a union because not every mutation is operator-initiated: billing-driven suspension and scheduled DPA-deletion run as the system, which needs a typed actor that isn't a global admin. The audit log already supports `actor_type: "system"`; the union types the call site so a system mutation can't masquerade as an operator.

`rename` is deliberately absent. A slug rename invalidates SSO callback URLs registered with external IdPs — the IdP holds an absolute URL pointing at the old hostname. v2 adds rename with an explicit operator runbook rather than pretending it's transparent.

With the service in place, admin endpoints shrink to wrappers:

```ts title="apps/admin/src/modules/tenants/handler.ts" {6}
suspendTenant.guard = [requireOperator("tenant.suspend")];
suspendTenant.handler = async (c) => {
  const { id } = c.req.param();
  const { reason } = await c.req.valid("json");
  await tenantOperations.suspend(id, { kind: "global_admin", admin: c.var.globalAdmin }, reason);
  return c.json({ ok: true });
};
```

Five lines after validation, and the four-piece coordination is invisible to the route. **Test boundary** on the service, not the handlers: each method tested for partial-failure rollback, dual audit row count, session-version monotonicity, and that post-commit invalidation is actually called.

## Operator authentication

The admin worker's identity boundary spans three things: verifying the CF Access JWT, the enrollment-token flow on first login, and DB-side activity tracking. Left as separate middleware snippets, it's hard to reason about as one boundary. One function gives the admin worker a single "who is this operator?" call with a typed result:

```ts title="apps/admin/src/auth/authenticate-operator.ts"
type AuthFailure =
  | { kind: "missing_token" }
  | { kind: "invalid_token" }
  | { kind: "service_token" }
  | { kind: "enrollment_required" }
  | { kind: "deactivated" };

class JwksCache {
  async get(): Promise<ReturnType<typeof createRemoteJWKSet>>;
  reset(): void;
}

export async function authenticateOperator(
  c: AdminContext,
  deps: { jwks: JwksCache; db: DrizzleClient },
): Promise<{ ok: true; admin: GlobalAdmin } | { ok: false; failure: AuthFailure }>;
```

What it hides: CF Access JWT verification against the team JWKS; service-token rejection; the first-login enrollment-token claim flow; the `lastActiveAt` ping; a stable failure mapping for the SPA (`ENROLLMENT_REQUIRED`, deactivated, invalid token). **Test boundary:** JWT success and failure, service-token rejection, the enrollment-token claim race, a deactivated user, and JWKS reset behavior — all exercised against this single interface.

## Operator authorization

The earlier design answered "what can an operator do?" with four separate pieces — policies, a `whereGlobalAdminRole` builder, an `adminBypassTenantIsolation` middleware, and a `buildGlobalAdminPrincipal` attribute layout. A single permission matrix, with the action type *derived* from it, makes the answer one lookup:

```ts title="packages/authorization/src/operator.ts" {16}
export const OPERATOR_PERMISSIONS = {
  "tenant.create":         ["super_admin", "support"],
  "tenant.suspend":        ["super_admin", "support"],
  "tenant.restore":        ["super_admin", "support"],
  "tenant.delete":         ["super_admin"],
  "tenant.invite_admin":   ["super_admin", "support"],
  "tenant.list":           ["super_admin", "support", "read_only", "security"],
  "tenant.view":           ["super_admin", "support", "read_only", "security"],
  "platform.view_audit_logs_global": ["super_admin", "support", "read_only", "security"],
  "platform.view_system_metrics":    ["super_admin", "support", "read_only", "security"],
  "platform.manage_feature_flags":   ["super_admin", "support"],
  "platform.manage_global_admins":   ["super_admin"],
} as const satisfies Record<string, readonly GlobalAdminRole[]>;

// Type DERIVED from matrix keys — no separate union to drift.
export type OperatorAction = keyof typeof OPERATOR_PERMISSIONS;

export const requireOperator = (action: OperatorAction) =>
  createMiddleware<AdminEnv>(async (c, next) => {
    const operator = c.get("globalAdmin");
    if (!operator) return c.text("Forbidden", 403);
    if (!OPERATOR_PERMISSIONS[action].includes(operator.role)) {
      return c.text("Forbidden", 403);
    }
    return next();
  });

export function canOperator(admin: GlobalAdmin, action: OperatorAction): boolean {
  return OPERATOR_PERMISSIONS[action].includes(admin.role);
}
```

The key move: `OperatorAction` is `keyof typeof OPERATOR_PERMISSIONS`. Every action in the matrix is automatically valid, and an unknown action is a compile error — no second union to keep in sync. The `as const satisfies Record<...>` clause keeps literal types while checking the shape.

This matrix coexists with the existing `whereGlobalAdminRole` policy builder. `OPERATOR_PERMISSIONS` is the source of truth for **operator-only actions** on `tenant` and `platform` resources; `whereGlobalAdminRole` remains for the rare case where a `global_admin` touches an **org-scoped resource** through the existing `authorize("...")` Hono adapter.

:::caution[Why `global_admin` is not in `systemAdminRoles`]
The existing evaluator's `systemAdminRoles` bypass returns "pass" for any principal in that list, **skipping condition evaluation entirely**. Adding `global_admin` to `systemAdminRoles` *and* using `whereGlobalAdminRole` policies would let the bypass short-circuit the per-role check — every operator would silently become a `super_admin`. So `global_admin` is added to `roles` but **not** to `systemAdminRoles`. The cross-tenant bypass is instead encoded in the action contract: operator actions on `tenant`/`platform` resources are apex-level by definition, with no `resolveOrganization` step.
:::

**Test boundary:** a matrix test generated directly from `OPERATOR_PERMISSIONS` — every `(action, role)` pair against its allow and deny case.

## SSO provider repository

The earlier design had a `secrets.ts` with two functions wrapping two SQL calls — the textbook shallow module. Worse, plaintext IdP secrets were passed around freely, so one accidental log line could leak every tenant's IdP credentials. The repository makes the safe path the only path: reads never return plaintext, and plaintext is reachable only inside a scoped closure.

```ts title="apps/server/src/modules/sso-config/repository.ts"
// Co-located with the sso-config module, NOT a separate package.
export class SsoProviderRepository {
  constructor(private deps: { db: DrizzleClient; secretsKey: string }) {}

  // Reads NEVER return plaintext.
  async findByOrg(orgId: string): Promise<Omit<SsoProvider, "encryptedSecret">[]>;
  async findById(providerId: string): Promise<Omit<SsoProvider, "encryptedSecret"> | null>;

  // Plaintext access only via a scoped closure.
  async withDecryptedSecret<T>(providerId: string, fn: (secret: string) => Promise<T>): Promise<T>;

  async create(input: { orgId; providerId; issuer; clientId; clientSecret; ... }): Promise<SsoProvider>;
  async rotateSecret(providerId: string, newClientSecret: string): Promise<void>;
}
```

Complication: Better Auth's SSO plugin reads provider rows directly from `node_modules`, so those reads can't be intercepted. To encrypt at rest while keeping Better Auth working, the underlying table stores ciphertext and a Postgres view exposes plaintext for Better Auth alone:

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;

-- Underlying table stores ciphertext.
ALTER TABLE sso_providers ADD COLUMN client_secret_encrypted bytea;
-- (Migrate existing plaintext into the encrypted column.)
ALTER TABLE sso_providers DROP COLUMN client_secret;

-- View exposes plaintext; Better Auth reads from the view.
CREATE VIEW sso_providers_decrypted AS
  SELECT id, ..., pgp_sym_decrypt(client_secret_encrypted, current_setting('app.sso_key')) AS client_secret
  FROM sso_providers;
```

The decryption key is provided per session with `SET LOCAL app.sso_key = '...'`. Better Auth's adapter reads from `sso_providers_decrypted`; application code reads the raw encrypted `sso_providers` by default. `withDecryptedSecret` opens a connection, sets the session key, queries the view, hands the secret to the closure, and closes the connection so the key can't be reused.

:::tip[Defense in depth]
Logger middleware (`@repo/shared/logger`) strips any field named `secret`, `clientSecret`, or `enrollmentToken` from structured log output — even a careless log call can't leak a credential.
:::

## Custom hostname lifecycle

The earlier design split one concept across three pieces: `cloudflare-api.ts`, the `tenancy` HTTP module, and the `hostname-reconciler.ts` cron handler. A single service owns the whole lifecycle — add, verify, reconcile, remove — so the cron and the HTTP routes call the same code path.

```ts title="apps/server/src/services/custom-hostnames/index.ts"
export class CustomHostnameLifecycle {
  constructor(private deps: { db; cfApi; auditLogService; emailService; invalidator: FanOutInvalidator }) {}

  async add(orgId: string, hostname: string, by: TenantOperator): Promise<TenantCustomHostname>;
  async verifyTxt(hostnameId: string): Promise<{ verified: boolean; errors?: string[] }>;
  async reconcile(hostnameId: string): Promise<{ statusChanged: boolean }>;
  async remove(hostnameId: string, by: TenantOperator): Promise<void>;

  // Called from cron — wraps reconcile() across all non-terminal rows.
  async reconcileAll(): Promise<{ scanned: number; updated: number }>;
}
```

Co-located in `apps/server` rather than promoted to a package: it has three call sites and all three live in `apps/server` (the HTTP module routes, the cron scheduled handler, and the admin worker's support actions via `ApiBinding` RPC). One service, three consumers — no package needed. The state machine these methods drive is in [Custom Hostnames](/multi-tenant/custom-hostnames/). **Test boundary:** state-transition tests with a mocked CF API; the reconciler cron becomes a thin caller of `reconcileAll()`.

After `@repo/tenancy` lands in Phase A, the remaining Phase C work is roughly two weeks of focused refactoring.

## Why deepen now, not later

Shipping Phases A and B first and consolidating later lets the workers accumulate inconsistencies — different cache-key formats across middlewares, different audit-emission patterns across routes — that only get harder to unify after the fact. Moving `@repo/tenancy` into Phase A avoids the worst of that drift; Phase C finishes the remaining consolidations before the admin and control-plane surface grows too broad to refactor cheaply. The cost is paying for boundary design once, upfront. The win: Phase A and B handlers target the deep boundary from day one and never grow shallow.

## Pitfalls when building deep modules

:::caution[Don't hide state in module scope]
Deep modules that need caches (JWKS, tenant resolution) must **expose the cache as an injected dependency**, not stash it in module scope. Module-scope state forces tests to call `vi.resetModules()` between cases; an injected cache is just another mocked dep.
:::

- **One `AGENTS.md` per package** — a project convention, scoped to that package's role.
- **No cyclic dependencies.** `@repo/tenancy` imports schemas from `@repo/db`, so `@repo/db` must **never** import from `@repo/tenancy`. Same rule for `@repo/auth-tokens`.
- **Refactor order is strict.** Schema migrations before the tenancy package; the tenancy package before tenant-operations; `@repo/auth-tokens` before tenant-operations (it uses `org.sessionVersion`).
- **`AdminApiEntrypoint` is the only route from `apps/admin` to `apps/server`.** Don't expose admin RPC methods on the existing `ApiEntrypoint`, which is also reachable from `apps/auth`.
- **Test at the boundary, not inside it.** Resist unit-testing every internal helper — those tests just make refactoring painful.
