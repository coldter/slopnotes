## Goal

Practice schema evolution with Flyway. Five versioned SQL migrations build a blog schema — users, posts, roles, tags, seed data. Flyway runs them automatically on Spring Boot startup; a REST controller lets you inspect what got applied.

Like `node-pg-migrate`, Knex migrations, or Go's `golang-migrate`: ordered, checksummed SQL files that move the schema forward one version at a time, with a history table tracking what ran.

## What you'll build

<Steps>

1. Run the app and verify all five migrations were applied.
2. Add `V6__add_updated_at_to_posts.sql` — new column + trigger.
3. Add `V7__create_comments_table.sql`.
4. Add a repeatable migration `R__create_user_stats_view.sql`.
5. Edit `V1__create_users_table.sql` and watch Flyway's checksum validation reject it.
6. Use `flyway.repair()` to fix the checksum error.

</Steps>

## How Flyway versioning works

```text
V2__create_posts_table.sql
│  │└──────────────┬──────┘
│  │               └── description
│  └── double underscore separates version from description
└── prefix: V = versioned (run once), R = repeatable (rerun on change)
```

- **`V` prefix** = versioned migration. Runs exactly once, in version order. Flyway records its checksum in a history table so the file can never silently change after the fact.
- **`R` prefix** = repeatable. No version; reruns whenever its checksum changes, after all pending versioned ones. Good for views, stored procedures.

## The worked solution

Migrations are plain `.sql` files under `src/main/resources/db/migration/` — no migration code to write.

### application.yml

Spring Boot autoconfigures Flyway from the same datasource. `schemas` is where Flyway creates and tracks history; `baseline-on-migrate` lets Flyway adopt a non-empty database.

```yaml title="src/main/resources/application.yml" {7-11}
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/kotlin_course
    username: dev
    password: dev

  flyway:
    enabled: true
    locations: classpath:db/migration
    schemas: mod10_database
    baseline-on-migrate: true

server:
  port: 8081
```

### The migration chain

Each file is ordinary SQL. `V1`/`V2` create tables (note the FK with `ON DELETE CASCADE`). `V3` shows an additive `ALTER TABLE`. Everything is namespaced into `mod10_database`.

```sql title="src/main/resources/db/migration/V1__create_users_table.sql"
CREATE TABLE IF NOT EXISTS mod10_database.users (
    id          BIGSERIAL PRIMARY KEY,
    name        VARCHAR(255) NOT NULL,
    email       VARCHAR(255) NOT NULL UNIQUE,
    active      BOOLEAN NOT NULL DEFAULT true,
    created_at  TIMESTAMP NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS idx_users_email ON mod10_database.users (email);
```

```sql title="src/main/resources/db/migration/V2__create_posts_table.sql"
CREATE TABLE IF NOT EXISTS mod10_database.posts (
    id          BIGSERIAL PRIMARY KEY,
    title       VARCHAR(255) NOT NULL,
    content     TEXT NOT NULL,
    author_id   BIGINT NOT NULL REFERENCES mod10_database.users(id) ON DELETE CASCADE,
    created_at  TIMESTAMP NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS idx_posts_author ON mod10_database.posts (author_id);
```

```sql title="src/main/resources/db/migration/V3__add_user_role.sql"
ALTER TABLE mod10_database.users
    ADD COLUMN role VARCHAR(50) NOT NULL DEFAULT 'user';

CREATE INDEX IF NOT EXISTS idx_users_role ON mod10_database.users (role);
```

`V4` introduces a many-to-many: `tags` plus a `post_tags` join table with composite primary key. `V5` seeds data with `ON CONFLICT … DO NOTHING` so re-running is harmless.

```sql title="src/main/resources/db/migration/V4__create_tags_and_post_tags.sql"
CREATE TABLE IF NOT EXISTS mod10_database.tags (
    id      BIGSERIAL PRIMARY KEY,
    name    VARCHAR(100) NOT NULL UNIQUE
);

CREATE TABLE IF NOT EXISTS mod10_database.post_tags (
    post_id BIGINT NOT NULL REFERENCES mod10_database.posts(id) ON DELETE CASCADE,
    tag_id  BIGINT NOT NULL REFERENCES mod10_database.tags(id) ON DELETE CASCADE,
    PRIMARY KEY (post_id, tag_id)
);

CREATE INDEX IF NOT EXISTS idx_post_tags_tag ON mod10_database.post_tags (tag_id);
```

```sql title="src/main/resources/db/migration/V5__seed_sample_data.sql"
-- Seed users
INSERT INTO mod10_database.users (name, email, role) VALUES
    ('Alice', 'alice@example.com', 'admin'),
    ('Bob', 'bob@example.com', 'user'),
    ('Charlie', 'charlie@example.com', 'user')
ON CONFLICT (email) DO NOTHING;

-- Seed tags
INSERT INTO mod10_database.tags (name) VALUES
    ('kotlin'), ('spring'), ('database'), ('tutorial')
ON CONFLICT (name) DO NOTHING;

-- Seed posts (subqueries resolve user IDs by email)
INSERT INTO mod10_database.posts (title, content, author_id) VALUES
    ('Getting Started with Kotlin', 'Kotlin is a modern JVM language...', (SELECT id FROM mod10_database.users WHERE email = 'alice@example.com')),
    ('Spring Boot Basics', 'Spring Boot makes it easy to create...', (SELECT id FROM mod10_database.users WHERE email = 'alice@example.com')),
    ('Database Access Patterns', 'There are four main approaches...', (SELECT id FROM mod10_database.users WHERE email = 'bob@example.com'));
```

### Application.kt — verifying what ran

No migration logic in Kotlin — Spring Boot triggers Flyway during startup. This controller reads back results via `flyway_schema_history`.

```kotlin title="src/main/kotlin/com/example/Application.kt" {13-15,36-43}
package com.example

import org.springframework.boot.autoconfigure.SpringBootApplication
import org.springframework.boot.runApplication
import org.springframework.jdbc.core.JdbcTemplate
import org.springframework.web.bind.annotation.GetMapping
import org.springframework.web.bind.annotation.RequestMapping
import org.springframework.web.bind.annotation.RestController

@SpringBootApplication
class Application

fun main(args: Array<String>) {
    runApplication<Application>(*args)
}

@RestController
@RequestMapping("/api")
class MigrationVerifyController(private val jdbc: JdbcTemplate) {

    @GetMapping("/tables")
    fun listTables(): List<Map<String, Any>> = jdbc.queryForList("""
        SELECT table_name,
               (SELECT count(*) FROM information_schema.columns c
                WHERE c.table_schema = t.table_schema AND c.table_name = t.table_name) as column_count
        FROM information_schema.tables t
        WHERE table_schema = 'mod10_database'
        ORDER BY table_name
    """.trimIndent())

    @GetMapping("/migration-history")
    fun migrationHistory(): List<Map<String, Any>> = jdbc.queryForList("""
        SELECT version, description, type, installed_on, execution_time, success
        FROM mod10_database.flyway_schema_history
        ORDER BY installed_rank
    """.trimIndent())

    @GetMapping("/users")
    fun users(): List<Map<String, Any>> =
        jdbc.queryForList("SELECT * FROM mod10_database.users ORDER BY id")

    @GetMapping("/posts")
    fun posts(): List<Map<String, Any>> = jdbc.queryForList("""
        SELECT p.id, p.title, u.name as author, p.created_at
        FROM mod10_database.posts p
        JOIN mod10_database.users u ON u.id = p.author_id
        ORDER BY p.id
    """.trimIndent())
}
```

:::caution[Never edit an applied migration]
Once a versioned migration has run, its file is frozen — Flyway stored a checksum. Editing `V1` after it ran fails startup with a *checksum mismatch*. That's a guardrail, not a bug. The fix is `flyway.repair()`, or better: write a new migration (`V6`, `V7`, …) to change applied schema.
:::

## Run it

<Steps>

1. Start PostgreSQL from `shared-infra`:

   ```bash
   cd shared-infra && docker compose up -d postgres
   ```

2. Run the app — Flyway applies all pending migrations on startup:

   ```bash
   ./gradlew bootRun
   ```

3. Verify:

   ```bash
   curl http://localhost:8081/api/tables
   curl http://localhost:8081/api/migration-history
   curl http://localhost:8081/api/users
   curl http://localhost:8081/api/posts
   ```

</Steps>
